# P0：阻断"可信委托"承诺的问题

## P0-1 · `resume` 反序列化崩溃根因定位与修复

**现象**：手工测试中多次执行 `hearth resume <session_id>` 后进程 core dump，需手动终止/重启，而不是报出一个可读错误。

**根因假设（未经源码验证）**：`resume` 路径大概率是对落盘的会话状态做 `serde_json`/`bincode` 反序列化后直接 `.unwrap()` 或依赖 panic 传播，某种边界条件（并发写入中途 kill、字段类型不匹配、空文件、半截 JSON）触发了 panic，且该 panic 没有被 `catch_unwind` 或进程级 panic hook 拦截，最终变成了 SIGABRT/core dump 而不是"任务失败但进程存活"。

**动作**：
1. 用真实的手工测试环境复现一次 core dump，拿到完整 backtrace（`RUST_BACKTRACE=full`）。
2. 定位具体是哪一步反序列化/断言失败。
3. 把这条路径改造成：任何反序列化失败都返回 `Result::Err`，由上层转成清晰的用户可读错误（"会话状态文件已损坏，无法恢复：<原因>，可用 `hearth sessions` 查看其他会话"），**不允许 panic 逃逸出这个函数**。
4. 如果确认是并发写入导致的半截文件，参照 `project-sync` 里 EVENT_LOG 已经用过的"O_APPEND + 文件锁"模式，给会话状态文件加同样的写入保护，不要重新发明一套。

**验收·正面**：正常落盘的会话能被 `resume` 正确恢复，行为不变。
**验收·负面**：人为构造三种畸形状态文件（①截断到一半的 JSON ②字段类型错误 ③空文件），分别执行 `resume`，断言：进程不 core dump，命令以非零退出码 + 可读错误信息结束，且进程退出后**不留下僵尸/损坏更严重的文件**。

## P0-2 · Agent Loop 顶层 wall-clock 超时缺失

**现象**：手工测试记录末尾（`cargo build` 触发后）`hearth chat`/`repl` 内的任务执行挂起，无法自行结束，测试者最终手动 kill 进程结束记录。

**根因假设**：内部工具（如 `bash`）有单次调用超时（默认 30s），但整个 Agent Loop（Plan→Act→Observe→Reflect 的多轮循环）没有一个"这一整个任务最多跑 N 分钟"的顶层截止时间。单次工具超时不能防止循环本身在 replan/continue 之间无限打转。

**动作**：
1. 在 `agent-core` 的 Loop 结构上增加一个可配置的 **任务级 wall-clock deadline**（区别于现有的 `max_steps` 预算和单工具超时），默认值建议 10-15 分钟，可通过 config/CLI 覆盖。
2. deadline 触发时的行为：像 `budget_exhausted` 一样，走"Giving up"这条已有的干净收尾路径（不要新发明一套退出机制，复用现成的 `budget exhausted` 收尾逻辑，只是触发条件从"步数用尽"改为"时间用尽"）。
3. `hearth chat`（一次性任务）作为顶层命令，也应该有一个更外层的进程级超时兜底（防止 deadline 机制本身有 bug 时进程仍然不退出），可以简单到"deadline + 30s 宽限后 SIGKILL 自己"。

**验收·正面**：正常任务在 deadline 内完成，行为不受影响。
**验收·负面**：构造一个会持续 replan 的场景（比如反复失败的 bash 命令），断言：任务在 deadline 到达后收到干净的 "Giving up: deadline exceeded" 收尾，进程退出，不需要人工 kill；同时确认 deadline 期间预算/步数计数依旧正常写入，不产生数据不一致。

## P0-3 · 会话状态文件 schema 版本化 + 迁移层

**现象（诊断证据不完整，需源码确认）**：二进制字符串扫描能找到 `schema_version` 字面量，但只关联在事件信封（`EnvelopedEvent`）链路上；没有直接证据证明会话持久化文件（`repl.rs` 里 `restore_history`/`restore_task_graph` 读取的那个状态文件）也有版本号字段。这与 P0-1 的 core dump 可能同源——如果状态文件格式在版本间悄悄变了形状，没有版本号的反序列化器只能要么恰好兼容、要么直接 panic。

**动作**：
1. 先确认：会话状态文件当前有没有版本字段。如果有，本任务只需要补充"未知版本拒绝并给清晰错误"的分支（同 F1 的思路），标记本任务"部分完成，原假设不完全成立"。
2. 如果确实没有，参照 `project-window-sync-design.md` 里 F1 的既有设计（EVENT_LOG 的 `schema_version` + migration layer），给会话状态文件也加上同样机制：写入时带版本号；读取时按版本号分派到对应的反序列化逻辑；遇到未知版本，明确拒绝并报错，不静默用错误的结构体硬解。

**验收·正面**：当前版本的状态文件正常读写。
**验收·负面**：构造一个 `schema_version` 字段被篡改成未来版本号的状态文件，断言 `resume` 拒绝加载并给出"版本不兼容"的清晰提示，而不是尝试硬解导致行为异常或崩溃。

## P0-4 · 工具调用前置目标校验（通用写前确认模式）

**现象**：手工测试中，用户明确指示"记录到 `BUG_LEDGER.md`"，但 agent 中途创建了一个新文件 `hearth_bug_log.md` 并往里写，且没有察觉这是个偏离指令的行为，导致两份内容不同的文件用了同一套编号，产生了混乱的、自相矛盾的记录。

这不是某个工具的 bug，是**"确认写入目标与用户指令一致"这一步骤在流程里缺失**——这个问题会在任何要求"写到指定文件/指定位置"的任务里复现，不限于 bug 记录场景，属于通用问题。

**动作**：
1. 在写入类工具（`write_file`、`apply_patch`）的执行前，如果本轮 Plan 阶段的目标文本里显式提到了一个具体文件名/路径，而工具调用的实际目标路径与之不一致，触发一次强制的"路径不一致确认"——可以是要求 planner 在 gap 里显式记录"用户指定路径 X，但即将写入 Y，原因是..."，而不是允许静默地写到别处。
2. 更轻量的实现方式：在 `write_file`/`apply_patch` 分发前加一个校验函数，对比"最近一次用户消息里出现的文件名/路径 token"和"本次工具调用的 path 参数"，不一致时在事件流里显式产出一条 `path_mismatch_warning`，让 Observer 层能捕捉到，用户也能在终端看到警示，而不是完全没有信号。
3. 这条不要求做到语义完美（不可能 100% 准确识别"用户指定的文件名"），但**至少要能捕捉到"用户消息里字面提到的文件名和实际写入路径完全不同"这种最粗粒度的偏离**，这已经能挡住这次实测遇到的具体场景。

**验收·正面**：用户要求写入某文件、agent 也确实写入该文件时，无警示、正常执行。
**验收·负面**：故意构造"用户要求写入 A.md，工具调用却传入 B.md"的场景，断言产出 `path_mismatch_warning` 事件且终端有可见提示，不是静默执行。

## P0-5 · 上下文压缩语义修正：归档而非删除

**现象**：手工测试反复触发 BUG-009/010——上下文达到 100% 后，同一次多轮对话内，用户追问更早的历史内容，agent 明确答复"无法读取之前被压缩/移除的历史"。

**根因假设**：当前压缩实现（`maybe_compact`）很可能是把旧轮次的消息**直接从 prompt 消息数组里删除**，且没有在磁盘上保留一份可检索的原文，导致"压缩"等价于"永久丢失"。

**动作**：
1. 确认压缩逻辑目前是否已经把被压缩的原始消息写到磁盘（哪怕只是 transcript 文件里）。如果已经写了，问题只在于**没有一个工具能让 agent 在需要时把它读回来**——那就只需要新增一个内部工具（如 `recall_history` 或复用 `read_file` 指向 transcript 路径）。
2. 如果压缩时原文本身就没有落盘（真的是"计算内存里删了就没了"），需要在压缩发生前，先把被折叠的原始消息追加写入一个专门的 transcript 归档文件，再从活跃上下文里移除。
3. 压缩后的摘要（folded summary）本身应该在 prompt 里保留一条明确的"如果需要更早的细节，可以调用 XX 工具查询归档"的提示，让 agent 知道自己有找回历史的手段，而不是简单地回答"无法读取"。

**验收·正面**：正常长对话中，压缩后近期任务的执行不受影响。
**验收·负面**：构造一个会触发压缩的长对话，压缩发生后，用户询问被压缩掉的具体历史内容，断言 agent 能通过归档检索工具找回原文并正确回答，而不是回复"无法读取"。

# P1：通用体验与高频故障

## P1-1 · Token 缓存命中率可观测性缺失

**现象**：二进制字符串取证确认，`OpenAiUsage` 结构体只有 3 个字段（`prompt_tokens`/`completion_tokens`/`total_tokens`），没有解析 DeepSeek 等 OpenAI 兼容 API 会额外返回的 `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens` 字段。这意味着现在**用户和系统本身都无法知道真实缓存命中率**，任何关于"命中率不高"的判断目前都只能来自外部账单，不是 Hearth 自己的遥测。

**动作**：
1. 给 `llm-openai`（以及其他兼容通道，如果 provider 支持）的 usage 反序列化结构体补上 `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`（字段名以对应 provider 实际文档为准，做成 `Option<u32>` 兼容不支持该字段的 provider）。
2. 把这两个字段透传到 `introspect` 输出和每轮任务结束的统计里，格式类似现有的 `context_fill_pct`。
3. 这个改动本身不解决命中率问题，只是**装上仪表**，为 P1-2 的诊断和后续验证提供真实数据，不要跳过这步直接去猜 P1-2 怎么改。

**验收·正面**：使用支持缓存的 provider（DeepSeek）跑一轮对话，`introspect` 能看到非零的 `cache_hit_tokens` 或明确的 0（真实反映情况，而不是字段缺失）。
**验收·负面**：切换到不支持该字段的 provider（如 Ollama 本地），断言解析不因为字段缺失而报错或 panic，缺省显示为 `None`/`不适用`。

## P1-2 · LLM 请求体稳定前缀未强制字节级稳定

**现象**：与 P1-1 同源，是命中率异常的直接怀疑对象。

**动作**：
1. 在 P1-1 装上仪表之后，跑两轮连续对话，把实际发给 provider 的完整请求体 JSON dump 下来，逐字节 diff，找到从哪个位置开始两次请求不一致。
2. 常见根因排查方向（按可能性排序，供参考，不代表一定是这几个）：
   - system prompt / 工具 schema 的序列化是否用了顺序不稳定的容器（如 `HashMap` 而非 `BTreeMap`/`IndexMap`），导致同一份逻辑内容序列化出不同字节序。
   - 是否有时间戳、`span_id`、随机生成的 UUID 等易变内容被拼接在了消息数组的**前部或中部**，而不是仅追加在末尾。
   - system_text 是否是"每轮重新用字符串拼接生成"而不是"启动时序列化一次、全程复用同一份 `Bytes`/`String`"。
3. 根据实际 diff 结果修正，把"稳定段"（system + 工具 schema + 项目级静态上下文）和"动态段"（历史消息 + 当前用户输入）在代码层面显式分开处理：稳定段应该只在会话开始时构造一次并复用，不应每轮重新拼接。

**验收·正面**：修复后，连续两轮请求的稳定段字节完全一致（diff 为空），`prompt_cache_hit_tokens` 在第二轮起明显非零。
**验收·负面**：故意在稳定段插入一个易变字段（如临时把时间戳挪到 system prompt 里）作为对照组，确认此时命中率确实归零——用来证明这套诊断方法本身是有效的，不是巧合。

## P1-3 · Provider 限流(429)风暴熔断策略

**现象**：手工测试记录里连续出现大量 429（`rate limit`）错误，日志显示每轮用户输入后，agent 仍然按相同节奏对同一个已知受限的 provider 发起重试，直到单轮重试上限（约 5 次）耗尽才停止，下一轮用户输入后又重新开始一轮同样的重试。

**动作**：
1. 引入跨轮次的熔断状态：某个 provider 在短时间窗口内（如 60 秒）连续触发 N 次 429，标记该 provider 进入"冷却"状态，冷却期内新请求直接跳过重试、快速失败并提示用户，而不是每次都重新走满 5 次重试。
2. 如果配置了多 provider 的 `FallbackChain`，429 应该被明确归类为"应该触发 fallback 切换"的错误类型（如果当前还不是的话），而不是单纯的"退避重试同一个 provider"。
3. 用户可见的错误提示应该更具体：区分"临时限流，建议稍后重试"和"免费额度耗尽，需要升级套餐/换 key"这两种情况（从手工测试的错误信息看，429 消息体里其实已经带了"免费用户限额"这个信息，但目前只是原样透传裸消息，没有转成结构化的用户建议）。

**验收·正面**：正常请求不受影响。
**验收·负面**：模拟连续 429（可以用 mock provider 或本地假 endpoint），断言：熔断在 N 次后生效，冷却期内的请求不再发起真实网络调用即快速返回明确提示；如果配置了 fallback provider，断言熔断后自动切换到备选 provider 而不是持续卡在受限的那个。

## P1-4 · 超时策略分层重设计

**现象**：`bash` 工具默认超时 30 秒，导致 `cargo build` 等正常需要几分钟的任务反复被杀；手工测试后期，测试者需要自己手动传 `timeout_secs:190` 才能绕开。与此同时 P0-2 指出顶层反而完全没有超时。这是同一个"超时策略"课题的两端都没设计好。

**动作**：
1. 把默认超时从"一刀切 30 秒"改成按命令特征分档，或者更简单地——大幅提高默认值（如 120s），同时保留 `timeout_secs` 参数供 agent 按需覆盖；如果 planner/agent 本身有能力判断"这是一个可能长跑的命令"（如识别到 `build`/`test`/`install` 等关键词），应该主动传更长的超时，而不是依赖默认值。
2. 确保这一层的超时策略和 P0-2 的顶层 deadline 是独立配置、互不覆盖的两层，文档里需要清楚写明两者的关系（工具超时管单次调用，deadline 管整个任务）。

**验收·正面**：常见的构建类命令（`cargo build`/`npm install` 等）在默认配置下不会被误杀。
**验收·负面**：构造一个真正应该被超时终止的死循环命令，断言在配置的超时时间点被正确终止，不会因为默认值调大就变成实质上的"无限等待"。

## P1-5 · local(auto) 模式下只读命令误要求 `--url`

**现象**：`hearth -h` 明确写"`--url` 提供则连远程 service；缺省 auto 直跑"，但手工测试中 `status`/`history`/`tools`/`replay` 在没有传 `--url` 的情况下报错要求提供 URL，而 `sessions` 命令在同样条件下能正常工作——同一个"local 模式"下，不同命令的数据访问路径不一致。

**动作**：审计所有子命令的数据访问路径，确认哪些命令背后是"直接读本地文件"、哪些是"必须经过一个跑着的 service"。凡是概念上应该能在 local 模式下工作的只读命令（查状态、查历史、查工具清单、查重放记录），都应该有一条不依赖 HTTP service 的本地读取路径，和 `sessions` 保持一致的行为模式。

**验收·正面**：`sessions` 命令在 local 模式下继续正常工作（回归确认不要改坏）。
**验收·负面**：不传 `--url`，依次执行 `status`/`history`/`tools`/`replay`，断言全部能在 local 模式下正常返回结果，不再报错要求远程 URL。

## P1-6 · `config get`/`session` 子命令缺失

**现象**：`error: unrecognized subcommand 'get'` / `'session'`。

**动作**：`hearth config` 目前只支持 `set`，补上对称的 `get <key>`；确认 `session` 是不是 `sessions` 的误输入引导缺失——如果确有计划中但未实现的 `session` 子命令，补上；如果只是命令命名的笔误，在错误提示里给出"你是不是想输入 `sessions`"这种纠错建议（clap 通常有内建的相似命令建议能力，确认是否已启用）。

**验收·正面**：`hearth config get provider` 能正确返回当前配置值。
**验收·负面**：`hearth config get 不存在的键` 返回明确的"未知配置项"错误，而不是空值或 panic。

## P1-7 · REPL 长文本粘贴被拆成两次输入

**现象**：用户明确反馈"一粘贴过去，就会分成 2 次对话内容"。

**根因假设**：REPL 的多行粘贴支持依赖用户手动输入 `{`/`}` 包裹（见 `hearth -h` 里的提示），如果输入源在没有走这个显式包裹语法、且粘贴内容到达 stdin 的速度超过了逐行读取循环处理单行的速度时，读取逻辑可能把一次粘贴误判成两次独立的、以换行结束的普通输入。

**动作**：确认终端是否已启用 bracketed paste 模式（大多数现代终端支持，能让程序准确识别"这是一次粘贴"而不是"用户手动敲了很多行加回车"）；如果 REPL 的输入循环没有对接 bracketed paste 事件，补上这个支持，作为比"手动输入 `{`/`}`"更自然的粘贴体验；如果暂时不支持 bracketed paste，至少要在文档里明确告知用户"长文本粘贴必须用 `{`/`}` 包裹，直接粘贴不保证完整性"，避免用户以为是随机出现的 bug。

**验收·正面**：使用 `{`/`}` 包裹的粘贴方式继续正常工作（回归确认）。
**验收·负面**：在支持 bracketed paste 的终端下直接粘贴一段包含多个换行的长文本（不使用 `{`/`}`），断言被识别为一次输入，而不是拆成两次。

## P1-8 · `apply_patch` 对空白/缩进过度敏感

**现象**：多次出现 `search block not found ... check exact whitespace/indentation`，即使搜索的内容逻辑上确实存在于目标文件中。

**动作**：确认当前 SEARCH/REPLACE 匹配逻辑是否要求逐字节精确匹配空白字符；如果是，增加一个"宽松匹配"的回退档位——先尝试精确匹配，失败后尝试忽略行尾空白/统一换行符（`\r\n` vs `\n`）后再匹配一次，仍失败才真正报错。这个问题在手工测试里反复出现，说明当前的精确匹配策略过于脆弱，是高频摩擦点。

**验收·正面**：精确匹配的 patch 继续正常工作。
**验收·负面**：构造一个 search 块与文件实际内容仅有行尾空白/换行符差异（内容逻辑完全一致）的 patch，断言在宽松匹配下能成功应用；再构造一个内容确实不存在的 search 块，断言仍然正确报错，不会错误地"宽松"到接受完全不相关的内容。

## P1-9 · 结构化执行报告自动生成

**现象**：用户明确反馈手工测试的效率瓶颈是"发现问题→反馈问题→修复问题"周期太长，本质原因是每次都要重新翻几千行终端记录才能定位问题。

**动作**：每次任务（`chat` 一次性执行，或 `repl` 里的每一轮）结束后，除了终端的实时渲染，额外在 `.hearth/reports/<session_id>/<run_id>.md` 生成一份结构化摘要，至少包含：
- 本轮目标文本
- 执行的工具调用列表（工具名+关键参数+成功/失败）
- 触发的审批请求及结果
- 是否触发了 replan/give_up，如果是，附上 reflect 阶段给出的原因
- 最终产物文件列表（新建/修改了哪些文件）
- 消耗的 token/步数/耗时
- 任何 ERROR 级别日志的摘录（不是全文转储，是提炼后的要点）

这份报告的目的是让用户（或下一个审查的 AI）**不需要翻原始终端 log 就能快速判断这一轮任务是否正常**，直接服务于用户提到的"测试效率太低"这个核心痛点。

**验收·正面**：正常完成的任务能生成完整、字段齐全的报告。
**验收·负面**：构造一个中途失败并 give_up 的任务，断言报告里明确记录了失败原因和最后的状态，而不是报告缺失或字段为空。

# P2：卫生、一致性与可诊断性

## P2-1 · 后端裸日志泄露到终端，违反"事实产生权公理"

**现象**：手工测试记录里多次出现 `2026-08-26T19:11:17.114711Z ERROR agent_core::scheduler: tool dispatch failed ...` 这类原始 `tracing` 日志行，与 REPL 自己的彩色渲染输出混在一起直接打印到终端。项目自己的架构文档明确写着"后端产生事实，前端只投影事实……后端禁止返回颜色/HTML/坐标等呈现语义"，裸 tracing 日志绕过 `render::` 层直接写到 stdout/stderr，某种程度上违反了这条自己定的规矩——虽然它不是"呈现语义"，但它是**未经结构化就直接呈现给终端用户**的后端内部日志，理应先转成 `AgentEvent`，再由渲染层决定怎么展示。

**动作**：审计有多少 `tracing::error!`/`tracing::warn!` 调用点，其内容本该对应一个用户可见的错误，却没有同时产出对应的结构化 `AgentEvent`；把这些补齐，让终端渲染层始终基于 `AgentEvent`，而不是依赖 tracing 的日志格式化输出"顺便"也出现在了终端上。

**验收·正面**：正常错误场景，用户能看到清晰的、经过渲染层格式化的错误信息。
**验收·负面**：故意触发一个已知的错误路径，断言终端输出的是渲染层格式化后的信息，而不是裸露的 `ERROR agent_core::xxx:` 格式字符串。

---

## P2-2 · 文件系统访问入口沙箱校验一致性审计

**现象**：手工测试证实了 `read` 工具正确拒绝了 workspace/home 之外的路径读取（`path outside allowed roots ... denied`），这是正向证据。但没有证据表明 `write_file`、`bash` 的工作目录切换、`apply_patch` 是否都经过了同一套 canonicalize + 前缀校验。

**动作**：逐一确认每个接触文件系统的工具入口，是否都调用了同一个统一的路径校验函数，而不是各自实现一套（各自实现是最容易出现遗漏的模式）。特别关注 `bash` 工具——它能执行任意命令，命令内部的文件访问是否也受 landlock 约束，还是只有 `read`/`write_file` 这类"结构化工具"受限，`bash` 里的裸文件操作全靠 landlock 兜底（如果是后者，说明这层防御其实是 sandbox crate 统一做的，`read`/`write_file` 的校验只是应用层的"提前拦截、给出更友好的错误"，这个区分需要在报告里写清楚）。

**验收·正面**：合法路径的读写操作全部正常。
**验收·负面**：分别对 `write_file`、`bash`（尝试用 `cat`/`echo` 读写 workspace 外的路径）构造越界访问，断言全部被拒绝，拒绝方式（应用层友好报错 vs sandbox 层强制终止）分别记录清楚。

---

## P2-3 · 配置优先级规则统一

**现象**：`hearth -h` 中 `--url`/`--api-key` 等 CLI 参数优先级最高，其余据既有文档是 "CLI > env > config.toml > 内置默认"；但 `HEARTH_EGRESS_ALLOWLIST` 这一项文档写的是"config 加 `egress_allowlist` 字段 + 进程 env，**env 优先合并**"——这与其他配置项的优先级方向不一致（其他键是 config 通常在 env 之后被覆盖，这里反过来）。

**动作**：明确这是有意为之（比如出于安全考虑，出网白名单希望环境变量能强制收紧，不被配置文件放宽）还是历史遗留的不一致；如果是有意为之，在文档里显式标注"此项例外，原因是……"；如果是遗留不一致，统一到全局规则。这条任务的重点不是"哪种规则更好"，而是**消除用户猜不透优先级导致的排查成本**。

**验收·正面**：常规配置项按文档声明的优先级生效。
**验收·负面**：针对 egress allowlist，构造 config 和 env 同时设置但值不同的场景，断言最终生效值符合文档新写明的规则（无论最终选哪种规则，行为要和文档一致，不能文档说一套、代码做另一套）。

---

## P2-4 · 新增 `hearth config show` 诊断命令

**现象**：目前想知道"某个配置项最终生效的值是什么、来自 CLI/env/config.toml/默认值里的哪一层"，只能靠猜测或者翻 config.toml 手工核对，这也是导致 P2-3 这类问题排查慢的原因之一。

**动作**：新增一个诊断子命令（建议 `hearth config show` 或 `hearth doctor`），逐项打印每个配置键的**最终生效值**和**来源**（如 `provider = openai (来源: config.toml)`、`egress_allowlist = example.com (来源: env HEARTH_EGRESS_ALLOWLIST，覆盖了 config.toml 中的值)`）。这个命令的直接价值是：用户下次遇到"为什么这个配置好像没生效"，一条命令就能看清楚，不需要再手工测试排查。

**验收·正面**：命令输出覆盖所有已知配置键，来源标注准确。
**验收·负面**：构造一个 CLI 参数、env、config.toml 三层都设置了同一个键但值不同的场景，断言输出的"最终生效值"与实际运行时真正使用的值一致（可以用该配置项实际产生的行为反向验证，比如设置三层不同的 provider，实际发起请求时用的是哪个）。

## P2-5 · 文档数值声明系统性核对

**现象**：手工测试已确认一例——文档声称 `write_file` 有约 3000 字符截断，实测 3200 字节完整写入无截断，两者不符。

**动作**：把 `README.md`、`docs/hearth-cli-design.md`、`docs/hearth-cli-guide.md` 里所有带具体数字的行为声明（阈值、超时时间、白名单数量、重试次数等）列一张清单，逐条跑一次实际验证，标记"文档准确/文档过期/文档从未准确过"，过期的直接改成实测值，或者改成"不做具体数值承诺，行为以代码为准"这种更保守的表述。

**验收·正面**：核对清单完整覆盖所有可枚举的数值声明。
**验收·负面**：抽查至少 3 条改动后的文档表述，逐条实测确认与实际行为一致。

## P2-6 · 工具调用幂等性审计

**现象**：Plan→Act→Observe→Reflect 循环里，Reflect 阶段可能判定 `replan`，重新规划后可能重新生成相似甚至相同的工具调用。如果某次 `write_file`/`bash`（有副作用的命令，如 `rm`、追加写入）在 Observe 阶段之前进程异常退出（比如刚好撞上 P0-1 那种崩溃），下一次 `resume` 或 `continue` 会不会重新执行一次同样的副作用操作，造成重复写入/重复删除？

**动作**：梳理 Act 阶段执行工具调用与该调用结果落盘之间是否有一个原子性保证（"要么工具执行且结果记录成功，要么都不算数"）；对于明确不是幂等的操作（如追加写入、`rm`），评估是否需要引入一个操作日志/去重键，防止同一个逻辑步骤被物理执行两次。

**验收·正面**：正常无中断的任务执行不受影响。
**验收·负面**：人为在某次 `write_file` 执行完成但结果尚未记录时杀掉进程，`resume` 后断言不会对同一份内容重复追加/重复写入。

---

## P2-7 · SIGTERM 与 Ctrl-C 优雅关闭对等性核实

**现象**：文档提到 Ctrl-C（SIGINT）取消当前轮次后能恢复继续对话，但二进制字符串扫描没有找到与 `SIGTERM` 或通用信号处理相关的字面量（这个证据强度较弱，因为 Rust 的信号处理常通过 `tokio::signal`/`libc` 数值常量实现，不一定留下可读字符串，请以源码为准）。

**动作**：确认进程收到 `SIGTERM`（常见于被进程管理器如 systemd/Docker 优雅终止时发送）是否走和 Ctrl-C 一样的收尾路径（落盘 transcript、标记 session 状态、不留半截文件）。如果 `SIGTERM` 目前是默认行为（直接被内核终止，无自定义处理），需要补上和 `SIGINT` 对等的处理逻辑，这对未来在容器/进程管理场景下运行 Hearth 是必要的地基能力。

**验收·正面**：`SIGINT`（Ctrl-C）现有行为保持不变。
**验收·负面**：向运行中的 `hearth repl` 进程发送 `SIGTERM`，断言 transcript/会话状态被正确落盘，且下次 `resume` 能正常恢复到中断前的状态。
