### 7.1 先说支持的（三条）

| 项 | 意见 | 理由 |
|---|---|---|
| **T-2 裁 (a)** 归档主线、分支留档不合并 | ☑ **支持** | 归档 = **如实封存**，不是宣布成功。且本件明载"三条限制同封存""零余量不满足回主线条件"——**这是诚实的**，比绝大多数归档动作都诚实。 |
| **T-1 裁 (b)** 豁免 L2 独立对照轮、并入 cognition 验收回收 | ☑ **支持** | 归档版不需要对标结论；主力底座天然就是对照面，"一份跑测两用"避免了重复投入。 |
| **T-5** 出口 IP 变更不构成不可比因素 | ☑ **认同** | provider / model / key 三者未变，可比性阻断条件是"换 provider = 换模型层"，不是出口 IP。 |

### 7.2 **请求修正的一条**：签发判据

**问题**：签发件"〇、签发前抽验记录"6/6 全中，据此得出"**具备签发条件**"。

但请看这 6 条的**性质**：

| # | 抽验内容 | 性质 |
|---|---|---|
| 1 | 文件在不在（Glob） | 过程产物 |
| 2 | 函数接入没（grep） | 过程产物 |
| 3 | 门禁过没过（读日志尾） | 过程产物 |
| 4 | 调用点改没改（grep） | 过程产物 |
| 5 | 标注写没写（grep） | 过程产物 |
| 6 | 措辞改没改（grep） | 过程产物 |

**六条全部是"过程产物齐备"，没有一条验证"东西能不能用"。**

**而本次报批件新增一条硬证据（E19）使这个问题变得不可回避**：

> **`golden` 在 `crates/` 中出现 0 次。**
> **493 条测试，零黄金断言——没有一条断言"面对真实会话，输出应该是什么"。**

这意味着：**门禁 493/0 全绿，在逻辑上不能推出产品可用。** 两者之间没有桥梁。

**而桥梁恰恰存在**：`release/手工测试v0.2.23-2026-0.9-0.3.txt` 就是**唯一一份真实世界的可用性证据**（5,249 行真实开发会话）。它的结论是**不能用**——28 次完成 0 次核验、70% 放弃被改判成成功、已知 0/16 标为 100%。

> **一句话**：
> **这份签发件用 6 条"东西做完了"的证据，签发了"东西可以封存了"。做完了 = 可以封存，这个推理对归档是成立的。**
> **但它同时被读成了"东西可以用了"——而这个推理不成立，且整个材料包里没有任何一条证据支持它。**

**具体请求**：

| 请求 | 内容 |
|---|---|
| **修正判据表述** | "具备签发条件"改为 **"过程侧待办已归零，具备**归档**条件"**。归档 ≠ 验收，两者不得混用同一个"具备条件"。 |
| **增设可用性判据** | 归档报告须**并列记载**三项，缺一不可：① tag 树门禁（486/0）② 分支树门禁（493/0）③ **最近一次真实会话的可用性结论**（由外部窗口或人工窗签署） |
| **补充披露** | 归档报告须明载"**golden 断言数为 0，门禁全绿不代表可用性已验证**"，防止后续引用者误读 |

### 7.3 **请求升级的一条**：引擎侧发现不得全部归入"非阻塞挂账"

签发件 §四 把若干事项登记为"非阻塞挂账（不进冻结硬清单，登记防遗失）"。

**我的意见**：至少三条应从"非阻塞挂账"升级为 **"cognition 落地前的阻塞项"**：

| # | 项 | 为什么是阻塞项 |
|---|---|---|
| 1 | **Observe 空转**（E12） | cognition 层的输入是"事实"还是"产物"，取决于 Observe 是否真的观察。**Observe 现在是空房间，cognition 拿不到事实。** |
| 2 | **40 条硬切片 + 摘要被丢弃**（E18） | 决定长会话能否保持连续。**cognition 层的全部价值建立在"跨轮连续性"上**，这一条不修，cognition 建不起来。 |
| 3 | **完成判定 keyed to 写盘 / 自证循环**（R1/R2） | 决定 cognition 收到的"完成"信号**可不可信**。若完成信号本身不可信，cognition 层学到的策略全是噪声。 |

**理由**：这三条是 **harness 层的结构病**，不是 engine 层的缺陷。

> 双底座裁定把 cognition MVP 放在主力底座（Codex CLI 等）上，**短期确实绕开了 Hearth 引擎不可用这个事实**——这个决定是对的。
> 但"1+1>2"的终局是 cognition 层**落回 Hearth**。
> **现在不记这三条为阻塞项，等 MVP 验证完价值、回头发现引擎接不住，那时的返工成本最高。**
> **绕开 ≠ 消失，只是把账单推到了更贵的时点。**

### 7.4 一条流程建议

> **把"真实会话可用性"设为归档的独立判据，而不是靠门禁数字代理。**
>
> 具体：归档报告须附一份"最近一次真实会话的可用性结论"，由外部窗口或人工窗签署，与 486/0、493/0 **并列**呈现。
> 三个数字各注口径，**不得混标，也不得以门禁数冒充可用性结论**。
>
> —— 这与签发件 T-2 对门禁口径的处理（486/491/493 分列、禁引 497）是**同一个纪律**，只是把它从"门禁数字之间"扩展到了"**门禁数字 vs 可用性**"。
