# 手工测试日志挖掘 · 维度字典 v1（固定口径）

> 用途：**换模型复跑挖掘时，维度不得增删，只可加样本**，否则多轮结果不可比对。
> 使用者：任何模型 / 窗口。先跑工装拿到数字，再按本字典逐项产出结论。
> 工装：`.workbuddy/mine_deep.py`（第2层）、`mine_deep2.py`（第3层）、`mine_logs.py`（第1层·历史全语料）

---

## 0. 输入与格式前提（先确认，否则数字全错）

| 项 | 口径 |
|---|---|
| 日志格式 | PowerShell + ssh 录屏 + hearth REPL 混合。**不是纯会话日志** |
| 用户输入行前缀 | `hearth>` 或 ` `（另有 ` ` 回显行，会重复一次，计重复时去重） |
| 工具调用行 | `⚙ <tool> → …` |
| 工具结果行 | `  ✓ …`（成功）/ `  ✗ …`（失败） |
| 终态行 | `✓ Done (N steps)` / `✗ Done (N steps)`，**以终态行计数成功率，不采信系统自报的"目标达成"文案** |
| 压缩标记 | `[compacted` |
| 行号 | 直接引用文件行号（`ALL` 合并包需换算：`ALL = 9372 + v0.2.4原行号`） |

**常见坑（已踩过，勿重蹈）**
1. 把回显行当独立输入 → 用户原话会翻倍。
2. 用关键词计数当"失败数" → 会高估（如 `stalled` 出现 10 次但仅 2 次致终态失败）。**终态归因优先于关键词计数**。
3. `2>/dev/null` 出现在命令里 ≠ 失败（那是惯用法），须看退出码/渲染符号。
4. 编码：部分日志存在 UTF-8 被按 GBK/cp1252 解码的乱码段；用 `errors='replace'` 读，关键行手动复核。
5. **⚠️ 结果归属窗口被相位标记截断**（守门人实测踩过）：工具结果行（`✗ 工具出错`）出现在 `◆ Act` / `💭 [act]` 等相位标记**之后**。若"遇到相位标记即停"，会得到 **0% 失败率**的假象（与已知失败数矛盾时必为脚本 bug）。**正确窗口 = 从 `⚙ X` 扫到下一个 `⚙` 之前**。
6. **自校验铁律**：任何统计结果与已知事实矛盾（如"零失败"但日志里有失败行），**先怀疑脚本、再怀疑世界**。本字典第 5 条即由此产生。

## 第 1 层 · 频次表（谁多了谁少了）

对每个版本统计，**按版本分列**：

| 维度 | 说明 |
|---|---|
| 终态 ✓ / ✗ | 成功率 |
| Giving up / give_up | 放弃计数 |
| `权限不够`、exit 159、`核心已转储` | 权限与 seccomp 击杀 |
| `compacted` | 压缩次数 |
| `待问=[1-9]` / `待问=` | 澄清通道使用率（分子分母都要给） |
| `missing_goal_source` | 标记次数（**须同时给"每份草案块内计数分布"**） |
| 401/429、read body、timed out | 通道与超时故障 |
| 工具调用：bash / write_file / apply_patch / read / glob / web_fetch | 工具偏好（**edit 工具不存在，勿单列**） |
| 用户原话行数、用户催"继续"次数 | 交互负担 |
| 目标修订 revision 最大值与次数 | 目标稳定性 |

## 第 2 层 · 轨迹与结构（为什么会失败）

| 维度 | 定义 | 判读要点 |
|---|---|---|
| **失败终态归因** | 对每个 `✗ Done`，回溯 25 行，归为：give_up / stalled / deadline / 工具错 / verify失败 / 预算 | **以此为准，不用关键词计数** |
| **成功/失败步数均值** | 分别统计 | 失败步数 / 成功步数 = 步数浪费倍数 |
| **假成功** | 终态为 ✓，但前 30 行内含 `✗ 工具出错` / `exit code: [1-9]` / `权限不够` / `not found` | 占比越低越好（RC20 修复后应趋近 0） |
| **压缩邻接** | 每个失败点到最近 `[compacted]` 的行距；统计 ≤200 行的占比 | 占比高 ⇒ 压缩与失败相关（RC5 证据） |
| **重试/迷航** | 完全相同命令出现 ≥3 次 | 重复越多 ⇒ 上下文失忆越重 |
| **产出物写后验证率** | `write_file` 之后 12 行内是否出现 read/bash(cat/ls/head/test -f) 回读 | 反映"是否闭环" |

## 第 3 层 · 证据链与用户体验（用户实际感受到什么）

| 维度 | 定义 |
|---|---|
| **连续性追问** | 用户问"还记得吗 / 第一个问题"等 → 抽取系统响应形态。**判据：是否产出回答，还是被转成 `🔁 目标已修订`** |
| **复发抱怨的临场上下文** | 用户说"又出现…"/"又失败…" → 取前 14 行：看系统刚报了什么（常是 `✓ Task completed`） |
| **不完整回复** | 用户抱怨"没回复完"；以及以 `…` 结尾的行数（工具输出截断） |
| **脚手架外泄** | 用户可见输出中出现 `[INTERNAL REFLECTION`、`[Step N of` 等内部前缀 |
| **用户抱怨 → 上文关联** | 每条抱怨取前 2–4 行系统输出，判定"抱怨紧邻的是成功还是失败" |

## 第 4 层 · 源码根因（每个现象追到产生它的那行代码）

| 维度 | 方法 |
|---|---|
| 锚点定位 | 对每条现象，到 `crates/` 找到生产路径行号（**注释/自述不算证据**） |
| 代差考古 | 日志文案 ↔ `git log -S "<文案>"` 比对，确认日志二进制是否早于某 commit（**代差会使野外证据失效**） |
| 根因归并 | 多条现象是否同一根因（如 RC36+RC33+give_up 88% 同源于输入分类缺口） |

## 第 6–10 层 · 模式、衰减、意图、工具、成本

| 层 | 维度 | 定义 |
|---|---|---|
| L6 | **成功模式对照** | 成功轮 vs 失败轮的：步数中位数、1–2 步完成率、各工具使用率 → 提炼**正面判据** |
| L7 | **会话衰减** | 按会话位置四分位统计成功率 / 步数中位数 / 累计压缩数 |
| L8 | **意图类型 × 结果** | 把每轮触发输入分为：任务 / 问询 / 控制 / 元访谈 / 纠偏，与终态交叉制表 |
| L9 | **工具健康度** | 每个工具的调用数 / 失败数 / 失败率；**结果归属窗口 = 从 `⚙ X` 扫到下一个 `⚙` 之前** |
| L10 | **成本与杠杆** | 失败路径步数占比、失败轮 vs 成功轮步数、修复项按 影响面×严重度÷成本 排序 |

**公共底座**：L6/L7/L8 都需要"**触发该轮的用户输入 → 该轮终态**"的关联——取终态行之前最近的一条 `hearth>` 行。

工装：`mine_l678.py`（L6-8）、`mine_l9b.py`（L9 修正版）、`mine_l910.py`（L10）、`mine_l5.py`（元指标）。

## 输出契约（每个模型都必须给的 5 个数）

1. **成功率**（终态行口径）+ 成功/失败步数均值
2. **失败终态归因分布**（按第2层分类表）
3. **假成功率** 与 **产出写后验证率**
4. **失败压缩邻接占比**（≤200 行）
5. **连续性追问命中/被回答数**（第3层）

外加：**新发现的 RC 卡片**（须带 `文件:行号` 锚点）+ **与上一轮结论的偏差**（证伪/修正必须显式写出，如"RC32 由 P0 降级 P1"）。

## 纪律

- **不信报告信源码**：模型给的结论若依赖源码行为，必须回到 `crates/` 找到行号；commit message 与代码注释**不算证据**（已多次证实自述与实现不符）。
- **自我修正显式写**：与上一轮冲突时，写清"上一轮 X，本轮修正为 Y，原因是 Z"。
- **不修 crates/**：挖掘窗口只产出发现与判据，整改交执行窗口。
