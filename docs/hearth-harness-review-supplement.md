# Hearth Harness 补全设计 · 评审补充

> 补 `hearth-harness-improvement-design.md`（v0.2 瘦身版）。
> 原版诊断正确、砍项果断。但"确定性验证层"和"错误分类"两块核心方案里，有四个锻造九轮踩过的坑没补。
> 本补充不推翻原方案，只把这几块落实到可施工、可验收、可防回归。

---

## 补充1：验证层缺"触发时机 + 与 Loop 的对接"（最大缺口）

原稿 §3.2 说"每个写盘工具执行后，调度器自动追加一次产物校验"，但没说清楚：

**问题**：per-step 验证 vs 完成时验证——两者代价差一个数量级。若每个 write_file 都跑 `cargo check`，蛇棋任务写 20 个文件就要跑 20 次编译，节奏全毁。

**定版建议**：

| 触发时机 | 校验内容 | 代价 |
|---|---|---|
| **写盘后（轻）** | 存在性 + 字节数 > 0 + 扩展名匹配 | 秒级，每个文件都做 |
| **自报完成时（重）** | 最终产物完整性（三文件齐全 + 可运行/可编译） | 一次，任务级 |

**关键**：轻校验每个写盘都做（防"写了空文件就声称写完"）；重校验只在 agent 自报 `Done` 时做一次（防"三文件只写出两个就声称完成"）。

**与 Loop 对接**（这是执行窗口最容易做错的地方）：

```
写盘工具完成 → emit VerifyEvent{path, status: "pending"}
  → 轻校验（存在性/字节数）
    → pass → 继续 loop（无感，只是多了个事件）
    → fail → VerifyEvent{status:"fail", reason} → 喂回 loop → replan

agent 自报 Done → 重校验（产物完整性 + 可运行）
  → pass → 真正 Done
  → fail → 回喂缺失清单 → replan（上限 N 次，防死循环）
```

**必须遵守**：验证是**事实产生**（BE 给 `verify: pass/fail` 语义），不是 LOOP 自己猜。校验逻辑独立成函数，loop 只消费结果。

## 补充2：错误分类缺"三级判定映射表"

原稿 §3.1 说"瞬时/参数/不可恢复三级，分别 retry/replan/give_up"，但没有判定规则。执行窗口会自由发挥——这是锻造期"盲目重试 6 次"的另一种死法。

**定版建议**——给一个明确的映射表，而非让执行窗口自拟：

| 错误信号 | 分类 | 动作 | 判定依据 |
|---|---|---|---|
| 网络超时 / 连接重置 / 读 body 中断 | 瞬时 | **retry**（短退避，上限 2 次） | 供应商传输层错误 |
| HTTP 400 / 参数校验失败 / 工具参数缺字段 | 参数 | **replan**（改参数重来，不盲目重试） | 请求本身有问题 |
| HTTP 500 / 供应商内部错误 / 内容策略拒绝 | 不可恢复 | **give_up**（标记原因，不空转） | 重试无意义 |
| 验证层 fail（产物不完整/编译不过） | 参数→replan | **replan**（把缺失/错误喂回） | 见补充1 |

**铁律**：**同请求的瞬时错误最多 retry 2 次**——第 3 次还失败，就升级为不可恢复 give_up。这是"象棋 6 次卡死 245s"的直接药方。

## 补充3：缺"回归保护"——锻造九轮最核心的教训

这是本补充最重的一条。**原稿通篇没提 regression 保护机制。**

锻造九轮的结论是：**没有 wiring 断言的修复，等于没修复**——下一个版本就能无声退化回去。hearth 现在是新起点，如果不从 v0.1.2 就开始挂断言，等 v0.5 回头看，参数容错、传输降级、验证层全退化干净了。

**定版建议**：每修一个真机 bug，就挂一条轻量回归测试（不一定要 Rust 的 wiring 系统，可以是 `tests/` 下的 pytest / cargo test）：

| 修复项 | 回归测试 | 断言什么 |
|---|---|---|
| write_file 参数容错 | `test_write_file_long_content` | 超长 content 不截断、不 missing |
| 供应商传输降级 | `test_provider_transient_retry_capped` | 瞬时错误重试 ≤2 次，第 3 次 give_up |
| 验证层 | `test_verify_detects_incomplete_output` | 三文件缺一 → 验证层 fail（不是 pass） |
| 错误分类 | `test_error_classification_table` | 400→replan / 500→give_up / timeout→retry |

**验收口径（复用锻造期的 V3）**：新测试必须**先红后绿**——在修复前代码上跑是 FAIL，修复后是 PASS。只交绿的测试不接受（没牙齿的测试等于没写）。

## 补充4：验收标准不可量化——"单次成功"不可信

原稿 §6 阶段二验收说"三文件齐全且能打开"，但没说**跑多少次里多少次成功**。

马拉松教训：单次成功是运气，重复成功才是能力。

**定版建议**：验收改为**N 次里 M 次**：

| 任务 | 验收口径 |
|---|---|
| 贪吃蛇 | 5 次跑里 ≥4 次三文件齐全可运行（80%） |
| 象棋 | 5 次跑里 ≥3 次不卡死不截断（60%，象棋历史最难） |
| 通用 | 任一任务连续 3 次全绿才判"已修复"，否则打回 |

**为什么**：真机崩的 bug 是概率性的（超长输出、网络抖动），单次过只能证明"这次运气好"。重复过才证明"螺丝真的拧紧了"。

## 补充5：轻量 transcript 落盘不该"后置"——这是补全其他所有项的前提

原稿 §3.3 把可观测性后置，§8 说"失败无法复盘 → 后置"。**这条有风险。**

锻造九轮最痛的教训就是：`560 runs 零 transcript`，导致 P1/P3 的根因定位走了弯路。如果 hearth 现在不落盘，v0.2 验证层做完后，失败照样无法复盘——等于给"自报完成实则没跑通"换了件衣服，问题还在。

**定版建议**：**最小 transcript 落盘，不进 v0.2 但必须进 v0.1.2 或紧随其后**：

```
每个 run 结束 → 追加一行 JSONL 到 results/transcripts/<session_id>.jsonl：
  {goal, tool_calls 序列, verify_result, final_status, wall_secs}
```

就一行，几百行代码都不用。它的价值是让 v0.2 验证层的失败有据可查——否则验证层 fail 了，你都不知道 agent 到底写了什么、为什么 fail。

**这条和"平台化"不同**：ThreadStore/App Server 是超前，但 transcript 落盘是"单人能复盘自己失败"的最小前提，属于稳定输出的必要项，不该和可观测性系统化一起后置。

## 补充汇总：对原稿的四处改动

| # | 原稿现状 | 补充定版 |
|---|---|---|
| 1 | 验证层无触发时机/对接 | 写盘后轻校验 + 完成时重校验，验证结果作为事实事件进流 |
| 2 | 错误分类无判定规则 | 三级映射表 + 瞬时重试 ≤2 次硬上限 |
| 3 | 无回归保护 | 每修一个 bug 挂一条回归测试，先红后绿 |
| 4 | 验收不可量化 | N 次里 M 次，连续 3 次全绿才判修复 |
| 5 | transcript 后置 | 最小 transcript 落盘提前到 v0.1.2，不复盘则验证层白做 |

---

## 对 v0.2 排期的净影响

原稿估 v0.2 = 3-5k 行。补上回归测试（+500 行）+ transcript（+200 行）后，v0.2 仍是 4-6k 行量级，**不改变"瘦身"定性**，但把"能跑完 + 完成可信"从口号变成"能跑完 + 完成可信 + 失败可复盘 + 修复不回归"。

*锻造九轮用 20 个版本证明了一件事：能跑通是起点，不是终点。补全的方向对——只是别忘了把"防回归"和"可复盘"这两颗最贵的螺丝，从第一天就拧上。*
