## 一、D-38 · 索引无界读入（第 5 个落点）

```rust
fn parse_rust_file(&mut self, file_path: &Path) -> Result<()> {
    let source = std::fs::read_to_string(file_path)?;   // ← 无任何上限
```

**可达性**：`index_tree` 遍历的是**会话 workspace**（`walk_and_parse` 只跳过
`target/` 与点目录），而 workspace 是 agent 自己写的——一个多 GB 的 `.rs`
（生成代码 / 误命名的数据文件 / dump 内容）即可把索引进程 OOM。

**修法**：

```rust
let size = std::fs::metadata(file_path).map(|m| m.len()).unwrap_or(0);
if size > MAX_INDEX_FILE_BYTES {            // 8 MiB
    tracing::warn!("code-index: 跳过 …（> 上限）");
    return Ok(());
}
```

**刻意选择"跳过"而非"截断读取"**：被截断的源码会产出**错误的符号表**，
那比"这个文件没被索引"更糟（**不静默**：跳过必留 tracing 警告）。

## 二、D-39 · 二次方膨胀（红检中量出来的真问题）

### 2.1 现象

第一次红检（临时短路大小守卫）时，测试**跑了 2 分钟以上仍未结束**，只能手动终止。
按"先红后绿"的要求去看红侧到底在干什么，结果发现：

```rust
for i in 0..node.child_count() {
    let child = node.child(i);      // ← tree-sitter 的 child(i) 是 O(i)
```

**`Node::child(i)` 每次都要从第一个子节点数过去** ⇒ 对整个孩子列表是 **O(n²)**。
那个 8 MiB 文件约 74 万个顶层节点 ⇒ ~5×10¹¹ 次指针步进 —— **这就是"挂住"**。

同一文件里还有第二处同型问题：

```rust
let content = source.lines().skip(start.row).take(end.row - start.row + 1)...
```

`source.lines()` **每个 chunk 都从头数一遍** ⇒ O(文件行数 × chunk 数)。

### 2.2 修法

| 位置 | 前 | 后 |
|---|---|---|
| `extract_symbols` | `for i in 0..child_count() { node.child(i) }`（O(n²)） | `node.children(&mut cursor)`（O(n)） |
| `chunk_file` | 同上 | 同上 |
| `chunk_file` 取行 | `source.lines().skip(...).take(...)`（每 chunk O(L)） | 预先 `let lines: Vec<&str> = source.lines().collect()`，按下标切片（O(L) 一次） |

> 附带收益：`children()` 永不产出 `None`，原 `CODEIDX-1` 的 "skip the slot"
> 防御随之不再需要（该防御针对的正是 `child(i)` 可能缺位）。

### 2.3 实测对照（同一测试、同一 8 MiB 文件）

| 状态 | 结果 |
|---|---|
| 无大小守卫 + **未**修 O(n²) | **> 2 分钟仍未结束**（手动终止） |
| 无大小守卫 + **已**修 O(n²) | **2.40s** 结束，且**如预期 FAILED**（`huge_marker_fn` 出现在符号表里 → 证明"守卫才是决定性的那一层"） |
| 有大小守卫（最终态） | **0.01s**，ok |

## 三、"先红后绿"证据链

```
红（守卫短路 + O(n²) 未修）：> 2 min 挂住（手动终止）
红（守卫短路 + O(n²) 已修）：2.40s，FAILED —— 断言"超大文件的符号不得出现"
绿（守卫在位）            ：0.01s，ok
```

**永久回归测试**：`test_p0_12_index_skips_oversized_files`
—— 造一个**合法 Rust** 的 8 MiB+ 文件（超长注释 + 一个可识别符号），
断言"正常文件照常索引、超大文件必须被跳过"。
（刻意用合法 Rust：若"没被索引"是因为解析失败，断言会以另一种方式暴露。）

> O(n²) 那条**没有**写成永久测试：唯一可判据是耗时，而耗时断言在 CI 上必然抖动。
> 它的回归保护来自"红侧实测记录 + 代码注释写明量级"。

## 五、**新门禁第一次全量跑就抓到自己的源码与战报**

P0-11 刚建好的 `secret_scan_gate`，在本次全量门禁里报出：

```
密钥扫描门禁未过：发现 2 个文件含未登记的疑似明文密钥：
  - crates/codex-cli/tests/secret_scan_gate.rs  ×1
  - docs/P0-11战报·入库卫生与密钥扫描门禁 v1.0（…）.md  ×1
```

**真因**：PEM 规则原用零散字面量 `PRIVATE KEY-----` —— 而**扫描器自己的源码**
和**描述它的战报**里都必须写出这串文字，于是"说明文字"被判成命中。

**修法**：只认**完整头行**，且头行由 `{begin}` 插值拼出（字面量在源码里**不连续**）：

```rust
let begin = "BEGIN";
let pem_markers = [
    format!("-----{begin} RSA PRIVATE KEY-----"),
    format!("-----{begin} PRIVATE KEY-----"),
    format!("-----{begin} OPENSSH PRIVATE KEY-----"),
];
```

> 这条恰好验证了 P0-11 战报里那句"**门禁必须自带红侧证明**"——
> 它在第一次真实使用时就证明了**自己会拦**（把误报也拦了），
> 而不是"写完了看起来很对"。

## 六、方法论沉淀（第 11、12 个变体）

> **第 11 个：「无界」不只有内存一种形态。**
> 前五张卡都在治"读太多字节"；本卡量到的却是"**算太多次**"——
> `child(i)` 的 O(n²) 与 `lines().skip()` 的 O(L·k)，都不会多吃一字节内存，
> 但会把一次索引变成**看起来像死锁的挂起**。上限只解决前者。

> **第 12 个：「验证一个上限有效」和「验证一个上限必要」是两件事。**
> 若我写完大小守卫就收工，就永远不知道 O(n²) 的存在——
> 因为守卫会把病态输入挡在门外，**症状随之消失**。
> 红检（临时短路守卫）把"被守卫掩盖的第二个缺陷"逼了出来。

**固化为检查项**：
1. **凡"先看大小再读"的守卫，问一句"守卫之后剩下的输入规模，处理代价是几阶"**——
   上限只限制输入**大小**，不限制算法**阶数**；
2. **凡遍历 AST/树/长列表，用游标/迭代器（`children`/`walk`），禁用 `child(i)` 式索引循环**；
3. **凡在循环里"从头数到第 n 行/第 n 个"的写法（`skip`/`take`/`lines()`），先问能不能预切一次**。
