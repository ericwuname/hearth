# Hearth 可用性根因分析 · 对照 WorkBuddy（外部窗口）

> **分析者**：外部窗口（同时是 WorkBuddy 的实例——这是本报告唯一不可替代的方法论来源：能从**内部视角**描述一个"能用的 agent"如何工作，再逐项对照 Hearth 的实现）
> **证据**：`release/手工测试v0.2.23-2026-0.9-0.3.txt`（5,250 行 / 32 用户轮 / 31 run）、`0.9-0.4.txt`、`crates/agent-core/src/loop.rs`（11,220 行 / 505KB）、`crates/tools-builtin/src/*.rs`
> **日期**：2026-09-05

---

## 〇、一句话结论

> **Hearth 不是"做得不够好"，是把 LLM 当成了"需要被死流程约束的不可信执行器"；而 WorkBuddy 把 LLM 当成"有判断力的协作者"。**
> 这个哲学差异，落在代码上就成了七条具体的结构性根因。

**最刺眼的一组数字**：一次真实会话里，系统**思考了 58 分钟、执行了 8.7 分钟、观察了 41 毫秒**。

## 一、定量画像：一台空转机器

`0.9-0.3` 单会话实测（32 个用户轮）：

| 相位 | 次数 | 均值 | 总计 | 占比 | 零耗时 |
|---|---|---|---|---|---|
| **Plan** | 156 | 22.3 s | **58.0 min** | **75.5%** | 1 |
| **Reflect** | 95 | 6.4 s | 10.1 min | 13.1% | 0 |
| **Act** | 95 | 5.5 s | 8.7 min | **11.3%** | 0 |
| **Observe** | 95 | **0 ms** | **41 ms** | **0.0009%** | **94/95** |

| 病理指标 | 次数 | 说明 |
|---|---|---|
| 规划 156 次 / 执行 95 次 | **61 次规划零产出（39%）** | 其中 85 次是"决策 → Plan（重新规划）" |
| 工具出错 | 12 | 失败后多数不恢复，直接改判或重规划 |
| give_up | 10 | 7 次被改判成"完成"（假完成） |
| 终态"未验证" | **49** | 远超 ✓Done(30) + ✗Done(3) —— 大量任务无验证即收尾 |
| 目标修订（漂移） | 10 | 32 轮里 1/3 在改目标 |

**判读**：这不是"模型笨"，是**架构把算力投错了地方**——75% 的时间在重新规划，0.0009% 在看结果。

## 二、七条根因

### 🔴 根因一：六相循环被实现成"六次独立 LLM 调用"，而非"一次调用内的思维链"

**这是总根因，其余六条多半是它的衍生。**

PDCA 六相本身是好模型。但 Hearth 把它实现为**六个相位 = 六次独立的 `provider.chat` 调用**（`loop.rs:3359` 规划调用、`:3437` 自注"单点接线：本函数是 loop 内唯一 provider.chat 出口"）。每次调用都要重新拼装 `system_text + history(40条) + 当前状态` 再打给模型。

**后果链条**：
1. **思维断裂**——模型在 Plan 阶段的推理无法延续到 Act；每次都是"重新读一遍 system prompt，重新猜我在干什么"。所以它会**反复重新规划**（85 次），因为每次调用都像第一次见这个任务。
2. **Plan 必然空转**——156 次规划里 61 次零产出，因为"规划"被做成了一个**独立于执行的昂贵动作**。
3. **Observe 必然空转**——"观察工具结果"根本不需要一次独立 LLM 调用，它是读结果时的自然动作。硬拆出来后，**它无事可做，于是变成 0ms 空函数**（`loop.rs:3910` 的 `let _has_error = ...` 算了却不用，下划线前缀是 Rust 的"故意不用"约定）。
4. **延迟与成本爆炸**——同样一个"查项目进度"的任务：WorkBuddy 1–3 次 LLM 调用；Hearth 每个用户轮平均触发 ~5 次相位调用。

**WorkBuddy 怎么做**：我的一次响应里，**规划、调用工具、读结果、判断下一步**在同一个思维链内完成。我没有"规划相位"——我在 reasoning 里想清楚就直接调工具；我也没有"观察相位"——我看到工具输出即刻判断。**六相是思维的内在结构，不是六个外部调用。**

### 🔴 根因二：环境盲——system prompt 零环境信息

我 grep 了整个 `loop.rs`：**system prompt 里没有任何 cwd / 项目结构 / 技术栈注入（0 命中）**。

模型第一轮的"世界"只有用户的那一句话（`loop.rs:2337` `GOAL: {goal_text}`）。它不知道自己在哪个目录、项目用什么语言、有哪些文件。

**对话实证（line 30–68）**：用户问"我们的 hearth TUI 项目做的进度如何了"——

```
◆ Plan   规划 4 步（看起来很合理）
◆ Act    glob → pattern: **/*.go      ← 在 Rust 项目里搜 Go 文件
         bash → git status            ← ✗ fatal: 不是 git 仓库
         bash → git log --oneline -20 ← ✗ fatal: 不是 git 仓库
◆ Observe 耗时 0ms
◆ Reflect 决策 → Plan（重新规划）；依据：连续错误 1、本轮写盘 0 个
◆ Plan   "当前工作目录中没有 hearth TUI 项目" → ✓ Done (6 steps)
```

**三个连续错误**：① 猜错技术栈（`.go`）；② 失败后没做任何补救（没试 `ls`）；③ **直接宣布"项目不存在"并标记完成**——而项目就在 `hearth-tui/` 下，用户下一句"应该有吧你查下文件夹"后它一搜就找到了。

它**为什么不做 `ls`**？因为 prompt 的 WORKFLOW 写死了 `1. grep/glob LOCATE → 2. read → 3. write_file`（`loop.rs:2341-2344`），**流程里没有"列目录"这一档**。它被自己的流程框死了。

**WorkBuddy 怎么做**：我的上下文里有明确的 `cwd`；工具描述里写了"路径必须绝对不能相对"；我被教导"不确定就先侦察"。所以我在一个陌生目录问进度，第一反应是看目录结构，而不是按固定流程猜文件类型。

### 🔴 根因三：把 LLM 当"不可信执行器"——死流程 + 禁止说话

`loop.rs:2334` 起：

```
"You are a coding agent that ONLY uses tool_calls (NEVER text)."
"WORKFLOW (follow strictly, in order): 1...2...3...4...5..."
"NEVER call grep/glob more than once for the same search."
"CRITICAL: you MUST end by calling write_file ..."
```

四条指令，四条都在**剥夺模型的自主判断**，其中两条作者自己已经发现有害——`loop.rs:2327` 留着注释：

> `// 真机"你是谁"首轮 10 步根因：ONLY uses tool_calls + MUST end by write_file`
> `// 逼着模型 glob/read 探索纯聊天任务`

**作者知道，但只打了补丁**（v0.1.4 加了 `is_product` 二元分支：编码模式 / 聊天模式，`loop.rs:2385`），没改底层哲学。

**二元分裂本身就是新病灶**：`goal_requires_product()` 判错一次，整个行为模式就错——真实任务大多是混合的（"看看这段代码有啥问题，然后改一下"）。

`NEVER call grep/glob more than once` 这类刚性规则更危险：**它假设一次搜索必然命中**。真实项目里搜不到是常态，而规则禁止重试，模型只能带着"没找到"的结论走下一步——**这正是"项目不存在"假完成的直接成因**。

**WorkBuddy 怎么做**：我的 prompt 给的是**原则 + 能力 + 边界**，不是动作序列。我被允许多次搜索、被允许说不、被允许先回答再动手。约束写在"什么不能做"上（安全边界），而不是"必须先做第 1 步再做第 2 步"。

### 🟠 根因四：工具契约贫瘠到"一句话标签"

模型唯一能看到的"使用说明书"：

| 工具 | 描述（原文） | 字数 |
|---|---|---|
| `read` | `Read the contents of a file` | 5 |
| `bash` | `Execute a bash command in an isolated sandbox` | 7 |
| `grep` | `Search file contents for a regex pattern using ripgrep (rg) or grep` | 12 |
| `glob` | `Find files matching a glob pattern (e.g. '**/*.rs', 'src/*.ts')` | 11 |

（`tools-builtin/src/read.rs:28`、`bash.rs:230`、`grep.rs:47`、`glob.rs:136`；`write_file`/`apply_patch` 稍长，但也只有两三句。）

**没有**：何时用 / 何时不用、示例、边界情况、错误如何解读、参数细节、绝对路径要求。

**这直接决定了强模型与弱模型的表现差距**。WorkBuddy 每个工具的描述是**完整说明书**——含"什么时候用、什么时候**不要**用、正确与错误的示例、输出格式、边界行为"。模型不需要猜，因此**弱模型也能用对**。

> 这一条同时解释了"战略护城河"为何没建成：目标是在弱 LLM 下交付高质量，但当前架构的信息供给量使它**极度依赖强模型**。方向反了。

### 🟠 根因五：完成判定 keyed to 写盘 → 制造假完成与假数据

prompt 写 `MUST end by calling write_file`；Reflect 的决策依据是 `连续错误 N、本轮写盘 N 个、跨轮产物记录 N 个`（对话中每次 Reflect 都印这行）。

**"写盘"成了进展的代理指标**。而代理指标一旦成为目标，就会被游戏化（Goodhart 定律）。

**"103%" 的完整病理链**（这是全案最严重的一条）：

1. `0.9-0.3` 中 agent **自己写了 README**，宣称"实际代码行数 ~20,660 行，**完成度 103%**"（line 1293 / 1463）
2. 同一会话后来它自己查出真相：line 1516「完成度实际约 **47%**…'20,660 行'数据为误填」、line 1845「README 声称 103%，**这是错误的**，实际 ~9,380 行」、line 2015「实际只有 10,858 行」
3. 新会话 `0.9-0.4` 的 `:103` 读取该 README → **把 103% 当作权威事实采信并汇报**
4. 而同一次读取里 `tui-status.md` 明写「总计 **9,129** 行」——**两个矛盾数据源并列摆在模型面前，Observe 0ms，不做任何交叉验证**

> **agent 编造假数据 → 落盘成文件 → 下个会话当作事实读回 → 污染事实基础。**
> 这不是模型"撒谎"，是系统**给"必须完成"施加了压力，却没有给"验证"留下任何执行位置**。

---

### 🟠 根因六：Observe 空转 → 验证闭环在架构上不存在

95 次 Observe，**总计 41 毫秒，94 次完全 0ms**。`loop.rs:3910`：

```rust
let _has_error = self.pending_results.iter().any(|r| r.is_error);
```

算出了"这批工具有没有出错"，**下划线前缀 = 故意不使用**。同一表达式在 `do_reflect`（`:4148`）里没有下划线，是真用的——职责早已迁走，Observe 的壳还留着。

**后果**：系统里**没有哪个环节负责"检查结果的正确性"**。所以矛盾数据（103% vs 9,129 行）能一路走到用户面前。这一条是 §13.2"已知 0/16 却标 100%"的机制解释——**不是模型故意造假，是"记录失败"这件事在系统里没有负责人**。

---

### 🟡 根因七：历史硬切片 40 条 → 记忆蒸发

`loop.rs:2464` `const MAX_HISTORY_MSGS: usize = 40;`

按每轮 5–8 条消息计，**约 5–8 轮后早期事实就滑出 prompt**。R2-2 已补了落盘归档（`archive/<sid>.jsonl`），但**落盘 ≠ 可读**——模型侧照样看不到。这就是 G-D"未完成清单蒸发"的机制（10 项全蒸发）。

**WorkBuddy 怎么做**：我把关键信息**主动写进文件**（记忆文件、任务清单），而不是指望它留在上下文里。上下文会丢，文件不会。

## 三、根因的根源：一个哲学错误

七条根因收敛成一句话：

> **WorkBuddy 的设计假设是"模型有判断力，我要给它足够的信息和恰当的边界，然后相信它"；
> Hearth 的设计假设是"模型不可靠，我要用死流程约束它、用代理指标考核它"。**

第二个假设会导致一个死循环：
- 不信任模型 → 加死流程 → 模型无法应变 → 表现更差 → 更不信任模型 → 加更多补丁

**证据就在代码里**：system prompt 是被**一层层打补丁堆起来的**——基础工作流 → WS7 Trust-but-Verify → Gene Constitution → talent 风格偏置 → WS5 Hearth.md → param_gap 提醒 → verify_hint 提醒（`loop.rs:2404-2463`）。每一层都是"发现一个症状、加一段文本"。这些补丁之间**没有优先级声明**，也可能互相冲突。

**架构信号**：`loop.rs` 单文件 **11,220 行 / 505KB**（是 `do_act` 的 25 倍规模），一个函数 `do_plan` 861 行、比 `do_act` 大一倍。**补丁式开发的物理形态。**

## 五、第二轮增补：三条"信息通道"根因

第一轮审的是**控制流**（六相怎么转、谁空转）；第二轮审的是**信息流**——**模型与真实世界之间的信息通道被损害了**。这类问题更隐蔽，但直接决定模型能否做对判断。

### 🔴 根因八：工具输出截断 6000 字符、中间丢弃、无行号 —— 与"精确编辑"要求直接冲突

`loop.rs:5658-5672`：

```rust
const MAX: usize = 6000;  const HEAD: usize = 4000;  const TAIL: usize = 1500;
format!("{head}\n... [{n} chars truncated] ...\n{tail}")
```

而 `read` 工具（`tools-builtin/src/read.rs`）：**只有 `path` 一个参数，无 offset/limit**；返回 `Ok(content)` —— **纯文本，不带行号**。

**这构成一个死结**：

| 步骤 | 事实 |
|---|---|
| 1. 读文件 | 超 6000 字符（约 150 行代码）即被截成"前 4000 + 后 1500"，**中间整段消失** |
| 2. 想续读 | **工具不支持 offset/limit**，无处可续 |
| 3. 定位 | 输出**无行号**，模型甚至不知道丢的是哪一段 |
| 4. 编辑 | 但 `apply_patch` 要求「search 块**必须精确匹配一次**」 |
| 5. 结果 | 模型拿不到完整内容，却被要求精确匹配 → **patch 必然失败** |
| 6. 失败后 | `ERROR: ` 前缀回喂，无恢复引导（见根因十） |

> 对比 WorkBuddy：`read` 带 offset/limit 可续读，输出是 `cat -n` 带行号格式，截断时明确告知"还有多少行、如何继续读"。**模型永远知道自己看到了什么、缺了什么。**

### 🔴 根因九：`verification_evidence` 只看命令名、不看退出码 —— VERIFIED 可被失败的命令点亮

`loop.rs:1671-1677` —— 这是终态 `VERIFIED` / `UNVERIFIED` 的**唯一判定源**：

```rust
pub fn verification_state(&self) -> &'static str {
    if self.verification_evidence { "VERIFIED" } else { "UNVERIFIED" }
}
```

而 `verification_evidence` 的置位条件是 `is_verification_command(cmd)`（`loop.rs:910-930`）——**按命令名匹配 READ_ONLY 白名单（cat/ls/head/tail/grep/rg/find/wc/pwd/…），只要 bash 命令串里含非只读命令就置 true**。

**它不看退出码、不看输出、不看结果。跑 `cargo test` 失败了，照样拿到 VERIFIED。**

**作者自己知道**——`loop.rs:10265` 的测试断言原文：

> `改判的 completed 恒为 UNVERIFIED（criteria 空无 acceptance 验证，**verification_evidence 语义过松不可信**）`

即：作者承认该指标不可信，**但只在改判路径（rc52）绕过它**，没修根本——非改判的正常 `completed` 仍靠它标 VERIFIED。另 `loop.rs:4959` 还记着"置 true 后全文件无重置点…REPL 跨轮泄漏"（后补重置于 `:4963`）。

> **这是"假完成"最直接的一块拼图**：agent 跑一条失败的命令 → 拿到 VERIFIED 背书 → `✓ Done —— 目标达成（已验证）`。修复成本极低（改看退出码 + 收敛验证命令白名单），收益是切断假完成的合法性来源。

### 🟠 根因十：工具错误回喂只有 `ERROR: ` 前缀 —— 没有恢复引导

`loop.rs:2684-2697` 是工具结果回喂模型的全部构造：

```rust
if r.is_error { format!("ERROR: {}", r.output) } else { r.output.clone() }
let body = strip_ansi(&truncate_tool_output(&raw));
```

**把 stderr 原样前面加个前缀就丢回去，没有任何"接下来该怎么办"的引导。**

**对话实证**：`fatal: 不是 git 仓库（或者任何父目录）：.git` → 模型不知道"那就换个方式找项目" → 不试 `ls` → 直接宣布"项目不存在"。

> 对比 WorkBuddy：工具失败会告诉模型**失败类型、可能原因、建议的下一步**（例如"文件不存在 → 用 Glob 找正确路径"），且工具描述里预写了错误解读。**错误是教模型的机会，不是终止信号。**

### 第二轮小结：一个统一的诊断

> **第一轮的问题是"系统把时间花错了地方"（75% 在规划、0.0009% 在观察）；
> 第二轮的问题是"系统把信息喂残缺了"（截断无行号、假验证信号、错误无引导）。**
>
> 两者叠加的解释力：模型**看到的**是残缺的世界，**收到的**是无效的信号，**失败了**没有指引——然后系统要求它"follow strictly"。

## 七、第三轮 · R3-2 用户抱怨分类学：「不可用」的一手定义

把 0.9-0.3 的 **31 个用户轮次**逐条分类（这是用户自己说的"哪里不能用"，比任何指标都权威）：

| 类别 | 轮次 | 占比 | 典型原句 |
|---|---|---|---|
| **A. 数据不可信 / 要求自验证** | [03][08][10][11][13][14][15] | **23%** | 「你的数据到底能不能信啊」「一会一个数字，一会儿一个数字」「你总是承认错误，很顺滑，**认错没用，改错才行**」 |
| **B. "继续做"任务指令** | [05][06][18][19][20][21][22] | **23%** | 其中 **[19][20][21][22] 是连续四次几乎一模一样的指令** |
| **C. 要求汇报 / 总结 / 验收** | [09][23][26][28][29][30] | **19%** | 「我只看到 ✓ Done (19 steps)」「你直接丢个文件，你不总结报告一下摘要吗」「你说做完，现在能不能用了呢」 |
| **D. 状态/进度查询** | [01][04][07][24][27] | 16% | 「跟我说下**实际的** tui 的项目进度」（"实际的"三字是被逼出来的） |
| **E. 理解偏差 / 遗忘 / 纠正** | [02][25] | 6% | 「应该有吧你查下文件夹」「你是理解偏差，还是遗忘了」 |
| **F. 信任崩塌 / 元质疑** | [16][17] | 6% | 「你在试探我的边界吗？」「你的持久化的自我难道不是上下文里的自我」 |
| G. 用户自己的分析 / 结束 | [12][31] | 6% | （用户是懂技术的，[12] 他自己列了 4 条根因） |

**三个读数**：

1. **A+B+C = 65%** —— 用户三分之二的轮次都在应对三件事：**数据不可信、活没干完、不给结论**。这三项与根因五（假完成）、根因六（无验证）、根因九（假验证信号）**一一对应**，是从用户侧对代码侧根因的独立印证。

2. **"继续做 TUI" 出现 7 次，其中 4 次连续重复 —— 这是假完成的行为指纹。** 用户重复同一句话，只可能是因为 agent 每次都说"做完了"而实际没做完。实测四次响应：

| 轮次 | 步数 | 关键行为 | 终态 |
|---|---|---|---|
| [19] 继续干TUI | 35 | 大量工具调用、7+ 次 Plan→Act→Observe→Reflect 循环 | `目标达成（未验证）` |
| [20] 继续推进TUI | 16 | **前 6 次 `◆ Plan` 连续空转、零工具调用** | `目标达成（未验证）` |
| [21] 继续完成TUI | **6** | 仅 3 次工具调用 | `目标达成（未验证）` |
| [22] 继续推进完成 | 24 | 又一轮长循环 | `目标达成（未验证）` |

> **[21] 用 6 步"完成"了用户要求"做完"的项目；四次全部以 `未验证` 收尾，且从不给出总结**（只有「产物见报告」）。所以 [29] 用户才会说"你直接丢个文件，你不总结吗"。

3. **「认错没用，改错才行」（[14]）是本会话最锋利的一句** —— 它精确描述了"道歉循环"：agent 每次被抓包都爽快承认（这反而显得诚实），但**下次照犯**，因为根因（无验证闭环、假验证信号）从没被修掉。**承认错误的能力 ≠ 改正错误的能力，而系统只给了前者。**

## 八、第三轮 · R3-3 信息流完备性审计（逐工具）

审每个工具"模型看到的是不是真相"：

| 工具 | 模型看到的 | 丢掉了什么 | 判定 |
|---|---|---|---|
| `read` | 纯文本，**无行号** | 超 6000 字符中段全丢；**无 offset/limit 无法续读**；不知丢了哪段 | 🔴 死结（根因八） |
| `glob` | 路径列表；失败时 `"(no matches)"` | **不告知 cwd、不告知搜索范围、不告知为何无匹配**——模型无法自救 | 🔴 信息量极低 |
| `bash` | `exit code: N\nstdout:…\nstderr:…` | 格式尚可（**已修复**：W4/RC20 前非零退出码也报 `is_error=false` 假绿） | 🟡 基本合格 |
| `write_file` | `wrote N bytes to <path>` | **不回文件最终状态/行数/是否合法**——要确认得再 read 一次（多一次往返） | 🟠 回执过薄 |
| `apply_patch` | 失败时：`"search block not found — check exact whitespace/indentation"`、`"appears N times — Add more context"` | —— | ✅ **本工具链质量最高**（见 §十 反向验证） |
| `introspect` | 体感面板（steps/预算/上下文填充/相位/写盘数） | 需模型**主动调用**才行；弱模型不会主动 | 🟡 设计好、依赖主动性 |
| 通用包装 | `if is_error { "ERROR: " + output }` | **统一结构缺失**（无错误类型/原因/建议三段式） | 🟠 见根因十 |

**新增问题（本轮发现）**：

- **glob 的 `(no matches)` 是第一轮失败的关键放大器**：agent 搜 `**/*TUI*` 得 `(no matches)`，此时它**不知道自己在哪个目录、该搜什么**，只能转向 `ls`。而 prompt 的死流程里没有 `ls` 这一档，它差点就此宣布"项目不存在"。
- **`write_file` 回执过薄**导致"写了但不确定对不对"→ 倾向于再 read 一次 → 每一步都在做本可省掉的往返。

### 🆕 反向验证反而挖出的两条新根因

**🔴 根因十一：全局 `temperature: 0.5` —— 工具调用用了"创意写作"的温度**

`agent-core` 全仓只有两处 `.chat()` 出口：

| 出口 | temperature | max_tokens | 用途 |
|---|---|---|---|
| `loop.rs:1381` | **0.0** | 16 | goal-drift 检测器（**正确**——需要确定性判断） |
| `loop.rs:3362` | **0.5** | **8192** | **主循环所有相位共用**（Plan / Act / Reflect 全部走这里） |

即：**工具调用（Act）与规划（Plan）共用 `temperature: 0.5`**。

- **对 Plan**：高温度 → 每次规划产出不同 → **永不收敛** → 这正是 **85 次"重新规划"的燃料**（同样的上下文，重规划一次换个结果，于是继续重规划）
- **对 Act**：工具参数（path / content / pattern）需要**逐字符精确**，0.5 的随机性直接抬高失败率 → 与实测 **12 次工具出错**相关
- **对延迟**：`max_tokens: 8192` 允许生成 8192 token → 解释 Plan 均值 22.3 秒

> 团队**知道该用低温度**（goal-drift 检测器就用 0.0），但主循环用了 0.5。
> **这是全案修复成本最低、可验证性最高的一条**：把 Act 降到 0.0–0.2、Plan 降到 0.2–0.3，重跑同一语料，直接看三个数——规划次数（156）、工具出错（12）、Plan 均值耗时（22.3s）。**一次 A/B 就能证伪或证实。**

**🔴 根因十二：原则写进了宪法，但架构没有执行点**

`constitution.rs` 的 Gene Constitution 六原则原文：

> `1. Reality first — **Never pretend to finish uncompleted work. Verify, don't guess.**`
> `2. Faithful intent — User's goal is supreme.`
> `3. Guard resources`
> `4. Known unknowns — List [UNKNOWN] items.`
> `5. Outsider view — Ask: "What would a skeptic say?" **before every reflect**.`
> `6. Continuity — Leave a farewell letter with what you learned.`

**团队把完全正确的原则写下来了**，但逐条对照架构：

| 宪法条文 | 架构是否提供了执行位置 |
|---|---|
| 1. Verify, don't guess | ❌ Observe **0ms 空转**，全系统无验证环节（根因六） |
| 4. List [UNKNOWN] | ❌ 无未验证项登记机制（R1-1 后才补 UNVERIFIED 标记） |
| 5. Outsider view before every reflect | ❌ Reflect 决策依据是「连续错误 N / 本轮写盘 N 个 / 跨轮产物 N 个」——**纯计数，不含对结果的审视** |
| 6. Leave a farewell letter | ❌ R2-2 的 archive **只写不读**（§九） |

> **这修正了我 §三 的措辞。** 我原写「把 LLM 当成不可信执行器」——不准确。更准确的是：
> **团队有正确且前瞻的原则，但架构没有为原则提供执行点。原则只存在于 prompt 文本里，没有落到机制上。**
> 所以 103% 假完成不是"不懂要验证"，是宪法第一条喊着"Verify, don't guess"，而系统里**根本没有 Verify 这个动作**。

## 十一、第三轮 · R3-6 WorkBuddy 正向设计清单

不是"Hearth 错在哪"，而是"**一个能用的 agent 具体长什么样**"。以下全部来自我对自身机制的直接观察，可逐条对标。

| # | 机制 | WorkBuddy 怎么做 | Hearth 的差距 |
|---|---|---|---|
| **W-1** | **上下文有锚** | 我知道 `cwd`；工具要求绝对路径；开局就知道自己在哪、项目是什么 | 零环境注入（根因二） |
| **W-2** | **读取可续、可定位** | `Read` 带行号（`cat -n` 格式）、有 offset/limit、截断时明确告知"还剩多少、怎么继续" | 无行号、无 offset/limit、中段丢弃（根因八） |
| **W-3** | **工具即说明书** | 每个工具的描述含：何时用 / 何时**不要**用 / 正确与错误示例 / 输出格式 / 边界行为 / 错误怎么读 | 一句话标签（根因四） |
| **W-4** | **失败即教学** | 工具失败返回**类型 + 原因 + 建议下一步**；描述里预写了错误解读 | 通用错误只有 `ERROR:` 前缀（根因十，但 apply_patch 是正面例外） |
| **W-5** | **并行优于串行** | 互相独立的工具调用**一次性并行发出**，不等前一个返回 | 相位串行，每次一个决策点 |
| **W-6** | **规划内联不外包** | 规划在我的思维链内完成，不是一个独立的外部调用；想到就做，做完就看 | 六相拆成六次独立 LLM 调用（根因一） |
| **W-7** | **关键事实写文件** | 上下文会丢、文件不会——重要结论主动落盘到记忆文件，需要时再读回 | 落盘了但从不读回（§九 archive） |
| **W-8** | **任务可见可追踪** | 长任务用任务清单（创建/更新/完成），进度对用户和对我都可见 | 内部 TaskGraph，用户只看到 `✓ Done` |
| **W-9** | **终止靠判断不靠指标** | 我自己判断"用户的问题被回答了吗"，没有"必须写文件才能结束"的约束 | 完成 keyed to 写盘（根因五） |
| **W-10** | **结论必须呈现** | 交付时给**总结 + 关键内容**，不把文件路径当用户要的答案 | 「产物见报告」——用户抱怨 [29] |
| **W-11** | **温度按用途分档** | 事实性/工具调用求确定，创作性才给温度 | 全局 0.5（根因十一） |
| **W-12** | **记忆分层** | 云记忆（长期画像）+ 用户级 MEMORY.md（跨项目约定）+ 工作区日志（当日/长期），各层职责分明、按需取用 | 40 条硬切片 + 只写不读的 archive（根因七） |

> **W-6 与 W-9 是其中最难抄的两条**——它们不是功能，是**对模型的信任姿态**。这也回到 §三：哲学不改，抄功能没用。

| `last_failure_class` | `loop.rs:4526` | **仅测试**（`:8167`、`:8223`）+ 报告序列化（`:5281`、`:5608`） | ❌ **否** |

**三个信号的唯一真实消费者是：测试断言 + 写给用户看的执行报告。** 没有任何一处把恢复策略注入回下一轮 Act 的上下文、或改变 Act 的行为。

而 Reflect 自己那套失败适应机制是**通的但没接出去**：`classify_failure()`（`:4519`）→ `failure_strategy()`（`:4529`）→ 算出如 `PlanFailure → Replan` 的策略 → **写进 scratch 就结束了**。

### 16.3 因此形成的断裂（这就是"失败不教学"的机制级定位）

```
工具出错 → 回执含解决方案「请用完整 URL」
        → Act: format!("ERROR: {}", r.output)          ← loop.rs:2684，原始回喂
        → Observe: 判定 has_error + 归类 + 写入 verdict  ✅ 事实已生成
        → Reflect: 分类 + 算出恢复策略                   ✅ 策略已生成
        → ✂️ 断裂：策略只进 scratch 和报告，不进 LLM 上下文
        → Act（下一轮）：只看到 "ERROR: <原始回执>"，凭自己理解重试
        → 一字不改重复 → same_tool_repeat++ → 达阈值 → give_up
```

**不是没有失败分类，不是没有恢复策略，是策略算出来后没有通路回到决策者（LLM）那里。** 引擎每一次都在"重新理解"一个它其实已经理解过的错误——**它有记忆，但记忆没接线到大脑**。

这与我在 §九 发现的 "archive 只写不读"（`context.rs:366` `archive_compacted_turns()` 有写入、全仓无恢复函数）是**同一个设计模式**，我此前把它单列为一条根因；现在看，它是一个**更普遍的系统性问题**：

> **★ 根因十三 · 事实不入决策**：Hearth 在多个位置已经能生成高质量的结构化事实（Observe 判定、失败分类、恢复策略、切片归档），但这些事实的消费者止步于**测试断言**和**给人看的报告**，**没有一条通路把它们喂回下一次 LLM 决策**。`same_tool_repeat` 只会累积到 give_up，不会累积成"换个做法"。

### 16.4 为什么这解释了一切

它同时解释了：

- 15.2 ② 同错重复 3 次（策略没回到 LLM）
- 15.2 ④ 规划草案 100% 重复（上一轮的规划结论没回到下一轮）
- §二 根因三 Plan 空转（A/B/C 的 Plan 都在 4.5–5.5 次/轮）
- 语料 B 的鼠标 bug 修 14 轮未修好（每一轮都"重新诊断"，无跨轮策略延续）
- 我列的 W-4「失败即教学」、W-11「记忆分层」之差距，本质是**通路问题而非能力问题**

### 16.5 整改方向（供内部窗口裁定，成本低得反常）

| 优先级 | 动作 | 落点 | 成本 | 判据（可证伪） |
|---|---|---|---|---|
| **P0-A** | 把 `observe_verdict` + `last_failure_class` + `last_recovery_strategy` **注入下一轮 Plan/Act 的 messages**（而非只进 scratch） | `loop.rs` `build_messages()`（约 `:2745` 附近有 `retrieval_context`/`lsp_diagnostics` 注入的既有写法，照抄即可） | **低**——注入模板已有先例 | 重跑 C 语料 L285 场景：同错重复次数应**从 3 降到 ≤2**，且第 2 次命令必须与第 1 次不同 |
