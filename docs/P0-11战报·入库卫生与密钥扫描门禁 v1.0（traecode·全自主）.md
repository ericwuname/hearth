## 一、D-5 · `.hearth-diag` 脱离跟踪

**问题**：`crates/{agent-core,service}/.hearth-diag/` 下的运行期诊断 jsonl **被 git 跟踪**，
而它们**每跑一次测试就新增/改动**：

- 每次 `git status` 都被几十个文件污染（本会话开头即是）；
- 更关键：它是 **2026-09-30 明文密钥事故的现成入库入口**——
  一次"文档归档"提交就可能把它们连内容一起带上（事故根因正是这个机制的产物）。

**处置**：
- `.gitignore` 增加 `.hearth-diag/`；
- `git rm -r --cached` **40 个已跟踪文件**（**内容全部保留在磁盘**，仅脱离索引）。

**效果**：`git status` 从此干净（只剩有意不 commit 的事故报告）。
未做（**待顶层裁决，不自主处置**）：删磁盘上的运行期文件；历史提交清理。

## 二、D-6 · 密钥扫描门禁（从"一次性人工动作"变成"常设门禁"）

### 2.1 为什么（根因）

事故复盘原话：**"脱敏是一次性动作，一次'文档归档'提交就把它撤销了"**。
没有常设门禁 ⇒ 同样的事必然再发生。

### 2.2 建成物

`crates/codex-cli/tests/secret_scan_gate.rs` —— 一个 **cargo test 门禁**：

| 项 | 设计 |
|---|---|
| 扫描范围 | `git ls-files`（= **会被入库的内容**；运行期产物天然排除） |
| 识别 | 高置信前缀（`cpk-` / `sk-` / `sk_live_` / `ghp_` / `gho_` / `xoxb-` / `xoxp-` / `AKIA` / `AIza`）+ PEM `PRIVATE KEY-----` |
| 三段过滤 | ① 词边界（前缀左邻不得是字母/数字/`-`/`_`）② 命中体 ≥16 字符 ③ 命中体需含数字且不含占位词 |
| 白名单 | `ACCEPTED`：文件 → 允许命中数，逐条注明来源裁决 |
| 输出 | **只打印文件与命中数**（测试日志也是公开的，绝不打印命中内容） |
| 缺失环境 | git 不可用时**明确打印 SKIP 原因**（不静默假装通过） |
| 盲区 | 文件头显式列出 3 条（无前缀约定的口令 / 二进制 / 未跟踪文件），**不许当"扫过就安全"** |

### 2.3 三轮"红"——过滤器不是拍脑袋加的

| 轮次 | 结果 | 暴露的问题 |
|---|---|---|
| 1 | **13 个文件命中** | 误报两族：`.env.example` 的 `sk-your-real-deepseek-key`、契约测试的 `sk-test-placeholder-…`（**占位符**） |
| 2 | **8 个文件** | 加"含数字 + 无占位词"后仍有误报：**`task-order-v16-….md`** —— "ta**sk-**order" 后接版本号，含数字且够长 |
| 3 | **1 个文件** | 加**词边界**后只剩真命中 |

### 2.4 绿（最终）

```
secret_scan_gate PASS: 扫描 2255 个已跟踪文件；白名单内 3 项已裁决接受风险。
```

### 2.5 **修正了泄露面积的判断**

此前（事故报告）记录为"1 个文件 3 把 key"，实测**真 key 落在 3 个文件**：

| 文件 | 命中 | 性质 |
|---|---|---|
| `docs/p0-usability/r9-reports/data/r12-dot-bashrc-anchor.txt` | ×4 | **原始落点**（3 把 key，其中一把出现两次） |
| `docs/p0-usability/r9-reports/data/v20-user-transcript-f852f409.jsonl` | ×1 | 录屏文字稿带出的同一把 `cpk` |
| `docs/p0-usability/r9-reports/TUI-polish3发射…v1.1（评审窗→顶层）.md` | ×1 | 验收报告里作为"发现项"引用的同一把 `cpk` |

三者均属**已裁决接受风险**（不轮换 / 保持 public / 不清理历史）→ 进白名单并注明来源。
**注意**：门禁**不会**替用户决定"要不要清掉它们"——这属产品/安全方向抉择，已上报。

## 四、方法论沉淀（第 10 个变体）

> **"人工纪律不是纪律。"**

事故的根因不是"某人忘了脱敏"，而是**"脱敏"这个动作没有任何机器在执行**。
同类现象在本规划里已出现三次：

| 一次性人工动作 | 已固化的机器门禁 |
|---|---|
| 脱敏（事故根因） | **本卡的 `secret_scan_gate`** |
| "记得不要提交 `.hearth-diag`" | **`.gitignore` + 脱离跟踪** |
| "记得先红后绿" | 每卡战报里必须给出**可复现的红侧证据** |

**固化为检查项**：
1. **凡"注意事项 / 纪律 / 约定"，问一句"有没有机器在执行它"**——没有就是迟早会破；
2. **新建门禁必须自带"红侧证明"**（本卡三轮红），否则无法证明它真的会拦；
3. **门禁必须自报盲区**——把"扫不到的东西"写在文件头，避免产生虚假安全感。
