## 一、最重磅发现 · 三个"只写不读"的死接线（✅ 已亲验）

### 1.1 `retriever` 与 `lsp_bridge`：注入了，永远没人查

**亲验方法**：在 `crates/agent-core/src/` 全目录检索 `self.retriever` 与 `self.lsp_bridge`。

**结果：全目录仅 2 处命中，且两次都是赋值。**

```
loop.rs:2018    self.lsp_bridge = bridge;          ← 写
loop.rs:2023    self.retriever = Some(retriever);  ← 写
```

**零次读取。** 即：

| 字段 | 生产后果 |
|---|---|
| `retriever`（`loop.rs:924` 声明，默认 `None`，service 在 `main.rs:539` 注入） | **注入后永不被查询**——检索能力全程不生效 |
| `lsp_bridge`（`loop.rs:922` 声明，默认 `NoopLspBridge`，service 在 `main.rs:549` 注入 `RustAnalyzerBridge`） | **注入后永不被查询**——LSP 诊断全程不生效 |

**连带**：`code-index` 只在 `service/main.rs:511` 启动时**建索引**（`:511-538`），而检索方从不查询 → **索引建完即废**。

**旁证（○）**：`Event::LspDiagnostics`（`loop.rs:243`）只有枚举定义与一处映射，**全仓无任何生产者**——
与"`lsp_bridge` 从不被读"互相印证：LSP 这条线**从未接通**。

> 这是本项目历史上"从未接线的五版旧债"模式的**又一次复现**。

### 1.2 整 crate 死亡 · `project-sync`（✅ 已亲验）

**亲验方法**：全仓 Cargo.toml 检索 `project-sync`；全仓 `.rs` 检索 `project_sync`。

| 检索 | 结果 |
|---|---|
| `crates/**/Cargo.toml` 含 `project-sync` | **仅 1 处** = 它自己的 `name`（`project-sync/Cargo.toml:2`） |
| 全仓 `.rs` 含 `project_sync` | **0 处** |

**结论**：**没有任何 crate 依赖它，没有任何代码引用它** → 「`cargo build` 的任何二进制都不含它的一个字节」。
而它本身有 **2,228 行源码 + 45 个测试**，且这 45 个测试**每次 `cargo test --workspace` 都在跑**
（测试全绿 → 制造"这块是活的"的假象）。

## 八、本报告的元结论（比清单更重要）

1. **`cargo test --workspace` 全绿 ≠ 功能可用**。本轮最严重的三个缺陷
   （只写不读 ×2、死 crate ×1）**在测试里全绿**——因为单测覆盖字段、不覆盖接线。
2. **"从未接线"是本项目复发率最高的债务类型**（历史已记"五版旧债"，本轮又查出 4 处）。
   根因是**缺少一条"接线断言"**：现有 wiring spec 只锁"某字符串在某文件里"，
   **锁不住"这个字段真的被读过"**。
3. **可复用的自动门禁建议**（未实施）：对 `retriever`/`lsp_bridge` 这类字段，
   加一条"**字段必须存在读取点**"的静态检查 —— 正是本次亲手验出问题的那条 grep，
   完全可以固化成 CI 断言。
