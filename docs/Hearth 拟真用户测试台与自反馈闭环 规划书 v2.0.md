# 1. 目标与可行性结论

| 用户设想 | 可行性 | 关键判断 |
|---|---|---|
| 模拟不同种类的人使用 Hearth，生成测试日志，跑几十上百次 | ✅ 可行 | 拟真用户 = 「另一个 LLM 角色驱动 hearth 终端」+ persona 语料库 + 双通道日志。**纯开发侧工具，不进 Core** |

**红线（贯穿全文，不可协商）**：拟真测试台是**开发侧工具**（`tools/simuser/`），永远不进 Hearth Core——它测 Core，不是 Core 的一部分。

# 2. 为什么做

CLOSURE-01 的教训（四方共识）：**脚本化验证的覆盖范围 ≠ 真实交互可靠性**。四包脚本化证据没暴露的东西，用户 90 分钟盲测全暴露了（24 连败吸引子、裸 ERROR 泄漏、内容截断、introspect 误路由）。手工盲测的两个工程缺陷：①不可重复（人的状态/输入不可复现）；②样本量太小。

**三条必须记住的实证**：

1. **同一份日志，两个成功率**。v0.2.18 盲测：字符串口径 33.3%（12/36）、逐轮归因口径 **28.6%**（10/35）。指标本身必须先被冻结定义，否则测试台规模化后只会把噪声放大（→ §4.7）。
2. **5.6% 的输入承担了绝大部分缺陷发现**。历史手工日志中"复发抱怨/纠偏/追问失败原因"类高收益探针仅 30 条 = 全部用户输入的 5.6%。若按自然分布 1:1 采样，发现率会低到失去性价比（→ §4.6 放大纪律）。
3. **跨版本成功率不可直接比**。v0.1.x / v0.2.0/0.2.3/0.2.4/0.2.5 终态文案不含 `Task completed/failed`，其 0/0 不是"全部失败"。可比较区间为 v0.2.8+（52.4% → v0.2.10 76.1% → v0.2.15 55.0% → v0.2.18 **28.6%**）。

# 3. 语料基础（两层 + 十轮深度挖掘）

## 3.1 两层语料（互补，不可互相替代）

| 层 | 语料 | 规模 | 用户形态 |
|---|---|---|---|
| **执行层** | `release/手工测试v0.*.txt`（Hearth CLI 日志） | 13 份 / 79,659 行 / **531 条用户输入** | 执行/调试型：继续/重跑 **26.9%** 主导 |
| **战略层** | `release/拟真用户参考语料/`（跨 provider 真实对话） | 7 文件 / ≈18MB / **4,681 条用户话语** | 战略/设计/创作型：选型对比 **18.9%**、设计头脑风暴 **14.5%**、继续仅 **10.1%** |

两层分布**几乎不重叠** → SimUser **必须双模态**（§4.3），只模拟执行层等于只测了一半真实用户。

**战略层格式**：A `### User`/`### Assistant`（Codex CLI 导出，带时间戳）×4 ／ B1 `我：`（DeepSeek 网页）×1 ／ B2 `**用户:**`/`**元宝:**` ×1 ／ C 纯叙事文 ×1（不可解析轮次，作创作分享参考）。

## 3.2 十轮深度挖掘（战略层，确定性正则，全部可复算）

| 轮次 | 维度 | 关键数字 |
|---|---|---|
| R1 | 任务域图谱 | 设计744 / 编码743 / 元认知710 / 评估709 / 创作485 / 文件操作473（共 10 域） |
| R2 | 长度与结构 | **100–300 字 36.8%** 为主力；>5000 字 15 条；含代码块 58 ／ 含表格 4 |
| R3 | 多任务复合指令 | 复合度 **≥2 = 39.6%**、≥3 = 21.9%、**≥5 = 8.3%** |
| R4 | 指代/上下文依赖 | 含指代 **36.7%**；纯上下文依赖（≤30 字且指代开头）**158 条** |
| R5 | 纠错升级链 | **41 条链**（2 连 36 / 3 连 5） |
| R6 | 语气光谱 | 中性 89.9% / 急切 3.0% / 疲惫 2.7% / 鼓励 2.2% / 调侃 1.1% / 失望 0.9% / 愤怒 0.2% |
| R7 | 领域实体 | 含真实编码上下文（`await`/`logger.info`/`try-except`/`def`），无敏感信息 |
| R8 | 句式风格 | **陈述喂料 38.3% > 疑问 36.8% > 祈使 10.7% = 条件 10.7% > 模糊委托 3.6%** |
| R9 | 失败-追问链 | 贴错误原文 **94** / 质问 24 / 换说法 11 / **放弃仅 1** |
| R10 | 会话结构 | **330 个会话**：<10 轮 189 为主，长尾 **≥70 轮 5 个、≥110 轮 2 个**；开局「指向文件/路径」208/330 |

**三个反直觉、直接改变设计的发现**：

1. **"陈述/喂材料"比"下指令"更多**（38.3% vs 10.7%）——用户常以"我把东西放这了，你看着处理"交互，而非明确指令。早期 persona 全是指令型，这是覆盖缺口（→ 场景 `material-dump`）。
2. **40% 的输入是复合指令，8.3% 一句塞 ≥5 个子任务**——不是边缘情况，是常态。planner 拆解能力是主战场（→ 检测器 `multi_intent_drop`）。
3. **真实用户极少显式放弃**（仅 1 次），多是沉默离开 → "放弃"不得作为 SimUser 的常见终止条件。

> ⚠️ **口径自纠记录**：R6 首版"调侃"正则含单字「可」，把"可以/可是/可能"全误判，虚高至 1119 条；去掉该字后重算为 **51 条**。引用本表请用修正值。

## 3.3 ⚠️ 语料的代表性边界（引用任何数字前必读）

**4,681 条话语本质上来自同一个人类主体**，跨越的是 provider 与场景，**不是用户**。因此：

1. **深度 ≠ 多样性**。10 轮挖掘把一个人的行为描述得更精细，但没有让它代表"各种人"。
2. 凡以本语料得出的分布数字，只能声称「**该主体在跨 provider / 跨场景下的行为分布**」，**不得**声称"真实用户总体分布"。
3. 要获得真正的多用户多样性，只有两条路：① 引入更多人类主体的语料；② 以本语料为**校准锚点**，在其周围参数化扰动出多个人格样本（§4.2）——但**扰动出的样本必须标注为合成，不得冒充真实**。

> 这是本语料不可消除的边界。任何绕过它的说法都是自嗨。

# 4. 拟真用户测试台（SimUser）设计

## 4.1 为什么放弃"类别文件式 persona"

早期设计用 12 个类别文件（operational 7 + strategic 5）。类别是**一维标签**，无法表达"一个着急的设计型用户、用 5 合 1 复合句、喂了一段材料、还依赖上文"这种真实组合。要"承接各种场景"，persona 必须是**向量**而非**枚举**。

## 4.2 人格向量定义（核心）

```yaml
# tools/simuser/personas/_vector_schema.yaml
persona_vector:
  mode:                operational | strategic        # 模态
  task_domain:         <R1 十域之一>                   # 设计/编码/元认知/评估/创作/文件/排查/选型/流程/闲聊
  sentence_style:      <R8 五类之一>                   # 陈述喂料/疑问/祈使/条件/模糊委托
  tone:                <R6 七类之一>                   # 中性/急切/疲惫/鼓励/调侃/失望/愤怒
  intent_complexity:   1 | 2 | 3 | 4 | 5+              # 一句塞几个子任务
  context_dependency:  true | false                    # 是否含指代、依赖前文
  input_length_bucket: <R2 八桶之一>                   # 0-10/10-30/30-60/60-100/100-300/300-1000/1000-5000/5000+
```

**采样纪律（三条，不可省）**：

1. **按实测分布采样，不拍脑袋**。每维权重直接取 `corpus_seed_dataset.json → deep_rounds.R*` 的实测频率。
2. **★ 必须用联合分布，不得各维独立采样**。独立采样会产生现实中不存在的组合（如 strategic + 编码工程 + 愤怒）。**实现采样器前须先计算维度间相关系数**（至少 mode×task_domain、mode×length、tone×style），用联合/条件分布采样。此步不做，人格就是假的（→ §8 门禁 G1/G2）。
3. **弱类强制放大**。愤怒(0.2%)、失望(0.9%)、放弃(1 次)、上下文耗尽(2 条种子)、接力(9 条种子)——稀有但历史缺陷产出最高，采样权重须刻意放大。

**措辞纪律**：所有维度样例**逐字取自 `corpus_seed_dataset.json`**（已脱敏），**禁止编写者造句**——否则测的是"我们想象中的用户"。

## 4.3 双模态

| 模态 | 基线来源 | 主导行为 | 主要用途 |
|---|---|---|---|
| `operational` | Hearth CLI 日志 | 继续/重跑 26.9% | 执行、调试、恢复路径 |
| `strategic` | 跨 provider 语料 | 选型 18.9% / 设计 14.5% | 设计、选型、创作、接力、上下文耗尽 |

SimUser 须支持 `mode = operational | strategic | blend`（可配）。

## 4.4 关键机制

1. **双通道日志**（核心价值）：终端侧（用户看到的一切，含裸 ERROR 与截断）vs Hearth 侧（telemetry + scratch + archive 时间戳 + 归因期 planner dump），按 session_id + 时间戳对齐 → **"系统做了什么" vs "用户看到了什么"的 diff** 直接量化 Projection isolation / completeness，P0-C 四层 completion 从此可测。
2. **拟真 = 自适应而非回放**：模拟用户 LLM 看到 Hearth 的真实输出后自己决定下一句；只有"污染前缀重放"类场景用逐字剧本。模拟用户**盲于 Hearth 内部**（只准看终端输出，禁止读 `.hearth/`、telemetry）。
3. **★ 模拟用户默认异源**：模拟用户与被测 Hearth 若同源（同用 Agnes），**同一个模型的盲区会在"用户侧"和"系统侧"同时出现**，这类缺陷永远测不出来——验证悖论的另一种形态。
   → **默认异源**（智谱 / 本地 Ollama `qiyuan-8b`）；同源仅作**标注对照条件**跑一组，用于分离"模型共模"与"系统缺陷"。
4. **确定性控制**：persona 版本 + scenario seed + provider/model/温度 + budget 固定并记录；每跑记录 full event log。
5. **诚实性纪律**：判定指标全部用**确定性比对**（RESULT 文件、测试通过、日志计数），模拟用户的"感觉"只做线索不做证据（INV-G）。

## 4.5 场景库（矩阵式生成 + 确定性回放基线）

**矩阵生成（据 R1–R10）**：

| scenario | 生成依据 | 验证目标 |
|---|---|---|
| `multi-intent-5way` | R3 复合度≥5（389 条真实样本） | 子任务**是否被全部执行** |
| `anaphora-blind` | R4 的 158 条纯上下文依赖输入 | 脱离前文后 agent 是否瞎猜 |
| `correction-escalation` | R5 的 41 条纠正链 | 纠正是否被吸收，还是原地打转 |
| `paste-error-probe` | R9 的 94 次贴错误原文追问 | 错误原文能否被正确归因 |
| `longpaste-5k` | R2 的 15 条 >5000 字输入 | 超长输入是否被静默截断 |
| `longsession-70plus` | R10 的 ≥70 轮会话 | 长会话污染累积（有真实依据，非人为拉长） |
| `material-dump` | R8 陈述喂料 38.3% | 只给材料不下指令时能否推断意图 |
| `vague-delegation` | R8 模糊委托 3.6% | "你看着办"类输入的处理质量 |

**确定性回放基线（保留）**：`pollution-prefix-v0218`（v0.2.18 run-001..012 逐字重放，截止点定死在 run-012 结束处——依据：首个 T4 在 run-003 且该轮成功、其后 9 轮零 T4；用"首个 T4"截断会重放出一个历史上并不失败的会话）、`continue-after-complete`、`rc48-sortlib`、`meta-diagnostic-loop`、`longsession-50turns`。

## 4.6 采样放大纪律（有意偏差，须显式声明）

高收益探针仅占自然输入 **5.6%**（执行层）+ 接力/上下文耗尽 **1.1%**（战略层）。测试台会**刻意放大**这类行为，否则发现率低到失去性价比。

→ **必须在所有报告中显式声明「测试台分布 ≠ 真实用户分布」，成功率类结论不得当作真实用户成功率上报**。

## 4.7 指标口径冻结（防 RC51 复发）

坏测量方法会被复用。测试台规模化前，指标必须写死并版本化：

| 指标 | 冻结定义 | 反例（禁止） |
|---|---|---|
| success_rate | **逐轮归因口径**：按 run 边界取该轮首个终态，分子 = 首个终态为 completed 的 run 数 | `grep -c "Task completed"`（会重复计、跨轮串） |
| consecutive_failure | 连续终态为 failed 的 run 数（run 边界同上） | 按失败关键词计数 |
| 压缩/归档"是否发生" | **只允许字节数 + mtime + 文件数** | `wc -l`（末行无换行系统性少计，RC49 已证伪） |
| 跨版本可比性 | **只在 v0.2.8+ 可比** | 把老版本 0/0 读成"全部失败" |

定义写入 `tools/simuser/metrics.yaml`，**版本号随 persona/scenario 一起冻结**；改定义 = 升版本，旧数据不得与新数据混表。

## 4.8 检测器清单（15 个）

| # | 检测器 | 判据（确定性） | 对位缺陷 |
|---|---|---|---|
| 1 | projection_leak | 终端出现 `^\d{4}-\d{2}-\d{2}T.* (ERROR\|WARN) agent_core\|sandbox\|planner` | RC38 / Projection isolation |

| 5 | compaction_adjacency | 失败点距压缩点 ≤200 行 | RC5 / RC37 |
| 6 | truncated_output | 输出以 `…` 结尾 / 缺失 `[N chars truncated]` 标记 | RC35 / 截断族 |
| 7 | giveup_completed_coexist | 同一 run 内 `give_up` 与 `Task completed` 共存且无 `*_OVERRIDDEN` 痕迹 | F9 / 拦截链可观测性 |

| **12** | **anaphora_resolution_fail** | 纯上下文依赖输入后一轮失败率显著高于独立输入 | R4 158 条 → 上下文保真 |
| **13** | **escalation_run** | 连续 ≥2 轮纠正信号未收敛 | R5 41 条链 → 纠正未吸收 |
| **14** | **paste_error_probe_quality** | 用户贴错误原文后，agent 给出归因 vs 泛化道歉 | R9 94 次 → 诊断能力 |
| **15** | **longpaste_truncation** | 输入 >5000 字时输出/scratch 是否静默截断 | R2 15 条 → 截断族 |

每 run ≈ 40–60 步 ×（Hearth 调用 + 用户模拟调用）≈ 100–150 次 LLM 调用；**100 跑 ≈ 1.0–1.5 万次/周**，占 Agnes 配额 15–20%。先 30 跑起步。

# 5. Hearth 内 AI 自记录问题闭环（file_issue）

## 5.1 闭环全图

```text
Hearth 运行中（住户 AI）
    ↓ 发现异常
file_issue{category, severity, evidence 指针, description}   ← Core 内新工具
    ↓ append-only: .hearth/issues/<session>.jsonl
开发侧收集器 → 跨会话聚合 + 去重 + 三角验证
评审窗口判级（CONFIRMED / NEW F1 / FALSE POSITIVE / DEFERRED）
    ↓
顶层立项 → 执行窗口修复 → 测试窗口回归 campaign
    ↓
CHANGELOG + known-issues.md → 回注 Hearth 会话上下文
```

## 5.2 设计要点（五条纪律）

1. **self-report ≠ evidence（INV-G）**：issue 必须带 session_id / step / tool call / 日志路径等**可复核指针**，开发侧三角验证通过才算 CONFIRMED。
2. **限流与去重**：每会话 ≤3 条；`known-issues.md` 注入会话上下文，已知问题不重复报。
3. **复用不新建**：收敛 civ_note / run report / InteractionRequest 的出口，不建第二套事实模型（M8）。
4. **冻结边界**：file_issue 是 **Core 代码改动**（加性、零权威变化、sandbox 内 append-only 写），**必须走正式任务书审批**，随 v0.2.19 修复批落地，不悄悄进。
5. **★ 确定性触发兜底**（不可省）：
   > 若只由模型主动发起，就依赖模型"自觉"——而"不自觉"正是本系统的已知缺陷（历史上多次出现"自述已验证"为假）。
   > **双通道**：
   > - **系统侧（不依赖模型）**：`stalled` / `give_up` / `approval_denied` / `verify_failed` / 工具五态异常命中时，由 loop 自动写一条结构化 issue（与 F9 `giveup_unverified` 标记同构）；
   > - **模型侧（可选补述）**：在此基础上补 category/描述，**不得删除确定性记录**。
   > 落盘须 **session 隔离**（复用 RC49 教训）；issues **不进 LLM 可见上下文**（除 `known-issues.md` 摘要），避免成为第二事实源。

# 6. 窗口分工：测试与修复必须分离

1. **Blind 原则**：修 bug 的人再测会不自觉绕开雷区；盲测的全部价值来自"非执行窗口、无预设剧本"，工程化时不能把它弄丢。
2. **归因纯净**：campaign 期间版本冻结；边测边改会让同一批数据横跨多个 binary。
3. **零成本**：多窗口工作流已现成。

**运转节奏（campaign 制）**：

```text
测试窗口：campaign N（30-100 跑，版本冻结）→ 原始记录 + 检测器自动标记
评审窗口：判级 + 按层归聚类（mechanism/decision/model/provider/environment）
顶层：立项修复批（一次性攒批）
执行窗口：批量修复 + 单元级 smoke 自测
测试窗口：campaign N+1（含 N 轮失败场景重放 = 回归）
```

折中许可：执行窗口可跑单元/fixture 级自测（先红后绿照旧）；**campaign 级验证必须由测试窗口独立执行**。

# 7. 验收标准（四维，全过才算保真）

## A. 三形态（缺一不可）

1. 前段高成功率 + 后段连败的会话形态；
2. **入口事件 =「继续」型输入失败**（对应 v0.2.18 run-013）；
3. **压缩晚于入口 ≥10 轮**（v0.2.18：入口 run-013 vs 首次压缩 run-024）。

> 只复现"后段连败"不够——那可能只是"随便都会失败"。

## B. 双模态分布对齐

| 模态 | 指标 | 基线 | 容差 |
|---|---|---|---|
| operational | 继续/重跑占比 | 26.9% | ±8pt |
| operational | 短指令 ≤30 字 | 38–68% | 落区间 |
| strategic | 选型/对比占比 | 18.9% | ±8pt |
| strategic | 设计/头脑风暴占比 | 14.5% | ±8pt |
| 通用 | 高价值稀有类（高收益探针 + 接力 + 上下文耗尽） | 自然 5.6% + 1.1% | **强制放大至 ≥8pt** |

## C. 任务域覆盖（R1）

10 个任务域**每域至少覆盖**；其中设计 / 编码 / 元认知 / 评估四大域**各 ≥10%**。

## D. 结构覆盖（R2 / R3 / R4 / R10）

| 指标 | 基线 | 要求 |
|---|---|---|
| 复合度 ≥3 输入占比 | 21.9% | ±8pt |
| >5000 字超长输入 | 15 条（0.3%） | 至少覆盖，**不得静默截断** |
| ≥70 轮长会话 | 5 个 | 至少 1 次 |
| 纯上下文依赖输入成功率 | — | **不得显著低于独立输入**（若显著低 → 记为缺陷，非"用户没说清"） |

# 10. 维护纪律

1. **状态口径只用八词**（沿用总账 v3）：CLOSED / PARTIAL / OPEN-DIAGNOSED / OPEN-UNSTARTED / **NEEDS-RERUN** / DEFERRED / DECISION / ENV-DONE。
   > ⚠️ **"待复测"一词禁用**——历史曾把"从未实现"误记为"待复测"，会让顶层以为已修待验。此后"改了没验"一律写 NEEDS-RERUN，"从未排期"写 OPEN-UNSTARTED。
2. **CLOSED 必须带 `file:line` 锚点**；真机结论须绑版本 + session id + 日志路径。
3. **指标定义冻结**（§4.7），改定义 = 升版本，旧数据不混表。
4. **检测器上线先自检**（未修复样本大面积 FAIL）。
5. **语料引用须带 Q11 声明**（§3.3）。
6. 每次发版复核本规划书；历史版本（v1-draft / v1.1-砺 / v1.2-砺）**冻结，只维护本 v2.0**。
