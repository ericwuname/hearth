### ⚠️ 本次盘点第一发现（必须先看）

> **P4 全绿 ≠ 好用。Strong Acceptance 10 条里没有任何一条成功率门槛。**

P4 §20 的 Strong 标准是：①Projection 一致 ②RC52 被因果解释 ③无新的无限失败吸引子 ④路由稳定 ⑤Resume reteach=0 ⑥压缩不吞事实 ⑦Verification 不被 self-report 替代 ⑧无沙箱/审批绕过 ⑨SimUser 30+ run **指标稳定** ⑩真人盲测不出现已知 **F0 级**缺陷。

- 第 ⑨ 条要的是**稳定**，不是**达标**；
- 第 ⑩ 条只覆盖 **F0 级**（假完成/静默丢失/无限循环/沙箱绕过），**不含"成功率低"**。

而 v0.2.18 真人盲测的逐轮归因成功率 = **28.6%（10/35）**，第 13 轮起连续 24 轮零成功。P4 的修复优先级（Node 13）：P0 = Projection isolation/completeness + RC52 根因；P1 = RC53/54/Intent 边缘；P2 = Memory slice/Archive/UX——**没有一项以"提升成功率"为目标**。

**推论：P4 最可能的结局是"结构可信、行为可解释，但成功率仍是 28.6%"。** 若顶层把"冻结"理解为"做完了"，会在下一阶段开局就踩空。这是本次盘点最需要传达的一条。

## 2. 冻结可行性裁决

### 2.1 先拆词："冻结"有三层，混谈必错

| 层 | 含义 | 谁能宣布 | 当前状态 |
|---|---|---|---|
| **L1 包范围冻结** | P4 这 16 个 Node 的边界不再膨胀 | 顶层（现在即可） | ⚠️ **建议立即冻** |
| **L2 Core 冻结** | 事实模型（TaskGraph/TaskGoal/Terminal 九态/审批/沙箱/ContextBuilder）不再改 | **仅人工窗 + 外部 AI 窗双签** | 进行中（Node 15 出 CANDIDATE） |
| **L3 项目冻结** | 停止开发 / 交付收口 | 顶层 | ❌ **不该冻** |

### 2.2 L1 包范围冻结：**建议立即执行**

P4 有 16 个 Node（00–15），当前 **Node 00-01 已完成**（`tools/simuser/driver.py` 205 行真 PTY：`pty.openpty()` + `select.select()`；`analyzer.py` 234 行 13 个检测器；`metrics.yaml` 42 行），剩余 14 个。执行窗口期间任何"顺手加一项"都会稀释 RC52 归因这条主线的资源。

**建议口头裁定**：P4 边界以 §1 红线 + Node 00–15 为限，包内新增一律驳回，转入 v0.3 backlog。

### 2.3 L2 Core 冻结：**能给 CANDIDATE，不能给 FREEZE**

- P4 §17 明令：**禁止宣布 CORE FREEZE**，只能产出 `CORE FREEZE CANDIDATE`（八文件包）。
- 最终裁决 = 人工评审窗 + 外部 AI 评审窗 + 至少一次独立命令/证据复核。
- 当前工程状态已由 baseline.md 正式改写为 **`CORE FREEZE SUSPENDED / CORE REVALIDATION IN PROGRESS`**——CLOSURE-01 的 CORE FREEZE 结论**降为历史轨迹，不得再被引用为有效验收结论**。这点执行窗口做对了。

### 2.4 L3 项目冻结：**不能冻**

理由：A 组 6 个未来器官 + B 组 6 项用户设想 + **B4-2 桌面版**（用户明确的终态产品）均未落地。此时项目冻结 = 交付一个"结构可信但只有 CLI、成功率 28.6%"的中间态。

### 2.5 我的裁决建议：**CORE FREEZE v2 · CONDITIONAL**

若 P4 Node 15 的 Strong Acceptance 10 条全过，建议顶层签发 **带条件冻结**，且冻结文件必须强制写入两条 does-not-guarantee：

| 编号 | 内容 | 理由 |
|---|---|---|
| **DG-1** | **不保证成功率达标**——本轮未设成功率门槛，Strong ⑨ 只要求"指标稳定"，⑩ 只覆盖 F0 级 | 防止"冻结"被误读为"好用" |
| **DG-2** | **不保证未来器官存在**——Subagent/TUI/MCP/Persona/Semantic Memory/动态 Verification 六项未在包内 | 防止"冻结"被误读为"功能完整" |

> 补充：现有 `freeze-decision.md` 的 does-not-guarantee 段此前被核实为**零覆盖**（总账 v3 RC50 条已记）。这次不能重蹈。

### 2.6 冻结前必须先补的一个动作

**给下一阶段定一条可失败的成功率判据。** 否则 v0.3 的能力线改动会重演 RC51——"改了但无法证明有效"。具体见 §3.4 门禁 G-2。

## 3. v0.3 开发规划（建议）

### 3.0 核心主张：**P4 造尺子，v0.3 用尺子**

这是本规划的逻辑支点：

- 此前所有能力改进设想（I-1 多轮推理 / I-3 压缩重构 / I-6 模型自发现 / B2 之后的交互优化）**都卡在同一个问题上：没有尺子，改完不知道有没有效**。守门人在 I-2 评估里建议"最小对照实验"，但当时连可复现的 driver 都没有（P0 三版 harness 全失真：管道 stdin 56MB 刷屏 / `script -qec` 191MB 竞争 / resume goal 语义）。
- P4 交付后第一次具备条件：**真 PTY driver + 13 检测器 + 冻结的 metrics.yaml + 双通道 diff**。
- 所以 v0.3 不该是"继续拍脑袋加功能"，而应是**第一次用测量驱动的 capability 建设**。

**命名建议**：`P5-USABILITY-01 / v0.3「可用化」阶段`——与 P4 的「可信化」区分。版本号：P4 产出 v0.2.20（Node 05/06）→ v0.2.21（Node 13），v0.3 从 **v0.3.0** 起。

### 3.1 三条主线 + 一条横贯线

#### 主线 A · 能力线（最高优先）—— 把 28.6% 拉起来

| 序 | 内容 | 判据（可失败） |
|---|---|---|
| **A1** | **最小对照实验**：I-2 多轮推理 vs 单轮，各 3 次，比成功率/步数/成本 | 若多轮无显著优势 → **证伪，停止投入**（这是用户最在意的假设，必须先给结论） |
| **A2** | **I-7 异议识别与提问交互改进**（用户："问得僵硬、问得不关键"） | SimUser 上"追问/澄清类"任务的答案命中率 |
| **A3** | **I-6 模型能力自发现**（低成本快赢） | 32k 硬编码 → 按 provider 实际窗口；压缩触发点从 4–10% 回到合理区间 |
| **A4** | I-1 显式/隐式自适应（**依赖 A1 结论**） | 复杂任务分解质量 + 上下文膨胀不恶化 |

> A3 建议**优先于 A1**——成本最低、收益最确定（当前等于在真实容量 4% 处就开始丢记忆），且它是其他改进的干扰项（不先修，所有对照实验都在"半失忆"状态下跑）。

#### 主线 B · 记忆线 —— I-3 压缩重构（与 W5/RC5 合并立项）

| 序 | 内容 | 说明 |
|---|---|---|
| **B1（先）** | **摘要质量 B**：60 字规则墓碑 → 结构化/可检索摘要 | 守门人判断：**当前真正的伤害在 B 不在 A**；只改 A 不改 B，效果有限 |
| **B2** | 触发策略 A：方案③（近几轮全量 + 更早压缩） | 用户独立走到同一设计 |
| **B3** | **历史检索工具**（archive 检索升工具） | 用户原话"快速检索定位历史的某轮对话" |

判据：`compaction_adjacency` 检测器 + 压缩后目标召回率（可测、可失败）。

#### 主线 C · 产品线 —— 桌面版 / TUI

- 按"冰山比喻"最后做，**不阻塞核心假设验证**。
- ⚠️ **前置警告**：成功率没起来之前做桌面版 = 给一个 28.6% 的引擎装漂亮外壳。建议设门槛：**主线 A 达成判据后才启动 C**。

#### 横贯线 D · SimUser 常驻化

- Stage 2 收尾：补 3 个检测器（multi_intent_drop / paste_error_probe_quality / longpaste_truncation）+ **联合分布采样器**（G1 硬门禁：维度相关系数矩阵评审通过方可进 B2——独立采样拼出来的是假人）。
- SimUser 进季度体检 / 摩擦遥测进 CI（对应 W12）。
- **Q11 强制**：campaign 报告头部必须声明 persona 语料来自**单一人类主体**，禁止"真实用户成功率"表述。

## 4. 需顶层拍板的四件事
