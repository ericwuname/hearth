# 项目-窗口群协作框架设计 v2.1（含完整生命周期管理）

> 定位：一个项目 = 一个共享工作空间 + N 个独立会话窗口。
> 窗口之间**不通过中央编排器调度**，而是通过共享工作空间 + 任务流转规则自己协作。
> 每个窗口是独立的长对话 agent，有自己的上下文、记忆压缩机制和产出边界。
>
> **v2.1 变更（2026-08-01 审查定版）**：审查发现 8 个实质缺口，追加 §8「v2.1 审查补充」：
> 成本/预算控制、失败重试语义、Gate 脚本化、冲突仲裁层级、快照一致性、压缩摘要上限、
> 窗口沙箱隔离、窗口群 wiring 断言。§6 对接表同步修正（引用真实 API 与 wiring 15 条）。

## §1 核心模型：项目 → 窗口 → 任务流转

```
┌─────────────────────────────────────────────────────────┐
│                      项目容器                            │
│                                                         │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │ 窗口 A      │  │ 窗口 B      │  │ 窗口 C      │     │
│  │ 需求分析    │  │ 架构设计    │  │ 编码实现    │     │
│  │             │  │             │  │             │     │
│  │ 独立上下文   │  │ 独立上下文   │  │ 独立上下文   │     │
│  │ 长对话+压缩  │  │ 长对话+压缩  │  │ 长对话+压缩  │     │
│  │ 产出: PRD   │  │ 产出: 方案   │  │ 产出: 代码   │     │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘     │
│         │                │                │             │
│         └────────────────┼────────────────┘             │
│                          ▼                              │
│              ┌──────────────────────┐                   │
│              │   共享工作空间        │                   │
│              │   文件 / 进度 / 记忆  │                   │
│              └──────────────────────┘                   │
└─────────────────────────────────────────────────────────┘
```

**和原 ATO 设计的核心区别**：

| | ATO（编排器模式） | 窗口群模式（本设计） |
|---|---|---|
| 调度 | 中央编排器派活 | 窗口自己读任务板、自己领活 |
| 通信 | Orchestrator ↔ agent | 窗口 → 共享空间 → 窗口 |
| 创建窗口 | Orchestrator 创建 subagent | 需求窗口分析完 → 自动在项目下新建窗口 |
| 故障恢复 | Orchestrator 重试 | 任务板留标记 + 超时重分配 |
| 人类角色 | 在编排器处检查 | 在每个窗口的产出物上直接审核 |

## §2 项目生命周期

### Phase 1：需求窗口（单窗口阶段）

```
人创建一个项目 → 打开一个"需求窗口"
  ↓
需求窗口和人类聊项目背景、目标、约束
  ↓
聊够之后，需求窗口输出：
  - 项目范围文档（PRD）
  - 需要的窗口清单（角色×数量）+ 每个窗口的初始 prompt
  - 窗口间流转规则（谁先谁后、谁依赖谁）
  ↓
人类审核并确认 → 框架自动创建窗口群
```

### Phase 2：窗口群并行/串行工作

框架按流转规则自动启动窗口。例如软件开发项目：

```
窗口-需求分析（先跑）   窗口-架构设计（等需求分析完成）
       ↘                    ↓
        窗口-后端开发 + 窗口-前端开发（并行，等架构设计完成）
              ↘              ↓
        窗口-代码审查（等开发完成） + 窗口-测试（并行）
                   ↘          ↓
              窗口-文档 + 窗口-部署（等审查+测试完成）
```

### Phase 3：收尾与经验沉淀

所有窗口完成后 → 项目归档 → 组队决策卡写入经验库。

### "主窗口还管调度吗？"

**不管。** 需求窗口在 Phase 1 结束时定好流转规则，之后它就变成和别的窗口一样的普通窗口。调度 = 规则引擎（不是中心 agent）——流转规则在项目配置里，框架自动推任务、触发下一个窗口。

## §3 窗口的长对话与上下文压缩

### 每个窗口的本质

```yaml
窗口:
  id: "win-backend-01"
  role: "后端开发"
  context:
    max_tokens: 32000       # 硬上限
    current_tokens: 8421    # 当前用量
  state: "working"          # idle / working / blocked / done
  dependencies: ["win-arch-01"]   # 等这些窗口完成
  output: "src/**/*.rs"     # 产出路径
```

### 上下文压缩——你说的"避免对话过长导致截断丢失"

不是手动压缩，是**自动分层**：

```
窗口的完整对话历史（可能 500 轮）
        │
        ▼
   ┌─────────────────────────────┐
   │ 热层（最近 20 轮）           │ ← 完整保留，不进压缩
   │ 每轮完整 (tool_calls+结果)   │
   ├─────────────────────────────┤
   │ 温层（21-100 轮）            │ ← 每 5 轮压缩为一条摘要
   │ 保留关键决策+产出文件引用     │
   ├─────────────────────────────┤
   │ 冷层（101-500 轮）           │ ← 全部压缩为"历史要点"
   │ 仅保留：做了啥、产出什么       │
   └─────────────────────────────┘
```

**压缩触发条件**：
- `current_tokens > max_tokens * 0.7`（达到 70%）
- 或窗口每完成一个任务节点后自动触发

**压缩方式**：不是简单的截断——是让窗口自己**总结自己的温层/冷层**为一段结构化摘要，摘要里保留：
- 做了什么（任务清单 + 结果）
- 关键决策（选了什么方案、为什么）
- 产出文件列表 + 一句描述
- 未解决问题（给后续对话的上下文）

**验证**：压缩后窗口必须能回答"你上一阶段做了什么"——如果答不出来，压缩过度。

## §4 共享记忆——"是否需要共享，怎么共享"

### 不是所有记忆都共享

```
┌──────────────────────────────────────────────────────┐
│              共享层（所有窗口可读可写）                 │
│  项目进度板（谁在做、谁完成了）                        │
│  决策记录（选了 Axum 不选 Actix，原因 + 决策窗口标注）  │
│  规范/约束（API 格式、命名规范、目录结构）             │
│  冲突标记（窗口 A 和窗口 B 改同一文件 → 标记等待人判）  │
├──────────────────────────────────────────────────────┤
│              独立层（每个窗口自己持有）                 │
│  本窗口的对话历史（热/温/冷三层）                     │
│  本窗口的工具调用日志                                 │
│  本窗口的中间草稿                                     │
└──────────────────────────────────────────────────────┘
```

**共享规则**：
- 任何窗口的**最终产出**自动入共享层（代码文件、文档、决策记录）
- 任何窗口的**中间草稿**只在自己独立层——别的窗口不需要看一个没写完的方案
- 窗口间引用：窗口 B 读窗口 A 的产出 → 通过共享层文件路径引用，不通过"A 跟我说..."

**冲突检测**：两个窗口同时改同一个共享文件 → 框架自动标记冲突 → 通知涉及的窗口重新对齐 → 仍冲突则暂停等人。

## §5 任务流转机制——不靠中心编排器

### 流转规则是配置，不是代码

需求窗口在 Phase 1 结束时产出的流转规则：

```yaml
workflow:
  stages:
    - id: "architecture"
      windows: ["win-arch-01"]
      trigger: "project_start"
      gate: "人类审核方案"

    - id: "implementation"
      windows: ["win-backend-01", "win-frontend-01"]
      trigger: "stage:architecture:done"
      parallel: true
      gate: "lint + test 全绿"

    - id: "review"
      windows: ["win-review-01", "win-test-01"]
      trigger: "stage:implementation:done"
      parallel: true
      gate: "审查通过 + 测试全绿"

    - id: "release"
      windows: ["win-docs-01", "win-deploy-01"]
      trigger: "stage:review:done"
      parallel: true
      gate: "人类批准发布"
```

**框架做的事**：
1. 读规则 → 检查 trigger 条件 → 条件满足 → 启动该阶段的窗口
2. 窗口完成 → 检查 gate → gate 通过 → 标记 `stage:xxx:done` → 触发下一阶段
3. 窗口阻塞 → 超时未完成 → 标记阻塞原因 → 通知人类或降级（换模型/换策略）

**人类介入点**：只在 gate 处——人类说"方案可以了"→ 窗口群继续。人类说"代码不行"→ 标记阻塞原因 → 对应窗口重新处理。

## §5a 项目文件夹结构（框架如何发现和管理窗口）

```
my-project/
├── project.toml          ← 项目配置（名称、类型、流转规则、窗口清单）
├── .trash/               ← 软删除的窗口暂存 30 天
├── .archive/             ← 永久归档的窗口（只读）
├── .snapshots/           ← 自动快照（每小时或每次 window:done 时）
├── shared/               ← 共享工作空间（所有窗口可读写）
│   ├── progress.md        ← 项目进度板（谁在做、谁完成了）
│   ├── decisions.md       ← 关键决策记录
│   ├── specs/             ← 规范/约束文件
│   └── outputs/           ← 各窗口最终产出文件
└── windows/              ← 窗口目录（框架扫描此目录发现所有窗口）
    ├── win-requirement-01/   ← 需求分析窗口
    ├── win-arch-01/          ← 架构设计窗口
    ├── win-backend-01/       ← 后端开发窗口
    ├── win-frontend-01/      ← 前端开发窗口
    ├── win-adhoc-01/         ← 人类随手新增的临时窗口
    └── win-adhoc-02/         ← 同上
```

### 窗口扫描逻辑

框架启动时：`ls windows/` → 读每个子目录的 `window.toml` → 识别谁是什么角色、什么状态、有没有过期。

### 窗口命名规则

| 类型 | 命名格式 | 例子 | 谁创建 |
|---|---|---|---|
| 需求自动生成 | `win-{角色}-{序号}` | `win-backend-01` | 需求窗口分析后自动创建 |
| 人类手动新增 | `win-adhoc-{序号}` | `win-adhoc-01` | 人类随手新增 |
| 人类自定义名 | `win-{人类指定}` | `win-hotfix-login` | 人类建窗口时命名 |

**冲突检测**：如果人类命名了一个已经存在的名字 → 框架自动追加 `-2`、`-3`。

## §5b 窗口的生命周期（创建→工作中→完成→删除→归档→恢复）

```
┌─────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ pending │───→│ working  │───→│  done    │───→│ archived │
│ 等待触发 │    │ 执行中   │    │ 已完成    │    │ 已归档    │
└─────────┘    └────┬─────┘    └──────────┘    └─────┬────┘
                    │                                │
                    ▼                                ▼
              ┌──────────┐                    ┌──────────┐
              │ blocked  │                    │ .trash   │
              │ 阻塞     │                    │ 软删除   │
              └──────────┘                    │ 30天可恢复│
                                              └─────┬────┘
                                                    │
                                                    ▼
                                              ┌──────────┐
                                              │ cleaned  │
                                              │ 彻底清除  │
                                              └──────────┘
```

### 每个状态的判定

| 状态 | 怎么进 | 怎么出 |
|---|---|---|
| `pending` | 窗口被创建，等待触发条件 | trigger 条件满足 → `working` |
| `working` | 框架或人启动窗口 | 产出完成 + gate 通过 → `done`；或异常 → `blocked` |
| `blocked` | 依赖未满足 / 连续失败 / 人类暂停 | 依赖满足 / 人解封 → `working` |
| `done` | gate 通过 | 人确认 → 标记完成；或人选择 → `archived` |
| `archived` | 人手动归档 | 可恢复为 `done` |
| `.trash` | 人或框架软删除 | 30 天内可恢复；30 天后自动彻底清除 |

### 每个窗口的元数据文件 `window.toml`

```toml
[window]
id = "win-backend-01"
name = "后端开发窗口"
role = "backend-developer"
state = "working"
created_by = "auto"           # auto | human
created_at = "2026-08-01T06:00:00Z"

[context]
max_tokens = 32000
current_tokens = 8421
compression_count = 3        # 此窗口已被压缩的次数

[budget]                     # v2.1: 窗口级预算（§8.1，缺此段框架拒绝启动）
max_steps = 40
max_cost_cny = 0.5
provider = "deepseek"
timeout_min = 30

[dependencies]
upstream = ["win-arch-01"]    # 等这些窗口 done
blocks = ["win-review-01"]    # 这些窗口在等它

[outputs]
files = ["shared/outputs/src/"]   # 产出写入这些路径
gate = "lint + test 全绿"

[conversation]
total_turns = 147             # 对话总轮数
last_compressed_at = "2026-08-01T07:30:00Z"
snapshot_interval_hours = 1   # 每小时自动快照一次
```

## §5c 手工新增窗口怎么管理

你随手加一个窗口（比如临时需要找 bug、试验一个方案）——框架不能当成正式窗口来管，也不能完全不管。

### 自动分类

框架扫描 `windows/` 时：

```
if window.toml.state == "done"      → 跳过，不在活跃列表显示
if window.created_by == "human"     → 标记为 "adhoc"，不参与流转，不阻塞 gate
if window.dependencies 为空         → 独立窗口，不参与流转，人手动启动
```

**手工窗口的待遇**：
- 显示在项目窗口列表里，但标注 `[adhoc]`
- 不会因为阻塞而影响其他窗口的流转
- 人类要删就删——不会触发任何流转警告
- 对话历史一样自动压缩、一样自动快照

### 手工窗口升级为正式窗口

人类可以随时把 `[adhoc]` 窗口升级为正式角色窗口：
```
/project my-app window upgrade win-adhoc-01 --role "backend-developer" --depends "win-arch-01"
```
升级后框架把它纳入流转规则，下游窗口会等它完成。

## §5d 删除、归档、恢复

### 三档操作

| 操作 | 效果 | 恢复方式 |
|---|---|---|
| **软删除** | 窗口移到 `.trash/`，30 天后自动彻底清除 | `/project my-app window restore win-adhoc-01` |
| **归档** | 窗口移到 `.archive/`，永久保留但只读 | `/project my-app window unarchive win-backend-01` |
| **彻底清除** | 删除窗口目录 + 对话历史 + 快照，不可恢复 | 需要二次确认（「输入窗口 ID 确认删除」） |

### 不小心删了一个重要窗口？

```
.projects/my-app/.trash/win-backend-01/    ← 你的窗口在这里躺 30 天
```

30 天内都可以恢复。恢复后窗口状态回到删除前的那一刻——对话历史、上下文压缩状态、产出文件全在。

### 归档的窗口还占上下文吗？

不占。归档窗口是纯文件存储，不参与任何 active 计算。以后需要参考时可以以只读方式打开，读完之后重新归档。

## §5e 对话导出与引入

### 导出格式

每个窗口的对话可以导出为两种格式：

**Markdown（给人看）**：
```bash
/project my-app window export win-backend-01 --format markdown
# → 输出 my-project/exports/win-backend-01-conversation.md
```
格式：角色 + 时间 + 每轮内容（工具调用折叠为摘要行）。

**JSON（给机器/给别的 agent 引入）**：
```bash
/project my-app window export win-backend-01 --format json
# → 输出完整的 Message[] 数组，含 tool_calls、结果、元数据
```

### 引入外部对话

```bash
/project my-app window import --name "win-imported-01" --role "researcher" \
  --source ./external-conversation.json
```

引入后自动做三件事：
1. 解析 JSON → 注入为窗口的初始对话历史
2. 扫描历史中已有的产出文件 → 自动写入共享层
3. 运行一次上下文压缩（因为引入的历史可能很长）

**引入的典型场景**：
- 你在别的 AI 工具里聊了一个方案，想导入继续干活
- 另一个项目的窗口完成了类似的活，想复用它的经验作为新窗口的起点
- 归档窗口需要激活——先导出 → 再导入为 active 窗口

## §5f 快照与回滚

### 自动快照

```
每次触发条件（任一满足即快照）：
  - 窗口对话轮数每 +50 轮
  - 窗口从 working → done
  - 人类手动 /project my-app window snapshot win-backend-01
  - 上下文压缩执行前（防压缩坏）
```

快照 = 整个 `window.toml` + 对话历史的完整副本 + 当时共享层的文件快照。存 `.snapshots/win-backend-01--2026-08-01T08-00-00Z/`

### 回滚到快照

```
/project my-app window rollback win-backend-01 --to "2026-08-01T08:00:00Z"
```

**回滚后**：
- 窗口对话历史回到快照时刻
- 回滚之后的对话历史不会丢——存在 `.snapshots/rolled-back/` 里
- 回滚后的共享层变更不自动回滚（别的窗口可能依赖了这些变更）——框架只回滚窗口自身

**保持最多 10 个快照**，超出删最早。

## §5g 边界场景补充

| 场景 | 框架行为 |
|---|---|
| 两个窗口同名 | 新建自动追加 `-2`；升级时不允许重名 |
| 窗口依赖的窗口被删了 | 标记自身 `blocked`，原因 = "依赖窗口已删除"，等人类重新分配依赖 |
| 上下文压缩坏（压缩后丢关键信息） | 自动回滚到压缩前快照，用不同策略重压缩 |
| 窗口的产出文件被人类手动改了 | 框架检测文件 mtime 变更 → 通知窗口「产出已被外部修改，请重新验证」 |
| 项目文件夹被人类手动移动了 | 框架用 `project.toml` 里的 `project_id` 识别——不管文件夹在哪，同一个 ID 就是同一个项目 |
| 窗口模板 | 人类可以保存窗口 prompt 为模板：`/project template save "后端开发模板" --from win-backend-01`。下次一键创建。 |
| 流转规则被人中途改了 | 已触发的窗口不受影响；未触发的窗口按新规则执行 |
| 窗口群里有人类自己（不是 AI） | `window.toml` 中 `role = "human"` ——不参与自动流转、不消耗 token、不自动压缩。人在自己的窗口里手动干活，产出直接入共享层 |

## §6 与 codex-rust 现有资产的对接

| codex-rust 资产 | 窗口群模式怎么用 |
|---|---|
| `agent-core/loop.rs` 相位循环 | 每个窗口内运行完整 Init→Plan→Act→Observe→Reflect 循环 |
| `budget.max_steps` + `CostMeter` | 每个窗口的预算 = 步骤上限 + token 成本上限（见 §8.1） |
| `consecutive_errors` / `replan_count` / `steps_without_progress` | 窗口级失败重试与停滞检测语义（见 §8.2） |
| `experience` 经验库 | 窗口群结束后 → 组队决策卡入 experience（`category` 打标签）→ 下次组队更精准 |
| `subconscious` 潜意识门 | 每个窗口共享同一组 guard（宪法/成本/失误检测） |
| `nervous-system` NerveAction | 窗口成本超限时 `Simplify` / 停滞时 `Abandon`（见 §8.1） |
| `wiring` 断言（现 15 条） | 窗口群框架自身的质量闸门：窗口必须含必要产出文件 + gate 脚本（见 §8.8） |

| `ToolDispatcher::read_only_view` | 只读研究窗口直接复用（read/grep/glob 无写）——与 v12.7 子代理只读设计同源 |
| `merge_conflict` 字段（agent-types） | 共享层冲突标记的持久化载体（见 §8.4） |

## §8 v2.1 审查补充（2026-08-01 定版）

> 本节是对 v2.0 的 8 个实质缺口补充。编号与 §6 对接表一一对应。
> 全部补充均与 codex-rust 已实现资产对齐（源码核验：wiring 15 条 / loop.rs / experience schema）。

### §8.1 窗口级成本与预算控制（原 v2.0 缺失）

窗口是独立 agent，必须独立预算。每个窗口创建时声明：

```yaml
[budget]
max_steps: 40              # 步骤上限（对接 loop.rs budget.max_steps）
max_tokens: 32000          # 上下文硬上限
max_cost_cny: 0.5          # 单窗口成本上限（对接 CostMeter 记账）
provider: "deepseek"       # 窗口指定 provider（见 §8.7）
timeout_min: 30            # 窗口最长存活时间
```

**成本守卫**：窗口运行中 `CostMeter` 实时记账；超限时触发 `nervous-system` 的 `NerveAction::Simplify`（主动减少步骤）或 `Abandon`（放弃并标记 blocked，通知人类）。**不做无界消耗**——这是 v2.0 最大的缺口。

### §8.2 失败重试与停滞检测语义（原 v2.0 只有一句"超时重分配"）

窗口复用 codex-rust 三个计数器（源码实参）：

| 计数器 | 语义 | 窗口群行为 |
|---|---|---|
| `consecutive_errors >= 3` | 连续失败阈值 | 触发经验注入（弱模型）或 `Abandon` 标记 blocked |
| `replan_count < 3` | 重规划上界 | 超过 3 次 replan 仍无进展 → blocked，等人类 |
| `steps_without_progress` | 停滞检测 | 连续 N 步无产出 → `NerveAction::Simplify` |

**注意**：这些计数器是**每窗口实例**的，不是全局的——窗口 `blocked` 后重试 = 新 run()（计数器清零），但 `window.toml` 记录 `retry_count`（跨实例累计，上限 3，超限进 `.trash` 或等人类）。

### §8.3 Gate 必须脚本化（原 v2.0 是自然语言 gate）

v2.0 的 `gate: "lint + test 全绿"` 是自然语言——**不可执行、不可断言**。定版：gate 必须是**可执行脚本 + 退出码约定**：

```yaml
[outputs]
gate = "shared/gates/win-backend-01-gate.sh"   # 脚本路径
# 脚本约定：输出 VERIFY_PASS → 0 退出；否则非 0 + 输出失败原因
```

对接 `bench/verify.sh` 的既有约定（`VERIFY_PASS` 字符串 + 退出码）。框架只认脚本退出码，不解析自然语言。

### §8.4 共享层冲突仲裁层级（原 v2.0 只有"标记+通知"）

冲突不能只标记，要有仲裁路径。三层递进：

```
第一层：自动合并 —— 若两窗口改不同文件 → 无冲突
第二层：冲突标记 —— 同文件被两窗口改 → merge_conflict=true（agent-types 字段）
          + 双方窗口各存一份版本到 .snapshots/conflicts/
第三层：人类仲裁 —— 框架暂停下游，人类选版本 or 手动合并
          → 选定后清冲突标记，被否方窗口标记 blocked 等重做
```

`merge_conflict` 字段已在 `agent-types::FileChange` 存在（源码核验），窗口群直接复用为持久化载体。

### §8.5 快照回滚的一致性（原 v2.0 未定义下游感知）

v2.0 说"回滚不自动回滚共享层（别的窗口可能依赖）"——但没说**依赖方怎么感知**。定版：

```
回滚动作：
  1. 窗口自身对话/状态回滚到快照
  2. 写回滚事件到 shared/progress.md（"win-backend-01 回滚到 T0，产出 X 已撤销"）
  3. 检查 dependencies.blocks 里的下游窗口 → 标记 blocked，原因="上游产出已回滚"
     （下游不得基于已撤销的产出继续）
```

不自动回滚共享层文件（保留人类可选的独立性），但**必须通知下游**——否则产生悬挂引用。

### §8.6 压缩摘要上限（吸取 MAX_CONSTITUTION_CHARS=6000 静默截断教训）

codex-rust 的 `constitution.md` 注入有 `MAX_CONSTITUTION_CHARS=6000`，超出**静默截断**（源码实参）——窗口群压缩不能重蹈覆辙：

```
压缩摘要必须带长度上限（默认 2000 字符/层）：
  - 摘要生成时 LLM 明确收到长度约束
  - 压缩后框架校验摘要长度 + 关键字段（做了什么/产出/未解决）非空
  - 超限/缺失 → 自动回滚到压缩前快照，用不同策略重压缩
```

与 §5f 快照机制联动（压缩前必快照）。

### §8.7 窗口沙箱隔离（G0 结构基因映射）

codex-rust 的 G0 结构基因（landlock/seccomp 沙箱）应映射到窗口：

```
每个窗口 = 一个独立 sandbox 实例：
  - 只读：项目共享层 + 本窗口目录
  - 可写：本窗口 outputs 声明路径
  - 禁写：其他窗口目录 / .trash / .archive / 项目配置
```

复用 `ToolDispatcher` 的读写视图机制（`read_only_view` 已存在），窗口只写自己声明的产出路径——**物理上杜绝跨窗口污染**，与 §4 的"中间草稿不共享"呼应。

### §8.8 窗口群 wiring 断言（质量闸门）

窗口群框架自身必须有断言（对齐 codex-rust 15 条 wiring 的哲学——防火墙必须能断线变红）：

| 断言 | 锚定 | 断裂条件 |
|---|---|---|
| `window.toml-exists` | 每个 windows/*/ 必须有 window.toml | 缺文件 → 框架拒绝扫描该窗口 |
| `gate-script-exists` | window.toml 里 gate 指向的脚本必须存在 | 缺脚本 → 窗口 gate 永远失败 |
| `conflict-marked` | 两窗口改同文件时必须置 merge_conflict=true | 冲突未被标记 → 框架报错 |
| `budget-declared` | 每个窗口必须有 [budget] 段 | 无预算 → 拒绝启动（防无界消耗） |

这些断言是**框架的测试**（integration test），不是运行时检查——确保框架自身的工程质量。

### §8.9 多 Provider 窗口策略（原 v2.0 未提）

窗口可声明 `provider`（§8.1），与 codex-rust 已验证结论对齐：

```
- 复杂编码窗口（默认）：deepseek v4-flash（基线 90%±5%）
- 简单研究窗口：zhipu glm-4.5-air（成本低，经验注入有效）
- 天花板对照：deepseek-pro（仅 Q3 体检用，不日常）
- 窗口失败重试可降级换 provider：deepseek 连续失败 3 次 → 换 zhipu 重试
```

经验注入按窗口 provider 自适应（弱模型注入有效、强模型不注入——v19 结论）。

---

*设计原则复述：不造中央大脑。项目里有 N 个独立窗口，每个都聪明、都知道自己的活、都只读自己需要的共享层。它们不需要一个"领班"来分活——流转规则是配置，人类只在决定点介入。这个架构的核心假设和 codex-rust 锻造九轮验证过的同一条：边界越硬、上下文越干净、单元产出越可靠。v2.1 补充的预算/重试/沙箱/断言，就是把"边界硬"从口号变成可执行机制。*
