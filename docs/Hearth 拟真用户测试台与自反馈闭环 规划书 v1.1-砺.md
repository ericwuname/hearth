| 用户设想 | 可行性 | 关键判断 |
|---|---|---|
| 模拟不同种类的人使用 Hearth，生成测试日志，跑几十上百次 | ✅ 可行 | 拟真用户 = "另一个 LLM 角色驱动 hearth 终端"+ persona 语料库（**13 份手工日志 = 现成种子，531 条真实用户输入**）+ 双通道日志。**纯开发侧工具，不进 Core** |

# 1. 为什么做（沿用，数字更新）

CLOSURE-01 的教训（四方共识）：**脚本化验证的覆盖范围 ≠ 真实交互可靠性**。四包脚本化证据没暴露的东西，用户 90 分钟盲测全暴露了（24 连败吸引子、裸 ERROR 泄漏、内容截断、introspect 误路由）。手工盲测的两个工程缺陷：①不可重复（人的状态/输入不可复现）；②样本量太小。

> **补充一条本版新证据**：v0.2.18 盲测的成功率，用**两种口径**算出来是两个数——字符串口径 33.3%（12/36）、逐轮归因口径 **28.6%**（10/35）。**同一份日志、两个数字。** 这说明"指标"本身必须先被冻结定义，否则测试台规模化后只会把噪声放大（见 §2.5）。

**用户输入行为分布**（按用户输入行统计，非全文本）：

| 为什么 / 诊断原因 | 20 | 3.8% | diagnoser | ⚠️ 需区分"问系统自己的失败"（易触发继发失败）与"问领域知识" |

**persona 库定稿（七类，权重按上表设定）**：

```text
tools/simuser/personas/
├── continue-driver.md    # 26.9% 权重·最高优先级：完成型任务后的"继续/接着/再试"
│                          # 直接对应 RC47（继续续轮 give_up）与 RC52 吸引子入口
├── meta-interviewer.md   # 7.2% 权重·单条信息量最高：连问同一问题、质疑具体数字、追问记忆
├── corrector.md          # 12.8%：纠偏、否定、报 bug、复发抱怨
├── explorer.md           # 探索/状态/内观/身份自述
├── diagnoser.md          # 追问失败原因（须与 continue-driver 配对使用）
├── taskdriver.md         # 明确编码/文件任务，验结果
└── chatty.md             # 闲聊/情绪/模糊输入（交互面回归）
```

**persona 构造纪律**：每类 persona 的措辞样例**必须逐字取自真实日志**（引用 `release/手工测试vX.Y.txt` 行号），禁止编写者自己造句——否则测的是"我们想象中的用户"，而盲测的价值恰恰来自真实用户的"不规范输入"（v0.2.18 用户原话：「我给你的指令就不是很规范，你可能有很多东西都需要猜测」）。

## 2.2 关键机制（沿用 + 一处改判）

1. **双通道日志**（核心价值，不变）：终端侧（用户看到的一切，含裸 ERROR 与截断）vs Hearth 侧（telemetry + scratch + archive 时间戳 + 归因期 planner dump），按 session_id + 时间戳对齐 → **"系统做了什么"vs"用户看到了什么"的 diff** 直接量化 Projection isolation / completeness，P0-C 四层 completion 从此可测。
2. **拟真 = 自适应而非回放**：模拟用户 LLM 看到 Hearth 的真实输出后自己决定下一句；只有"污染前缀重放"类场景用逐字剧本。模拟用户**盲于 Hearth 内部**（只准看终端输出，禁止读 `.hearth/`、telemetry）。
3. **⚠️ 改判：模拟用户默认异源**（draft 写"同源可接受"→ 本版改为**默认异源**）：
   > 同源（模拟用户与被测 Hearth 同用 Agnes）意味着**同一个模型的盲区会在"用户侧"和"系统侧"同时出现**，这类缺陷永远测不出来——这是验证悖论的另一种形态。
   > **默认**：模拟用户用异源 provider（智谱 / 本地 Ollama `qiyuan-8b`）；**同源作为标注对照条件**跑一组（用于分离"模型共模"与"系统缺陷"）。成本极低（用户侧调用量远小于系统侧）。
4. **确定性控制**：persona 版本 + scenario seed + provider/model/温度 + budget 固定并记录；每跑记录 full event log。
5. **诚实性纪律**：判定指标全部用**确定性比对**（RESULT 文件、测试通过、日志计数），模拟用户的"感觉"只做线索不做证据（INV-G）。

## 2.4 成本估算（沿用）

每 run ≈ 40–60 步 × (Hearth 调用 + 用户模拟调用) ≈ 100–150 次 LLM 调用；**100 跑 ≈ 1.0–1.5 万次/周**，占 Agnes 配额 15–20%。先 30 跑起步。

## 2.5 新增：指标口径冻结（防 RC51 复发）

RC51 的教训是**坏测量方法会被复用**。测试台规模化前，必须先把指标写死并版本化：

| 指标 | 冻结定义 | 反例（禁止） |
|---|---|---|
| success_rate | **逐轮归因口径**：按 run 边界取该轮首个终态，分子 = 首个终态为 completed 的 run 数 | 用 `grep -c "Task completed"` 计数（会重复计、会跨轮串） |
| consecutive_failure | 连续终态为 failed 的 run 数（run 边界同上） | 按失败关键词计数 |
| 压缩/归档"是否发生" | **只允许字节数 + mtime + 文件数** | `wc -l` 行数（末行无换行即系统性少计——RC49 处已被证伪） |
| 跨版本可比性 | **成功率只在 v0.2.8+ 可比**（v0.1.x / v0.2.0/0.2.3/0.2.4/0.2.5 终态文案不含 `Task completed/failed`） | 把老版本的 0/0 读成"全部失败" |

每份指标定义写入 `tools/simuser/metrics.yaml`，**版本号随 persona/scenario 一起冻结**；改定义 = 升版本，旧数据不得与新数据混在一张表里。

## 2.6 新增：自动检测器清单（把评审窗的手工脚本产品化）

这几轮评审实际用过的检测器，应直接落进 `analyzer.py`——**这就是 L2（轨迹）/L3（单轮）评估栈的具体落点**，也兑现了"Observer OS 承载评估栈而非另起炉灶"的架构判断：

| 检测器 | 判据（确定性） | 对应缺陷族 |
|---|---|---|
| projection_leak | 终端出现 `^\d{4}-\d{2}-\d{2}T.* (ERROR\|WARN) agent_core\|sandbox\|planner` | RC38 / Projection isolation |
| consecutive_failure_run | 连续 N 轮 failed（N≥5 报警） | **RC52 吸引子** |
| t4_stall_burst | 单会话 T4 `identical TaskGraph` 次数 / 按 run 分布 | RC52 / T4 阈值敏感性 |
| revision_explosion | goal_revision 数 / 执行轮数 比值突增 | RC33 / RC39 |
| compaction_adjacency | 失败点距压缩点 ≤200 行 | RC5 / RC37 |
| truncated_output | 输出以 `…` 结尾 / 命中 `[N chars truncated]` 缺失 | RC35 / 截断族 |
| giveup_completed_coexist | 同一 run 内 `give_up` 与 `Task completed` 共存且无 `*_OVERRIDDEN` 痕迹 | F9 / 拦截链可观测性 |
| tool_misroute | 结构化工具名出现在 bash 命令串（如 `introspect` → exit 127） | RC53 |
| introspect_failure | 内部工具调用失败率按工具名分桶 | RC24-B 连带 |
| user_visible_completion | 内部 summary 存在 vs 终端正文长度（差值超阈值） | BUG-012 / P0-C |

**纪律**：检测器自身必须先自检（在未修复样本上应大面积命中，在干净样本上应零命中）——沿用"上线第一件事：在未修复代码上跑一遍确认它大面积 FAIL"的门禁惯例。

## 2.4' 验收标准（加严）

测试台第一验收（先红后绿）从"复现后段连败"**加严为三形态 + 分布对齐**：

**A. 三形态（缺一不可）**
1. 前段高成功率 + 后段连败的会话形态；
2. **入口事件 = 「继续」型输入失败**（对应 v0.2.18 run-013）；
3. **压缩晚于入口 ≥10 轮**（v0.2.18：入口 run-013 vs 首次压缩 run-024）。

**B. 分布对齐（与真实语料的量化距离）**

| 指标 | 真实语料基线 | 容差 |
|---|---|---|
| 继续/重跑类输入占比 | 26.9% | ±8pt |
| 短指令（≤30 字）占比 | 38%–68% | 落在区间内 |
| 用户输入平均长度 | 30–106 字 | 落在区间内 |
| v0.2.18 成功率（逐轮口径） | 28.6% | ±10pt |

→ **三形态 + 分布都对齐，才算测试台保真**。只复现"后段连败"可能只是"随便都会失败"，不足以证明测试台有效。

# 3. Hearth 内 AI 自记录问题闭环（file_issue）

## 3.1 闭环全图（沿用）

```text
Hearth 运行中（住户 AI）
    ↓ 发现异常
file_issue{category, severity, evidence 指针, description}   ← Core 内新工具
    ↓ append-only: .hearth/issues/<session>.jsonl
开发侧收集器 → 跨会话聚合 + 去重 + 三角验证
评审窗口判级（CONFIRMED / NEW F1 / FALSE POSITIVE / DEFERRED）
    ↓
顶层立项 → 执行窗口修复 → 测试窗口回归 campaign
    ↓
CHANGELOG + known-issues.md → 回注 Hearth 会话上下文
```

## 3.2 设计要点（四条纪律，其中第 5 条为本版新增）

1. **self-report ≠ evidence（INV-G）**：issue 必须带 session_id/step/tool call/日志路径等**可复核指针**，开发侧三角验证通过才算 CONFIRMED。
2. **限流与去重**：每会话 ≤3 条；`known-issues.md` 注入会话上下文，已知问题不重复报。
3. **复用不新建**：收敛 civ_note / run report / InteractionRequest 的出口，不建第二套事实模型（M8）。
4. **冻结边界**：file_issue 是 Core 代码改动（加性、零权威变化、sandbox 内 append-only 写），**必须走正式任务书审批**，随 v0.2.19 修复批落地，不悄悄进。
5. **⭐ 新增：确定性触发兜底**（draft 缺失，风险很高）：
   > file_issue 若只由模型主动发起，就依赖模型"自觉"——而"不自觉"正是本系统的已知缺陷（历史上多次出现"自述已验证"为假）。
   > **双通道**：
   > - **系统侧（不依赖模型）**：`stalled` / `give_up` / `approval_denied` / `verify_failed` / 工具五态异常命中时，由 loop 自动写一条结构化 issue（与 F9 `giveup_unverified` 标记同构）；
   > - **模型侧（可选补述）**：在此基础上补 category/描述，**不得删除确定性记录**。
   > 落盘须 **session 隔离**（复用 RC49 的 session 绑定教训）；issues **不进 LLM 可见上下文**（除 `known-issues.md` 摘要），避免成为第二事实源。

# 4. 窗口分工裁决：测试与修复必须分离（沿用）

1. **Blind 原则**：修 bug 的人再测会不自觉绕开雷区；本轮盲测的全部价值来自"非执行窗口、无预设剧本"，工程化时不能把它弄丢。
2. **归因纯净**：campaign 期间版本冻结；边测边改会让同一批数据横跨多个 binary（CFR 阈值优先级缺陷刚教训过我们）。
3. **零成本**：多窗口工作流已现成。

**运转节奏（campaign 制）**：
```text
测试窗口：campaign N（30-100 跑，版本冻结）→ 原始记录 + 检测器自动标记
评审窗口：判级 + 按层归聚类（mechanism/decision/model/provider/environment）
顶层：立项修复批（一次性攒批）
执行窗口：批量修复 + 单元级 smoke 自测
测试窗口：campaign N+1（含 N 轮失败场景重放 = 回归）
```
折中许可：执行窗口可跑单元/fixture 级自测（先红后绿照旧）；**campaign 级验证必须由测试窗口独立执行**。

# 5. 历史手工日志的挖矿结论（语料与基线，本版全面更新）

**语料规模**：13 份日志（v0.1.0 → v0.2.18）、79,659 行、531 条真实用户输入。

| 版本 | 行数 | 用户输入 | 成功率（逐轮口径） | T4 停滞 | 用户行为特征（persona 素材） |
|---|---:|---:|---:|---:|---|
| v0.1.x ~ v0.2.5 | 32,157 | 369 | **不可比**（终态文案不同） | — | 早期形态：探索、resume 排查、长会话 |
| v0.2.8 | 2,483 | 16 | 52.4%（11/21） | 0 | 探索型：翻"住户反馈"目录、自我认知提问 |
| v0.2.10 | 5,210 | 84 | 76.1%（54/71） | **10** | 自我认知深聊、任务+闲聊混合 |
| v0.2.15 | 2,121 | 21 | 55.0%（11/20） | 0 | 跨会话记忆测试、session 边界探测 |
| v0.2.18 | 3,702 | 41 | **28.6%**（10/35） | **27** | 元诊断追问、失败报告逐字回贴、长会话污染 |

**高收益探针行**（复发抱怨 / 纠偏 / 追问失败原因 = 历史上真正挖出缺陷的交互形态）：全语料 **30 条（占用户输入 5.6%）**，分布 v0.2.4:8 / v0.2.18:6 / v0.2.10:4 / v0.2.15:4 / v0.2.5:4 / v0.2.3:2 / v0.1.3:1 / v0.2.8:1。
→ **含义**：5.6% 的输入承担了绝大部分缺陷发现。persona 采样应**刻意放大这类行为的比例**（而非按自然分布 1:1 采样），否则测试台的"发现率"会低到失去性价比——这是测试台与自然用户分布最重要的一处**有意的偏差**，必须在报告里显式声明。
