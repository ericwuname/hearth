## 一、缺陷

```rust
let content = tokio::fs::read_to_string(&full).await
    .map_err(|e| anyhow!("read artifact {rel_path} failed: {e}"))?;
Ok(content)
```

调用链：`GET /api/v1/sessions/:id/artifact/open?path=…`
→ [routes.rs](file:///c:/Users/87465/Desktop/codex-rust-v1.0-final/crates/service/src/routes.rs#L282-L310) 把返回值**直接作为 `text/plain` 响应体**送出。

**为什么可达**：被读的文件就在**会话 workspace 内**，而 workspace 是 agent 自己写的——
一条 `cargo build 2>&1 | tee build.log`、一次大数据导出、一次网页抓取落盘，
都可能留下一个多 GB 的产物。**一次 GET 即可把服务端 OOM**（然后 `read_to_string`
失败还会让整个响应变成 400，掩盖真实原因）。

---

## 二、修复

新增约束 `MAX_ARTIFACT_BYTES = 8 MiB`（与 `read` 工具同口径）与一个有界读取辅助：

```rust
async fn read_text_capped(path: &Path, cap: u64) -> std::io::Result<(String, bool)>
```

- `take(cap + 1)` 有界读取（+1 字节用于判断"后面还有没有"）；
- **截断时**退到最后一个合法 UTF-8 边界（截断点可能切断多字节字符）；
- **未截断时保持原语义**：非 UTF-8 一律报错（不静默 lossy）；
- 命中上限 → 响应体末尾追加**明确留痕**：

```
[hearth] 产物超过 8 MiB，预览仅显示前 8 MiB（要看完整内容请在会话工作区内直接打开该文件）。
```

> `cap` 做成**参数**而非写死常量，是为了让单测能用 4096 这种极小值精确验证边界
> （8 MiB 的测试数据既慢又不精确）。
