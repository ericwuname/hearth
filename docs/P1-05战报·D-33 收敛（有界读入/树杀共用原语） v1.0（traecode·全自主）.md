## 一、为什么必须收敛（不是"代码洁癖"）

P0-06 / P0-07 / P0-08 / P0-09 / P0-12 五张卡反复修同一个缺陷族——"读入无上限"与
"进程不收尸"——结果在**四个 crate** 里各留了一份实现：

| 落点 | 当时的副本 |
|---|---|
| `sandbox` | `drain_capped_std` + `drain_capped_async` + `kill_process_tree` |
| `tools-builtin::read` | 有界文本读取（UTF-8 边界回退内联） |
| `agent-runtime::session` | `read_text_capped`（与前一份几乎逐行相同） |
| `agent-core::loop` | `drain_capped` + `kill_check_process_tree` |

**危险不在重复本身，而在"这四份的关键语义必须完全一致"**：

1. **必须"读到 EOF"** —— 用 `Read::take(cap)` 会在上限处停止读取，子进程随即
   **写满管道并永久阻塞**（把 OOM 换成死锁）；
2. **截断必须留痕**；
3. **文本截断要退到合法 UTF-8 边界**；
4. **杀进程要杀到"树"**（`Child::kill` 只到直接子进程）。

**只要有人改了其中一份的这一条，另外三份就成了"看起来一样、其实不一样"的定时炸弹。**
收敛后这四条不变式**只有一处定义**，并写在 `bounded_io` 的模块文档里。

模块文档写清四条不变式与**各自的取证来源**（哪张卡、什么现象、什么实测数字）。

### 2.2 四处调用点改为引用（本地实现全部删除）

| 落点 | 变化 |
|---|---|
| `sandbox` | 删本地 2 个 drain + 本地 `kill_process_tree`；`drain_capped_std` 用 `#[cfg(target_os="linux")]` 单独引入（非 Linux 上无消费者，否则 unused_imports） |

依赖方向：`bounded-io` 是叶子（只依赖 tokio io-util/fs + tracing），**无环**。

### 2.3 测试随实现走

原则：**实现去哪，纯辅助单测去哪；端到端测试留在原处。**

| 测试 | 去向 |
|---|---|
| `drain_capped_std/_async` 边界（含"必须排空到 EOF"） | → `bounded_io::tests`（4 条） |
| 有界文本读取（钳位 / UTF-8 边界 / 未截断拒绝非 UTF-8） | → `bounded_io::tests`（3 条） |
| `kill_process_tree(0)` 不误杀 | → `bounded_io::tests`（1 条） |
| NoopSandbox 正常语义不变 / 超限截断端到端 / 超时杀孙进程 | **留在 `sandbox`**（测的是沙箱后端行为） |
| S12 自检命令超时回收 | **留在 `agent-core`**（测的是 `run_check_cmd`） |
| `read` 工具单行超大文件有界 | **留在 `tools-builtin`**（测的是工具） |

`kill_process_tree` **不做独立单测**：它只在"真有子进程"时有意义，覆盖由上述两条
端到端测试完成（都断言目标进程确实消失）——这一条写进了 `bounded_io` 的测试注释，
避免后人误以为它没被测。

## 四、方法论沉淀（第 14 个变体）

> **"重复代码的危险不在重复，而在'它们被要求保持一致却分散在各处'。"**

普通的重复（三行相似代码）无害，甚至比过早抽象更好。
但本卡这四份**不是普通重复**：它们承载**同一组安全不变式**，
而每一条不变式都是**用真实事故换来的**（OOM、挂死、孤儿进程）。
这种重复的代价不是"多打几个字"，而是"**下次只改一处**"。

**固化为检查项**：
1. **凡"同一条不变式在多个 crate 各写一遍"，立即收敛**——判据是"改一处漏三处会不会出事"，
   而不是"代码长得像不像"；
2. **收敛时把不变式本身写进共享 crate 的模块文档**（含取证来源），
   而不是只搬代码——后人需要知道**为什么不能简化成 `take(cap)`**；
3. **测试跟着"被测对象"走**：纯辅助单测随实现迁移，端到端测试留在原处，
   并在原处留一行"搬去哪了"，避免后人以为覆盖丢了。
