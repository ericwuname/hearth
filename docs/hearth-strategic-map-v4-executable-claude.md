# Hearth 战略地图 v4.0（可执行版）

> **出品**：外部评估窗口（Claude）　**日期**：2026-09-03
> **性质**：在《战略地图 v3.0》的骨架基础上重写，目标是把"方向对"的部分变成"可检查、可执行、可复盘"的部分——不新增战略判断，是把已有判断落到能验证的地步。
> **和既有材料的关系**：不推翻 P4/P5 合并总报告、external-review-pack、战略地图 v3.0 的任何事实结论；这三份材料的数据基座本报告全部采信。本报告要解决的问题是——**这些正确的判断，怎么变成一份不会在下一次犹豫、下一次转向冲动面前散架的执行图。**
> **一句话定位**：v3.0 回答的是"往哪走"；这一版要回答的是"每一步怎么知道走对了，走错了怎么办，谁说了算"。

---

# 0. 先说这份地图和之前所有材料最大的不同

之前所有版本的战略讨论，包括 v3.0，共同的弱点是：**方向判断很多，检查点很少**。这两个月发生过的每一次问题——497:0、三层死锁两个月没被发现、CORE FREEZE 自己宣布自己合格、15 分钟内推翻决胜局又推翻——性质都是同一个：**判断在推进，但没有一道机制拦住"判断错了继续往前冲"**。

所以这一版的核心改动只有一件事：**每一个阶段，都配一条"入口检查"、一条"出口检查"、一条"如果检查不过该怎么办"**，而不是像 v3.0 那样用进度条百分比或"建议"这种软表述。

# 一、治理底盘（贯穿所有阶段，不属于任何单一阶段）

这一节是这份地图和前面所有版本最大的区别——以下规则不写进某一个 Stage，是**所有 Stage 共用的物理定律**，任何阶段违反了都算失败，不需要重新讨论。

## 1.1 证据纪律：四层，缺一层不算数

任何一条"能力已具备"的声明，必须能回答自己站在哪一层：

| 层 | 问题 | 例子 |
|---|---|---|
| L0 存在性 | 代码/文档里有没有这个东西 | "有一个 rollback 命令" |
| L1 行为 | 单元测试证明它按预期工作 | "rollback 单测通过" |
| L2 证据 | 真实运行场景下，独立第三方复现过 | "有人在 VM 上真的 kill -9 后 rollback 成功" |
| L3 用户可验证 | 用户不需要看代码/日志，凭界面呈现就能判断结果 | "用户看到的输出里明确写了回滚到了哪个版本" |

**规则**：任何验收报告只写到 L0/L1 就说"已完成"的，一律打回；只有写到 L2 才能进入下一阶段的入口条件；L3 是产品化之前的硬门槛，不是加分项。

这不是新发明——这是这两个月我们反复验证过的、唯一能防住"存在性≠行为、机制正确≠用户体验正确"这类反复出现的错觉的方法。**以后任何一份验收报告，必须显式标注自己在哪一层，不写层级的报告不予采信。**

## 1.2 独立评审：造的人不能是唯一裁决的人

**任何一次"是否可以进入下一阶段"的裁决，裁决人必须至少有一个不是该阶段的施工方。** 这不是走流程——CORE FREEZE 自我宣布这件事已经证明，同一个人既造又判，系统性地会高估自己的完成度，不是道德问题，是结构问题。

具体到这个项目现有的分工：执行窗口造，砺（评审窗）或外部 AI 窗判，两者不能是同一个实体在同一个阶段里既造又判。

## 1.3 验收强弱区分：两档，不能混用

- **弱验收**：能编译、测试通过、命令跑完、有输出。
- **强验收**：旧故障 → 新机制 → 真实行为改善（L2 证据）→ 回归无破坏 → 长程任务下依然成立。

**任何阶段的"出口条件"，必须是强验收，不能拿弱验收充数。** 这条已经在 CORE FREEZE 相关材料里出现过，这里正式确立为跨所有阶段通用的规则，不是某一次冻结特有的要求。

## 1.4 QUARANTINE：新想法先设计后端，不直接进施工队列

任何在当前阶段执行过程中冒出来的新想法（不管多有吸引力），一律先写成一份"设计草案 + 解封条件"文档，标注 QUARANTINE，不得直接改代码。解封条件必须是**可检查的具体条件**（比如"某几项前置指标达标"），不能是"感觉时机到了"这种主观判断。

这条规则本身就是这两个月吸取的教训——多轮推理/人格设计当时被正确挡在了 QUARANTINE 里，没有因为讨论得热烈就提前开工。**这个机制本身要作为治理底盘保留下去，不只用于那一次。**

## 1.5 决策分级：可逆低成本 vs 不可逆高成本，配不同的犹豫速度

任何一次"是否转向"级别的决策，先问两个问题：**这个决定可逆吗？撤销成本高不高？** 可逆、低成本的决定（比如轮换一个密钥），可以立刻拍板；不可逆、高成本的决定（比如放弃自研引擎），**必须要求自己至少给出一次独立于当下情绪的、写成文档并等待至少一个自然日冷却期的分析，才能拍板**。

这条是为了直接堵住这两个月里真实发生过的"15 分钟内、无新证据、单凭一句话就推翻一份精心设计的决胜局方案"这个具体事故——不是靠自觉，是靠一条硬规则：**凡是不可逆的战略决策，必须有冷却期，没有例外。**

## 1.6 情绪信号：记录，但不直接当决策依据

用户或任何窗口在过程中表达的沮丧、怀疑、"要不要干脆放弃"这类情绪性发言，**应当被记录，作为需要被解释的信号，但不能直接触发战略级决策**。正确的处理方式是：把这个情绪指向的具体问题（"为什么改了这么多次还是这样"）拆解成一个可以拿数据回答的问题，而不是直接把情绪本身当成裁决。

# 二、九个阶段（S0-S8）：每阶段都有可检查的入口/出口

沿用 v3.0 的阶段划分（结构合理，问题在于每阶段的验收太软），逐一补上入口/出口检查。

## S0 · Core Revalidation（当前所在阶段）

- **入口条件**：已发生（用户盲测暴露失败率）。
- **出口条件（未完成，见下）**：
  1. A 臂数据补齐（不是"重跑中"，是拿到完整数据并经独立方判读）；
  2. 明确回答"三层死锁模型覆盖了多大比例的原始失败"，不能笼统写"根因坐实"；
  3. 已知的、不经过三层死锁链路的另外两类现象（情绪吐槽误判、失败自诊断死循环）有明确处置——修复、或者证明已经不存在、或者显式记录为"移交 Cognition 层解决，不阻塞 S0 出口"。
- **未过出口条件时该怎么办**：不进入 S1，继续留在 S0，不允许"数据没到齐但先开始下一阶段"这种并行推进。

## S1 · HCC（Host Capability Contract）

- **目标**：定义"什么算一个合格的通用 Host"，不再靠"感觉 Codex 好"来选。
- **入口条件**：S0 出口条件全部满足。
- **补充维度（v3.0 遗漏，本版新增）**：H6 Extension 这一项，除了"有没有扩展机制"，必须加一条**"该扩展机制过去 12 个月的破坏性变更频率"**——防止半年后底座自己改了扩展面，Hearth Cognition 层大面积返工，重演一次"抄错答案"。
- **出口条件**：HCC v0.1 文档定稿，每一项（H1-H8）都能回答 required/optional/observable/testable 四栏，且 H6 的变更频率数据已经填入至少两个候选底座。

## S2 · Host Bake-off

- **目标**：跑同一份 golden 集，选底座。
- **入口条件**：S1 出口条件满足。
- **出口条件**：至少两个候选底座跑完完整 golden 集测试，产出可比较的成功率/中文体验/接 Agnes 或本地模型摩擦度数据，选型理由写成文档（不是口头拍板）。
- **本版新增的成本项**：明确列出"SimUser/PTY driver 移植到新底座 CLI"这项工作量估算，作为选型决策的输入之一，不要等选完了才发现移植成本远超预期。

## S3 · Hearth Cognition MVP

- **目标**：宪法治理/UNVERIFIED 标注/技能库 以 MCP/extension 形式接入选定底座。
- **入口条件**：S2 出口条件满足（底座已定，移植成本已知）。
- **本版最重要的修正**：**"事实校验对完成判定有否决权"这一条，必须在 MVP 里就实现最小版本，不能推迟到 S5（Evidence/Verification OS）。** 理由：这正是 Q2 应答里指出的问题——底座说"完成了"，Cognition 层必须能独立复核并有权把这个判断改写成"未验证"，这不是一个可以往后排的进阶能力，是防止"模型自报假完成"在新底座第一天就重演的必要条件。
- **出口条件**：①MVP 跑通中文 + 弱模型场景验收；②MVP 上跑一遍完整 golden 集（D3 已批的条件），成功率不低于 S2 阶段选定底座裸跑的成功率（即：加了 Cognition 层不能让底座原本的表现变差）；③"事实校验否决完成判定"这条路径至少有一次真实场景下的复现证据（L2 层）。

## S4 · Discovery Engine

- **目标**：帮助发现"原本不知道的问题"，不是一个预定义好的功能清单。
- **入口条件**：S3 出口条件满足。
- **出口条件**：至少一次真实使用场景下，Discovery 机制发现了一个此前完全没有被预期到的问题（不是提前设计好去发现的问题），并且这个发现被独立方确认是真实的、有价值的。这条出口条件故意设得"不好量化"，因为 Discovery 本身的定义就是发现意料之外的东西——但"至少一次真实案例"这个门槛依然是可检查的，不是空话。

## S5 · Evidence / Verification OS

- **目标**：把 S3 里的最小事实校验能力，扩展成完整的、可配置的验证体系。
- **入口条件**：S4 出口条件满足。
- **出口条件**：证据强度分级（L0-L3）在这一层被结构化地实现，而不是靠人工判断"这算不算验证过"；有明确的"这次验证的证据强度是多少"的机器可读输出。

## S6 · Memory / Learning / Feedback

- **目标**：把"这类任务过去做得准不准"这种历史结果，变成能影响未来行为的参数（呼应此前讨论过的"信用钱包"设想）。
- **入口条件**：S5 出口条件满足。
- **出口条件**：至少有一个具体的、可验证的行为分支（比如"验证严格度"这一个参数），是根据真实历史 done/failed 记录自动调整的，而不是写死的常量。**这条必须满足"功能性人格"的判断标准**（能否只改一个配置数值实现，不碰生成内容本身），不满足则退回设计阶段。

## S7 · Interaction Intelligence

- **目标**：更懂用户，交互层面更自然。
- **入口条件**：S6 出口条件满足。
- **本版提醒**：如果这个阶段涉及任何形式的多轮显式推理或人格差异化设计，**必须先查此前已经写好的 QUARANTINE 备忘录（多轮推理+功能性人格设计草案），确认解封条件是否已经满足，不得绕开这份备忘录重新设计一遍。**

## S8 · Product Layer

- **目标**：真正产品化。
- **入口条件**：S0-S7 全部出口条件满足，且已经过至少一次完整的周期性复检（见第五节）。
- **出口条件**：不在本版范围内详细展开——到这一步的具体验收标准，应该基于 S0-S7 走完之后积累的真实数据重新制定，现在写死没有意义。

# 三、五条红线（在原三条基础上新增两条）

原三条（来自战略转向路径书 v1.1，方向正确，保留）：

1. **接口**：只走标准扩展面，不改底座内核。
2. **顺序**：先跑通 MVP 再谈优化。
3. **范围**：不做 wrapper 增厚。

本版新增两条（解决原三条里"范围"这一条无法被检查、只能靠感觉判断的问题）：

4. **可归属性**：Cognition 层新增的每一块代码，必须能明确对应到六项认知能力（Intent/Evidence/Discovery/Memory/Learning/Interaction）中的哪一个，并能回答"如果这块代码不存在，golden 集里哪个具体场景会重新失败"。答不出来就是 wrapper 增厚，不需要等事后才发现。
5. **定期复健**：安排固定周期（建议每次底座或 Cognition 层发生实质性变更后，或至少每季度一次），重新用完整 golden 集跑一遍当前"底座+Cognition层"的组合，产出可比较的成功率数据。**这条红线是为了防止这个项目已经在自己的引擎上发生过一次的事——花两个月持续优化、却没人定期回头拿真实数据检查，直到失败率累积到 80% 才被发现——在新架构上无声重演。**

# 四、资产处置（沿用并确认既有清单，不重新制定）

《战略转向路径书》§四 的资产迁移清单本版全部采信，不重复。补充两条处置意见：

- **SimUser/golden 集测试基建**：明确认定为"核心资产，必须迁移"，不是可选项——因为这是这个项目唯一一套已经证明过有效的、能揭示"机制正确但真实行为不对"这类问题的工具。迁移成本已在 S2 出口条件里要求提前估算。
- **五张知识卡**：本版要求这五张卡不只是归档物，而要作为 S1（HCC 设计）和 S3（Cognition MVP 设计）阶段的**强制引用材料**——任何一份设计文档，如果和某张知识卡的教训直接相关，必须显式引用并说明"这次设计如何避免重蹈覆辙"，不能默认"大家都知道这个教训了"就跳过。

---

# 五、周期性复检机制（新增，此前所有版本都没有的一环）

除了红线 5 提到的固定周期复检，本版要求建立一个更轻量、更高频的机制：

**每完成一个阶段（S0→S1→S2……）的出口检查时，除了检查该阶段自己的出口条件，额外做一次"上一阶段是否还成立"的抽查**——比如进入 S2 时，抽查一下 S1 定义的 HCC 标准，有没有在 S2 的实际选型过程中发现自相矛盾或者遗漏的维度。这条机制的目的是防止"阶段推进变成单向的、不回头看的接力赛"，这正是这两个月里"四次局部正确的补丁，每次都把判定权从模型手里拿得更死"这个具体教训想要防的模式——**局部正确的判断，累积起来可能是系统性错误，唯一的解药是定期往回看，不是只往前走。**

# 六、当前所处位置与下一步

按本版的阶段划分，项目当前卡在 **S0 的出口条件**，尚未满足：

- [ ] A 臂数据补齐并经独立方判读
- [ ] 明确三层死锁模型的覆盖比例
- [ ] 情绪吐槽误判、失败自诊断死循环这两类现象的处置方式已确定

**下一步不是开始 S1（HCC 设计），是先把这三项 S0 出口条件走完。** 这不是保守，是这份地图的核心原则——阶段之间的推进必须靠可检查的出口条件驱动，不能靠"讨论得差不多了、该往前走了"这种感觉驱动，这正是这两个月反复出问题的根源，也是这一版地图存在的唯一理由。

# 七、一句话收束

> v3.0 已经把"往哪走"想清楚了，这份地图要解决的是另一件事：**每一步有没有一道拦得住的检查，拦不住的判断，走得再快也没有意义。** 这两个月最贵的教训不是某一个具体 bug，是"局部正确的决定，在没有回头检查的情况下，会累积成系统性的错误"——这条地图的每一条规则，都是在针对这一句话本身。
