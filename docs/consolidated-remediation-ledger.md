**最重要的四句话**：

1. **长程任务必死**：根 agent 的 `node.status` 永远不置 `Completed`，活性信号断裂 → 5 步 × 3 次 replan ≈ 15 步强制 GiveUp（`RC1`）。全量日志 GiveUp 计数 **157 次**。
2. **用户不知道它是完成还是放弃**：`give_up` / 真 error / 校验失败 **三态在终端显示完全一样**（都只是 `✗ Done (N steps)`），`status` 字段产生了但从不渲染（`RC8`/`RC9`）。**99 次"继续"不是习惯，是系统在静音模式下没给别的可用动作**（`RC19`）。
3. **纯读任务被判"没做事"**：验收口径硬编码成"必须写文件"，调研/问答类任务被强制 replan 烧光 budget（`RC10`/`RC17`）。
4. **纯读任务成功也会被判失败**：工具返回 `✓ DONE_SLEEP`、`0 errors`，系统仍 `give_up` 报 `✗ Task failed`（`RC21`）。用户看到的失败里，有一部分其实是"干完了却说没干完"。
5. **一半的"代码问题"其实是环境问题**：env 在 `.bashrc` 的非交互早退之后，脚本化调用一律拿不到 → web_fetch 全周期 35 次拒绝 0 次成功、sandbox 10 项失败。**治理后全量测试 370 passed / 0 failed，web_fetch 首次真正取回正文。**

本轮 18 条发现里有 **5 条是同一个模式**，建议顶层按"一类问题"而非"五个 bug"来处理：

### RC19 · REPL 模式默认砍掉全部 WARN —— 手工测试 90% 的数据量是在"静音"下产生的

| 项        | 内容                                                                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 源码       | `codex-cli/src/lib.rs:246-250`：`is_repl` 时 `default_filter = "hearth=info,error,lsp_bridge=off"`（**无 warn**）；非 REPL 才是 `hearth=info,warn,...` |
| 设计意图     | 注释（v0.1.4 R5）自陈：REPL 下 stderr 写同屏会打断 reedline 提示符重绘；权衡结论是 **"WARN 排障价值 < 输入体验"**                                                              |
| 实测影响     | 日志中 WARN 行：v0.1.0=14 / v0.1.1=75 / v0.1.2=42 / v0.1.3=43，**v0.1.5 起 = 0**。9 份手工测试有 7 份（占字符量约 90%）在静音模式下产生                                     |

### RC20 · 中文（与非英文关键词）错误在用户侧 100% 不可见，失败被渲染成绿色 ✓

| 项      | 内容                                                                                                                                        |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 源码     | `codex-cli/src/render.rs:86-92`：`is_err = output.to_lowercase().contains("error") \|\| contains("failed") \|\| contains("missing")`       |
| 断点     | **纯英文关键词子串匹配**。中文错误（"权限不够"、"错误的系统调用"、"出网被拒"）与非关键词英文错误（"Resolving timed out"）**一个都命中不了** → `is_err=false` → 渲染为绿色 `✓`                      |
| 现场实证 1 | 2026-08-29 `.133`：`✓ "curl: (28) Resolving timed out after 5002 milliseconds\nCODE=000"` —— 明确失败，绿色 ✓                                     |
| 现场实证 2 | 日志 v0.2.5:3443-3447：`write_file` 成功（9004 B）后，`chmod +x` → `exit code: 159 错误的系统调用（核心已转储）`，执行 → `exit code: 126 权限不够` ×2，**四条输出全部渲染为 `✓`** |
| 后果     | 用户看到满屏绿 ✓，实际全是失败。**这是"用户不知道它没完成"的直接成因之一**，与 RC8（三态同形）叠加                                                                                   |
| 建议     | ① 判定改为"退出码非 0 即失败"（工具层已有 exit code，无需猜字符串）；② 中文错误关键词入库；③ 渲染层不得自行判定成败，应由工具层返回结构化 `is_error`                                                |

### RC21 · 假失败：工具成功、0 errors，仍 give_up 并报 `✗ Task failed`

| 项   | 内容                                                                                                                                                                                                         |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现场  | 2026-08-29 `.133` 两次复现（T-B、T-DNS）：`⚙ bash ... sleep 40; echo DONE_SLEEP` → span 40,006ms → **`✓ DONE_SLEEP`** → `Giving up after 4 steps, 0 errors` → `give_up` → **`✗ Done (5 steps)` / `✗ Task failed`** |
| 关键点 | **0 errors、工具明确成功返回**，系统仍判定失败。与"假完成"相反，但同样是谎言，且更隐蔽——用户以为活没干完，实际干完了                                                                                                                                         |
| 关系  | 与 RC1 同源：`steps_without_progress` 只看 `node.status == Completed`，**不看工具是否成功**；根 agent 无置位路径 → 只要走了几步 plan/replan 就必然 give_up                                                                                |
| 附带  | 超时 kill 是干净的（`pgrep -af sleep\|curl` 无残留，cgroup 回收正常）                                                                                                                                                      |
| 建议  | 活性判据必须纳入"工具成功"这一信号；give_up 前若最后一步工具成功，应判完成而非失败                                                                                                                                                             |

### 🆕 RC24 · `> /dev/null` 触发破坏性审批门，且在 one-shot 模式下必然静默失败（P0）

**完整证据链（四环相扣，全部实测/源码确证）**

```
① 判定：agent-core/src/loop.rs:225-227
   if raw.contains("> /dev/") || raw.contains("> /proc/") || raw.contains("> /sys/") { return true }
   → `echo hi > /dev/null` 被判定为与 rm -rf / mkfs 同级的"破坏性命令"，需审批

② 矛盾：sandbox/src/lib.rs:385-393（T6, v0.2.3）
   显式为 /dev/null 加 landlock FS_RW，注释写明"null 设备写=丢弃，无副作用"
   → 沙箱层说安全、审批层说破坏性，同一系统的两层策略互相打架

   **【T6 条目勘误 · 2026-08-30 N1-SBX】**：本条历史记载"T6 已落地"与实证不符——
   T6 的 add_landlock_rule 对 /dev/null 传 FS_RW 全量集（含 11 个目录专有位），
   内核对非目录 parent_fd + 目录专有权必 EINVAL → 规则从未添加成功（warn+skip）。
   **T6 自 v0.2.3 起从未生效**，被旧审批门遮挡至 RC24 放行后才暴露。
   与 f0b4a54 假绿同族：历史"已验收"记载必须以实证为准。已由 N1-SBX
   （f8f549a，对象类型感知权限集）修复：非目录目标自动掩出为文件级四位。

③ one-shot 必失败：run_local.rs:319 `agent.set_interactive(true)`
   hearth chat 是一次性非交互进程，却被标记为交互模式 → 审批门发起
   → loop.rs:2300-2312 发起 blocking 交互（timeout: None, on_timeout: abort）
   → 无交互通道 → "⛔ approval — 批准? [y/N] ✗ 审批提交失败: no interaction state for session …"
   → **命令从未执行**，且错误信息不说"非交互模式无法审批"
   （对比：出网审批 loop.rs:1034 与预算询问 loop.rs:3156 都有 `self.interactive` 判空，
     唯独工具审批门没有 —— 这是一处遗漏的一致性缺口）

④ 绕过也无效：无空格写法 `2>/dev/null` 不含 "> /dev/"（少一个空格）→ 不触发审批
   实测：`echo hi 2>/dev/null` → NOSPACE_RC=1（重定向仍失败）
        `cat /dev/null`      → READ_RC=0（读成功）
   → **T6 的 landlock 修复只生效了读（FS_RO），写（FS_RW）未生效**
   → 这正是本日志 8 次「/dev/null: 权限不够」的根因
```

**危害**

- `> /dev/null` 是 shell 里最常见的丢弃输出写法，被误判为破坏性 → 大量正常命令被拦
- **一个空格即可改变安全分级**（`> /dev/null` 拦，`2>/dev/null` 放行）→ 启发式既误报又易绕过
- one-shot / CI 场景下命令**静默不执行**，用户只看到一句 "no interaction state"
- 全部失败渲染为绿色 `✓`（RC20 叠加）

**建议**  
① 审批判定改为语义化（白名单 `/dev/null` 这类无副作用设备，黑名单真正的破坏性操作）  
② 工具审批门补 `self.interactive` 判空，与出网审批、预算询问对齐

④ 修 T6：确认 `add_landlock_rule` 对 `/dev/null` 的 FS_RW 为何未生效（该函数失败目前只打 WARN 不阻断）
   **【已闭环 · 2026-08-30 N1-SBX f8f549a】**：根因 = FS_RW 混入目录专有权（READ_DIR/
   REMOVE_DIR/MAKE_*/REFER 共 11 位），非目录 parent_fd 必 EINVAL（内核语义，诊断矩阵
   C1-C5 实测）。修复 = 对象类型感知权限集（fstat 判型，非目录掩出 FILE_MASK 四位），
   FS_RO 同病同修。真机两层验收通过：add 零 EINVAL + 沙箱内 >/dev/null 写入成功
   （TC8_EXEC_OK）；目录/普通文件规则不回归。

### 补充：resume 的 core dump（exit 159）性质判定

`.131` 上 `hearth resume` 报 core dump / exit 159（SIGSYS）；`.133` 上实测 `hearth resume` **RC=0 正常恢复并回答**。  
→ **resume 路径本身没坏**；`.131` 上的 159 是 resume 触发的**工具调用撞上 seccomp 白名单缺口**（与 `chmod` 159、`getent` 159 同源）。  
→ 原排查方向「文件系统兼容性或信号处理」会把人带偏，实际应查**具体哪个工具用了白名单外的 syscall**。

### 防线 B · seccomp 能力缺口盘点 —— ⚠️ fail-closed 正确，但有两个能力缺口

**要盘点的命题**：seccomp 白名单（`sandbox/lib.rs:560-675`，99 syscall，默认拒绝 fallthrough = `SECCOMP_RET_KILL_THREAD`，fail-closed）是否漏放行 agent 常用能力。
