## 3. 点名裁定二：B1 判定歧义——**改判 RC52_REPRO**

### 3.1 事实（Node 14 测试报告 §155 已给全）

- B1 日志：**14 处 give_up** vs **2 处 provider_fail 字符串**，continue 终态 = failed。
- 判定器优先级规则：`provider_fail` 字符串**先于**终态判断 → B1 被误判 `PROVIDER_UNREACHABLE` 出分母。
- 既有纪律（Node 14 已确认）：**判定以 continue 终态为准**；`prefix_last_terminal` 只是辅助字段。

### 3.2 裁定

**B1 = `RC52_REPRO`，回归分母。** 理由三条：
1. 终态失败由 **give_up 主导**（14 处 vs 2 处），provider 字符串属瞬时噪声，不满足"provider 失败是主导原因"的归因门槛（第七层 DRIVER-INDUCED / provider 归因的举证责任在判定器，不在样本）。
2. 与 A 臂 fresh 修复生效（100%→0%）、B 臂其余 4 跑全 RC52_REPRO 的模式一致。
3. 修正后 B 臂 = **100% (5/5)**，原口径 100% (4/4)——**结论不变且更稳**，分母修复只增强不削弱原结论。

### 3.3 裁定附加条件（必做，防止 ≥30 runs 复发同类误判）

`~/fa/n14/n14_judge.py` 的优先级规则必须修：**provider_fail 判定前先做 give_up 主导性检查**（give_up 计数 ≥ 阈值且终态 failed → 归 RC52_REPRO，provider 字符串降为注记）。该文件在 VM 侧 `~/fa/`，**不在 crates/，不违反冻结纪律**。修后用 Node 14 的 B1 原始日志做回归用例（输入不变、判定由 PROVIDER_UNREACHABLE → RC52_REPRO）。

## 4. 评审发现（工单自身的问题）

### 4.1 🟠 阻断级（执行前必须处理）：harness 双源分叉（E7 家族模式）

工单 Step 2："复用 `~/fa/p4-rerun2` harness（driver.py + run_rc52_matrix.py 改 OUT → 新目录 `~/fa/n14-final`）"。
实测：**repo 侧 `tools/simuser/run_rc52_matrix.py` 的 `OUT` 仍是 `/home/wutao/fa/p4`（:16），未改**——即 VM 侧 harness 与 repo 侧已经分叉。这正是 E7 家族（binary/source 不同步）的 harness 版，且 E7 已三次复发。

**执行条件 COND-1**：campaign 开工前做**源归一**——以 repo 侧 `tools/simuser/` 为唯一真源（含 R-1 修复版），改 OUT 后同步至 VM，跑完**回传 repo**。禁止"VM 侧副本悄悄领先 repo"。

### 4.2 🟡 非阻断：B3 数字继承错误（13+3=16 ≠ 15）

工单 B3："检测器 13→15：补 `multi_intent_drop` / `paste_error_probe_quality` / `longpaste_truncation`"——**列了 3 个名字，13+3=16**。此矛盾源自总包 Node 10 原文（"补 3 个，总数 15"，Stage 1 实为 13），砺阶段盘点已指出过，工单未消化。**执行条件 COND-2**：顶层定夺——补 2 个到 15，或承认 16 并在 simuser-status 里写明口径。别再让这个数字漂进冻结包。

### 4.3 🟡 非阻断（登记不修）

- `run_c` 的 `task_terminal` 仍硬编码 `"chat"`（非真实终态）——砺 Node 03 验收清单 D-1，campaign 中 C 的 task 阶段终态不参与判定，影响有限。
- driver `TURN_TERMINAL_MARKERS` 只认 completed/failed，give_up/deadline_exceeded/cancelled 落到 timeout 口径——**判定时必须按"终态以日志为准、driver marker 仅辅助"执行**，否则 DRIVER-INDUCED 污染（与 B1 教训同源）。
- `_newest_changed_session` 取 mtime 最新者——campaign 串行跑无碍；**禁止并发跑矩阵**（与并发纪律一致）。
