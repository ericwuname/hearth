# Hearth 行业标准差距分析 · 证据材料需求清单 v1

> **用途**：本清单不是要求修复任何问题，只要求**如实采集材料**，交给外部评审方做量化的行业对标分析。
> **执行方**：负责审计的窗口 AI（有源码/运行环境访问权限）。
> **交付原则**：能跑出来的数字，不要手工数；能贴代码原文，不要只给行号；不确定/做不到的项，如实标注"做不到，原因是……"，不要near似地凑一个数字出来。**一份"缺了 3 项但每项都标注了原因"的交付，比"凑齐 10 项但有 2 项数字不可信"的交付更有价值。**

---

## 交付物总览

| 类别 | 名称 | 优先级 | 预计成本 |
|---|---|---|---|

## A. 测试总数权威口径

**背景**：连续三份报告（综合审查、功能全景审计、以及各自的逐 crate 加总）给出了三个不同的测试总数（351 / 339 / 194），且没有一份能自洽。这必须先解决，否则后续所有"质量证据"都建立在一个不可信的数字上。

**要求**：

1. 在项目根目录运行：
   ```
   cargo test --workspace -- --list 2>&1 | tee test_list_raw.txt
   ```
   如果本地/VM 环境 cargo 确实不可用，改为提供**最近一次 CI 门禁运行的原始日志**（不是摘要，是完整 stdout/stderr），并注明是哪次 commit、哪条 CI job。

2. 基于第 1 步的原始输出，生成一张**按 crate 分组的测试计数表**，格式：
   ```
   crate_name, test_count, source（cargo test 直接统计 / CI 日志解析 / 无法获取）
   ```
   **每个 crate 必须给出数字或明确写"无法获取，原因"，不允许留空或用"—"占位**（前两份报告里的"—"正是这次数字对不上的根源）。

3. 把这张表的总和，与 CI 门禁报告的"XXX passed"这个数字做一次显式核对，写明：**是否一致；如果不一致，差了多少，猜测原因是什么**（比如是否包含了 doctest、是否包含了 ignored 测试、是否两次统计的 commit 不是同一个）。

**验收标准**：交付后，我应该能确认"这个项目现在到底有多少个测试"这句话有且只有一个数字，且这个数字来自可复现的命令输出，不是人工统计。

## B. 真实运行可靠性遥测

**背景**：手工测试已经证实 `resume` core dump、`chat`/`repl` 可无限挂起，但这只是几次人工测试遇到的个例，无法回答"这个问题出现的频率有多高"，而这直接决定了它离"生产可用"有多远。

**要求（按可获得性从高到低排列，能做几项做几项）**：

1. **如果项目有任何形式的运行历史日志**（VM 门禁记录、CI 跑过的 replay、`.hearth/reports/` 或类似目录、甚至历史 shell 记录）：统计过去所有已知的 `hearth chat`/`hearth resume`/`hearth repl` 调用次数，以及其中：
   - 正常退出（Done）的次数
   - 异常退出/崩溃（core dump、panic）的次数
   - 需要人工 kill 才能结束的次数（无法自然超时收尾）
   - 给出这三类的比例（哪怕样本很小，比如只有 20 次，也如实报告"样本量=20"，不要因为样本小就不报）

2. **如果没有历史日志，无法回溯**：请明确说明"无历史遥测，原因是目前没有落盘执行报告机制"（这本身就是一条有效信息，说明 P1-9 结构化执行报告那条任务的必要性），然后改做一次**当场复现实验**：连续跑 20 次典型编码任务（可以用同一个简单任务反复跑，比如"读一个文件并加一行注释"），记录每次是否正常完成、耗时、有无异常，产出一张原始表格（不要只给汇总百分比，给逐次记录）。

3. 单独针对 `resume`：找出（或复现）至少 3 次 core dump 现场，附带 `RUST_BACKTRACE=full` 的完整 backtrace 原文，而不是"发生过 core dump"这句话本身。

**验收标准**：交付后，我应该能拿到一个"崩溃率/挂起率"的具体数字（哪怕置信区间很宽），而不是继续停留在"手工测试遇到过"这个定性描述。

## C. 关键源码原文摘录

**背景**：我目前所有判断都基于字符串取证（对二进制 `strings` 扫描）和报告转述的行号引用，从未见过一行真实源码。这导致很多判断只能停留在"大概率是这样"，无法精确到"就是这一行的问题"。

**要求**：请直接贴出以下文件的**完整原文**（不是摘要，不是"关键片段"，是整个文件或至少整个相关函数的完整代码），如果文件过长可以分次发：

1. `agent-core` 中实现 Plan→Act→Observe→Reflect 主循环的文件（大概率是 `loop.rs` 或类似命名），重点关注：有无顶层超时/deadline 机制。
2. `codex-cli`（或 `agent-runtime`）中 `resume` 命令的实现路径，包括它调用的 `restore_history`/`restore_task_graph`/反序列化相关代码。
3. `llm-openai` 中 usage 字段的反序列化结构体定义（即 `strings` 里看到的 `OpenAiUsage`），以及它是怎么被序列化进最终请求体的（重点看 system prompt / 工具 schema 部分是不是每次请求重新拼接，还是复用同一份稳定内容）。
4. `agent-core` 中 `maybe_compact`（上下文压缩）函数的完整实现，重点关注：被压缩的原始消息是否有落盘归档，还是直接从内存丢弃。
5. `observer` crate 里声称"零执行权"的核心校验逻辑，以及**所有订阅/消费 Observer 产生的事件的下游代码**（不只是 Observer 自己的代码，是所有读取它输出的地方）。
6. `bridge` crate 的当前完整内容（哪怕只有几十行），确认"声明依赖但零调用"这个结论准确，以及它现在处于什么状态（空壳/半成品/完整但未接线）。

**验收标准**：交付后，我应该能针对每一份代码给出具体到函数/代码块级别的判断，而不是"根据字符串猜测"。

## D. Hearth vs Codex CLI / Claude Code 对照实验

**背景**：这是回答"离行业标准差多少"最直接、最有说服力的方式——用同一个真实任务，跑一遍不同工具，比结果，而不是比功能清单。

**要求**：

1. 选 3-5 个有代表性、难度适中的真实编码任务（建议覆盖：一个简单的 bug 修复、一个需要读多个文件理解上下文的重构任务、一个需要运行测试验证的任务），任务描述要完全相同地喂给不同工具。
2. 每个任务分别用 **Hearth**、**Codex CLI**（如果有可用额度/权限）跑一遍，如果 Claude Code 也有条件跑，一并加入。
3. 对每次运行记录：
   - 是否一次性正确完成（无需人工介入纠正）
   - 总耗时
   - 总 token 消耗（如果能拿到）
   - 中途是否出现异常（挂起、崩溃、需要重试）
   - 最终产出代码的质量（这项可以主观打分，但要写出具体的评分理由，不要只给分数）
4. 汇总成一张对照表，逐任务逐工具列出以上指标。

**如果没有条件跑 Codex CLI/Claude Code**（比如没有额度或者环境限制）：请明确说明这一点，改为**只做 Hearth 自己的多次重复实验**（同一任务跑 5-10 次），至少能看出 Hearth 自身结果的稳定性/方差有多大，这也是有价值的数据，不强求横向对比。

**验收标准**：交付后，我应该能拿到至少一组"同任务、跨工具"或者"同任务、多次重复"的真实第一手数据，而不是继续凭我们之前几次手工测试记录去推测。

## E. Prompt 请求体稳定性原始 dump

**背景**：这是诊断"token 缓存命中率为什么不高"的关键证据，之前的判断全部停留在假设层面。

**要求**：

1. 找一个真实的多轮对话场景（至少 3 轮以上），在每一轮实际发给 LLM provider（DeepSeek 或 GLM，看现在接的是哪个）之前，把完整的请求体 JSON 原样落盘（可以临时加一行 debug 日志，dump 完再删）。
2. 把连续两轮的请求体做一次逐字节 diff，标出从哪个字符位置开始两次请求出现差异。
3. 如果 provider 的响应里带了缓存命中相关字段（如 `usage.prompt_tokens_details.cached_tokens`，具体字段名以实际 provider 文档为准），把这个字段的实际返回值也一并记录。

**验收标准**：交付后，我应该能看到"稳定前缀从哪里断裂"这个具体位置，而不是继续停留在"可能是时间戳/可能是 HashMap 顺序"这种猜测清单。

## F. 安全边界行为级证据

**背景**：`sandbox` 的 fail-closed 和 `observer` 的"零执行权"目前的核验方式（`force_seccomp_fail` 注入测试、grep 无反向依赖）分别是"接近行业标准的验证"和"不够格的验证"，需要把后者补齐到前者的水平。

**要求**：

1. 针对 Observer"零执行权"，设计并运行一次**行为级负面测试**：人为构造一个 Observer 检测到异常并产生事件的场景，跟踪这个事件流经的所有下游代码路径，确认没有任何一条路径最终触发了会产生副作用的执行接口（文件写入、命令执行、网络请求等）。如果暂时做不到全链路自动化追踪，至少手工走一遍调用链，把结果写清楚（"事件产生后依次经过 X → Y → Z，其中 X/Y/Z 分别做了什么，没有一处触发执行"）。
2. 针对 `cgroup fail-closed` 这个已知未做的缺口，确认当前实际行为是什么（是完全不限制，还是有软限制但不是 fail-closed），并说明如果 cgroup 初始化失败，现在的实际后果是"启动失败"还是"降级运行但不隔离"。

**验收标准**：交付后，"零执行权"和"fail-closed"这两个安全卖点级别的结论，应该有和 `force_seccomp_fail` 那条测试同等强度的证据支撑，而不是一条 grep 命令。

## 交付格式统一要求

- 每一类交付请单独成文件或单独成一段，标注清楚类别（A/B/C/D/E/F）。
- 任何数字类结论，必须附带**如何得到这个数字的原始命令或原始数据**，不要只给结论性的一句话。
- 任何"做不到"的项，请写清楚具体原因（权限不够/环境限制/功能本来就不存在/需要的时间超出预期），不要跳过不提。
- 如果某一类交付过程中发现了新的、任务书之外的问题，请一并如实记录，不需要为了"只交付要求的东西"而隐藏顺带发现的问题。

**优先级建议**：先做 A（成本最低，且是后续所有判断的基础），再做 C（有源码就能立刻大幅提升我判断的精度），B 和 E 可以并行，D 成本最高、放最后，如果时间/额度有限，D 可以先只做"Hearth 自己的多次重复实验"这个简化版本。
