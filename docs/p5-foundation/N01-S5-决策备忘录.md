# N01 · S5 出网收口方案裁决备忘录

**日期**：2026-09-01｜**执行**：执行窗（段 1）｜**用途**：供顶层在 N16 开工前定案
**纪律**：结论全部来自**本机实测**（.133，v0.2.20），不是源码推断、不是历史记录转抄。

---

## 0. 一句话结论

**沙箱内 bash 实际出不了网，卡点是 DNS 解析（非网络本身）。** 因此 S5 的紧迫性应重新排序：
**建议 N16a 从"必做的安全收口"降级为"先做可观测性显式化"**——把"静默超时"变成"结构化拒绝"，避免 agent 浪费步数反复重试；真正的网络收口（方案 ②）作为"未来若放行网络"的前置设施保留设计，**不必现在就上**。

---

## 1. 实测证据（.133，v0.2.20，VPN 出口 45.88.202.26）

### 1.1 对照组：沙箱外（同机直连）

| 目标 | 结果 |
|---|---|
| `https://api.agnes-ai.cn/v1/models` | **401**（端点存活） |
| `https://www.baidu.com` | **200** |
| `http://myip.ipip.net` | 200（返回出口 IP） |

→ **机器本身网络正常。**

### 1.2 实验组：沙箱内（经 hearth bash 工具执行）

| 探针 | 结果 | 判定 |
|---|---|---|
| `curl -s -o /dev/null -w '%{http_code}' --max-time 20 https://example.com` | `000` | ❌ 失败 |
| `curl ... https://www.baidu.com` | `000` | ❌ 失败 |
| `curl -s ... http://example.com`（明文） | `000` | ❌ 失败 |
| `getent hosts example.com` | **`bash: 第 12 行：610701 错误的系统调用（核心已转储）`，rc=159** | 🔴 **进程被信号杀死** |
| `curl -v`（verbose） | **`curl: (28) Resolving timed out after 15002 milliseconds`** | 🎯 **根因 = DNS 解析** |
| `ls -l /etc/ssl/certs/ca-certificates.crt` | 正常可读（182,140 B） | ✅ 排除 CA/TLS 原因 |

**根因链**：沙箱内 DNS 解析不可用 → curl 卡在 Resolving → 15s 超时 → 返回 000。
`getent` 直接触发**被拒 syscall 导致 core dump**，佐证 DNS 相关 syscall/路径被沙箱策略拦截（本项目 seccomp 默认 `KILL_THREAD`）。

### 1.3 与历史记录的对账（两条都只对一半）

| 历史记录 | 本次实测 | 判定 |
|---|---|---|
| 早期：「DNS 被拦出不了网」 | 净效果一致 | ✅ **方向正确** |
| 砺 09-01：「seccomp 放行 socket/connect，**bash curl 出网零管控**」 | 沙箱内 curl 实测 **000** | ⚠️ **净效果不成立**——socket/connect 是否放行无法验证（DNS 先挂，根本到不了 connect 阶段）；"零管控"作为**风险结论**是错的 |

→ 按总包要求「以最新实测为准，陈旧记录作废」：**"bash curl 出网零管控"作废。**

## 2. 对三个方案的影响

| 方案 | 原定位 | 基于实测的重新评估 |
|---|---|---|
| ① seccomp 硬拒 connect/bind/sendto/sendmsg | 可选（N16b），须推翻 P3 防线 B 裁定 | **边际收益进一步降低**：网络默认已不可用（DNS 层）。推翻既有裁定的代价 > 收益。**建议不做** |
| ② bash 命令级预检 + 审批门 | **必做（N16a）** | 价值仍在，但**性质变了**：主要价值从"防外泄"转为"**防浪费步数 + 显式化**"。建议降级为"先做可观测性"，收口逻辑随网络策略一起做 |
| ③ 本地代理 | 不做 | 维持不做 |

---

## 3. 建议（交顶层裁决）

**建议路径：先做「网络不可用显式化」，再议收口。**

1. **N16a′（新增，建议列为必做）**：沙箱执行网络类命令时，返回**结构化错误** `network_unavailable_in_sandbox`（含原因：DNS 被安全策略拒绝），取代当前的"curl 超时 15s"。
   - 收益：本次实测的探针任务消耗了 **13 步**（其中多步在重试 curl）；显式拒绝可把这些步数还给正事。
   - 成本：低（工具层返回结构化错误，不改沙箱策略）。
2. **可观测性缺陷单独立项**：`getent` 触发 **core dump**（"错误的系统调用（核心已转储）"）——seccomp `KILL_THREAD` 让进程崩溃而非结构化拒绝，对 agent 与用户都不可理解。建议对被拒 syscall 返回结构化错误（至少对常见探测命令）。
3. **S5 收口（方案 ②）保留设计、暂缓实施**：待"是否需要让沙箱内 bash 联网"这一产品决策明确后再上。若决定永不放行 → 只需第 1 条的显式化；若决定放行 → 先修 DNS 再上审批门（顺序不可颠倒，否则审批门形同虚设）。

## 4. 待顶层拍板的问题

1. 产品上是否需要**沙箱内 bash 联网**？（pip/cargo 拉依赖等场景会全灭——实测如此）
   - 若需要 → 先解 DNS，再上 S5 审批门（N16b 顺位提前）。
   - 若不需要 → 只做显式化（N16a′），S5 收口降级为可选。
2. `getent` core dump 这类"被拒 syscall 直接杀进程"是否立项修（可观测性 vs 沙箱策略改动范围）？
