## 五、三件套验收标准（逐件可判定）

### 5.1 宪法注入 MVP

| 项 | 验收标准（可判定） |
|---|---|
| 形态 | 以 `AGENTS.md` / 指令文件形式注入，**不依赖底座专属 API** |
| 生效 | 主力底座在**全新 session** 下加载该文件，行为符合宪法条款 |
| 证据 | 落盘：注入文件原文 + 底座加载日志 + 行为对照（有注入 vs 无注入） |
| 不过的判据 | 需改底座源码 / 需专属钩子才能注入 → **判不过**（违反红线 1） |

### 5.2 技能库 MVP

| 项 | 验收标准 |
|---|---|
| 形态 | **MCP server**（标准协议），至少一个技能可被底座发现并调用 |
| 生效 | 底座能列出该技能、能在任务中实际调用、调用结果可用 |
| 证据 | MCP 能力协商日志 + 一次真实调用的输入输出 |
| 不过的判据 | 技能依赖底座内部函数 / 需 patch 底座 → **判不过** |

### 5.3 校准观测 MVP

| 项 | 验收标准 |
|---|---|
| 形态 | 读取 session 日志（**per-adapter**），产出结构化校准数据 |
| 边界 | **只读，不介入控制流**（裁定 §二职责铁律）；不改写底座行为 |
| 生效 | 对一次完整 session 产出可解析的校准记录（含条目编号、终态、工具交换数等既有字段） |
| 证据 | 一份样本 session + 对应校准输出 |
| 不过的判据 | 需拦截/改写底座的完成判定才能取数 → **判不过**（该能力属第二批） |

## 八、三红线自检表（每项开工前/交付时各查一次）

| 红线 | 自检问句 | 违规处置 |
|---|---|---|
| **1 接口纪律** | 三件套是否只用了 MCP / 指令文件 / 通用 hooks？有无依赖底座专属 API？ | 有 → 标记**可移植性债务**，做成 **per-adapter 插件**，**不进认知层主体**；仍绕不开则该件判不过 |
| **2 顺序纪律** | MVP 是否先在标准底座（Codex CLI/Goose）落地？有无"顺手给 Hearth 引擎写适配器"？ | 有 → 立即停工并报顶层。引擎适配器**双门槛**：①L1 决胜局证明引擎接近可用 ②MCP client 实现成本 < 收益。**禁止让适配器变成继续往 loop.rs 投人的新借口**（E7/沉没成本教训） |
| **3 范围纪律** | 是否只做三件？UNVERIFIED 标注 / 完成判定观测有无混进来？ | 有 → 摘出，登记进第二批 |
