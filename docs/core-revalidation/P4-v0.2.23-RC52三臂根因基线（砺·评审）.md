| 臂 | 定义 | n | 终态 ✓ | ✓率 | give_up 真标记 | 产物 P4_OK |
|---|---|---|---|---|---|---|
| **A** fresh | 全新 REPL → 写文件小任务 → 继续型请求 | 15 | 15 | **100%** | 11 | 15/15 |
| **B** 前缀重放 | 逐字重放 13 条污染前缀 → 同一继续型请求 | 15 | 4 | **27%**（20%/40%/27% 三迭代） | 171* | 1/15 |
| **C** resume 续作 | chat 落会话 → resume 发继续型 | 10 | 1 | **10%** | 8 | 10/10 |
| **C** 首闭合 | 上述 chat 首轮本身 | 10 | 10 | 100% | 6 | 10/10 |

\* B give_up 171 含 26 条正文假阳（见 §2.1），真标记约 145。

> **迭代方差**：B 臂三迭代 ✓率 20%→40%→27%、C 臂 0%→0%→10%，说明 B/C 失败是**概率性**而非 100% 确定性——
> 这与 §1.2 第 5 条的**双因子**机制一致：因子 1（是否进 `give_up` 臂）本身是概率性的（stall 依赖 LLM 采样），
> 因子 2（`session_written_files` 是否非空）则决定进臂后的判决。两者相乘 ⇒ 观测到的迭代方差。

### 1.2 结论顺序（从表层到根因，含一处已推翻）

1. **表层**：A 通、B/C 挂 —— 若止步于此，任务书 §1.1 判据会读成「会话污染是主因」。
2. **A 臂 100% 是假象**：A 臂同样发生 11 次 `give_up`，只因续作前**已写过文件**才判 Done。
   「A 臂 100% = RC52 已修复」**不成立**——缺陷未消失，是被任务结构掩盖。
3. **初版根因（已推翻，保留作错路记录）**：曾判「事实校验唯一判据 = 写盘计数，不写文件必 failed」。
   **被 keystone 反证**（§3）：K1 纯问答 / K2 只读工具均 **✓ completed 且不写任何文件**。→ 写盘不是必要条件。
4. **（v1.1 中间结论，方向对但停在现象层）状态继承**：最终判定看起来取决于「上一已完成 turn 是否 satisfied」，
   续作请求继承该状态。此说在统计上成立（§3.6 转移矩阵证实），但**它是影子不是本体**。
5. **✅ 真因（RC-Ω，v1.2 源码级定稿）双因子因果链**：
   - **因子 1（触发）**：污染前缀 → 反复 replan / T4 stall / 步数耗尽 → **进入 `give_up` 臂**。
   - **因子 2（判决，决定性）**：`give_up` 臂的救回函数 `rc52_route_done_if_session_artifacts()`
     （`loop.rs:2110-2149`）要求 **`session_written_files` 非空 且 `consecutive_errors == 0` 且
     `completion_fact_check()` 通过**，才路由 Done；否则返回 `None` → 落 `loop.rs:4531`
     `LoopPhase::Error("give_up: cannot make progress")` → **`✗ Task failed`**。
   - **决定性变量 = 「本 session 到此刻是否曾写过任何文件」**（一个 session 级累加器，`loop.rs:978`）。
     所谓"继承 satisfied"的真实载体就是它：上一轮 ✓ 通常意味着写过盘 ⇒ 累加器 ≥1 ⇒ 后续 `give_up` 可被救回。
6. **⚠️ 由此推出的关键推论（本报告最有价值的一条）**：
   **v0.2.21 的 RC52 修复对 B 臂结构性无效**。修复的救回条件是"session 曾写过盘"，
   而 B 臂的失败恰恰是"整个 session 从未写过盘"→ 前置条件永不满足。
   这从源码解释了 Node 14 的观测：**A fresh 100%→0%（A 首轮写盘，救回生效）；B 前缀重放 100%→100%（救不回）**。
   同时解释了本窗 §2.5 的 `hydrat*` 全 0 —— **不是仪器坏，是 hydration 分支的前置条件永不满足**。
7. **两个放大器**（抬高 B/C 进 `give_up` 臂的概率，非判决因子）：
   - **放大器 1 会话污染**：前缀塞满历史 + 含 `✗ Done (5 steps)` 等失败样本 → 更易 stall。
   - **放大器 2 目标路由**：resume 的「继续你的提议吧」目标空泛 → `acceptance_criteria` 为空、无产物动词，
     既容易 stall 又无 criteria 可核验（`goal_requires_product()` 见 `loop.rs:167`）。

## 二、根因取证（n=103 give_up 样本）

### 2.1 仪器坑（先说清，否则下面的数字不可信）

**Hearth 终端日志带 ANSI 转义码**，`give_up` 的真实行形态是：

```
'\x1b[36m  give_up\x1b[0m'
```

两种朴素口径都会出错：

| 口径 | 结果 | 错因 |
|---|---|---|
| 按行精确匹配 `line == "give_up"` | 103 → **只匹配到 1** | ANSI 前后缀使整行不等 |
| 按子串 `"give_up" in text` 计数 | **虚高至 129** | 前缀重放把历史报告正文（如「`give_up` 原因可见（RC9）」）灌进上下文，B 臂 26 条假阳 |

**正确口径**：先 `re.sub(r'\x1b\[[0-9;]*m', '', line)` 去 ANSI，**再**要求 `line.strip() == "give_up"`。

#### 2.7.0 源码事实（全部锚点已于 2026-09-03 重新 grep 确认，非引用旧行号）

**判决点 A —— give_up 臂的唯一救回口**（`crates/agent-core/src/loop.rs:2110-2149`）：

```rust
fn rc52_route_done_if_session_artifacts(&mut self) -> Option<StepOutcome> {
    if !self.ctx_mgr.state().acceptance_criteria.is_empty() { return None; }   // 2112
    if self.written_files.is_empty()
        && !self.session_written_files.is_empty()
        && self.consecutive_errors == 0 {
        self.written_files = self.session_written_files.clone();               // 2124 hydration
    }
    if !self.written_files.is_empty() && self.consecutive_errors == 0 {        // 2126
        if let Err(rej) = self.completion_fact_check() { return None; }        // 2131 W3 拒绝
        return Some(StepOutcome { next: LoopPhase::Done, .. });                // 2143 救回 ✓
    }
    None                                                                       // 2148
}
```

**判决点 B —— 返回 None 之后的去向**（`loop.rs:4504-4533`）：

```rust
if fa01_criteria_empty {

}
tracing::warn!("Giving up after {} steps, {} errors", ...);                    // 4509
```

**累加器定义与维护**：`session_written_files: Vec<WrittenFile>`（`loop.rs:978`，初始化 `1529`，
写盘时追加、上限 64 条 FIFO `3726-3739`）。它**不随 run 边界清空**（这正是 v0.2.21 RC52 修复的内容）；
而 `written_files` **每轮清空**（`loop.rs:4729` 注释「本轮写盘记录/验证计数重置（跨轮不串）」）。

**reflect 投影三信号的来源**（`loop.rs:4608-4614`）：

```rust

```

→ 日志里那三个数字**就是**判决点 A 的三个输入。**这是本报告全部运行时读数与源码的对齐点。**

#### 2.7.1 因果链（双因子）

| 因子 | 内容 | 源码锚点 | 角色 |
|---|---|---|---|
| **1 触发** | 污染前缀 → 反复 replan / T4 stall / 步数耗尽 → 进入 `give_up` 臂 | T4 stall 判定（Tier3） | 概率性放大器 |
| **2 判决** | `session_written_files` 为空 ⇒ 救回失败 ⇒ `Error` ⇒ `✗ failed` | `2115/2126/2148 → 4531` | **决定性** |

**"状态继承"为何是影子**：上一轮 ✓ 通常意味着那一轮写过盘 ⇒ 累加器 ≥1 ⇒ 后续任何 `give_up` 都能被救回；
上一轮 ✗ 通常意味着到此刻累加器仍为 0 ⇒ 后续 `give_up` 必落 `Error`。
**所以"继承"是累加器状态的统计投影，不是独立机制。**

  ```
  💭 [reflect] 决策 → Error（终止）；依据：连续错误 0、本轮写盘 0 个、跨轮产物记录 0 个
  ✗ Done (29 steps)  ✗ Task failed
  ```

- **C1（继承 non-satisfied → failed）**：
  ```
  resume 本地会话 …（3 轮历史）  > 继续你的提议吧
  💭 [reflect] 决策 → Error（终止）；依据：连续错误 0、本轮写盘 0 个、跨轮产物记录 0 个
  ✗ Done (10 steps)  ✗ Task failed
  ```

**决定性变量（v1.2 精确表述）**：不是"本 turn 写没写文件"，也不是"上一 turn 是否 satisfied"，
而是"**到此刻为止本 session 的 `session_written_files` 是否非空**"。前两者都是它的相关量。

**为何 keystone1 六个全 ✓**（K1/K2 纯问答/只读、K3 写文件，均 completed，`give_up` 全 **0**）：
它们**从未进入 `give_up` 臂**（正常 Done 路径收口），因此判决点 A 根本没被调用。
→ keystone1 反证的是"写盘是完成的必要条件"，与 §2.7 的 give_up 臂判决**不在同一条代码路径上**，两者不矛盾。

**⚠️ 反例必须登记（Zb，逃逸样本）**：`keystone3b/Zb.log` 第 10 轮 `✗9`、第 11 轮续作 **`✓18`** ——
它从失败态逃逸了。逃逸路径在日志里完整可见：T11 前两次 reflect 均 `(0,0,0)→Plan`，
第三次模型真写了盘变成 `(0,1,1)→Done`。
→ **状态继承是强统计律（OR=75.1），不是确定性规则**；本 turn 自己产出产物即可脱离继承。
这与 §3.6 转移矩阵测得的 **7.0% 逃逸率（4/57）**定量吻合，Zb 就是那 4 例之一。

### 3.6 ✅ 判决性检验（改用转移矩阵，替代功效不足的 Z/V 单元）

**方法**：对已落盘的**全部**日志（v0.2.23 组 = `n14-final/iter1-3` + `keystone2/3/3b`，31 runs、227 次轮间转移），
逐轮抽取 `(用户输入, 终态标记)`，计算 **P(本轮 ✓ | 上一轮终态)**；并按输入是否为"续作型"分层
（续作型判据：长度 ≤26 且含 继续/接着/提议吧/开工/推进 等词；分类器为关键词法，见下方局限）。

**结果（v0.2.23 单一版本，S6 不混版）**：

| 当前轮类型 | 上轮 ✓ → 本轮 ✓ | 上轮 ✗ → 本轮 ✓ | χ² (df=1) | OR | Fisher p |
|---|---|---|---|---|---|
| **续作型**（n=77） | **85.0%** (17/20) | **7.0%** (4/57) | **45.39** | **75.1** | **1.14e-10** |
| 非续作型（n=150） | 50.8% (30/59) | 18.7% (17/91) | 17.21 | 4.5 | 5.77e-05 |

**判读（三条，逐条给出它证明了什么）**：

1. **继承效应确实存在，且极显著**：续作型上轮 ✓→✓ 85%，上轮 ✗→✓ 仅 7.0%，OR=75.1。
2. **续作型与非续作型的效应量差 17 倍**（OR 75.1 vs 4.5）。这是**机制签名**：
   自带目标的请求靠自己的目标判成败（逃逸率 18.7%），空泛续作请求无目标可判 ⇒ 只能落回累加器状态（逃逸率 7.0%）。
   逃逸率对比 2×2 的 Fisher p=0.055（**方向一致但未过 0.05，如实登记为"趋势"，不作断言**）。
3. **跨版本复核（标注为跨版本引用，不进同一分母）**：历史组（`p4` 09-01 12:36 / `p4-rerun2` 09-01 18:21，20 runs）
   续作型上轮 ✓→✓ 45.5%、上轮 ✗→✓ **0.0% (0/29)** —— **方向完全一致**。
   → 继承效应**跨版本存在**，说明它是**设计属性而非 v0.2.23 回归**。这条同时排除了"某次改动引入"的假设。

**方法局限（必须与结论同页，否则外部顾问会误读）**：

| 局限 | 影响 | 缓解 |
|---|---|---|
| 续作型分类器是**关键词 + 长度**启发式 | 可能漏分/错分 | 已附示例样本；B 臂前缀中的"那你继续跑吧/继续跑吧"是设计内固定轮次，人工核对无误分 |
| 同一 run 内的多次转移**非独立**（同脚本 → 簇内相关） | 有效 n < 227，p 值偏乐观 | 即使按 run 数（31）保守折算，效应量 OR=75 仍远超随机；且 Za 提供了 **run 内自身对照** |
| 未做多重比较校正 | 3 张表 | 效应量与 p 值量级（1e-10）远超任何合理校正阈值 |
| 分类为"终态"依据 `✓/✗ Done (N steps)` 行 | 依赖渲染层 | 已用 `Task completed/failed` 行交叉核对，两者一致 |

**分析脚本与产物**：`~/fa/transition2.py`、`~/fa/version_split.py`；
落盘 `~/fa/transition.json`、`~/fa/transition_byver.json`（含全部逐 run 终态序列，可复算）。

| 续作型 P(✓ \| 上轮 ✓) | 85.0%（17/20） | 不应下降（防"一刀切放宽"把成功路径也改坏） |
| C 臂 resume 续作 ✓率 | **10%**（1/10） | > 0 |
| B 臂 ✓率 | **27%**（4/15） | 上升 |
| A 臂 ✓率 | **100%**（15/15） | 注意：这是**假象**（累加器非空的伪通过），修复后 A 与 B/C 应趋同而非维持 100% |
| `RC52_ARTIFACT_HYDRATION` 日志命中 | **0**（40 runs） | 若修复仍走原分支，此值应 > 0；若为 0 则说明修复未触及真实路径 |

**修复方向（本窗建议，非裁定；已带源码锚点）**：

根因在 `loop.rs:2110-2149` 的**救回条件过窄**——它只承认"产物"一种完成证据。
零产物 session（纯问答 / 只读 / 论述型续作）一旦进 `give_up` 臂就**没有任何救回路径**。

| 修法 | 落点 | 利 | 弊 / 风险 |
|---|---|---|---|
| **A（推荐）补一条非产物救回口** | `2126` 之后加分支：`criteria 空 + consecutive_errors==0 + 本轮有实质输出（工具调用 ≥1 或回答非空）` → 走 Done 但**打 `unverified` 标** | 不放宽已有产物校验（不退回 RC1 教训）；覆盖零产物 session | 需定义"实质输出"，有被 LLM 空转骗过的风险 → 必须打 unverified 标并计入指标 |
| **B 续作请求不进 give_up 臂** | 识别空泛续作 → 不设产物型 criteria，走独立问答判定路径 | 直击放大器 2 | 需可靠的续作识别器；本报告的关键词分类器**不足以生产化** |
| **C 放宽写盘校验** | 削弱 `2131 completion_fact_check` | 最省事 | **不建议**——会退回 RC1 教训，且 `test_w3_unrelated_artifact_rejects_done` 会红 |

**配套信号（B3）应观察**：`give_up` 臂被调用次数、`rc52_route_done_if_session_artifacts` 返回 `None` 的次数
及其分支原因（criteria 非空 / 累加器空 / fact-check 拒绝）—— **当前这三条无法从日志区分，属仪器缺口，建议同期补**。
