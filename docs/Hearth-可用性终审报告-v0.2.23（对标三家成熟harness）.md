## §0 执行摘要（一页结论）

### 0.1 实测结果：真实任务成功率约 8%

| 组 | 条数 | ✓ 完成 | ✗ 失败 | 严格判定为真完成 |
|---|---|---|---|---|

且 B 组 4 个「✓ 完成」里有 3 个是**假阳性完成**（详见 §3.1）——终态说成功，用户要的东西并没给。

- **规划草案僵化**：A3/A4/A5 连续三轮产出**逐字相同的 5 步计划**。用户每轮换了完全不同的意图，计划纹丝不动——因为目标文本（那条错误日志）被锚定为 `original_goal`，规划从它重新派生，新意图未被吸收。
- **意图丢失是常态**：A4/A5/A7/A8 四个用户输入实质是"追问/指令"，全部未被执行；模型自顾自跑 grep。
- **延迟**：plan span 普遍 5–45s，A9 达 **81s**。一次寒暄（A1）耗时 32s。

### 2.3 三家成熟 harness 的交互设计逻辑（对标基线）

> 来源：Claude Code 官方文档（权限模式 / Plan mode / checkpoint / 中断与纠偏 / 最佳实践）、Codex CLI 实践文档（TUI 五模式 / 斜杠命令 / 审批门）与 harness 综述。

| 设计维度 | Claude Code | Codex CLI | WorkBuddy（本产品） | 共同逻辑 |
|---|---|---|---|---|
| **核心循环** | 收集上下文 → 行动 → 验证，**每步输出驱动下一步** | 同一 harness loop：模型**每次工具结果后**决定下一步 | 连续流式：模型边说边调工具，结果即时可见 | **模型驱动、逐结果反应** |
| **谁宣告完成** | **模型自己**宣告 | **模型自己**宣告完成 / 撞审批门 / 预算尽 | 模型给结论并交付产物 | **完成是模型的判断** |
| **权限/自治** | 5 档（Manual / acceptEdits / plan / **auto 分类器后台拦风险** / dontAsk），明确为治"审批疲劳" | 3 档自治（每条命令批 / 只批写+命令 / 沙箱内全自治） | 分级工具权限 + 用户确认 | **自治度是可配置项，不是硬编码默认** |
| **计划** | Plan mode：只读探索 → 出计划 → 批准后才动手 | `/plan` → 批准 → 执行 → `/review` | 任务列表 + 流式计划 | 计划是**独立可选状态**，不是每轮强制闸门 |
| **纠偏** | Esc 立即停；输入纠正**不打断当前动作**，下一动作前生效 | TUI 中随时转向；`/fork` 分叉、`/resume` 回主线 | 用户随时插话重定向 | **人在环上、随时纠偏不重启** |
| **可回退** | Checkpoint：编辑前快照，Esc×2 回退 | `/fork` 保留完整 transcript 试错 | —— | 失败可回退而非终止 |
| **透明度** | 并排 diff、上下文用量指示器、自动压缩 | 流式渲染推理与 diff、内联审批、`/status`、`/compact` | 流式输出 + 产物卡片 + 可视化 | **改了什么始终可见** |
| **验证** | 官方建议"给 Claude 一个验证手段"为**最高杠杆** | `/review` + 要求产出验证证据（测试/构建输出） | 交付前自检与证据 | **以验证收尾，而非以写入收尾** |

**三家共识（关键）**：
> 循环的每一轮，模型看到上一步结果后决定「继续调工具 / 输出给用户 / 宣告完成」。**"完成"是模型的语义判断，不是框架对"有没有写文件"的统计判断。**

## §4 根因分析（矛盾论）

### 4.1 主要矛盾（升级版）

**此前定性**：控制导向架构 ↔ 流畅助手期待。
**本轮实证后升级**：真正的矛盾是——

> **「框架以『是否写盘』判定任务是否完成/是否有进展」　↔　「用户以『我的意图是否被满足』判定」**

- **普遍性**：所有 harness 都要判断"何时停"。
- **特殊性**：Hearth 把这个判断**从模型手里拿走**，交给一个以写盘为代理指标的启发式（Reflect 相位）。竞品把这个判断**留给模型**（模型宣告完成）。
- **同一性**：两者可统一——让模型宣告完成，框架只做**护栏**（预算/安全/审批），不做**判定**。
- **主要方面在 Hearth 侧**：判定权归属是 Hearth 的设计选择，可改。

### 4.2 机制证据链（完整闭环）

```
用户输入（问答/诊断类，本就不该写文件）
   ↓
Plan：模型产出计划（甚至产出很好的文字回答）
   ↓
Act：跑 read/grep/bash（只读工具，无写盘）
   ↓
Reflect 依据串：「连续错误 0、本轮写盘 0 个、跨轮产物记录 0 个」
   ↓
→ 无错误、但也没写文件 ⇒ 判定 give_up
   ↓
✗ Task failed —— 用户看到"失败"，但模型其实已经答了（A3/A6/A10）
```

反向（假阳性）：
```
用户意图 ≠ 写文件，但过程中发生了写盘（哪怕是上一轮的陈旧任务，B4）
   ↓
Reflect：「本轮写盘 1 个」⇒ 判定完成
   ↓
✓ Task completed —— 但用户要的东西根本没给
```

**同一个错位基准，同时制造了「假阴性」与「假阳性」两类失败。** 这解释了为什么 A 组 80% 失败、B 组 60% 假阳性完成——不是两个 bug，是一个根因的两面。

### 4.3 与既有缺陷台账的关系

| 既有编号 | 在本根因下的位置 |
|---|---|
| L0 / L6（盲规划、反应回路缺位） | **根因之一**：模型看不到中间结果，无法自我宣告"我已满足用户" |
| L1 / L1.5（写文件即完成、关键词分类） | **同一根因的入口侧**：契约由关键词分类器决定，而非模型理解 |
| L2 / L2.7（give_up、恢复依赖 criteria） | 同一根因的出口侧 |
| L3.5 / L3.6（无 diff、无叙事） | 放大后果：即便做对了，用户也"需要猜" |
| L5（静态敕令提示） | 强化机制：提示硬编码"必须 write_file"，把模型推向写盘，进一步喂养写盘基准 |
| F1（弱模型放大） | 放大器：弱模型更依赖框架正确判定 |

### 5.2 三个选项评估

| 选项 | 内容 | 预期 | 判断 |
|---|---|---|---|
| **A. 继续（范式改造）** | 以 W1 为主线：把反应回路改为模型驱动 + 完成判定归还模型；配套 W2/W5/W3/W6 | 成功率有明确上行路径（根因已清、目标架构已验证） | ✅ **推荐** |
| **B. 继续（增量打补丁）** | 继续加检测器、恢复分支、验收护栏 | **大概率不收敛**——见下方警告 | ⛔ 不建议 |
| **C. 止损** | 停止投入，转为维护/归档 | 若选 B 或直接放弃 W1，则 C 优于 B | ⚠ 条件性 |

### 5.3 ⚠ 关键警告：警惕"给栅栏打补丁"的自我强化循环

回顾项目演进，控制机制在**持续增加**：T4 stalled 检测、goal drift 检测、stuck loop 检测、Verification Reserve、acceptance criteria、FA01、nervous system、subconscious 守卫层……

**这些每一个单独看都是正确的工程，但叠加的净效果是：给一个"因为闸门太多而不好用"的系统，继续加闸门。** 这解释了为什么从 v0.2.x 到 v0.2.23，用户主诉（"报错就 give_up"、"需要猜结果"）**长期未变**——修复一直作用在症状层，根因（判定权归属）从未被触碰。

**判据**：若后续工作包的主体仍是"新增检测/新增闸门/新增恢复分支"，而非"移除判定权、归还模型"，则应触发止损评审。

### 5.4 继续的可证伪门禁（建议写入 W1 任务书）

> **门禁 G-W1**：W1 落地后，用**同一份盲测包（A10+B5，全新 session）**复测：
> - **通过**：实质性任务（A3-A10 + B1-B5，共 13 条）严格成功率 **≥ 70%**，且**零**"终态与内容背离"案例；
> - **不通过**：成功率 < 50%，或"终态与内容背离"仍 ≥ 3 例 → **触发止损评审**，重新评估项目去留。

同时设**过程门禁**：
- 每完成一个工作包，A 组失败数必须单调下降；出现"修完某包后 A 组失败数不降反升"→ 立即回退该包并复盘。

### 5.5 结论

**值得继续，但有条件**：
1. **W1 是唯一主线**，其他包（W2/W5/W7）作为配套，不得喧宾夺主；
2. **完成判定权必须归还模型**，框架只保留预算/安全/审批三类护栏（照搬 subconscious 层已被验证正确的护栏范式）；
3. **设 G-W1 门禁**，用同一份盲测包复测，不达标即止损评审。

**判断依据（不是沉没成本，是可复用性）**：引擎层（沙箱/安全/记忆/子 agent/resume 原语）是**难建且已建成**的资产，且竞品已验证目标架构可行、根因已机制级定位。这是"差一层窗户纸"的处境，不是"地基打错"的处境。但反过来，**窗户纸只有一次机会**——若 W1 后仍不达标，说明问题比当前判断更深，应止损。

## §6 最终结论

### 6.1 问题全景（按严重度排序）

| 层级 | 问题 | 编号 |
|---|---|---|
| **根因** | 完成/放弃判定以"写盘"为代理指标，判定权在框架而非模型 | RUN-1 / UX-2 |
| **根因** | 反应回路缺位：模型每周期 1 次调用、整批盲跑，无法基于中间结果自我判定 | RUN-2 / L6 |
| **放大器** | 反馈降质（中段截断）、预算被空转吃掉、replan 双计步 | RUN-3 / RUN-7 / L0.5 |
| **放大器** | 静态敕令提示把模型推向写盘，进一步喂养错误基准 | L5 / L1 |
| **后果** | 终态与内容背离、假阳性完成、部分成功被丢弃、意图丢失 | UX-1/5/6, UX-3/4 |
| **后果** | 用户"需要猜"：无 diff、无接手叙事、无回退纠偏 | UX-11/12, RUN-9 |
| **新增** | one-shot chat 无 checkpoint，kill 即全损 | RUN-5 / U-44 |
| **战略** | 弱模型放大（F1）：架构最依赖强模型，与"弱 LLM 也高质量"战略冲突 | F1 |

### 6.2 值得肯定的部分（避免只见短板）

| 项 | 实证 |
|---|---|
| **安全沙箱扎实** | Landlock+seccomp fail-closed、egress 白名单结构化拒绝（B1 的拒绝信息**规范且可行动**） |
| **UNVERIFIED 标注语义正确** | B3 正确标注「目标达成（未验证）」——诚实性设计到位 |
| **潜意识层是正确实现的护栏** | 仅对 3 条硬编码危险命令 Abandon，其余仅告警；**护栏范式在 Hearth 内部已有成功先例可照搬** |
| **模型本身质量够用** | A3/A6/A10 中 Agnes（低成本模型）给出了高质量、诚实、有结构的分析——**不必依赖昂贵强模型** |
| **resume 原语存在** | CLI `hearth resume` + state_revision 恢复路径（仅 chat 路径 checkpoint 有缺口） |

**最重要的正面信号**：模型输出质量是好的，框架把好的输出判成了失败。这意味着 **W1 的预期收益很高，且不需要换更贵的模型**。

### 6.3 一句话答复

> **Hearth 不是"地基打错"，是"差一层窗户纸"——但要捅破它，必须停止给栅栏打补丁，把完成判定权归还模型（W1）。给 W1 一次机会，并用同一份盲测包设 70% 成功率的止损门禁；不达标即止损。**
