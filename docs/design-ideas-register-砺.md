## I-1 · 显式 / 隐式推理自适应

**用户原话**（`手工测试v0.2.10.txt`）
- L2731：「我们是**显式推理**，还是**隐式推理**啊。你觉得那种方式更好呢」
- L2776：「所以**推理可以根据我的提问进行设计，简单的问题，进行隐式推理，复杂的问题可以显式推理**。但是我发现不同的 harness 的推理角度不同，推理出来的颗粒度不同，角度不同，导致后面的执行结果、方案不同。所以你说这个推理的设计该怎么设计才好呢」

**想解决**：复杂任务执行结果不稳定、不同 harness 推理颗粒度不一致导致方案漂移。

**现状对照**：当前 planner 单次 LLM 调用产出结构化计划（JSON），**无显式思维链步骤**；规划质量完全依赖单次输出。相关既有机制：`goal_drift` 检测（loop.rs:970-999）已是"**按阈值条件触发的额外 LLM 调用**"先例（最小步数 20）。

**初步评估**
- 收益：复杂任务分解质量可能提升；显式推理可留痕、可审计（对 Observer OS 第三权友好）。
- 成本：显式推理 = 更多 token + 更多延迟；**与既有成本红线冲突**——`loop.rs` 多处注释明确"不新增 LLM 分类调用——成本红线"（如 classify_user_input、goal_drift 的阈值设计均为此妥协）。
- 风险：显式推理文本进上下文 → 加剧上下文膨胀（与 RC5/RC42 同向）；颗粒度若不统一，反而放大"方案不同"的问题（用户自己在 L2776 指出的痛点）。
- 开放问题：①"简单 vs 复杂"由什么判定？（若用 LLM 判定 = 又加一次调用；若用规则 =  classifier 的覆盖缺口问题重现，见 RC39）②显/隐切换的边界如何避免抖动？

**守门人初步意见（非裁决）**：方向值得评估，但**"自适应"的判定器本身就是难点**——RC39 已证明纯规则分类器有覆盖缺口，而 LLM 判定有成本。建议若推进，优先按**任务类型路由**（复用已有 `goal_requires_product`）而非新造分类器。

## I-2 · 多轮推理（计划前多轮 + 执行中穿插推理）

**用户原话**
- L2902：「有些 harness 的推理模式，可能在**计划之前就进行多轮的显式推理**…第一轮推理，接着第二轮推理，接着第三轮推理，然后列下计划，然后再推理、修订计划、再推理、确认计划，然后执行、推理、推理、再执行…测试、推理、推理、验收、推理、报告」
- L3023 / L3093：「目前 hearth 项目的推理是什么情况，单轮，多轮？」（**连问两次**；第二次「这个问题你无法回答吗？」）
- L3227：「我发现如果让你执行稍微复杂的任务好像任务都会失败…你说的**单轮隐式推理，我后面会进行优化的，会加入多轮推理**，或许你就可以执行复杂任务了。**也许 hearth 项目目前的卡点就是在这里**」

**想解决**：复杂任务失败率高。

**现状对照**：当前一轮用户输入 = 一次规划 + PDCA 步进；**没有"计划前的多轮推理"阶段**。

> ⚠️ **顺带记录一个观察（非缺陷、属能力期待）**：L3023/L3093 用户连问两次"我们是单轮还是多轮推理"，**agent 未能回答**——即 **agent 对自身架构的元认知缺失**。这与 I-5（内观）直接相关，也解释了用户为何要反复用"你感觉如何"来间接探测。

**初步评估**
- 收益：计划前多轮推理理论上能提升复杂任务分解质量（业界 Codex/Claude 类 harness 确有类似设计）。
- 成本：**显著**（每个任务多 2-3 次 LLM 调用）；与成本红线冲突，比 I-1 更重。
- 风险：多轮推理会**大幅增加上下文消耗**，与 RC5（压缩失忆）叠加可能更糟——**推理越多、越快撞阈值、压得越狠、忘得越多**。
- 开放问题：多轮推理的产出如何结构化保存进 TaskGraph？压缩时是否保留推理结论？

**守门人初步意见（非裁决）**：**用户 L3227 的"卡点就在推理设计"这一假设，我实测数据不支持它是主因**——详见 §7 诚实回应。建议把它当作**待验证假设**，用最小对照实验证伪/证实后再决定是否投入（成本可控）。

## I-3 · 上下文压缩机制重构（3 方案 + 历史检索）

**用户原话**（L2361，完整）
> 「这样子会不会是导致你失忆的根源啊…**记忆被替换掉了**。我在思考，上下文机制是**按照临界值统一压缩**好，还是像是**履带**，到达临界值后，截断最早的一段对话，始终保持上下文临界范围，又或者是**上下文到了临界值的时候，保留最近几轮对话的全部信息，但是之前的对话全部进行压缩，这样不会有明显的丢失记忆感**。**然后你还可以检索对话内的历史信息，快速检索定位历史的某轮对话，获取详细信息**。这样会不会更顺畅，记忆更持久。」

- L2424：「你能联网搜搜看看**当前的 harness 上下文处理的方案是哪些**吗，最稳妥、最有价值的方案」（→ 用户明确要求做**业界方案调研**）

**想解决**：失忆、忘目标、执行偏差（即 RC5 / RC37 / RC42）。

**现状对照**：`context.rs:169/171` = 临界值（32k 字符）统一压缩 + 保留 2 轮；`summarize_turn` = **纯规则 60 字墓碑**（不调 LLM）。即**当前正是用户的方案①**，且摘要质量极差。

**⭐ 重要对齐**：用户的**方案③（保留近几轮全量 + 更早压缩 + 历史检索）与守门人此前给 RC5 的处置建议高度一致**——v1 总账 RC5 建议即为「扩字段 / 去 Debug 包裹 / KEEP_TURNS 可调 / **archive 检索升工具**」，v2 §7 W5 延续。**用户独立地、凭体感走到了同一套设计**，这提升了该方案的置信度。

**初步评估（关键区分）**
> **压缩有两个正交问题，必须分开决策**：
> - **A. 何时压 / 压多少**（触发与保留策略）——用户谈的三个方案都在这一层。
> - **B. 压成什么**（摘要策略）——**当前真正的伤害在 B**：`summarize_turn` 是纯规则 60 字模板，Assistant 全文 + tool_result 100% 丢弃（RC5）。
>
> **只改 A 不改 B，效果有限**：无论履带式还是分层式，被压掉的部分仍会变成 60 字墓碑。**建议 A+B 一起评估，且 B 优先级更高。**

| 方案 | 收益 | 成本 | 主要风险 |
|---|---|---|---|
| ① 临界值统一压缩（现状） | 实现简单、确定性强 | 低 | 压后剩墓碑，失忆明显 |
| ② 履带式滚动截断 | 保留近期原文完整 | 低-中 | 更早信息**直接消失**（连墓碑都没有）；仍丢内容 |
| ③ 近几轮全量 + 更早压缩 + **历史检索** | 兼顾近期完整 + 远期可回溯 | **中-高**（需 archive 索引/检索工具） | 检索工具本身要可靠；检索失败的兜底 |

**开放问题**：① KEEP_TURNS 取多少（2 / 4 / 6）？② 历史检索用什么检索式（关键词 / 语义）？③ 压缩摘要是否允许一次 LLM 调用（成本红线 vs 质量）？

**守门人初步意见（非裁决）**：**方案③ + 先修 B（摘要质量）** 是最优组合，且与既有 W5 建议重合——**若顶层推进 I-3，建议直接与 W5 合并立项，不要另起炉灶**（避免两套上下文方案打架）。另外 **L2424 要求的业界调研**属低成本高价值，可先做（不依赖立项）。

## I-4 · 隐藏式系统提示词

**用户原话**
- L258：「你每次的上下文注入这些影响，会让你的**上下文重复增加不少**，或许**隐藏式的系统提示词，会好点**」
- L222：「你的描述会受到 harness 这个身体的影响，回复也是，**就像是系统提示词**」

**想解决**：注入内容（体感内观、身份、约束等）每轮重复占用上下文。

**现状对照**：注入为**显式消息**（体感内观 payload 可见，loop.rs:1060 一带）。

**初步评估**
- 收益：减少每轮重复的上下文占用；用户侧输出更干净。
- 成本：低-中（改为 system 角色 / 或 provider 层固化）。
- ⚠️ **风险（需顶层权衡）**：与项目**可审计性公理**有张力——「后端产生事实，前端投影事实」+ Observer OS 第三权审计，都依赖**注入内容可见/可查**。隐藏化会降低可审计性与排障能力（本轮多处结论正是靠日志里可见的注入文本挖出来的——例如 `context_fill_pct` 的语义错位 RC40 就是从可见 payload 里发现的）。
- 开放问题：可否"**默认隐藏、审计可展开**"（如 `RUST_LOG` 级别或 `--show-injections`）？这或许可同时满足两侧。

**守门人初步意见（非裁决）**：**不建议直接隐藏**。若推进，采用"**默认隐藏 + 审计开关可展开**"的折中，保住可审计性这一项目公理。

## 7. ⚠️ 守门人对「卡点就在推理设计」这一假设的诚实回应

**用户假设**（L3227）：复杂任务失败源于**单轮隐式推理**，**加入多轮推理就能执行复杂任务**，"卡点就在这里"。

**我的实测数据不支持它是主因**：

| 证据 | 数据 |
|---|---|
| 成功轮长什么样 | 步数中位 **2**、1-2 步完成 **65-73%**、**几乎不动工具**（bash 0-2%）——成功根本不靠推理深度 |
| 失败轮长什么样 | 步数中位 **10-15**、bash 使用率 **70-71%**、烧掉总步数的 **44%** |
| 失败终态归因 | `give_up` **88%**（stalled 仅 12%） |
| give_up 的机制 | α：输入被误判为目标（RC39）→ 问题被当任务执行；RC43：progress 只认写，而写类调用已降到 **2.8%** → 天然拿不到进展记分 |
| 意图×结果 | 问询 82%、**元访谈 61%（最差）**——失败集中在"被当任务执行的对话"，而非"推理不够深的任务" |

**我的判断（供参考，非裁决）**：**当前的卡点是"判据与任务类型不匹配"，不是"推理轮数不足"**。
- 一个 2 步就能答对的问询，不会因为多推理两轮而变成 3 步成功；它现在失败是因为**被当成任务 → 去 bash 探索 → 拿不到 progress 记分 → give_up**。
- **但我不排除推理设计对"真正复杂的多步任务"有边际价值**——只是当前日志里这类任务样本很少（成功轮 65-73% 都是 1-2 步），**证据不足以支持或否定**。

**建议做法（低成本验证）**：把 I-1/I-2 当**待验证假设**，设计最小对照实验——同一组复杂任务（≥3 步、需工具），单轮推理 vs 多轮推理各跑 3 次，比较**成功率 / 步数 / 成本**。若多轮显著更优，再谈设计；若无差异，则该假设证伪，省下一大笔投入。

## 8. 状态与建议顺序

**全部条目状态：🔵 未评估 · 待顶层决定是否进入评估/设计**（I-5 为 🟡 已存在·待修复）。

**守门人建议顺序（初步意见，非裁决）**：

1. **I-5 → 先修 RC24-B**（成本极低，让已实现的内观工具恢复可用；用户高频依赖，29 次调用）
