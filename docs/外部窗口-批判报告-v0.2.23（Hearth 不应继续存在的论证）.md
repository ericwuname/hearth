## §1 存在性诘问：说得出只有 Hearth 能解决的问题吗？

**这是最锋利的一刀。一个项目若无法回答"只有我能解决的问题是什么"，它就没有存在理由。**

### 1.1 市场已经标准化，而 Hearth 不在标准上

> 2026 上半年事实：**30+ 个 coding agent harness 发布**，并已收敛到共享接口规范——**MCP（工具连接）、SKILL.md（项目级上下文）、OpenAI 兼容端点（模型接入）**三层同时标准化。

**Hearth 对这三项标准的支持：无。** 它是自建的 27 crate 私有架构。这意味着：
- 生态插件（MCP server）**一个都接不上**；
- 社区沉淀的 SKILL.md **一个都用不了**；
- 每换一个模型供应商都要自研适配。

**在一个已标准化的品类里做私有架构，等于主动放弃整个生态。**

### 1.2 护城河审计：Hearth 的三张"王牌"逐一对表

| Hearth 自认的差异化 | 免费竞品的对位事实 | 判定 |
|---|---|---|
| **Landlock + seccomp fail-closed 沙箱** | **Codex CLI：同样用 Rust 编写、同样在 Linux 上用 Landlock+seccomp、由内核强制隔离**（macOS 用 Seatbelt）。Apache-2.0 免费。 | ❌ **护城河 = 免费竞品的标配** |
| **弱模型 / 本地模型场景**（战略定位） | **Goose：Apache-2.0，Linux 基金会旗下（Agentic AI Foundation），桌面端+CLI，15+ provider 含 Ollama，local-first，主打本地模型。** | ❌ **战略定位被基金会项目正面覆盖** |
| **中文场景 / 自我认知层** | 中文能力内部自证是**坏的**：`patch.rs` 中文字节切片 panic 自 v0.2.20 已知，**到 v0.2.23 仍未修**（W7 "先行热身"始终没发货）；系统提示主体是**英文**硬编码。 | ❌ **中文是缺陷面，不是优势面** |

**一句话：Hearth 最强的两项技术资产，一项是 Codex CLI 的标配，一项是 Goose 的主场。**

### 1.3 行业共识：这条路的建议是"不要自建"

> 公开的 build-vs-buy 决策指引（2026）：
> - **Build 的前提条件**：「You have a platform team that treats the agent harness as a product」，适配团队规模 **20+ 工程师**；
> - **对本地/私有模型需求的建议**：「pick an open harness that supports local model backends and **configure it rather than writing your own orchestration from scratch**」——即 **Extend，不是 Build**；
> - **gut-check**：「if you're reading this post to decide, you probably don't need to build. Teams that genuinely need to build already know why before they start asking the question.」

**对照 Hearth**：实际投入是 1 人 + AI agent 窗口。距离 Build 路径的适配团队规模（20+ 工程师）差一个数量级。

> 另一篇直接以标题给出结论：**《Don't Build a Full Agentic Harness. Wrap One Instead.》**
> 「The more of the harness you own, the more control you have. **You also own more bugs, more security decisions, more context problems, and more ways for an agent to fail that are hard to explain.**」

**最后一句几乎是 Hearth 现状的判词——它现在正是"更多无法解释的失败方式"。**

## §4 架构自噬：复杂度已经变成负资产

### 4.1 上帝对象仍在膨胀

| 文件 | 行数 |
|---|---|
| `crates/agent-core/src/loop.rs` | **10,218** |
| `crates/agent-core/src/context.rs` | 1,295 |
| `crates/planner/src/lib.rs` | 1,247 |

**`loop.rs` 单文件 10,218 行**，且在项目记忆中早前记录为 9,916 行——**今天还在长**。

**但行数只是表象，真正致命的是状态复杂度（本轮新增量化）**：

| 指标 | 实测 |
|---|---|
| `AgentLoop` 结构体**状态字段数** | **61 个** |
| `loop.rs` 内 `if` 分支 | **254 处** |
| `loop.rs` 内 `match` 分支 | **50 处** |
| **单文件分支点合计** | **≈ 304** |

**61 个可变状态字段 × 304 个分支点，同时存在于一个文件里。** 这意味着：
- 状态空间在名义上是 **2⁶¹** 量级——**没有任何人（包括作者）能穷举或推理其行为**；
- 任何一次修改，其副作用面都不可预测；
- 这解释了为什么四次"局部正确"的补丁会合成死锁——**在 61 维状态空间里，没有人能预见到两处补丁会在第三个维度上打架**。

一个"循环"长到一万行、状态字段 61 个，它早已不是循环，而是一个**无人能整体推理的状态机泥球**。

### 4.2 同一个决策，两份分歧的词表（400 行之内）

```
loop.rs:194   const PRODUCT_ACTIONS: [&str; 34]     ← goal_requires_product 用
loop.rs:230   const PRODUCT_ACTIONS_EN: [&str; 12]  ← goal_requires_product 用
loop.rs:395   const PRODUCT_VERBS: [&str; 8]        ← classify_user_input 用
```

**「这是不是产物任务」这同一个语义判断，在同一个文件、相隔不到 200 行，存在两套完全不同、条目数也不一致（34+12 vs 8）的关键词表。** 这不是风格问题，这是**语义分裂**——两套规则必然在某个输入上给出相反答案，而这个 bug 无法被单元测试发现（因为两套各自都能过自己的测试）。

### 4.3 魔数四散，无中央配置

`MAX_DEPTH=2`、`GOAL_DRIFT_MIN_STEPS=20`、`MAX_REASONING_CHARS=2000`、`MAX_HISTORY_MSGS=40`、`MAX_TRANSIENT_RETRIES=4`、`MAX_SEARCH_STREAK=4`、`MAX/HEAD/TAIL=6000/4000/1500`、`MAX_CONSECUTIVE_ERRORS=3`、`MAX_STEPS_WITHOUT_PROGRESS=5`、`BUDGET_LOW_THRESHOLD=0.15`、`MAX_RETRIES=6`、`verify_replan_count<3`、`acceptance_replan_count<1`、`replan_count<3`……

**十几个互不相干的阈值散落在多个 crate，彼此的交互无人计算。** 这正是"每个机制单独看都对、合起来死锁"的温床。

### 4.4 四次补丁，每次都对，合起来死锁

| 补丁 | 动机（注释自陈） | 局部正确性 | 叠加后果 |
|---|---|---|---|
| R1 (v0.1.3) | 问答不该被逼写文件 | ✅ | 造出"问答/产物"二元分支，为分类依赖埋雷 |
| v20 gate | 只读不该算完成（T13/T19 失败） | ✅ | 把完成钉死在 `write_attempted` |
| v22 gate | 堵住绕过 v20 的第二条 Done 出口 | ✅ | 文本回答彻底丧失完成资格 |
| 修 B / Node 07 | **压住 "revision 峰值 71"** | ✅ | **所有疑问句不再更新目标 → 用户意图进不来** |

**共同点：没有一次触及"任务图节点永不 Completed"这个死锁铆钉**（`mark_nodes_completed_on_accept()` 唯一调用点在 Done 相位；do_observe/do_reflect 只管子 agent 结果）。

### 4.5 项目内部已经承认失控

- **REFLECT_FACT_CONFLICT**（loop.rs:4363-4395）日志原文：*"facts indicate real progress (artifacts exist, 0 errors) but Reflect decided give_up"* —— 项目**早已检测到自相矛盾**，但处理是 **observe-only**，注释写「**决策权问题另立研究**」。
- 过时注释：`loop.rs:3237`「本函数是 loop 内唯一 provider.chat 出口」——任务书已承认该注释与事实不符（`check_goal_drift` 绕过），列入 W7-c 待修注释。**注释在骗人，说明代码已经复杂到维护者自己都跟丢了。**

### 4.6 依赖表面积：与它自己的自我定位反着走

**取证**：`Cargo.lock` 中第三方依赖 **353 个**，内部 crate **27 个**。

**行业对照**：2026 年头部 harness 的一个明确架构取向是 **"compiled, dependency-light core"**——自包含二进制降低安装摩擦、减少在不同用户环境里崩坏的运行时表面积。

**批判**：一个把"安全沙箱、fail-closed、可审计"写进自我定位的项目，其供应链攻击面是 **353 个第三方 crate**。每一个都是潜在的 CVE、许可证风险，以及"上游 breaking change 就得跟着升级"的持续维护债。

**这与它宣称的价值方向相反**：你在内核层用 Landlock+seccomp 精心筑墙，却在用户态敞开了 353 扇门。

（诚实标注：353 对 Rust 项目并非异常数字，此条的力度在于**与自我定位冲突**，而非绝对数量过多。）

### 4.7 终止出口散落 18 条：项目自己登记了这个问题，然后没有修

**取证（本轮新增）**：

| 出口类型 | 出现处数 |
|---|---|
| `next: LoopPhase::Done`（完成出口） | **14 处** |
| `next: LoopPhase::Error`（失败出口） | **4 处** |
| **终止出口合计** | **18 条** |

**这些出口散落在 `do_plan` / `do_act` / `do_reflect` / 主驱动 / budget 检查 / T4 stall 检测 / v20 gate / v22 gate / 修 D 拦截 / FA01 分支……彼此独立、无统一判定入口。**

**而这一点，是项目自己发现的**：
- 缺陷台账 **P1-8** 明确登记「give_up 决策分散多出口（T4 plan 臂 Err 绕过 Reflect；RC52 回填在 plan/Reflect 臂重复）」；
- 当时的建议是「收口为单一 `should_give_up()`」。

**从登记到今天，收口没有发生。** 相反，期间又新增了 v22 gate、修 D 拦截、FA01 分支、`rc52_route_done_if_session_artifacts` 等**新的出口**。

> **这是"给栅栏打补丁"最精确的量化证据**：每修一次，终止出口不是变少，而是**变多**。18 条出口意味着"任务为什么结束"这个问题有 18 个答案——**这正是"终态与内容背离"（§5.2）的结构性来源**。

**判据**：一个系统若无法用一句话说清"它在什么条件下结束"，它就无法被信任。**Hearth 有 18 个答案。**

## §5 输出质量：一个无法反思自身的系统

### 5.1 决定性场景：它答不出"你为什么放弃"

**A7 用户输入**（逐字）：
> 「如果出现了报错你就 give_up，然后停止，难道不是你接收到报错的信息，然后重新思考，然后规划新的解决方案吗，为啥直接就是 give_up…」

**Hearth 的实际行为**：跑了一串 `grep`/`sed`，**三个子问题一个都没答**，33 步后 give_up → ✗ failed。

**这一条比 80% 失败率更能说明问题。** 一个被要求解释自身失败、却以"再次失败"回应的系统——
**它不是 agent，它是一个挂了 LLM 的批处理脚本。Agent 的定义性能力就是"基于反馈调整"；Hearth 恰恰在这个能力上失败，而且是在被直接质问该能力时失败。**

### 5.2 输出质量四宗罪（全部实录）

| 罪 | 实录 | 危害 |
|---|---|---|
| **终态与内容背离** | A3/A6/A10 模型给出高质量自我剖析（A6 甚至准确诊断"只做不说"是流程缺陷），终态却是 ✗ failed | 用户无法信任任何终态标记 |
| **幻觉不设防** | B5 对**故意编造**的 seccomp 日志做详尽"分析"，未先核实；还擅自写 /tmp 文件 | 编造输入 → 编造输出，全链路无校验 |
| **假阳性完成** | B2 第 3 步从未回答、B4 任务根本没做，仍判 ✓ 完成 | "完成"这个信号完全不可信 |
| **成功成果被丢弃** | B1 example.com 实测已返回 HTTP 200，因 baidu 撞白名单 → 整个 run 判 failed，**200 结果未交付** | 部分成功 = 全部作废 |

### 5.3 回归防护网对用户体验**完全敞开**：497 个测试，0 条黄金集断言

**取证（本轮新增）**：

| 检索 | 结果 |

| `crates/` 内 `replay41` / `黄金集` / `golden` | **零命中** |
| 测试函数总数（`#[test]` + `#[tokio::test]`） | **497** |

**即：497 个测试里，没有任何一个断言「A 组 10 条黄金输入必须 ≥N 条成功」；也没有任何一个把手工测试中已反复复现的失败（give_up 链、终态与内容背离、假阳性完成、成功结果被丢弃）固化为回归用例。**

**后果链**：
1. **80% 的黄金集失败率存活了 10 个版本，从头到尾没有触发过任何一个红灯**——不是因为它隐蔽，而是因为**没有任何测试在看它**；
2. 测试套件保护的是"helper 函数的局部正确性"，不是"用户可感知的行为正确性"；
3. **「CI 全绿 = 产品可用」这个等式在此彻底失效。**

**方法论注**：这是"用可测量的代理指标替代真正重要的指标"的经典病例。497 这个数字听起来像质量证据，实则是**安全感的安慰剂**——它让项目在 80% 失败率面前依然确信自己"工程严谨"。

**最刺眼的一句**：项目有 **约 500 份文档**记录产品为什么失败，却**没有 1 个测试**阻止产品继续以同样的方式失败。文档在描述问题，测试在放纵问题。

### 5.4 单位经济学：一次提问要付十倍的钱

**实测基线**（B5 第 9 步 `introspect` 输出，逐字）：`system_chars=4697`、`history_chars=9837`、`total_chars=14534`。

**结构性事实**：
- `build_messages()`（loop.rs:2195）**每个周期重建** system prompt + 全量历史；
- 修正 C-1 已证：**每周期 2 次模型调用**（Plan + Reflect）。

**放大测算**（以 A7 的 33 步 ≈ 8 个周期为例，保守估计）：

| 项 | 计算 | 字符量 |
|---|---|---|
| Plan 调用（8 × [静态提示 4,697 + 均历史 ~6,000]） | 8 × 10,697 | ≈ 85,600 |
| Reflect 调用（8 × ~3,500） | 8 × 3,500 | ≈ 28,000 |
| **单任务合计** | | **≈ 113,600 字符（≈ 28K tokens）** |
| *其中：纯静态提示的重复发送* | *8 × 4,697* | *≈ 37,600 字符（≈ 9.4K tokens）* |

**对照增量式（竞品）**：8 轮 × 仅新增 delta ≈ 1,200 字符 ≈ **9,600 字符**。

→ **放大倍数 ≈ 10–12×**。而**光是那 4,697 字符静态提示的重复发送量，就已超过竞品跑完整个任务的总量**。

**再叠加失败率**（实质任务成功率 ≈ 8%）：

> **每得到一个成功的实质任务，期望消耗 ≈ 28K tokens ÷ 8% ≈ 350K tokens。**

这不是"有点费"，是**单位经济学上不成立**。而且失败烧的不只是 token，还有**时间**——A7 跑了约 2 分钟、33 步，然后 ✗ failed；A9 光规划就 81 秒，然后 ✗ failed。

对一个自述"缺钱"的项目，把预算花在**重复发送同一段静态提示**和**为失败任务买单**上，是最不该犯的浪费。

（诚实标注：放大倍数是基于 introspect 实测点与周期数的**结构估算**，非逐轮精确计量；量级结论稳健，精确值需 Phase E 计量。）

## §6 用户体感：它连"及格线"都没摸到

对标三家成熟 harness 的**行业标配**（Claude Code / Codex CLI / WorkBuddy 共有）：

| 标配能力 | 三家 | Hearth |
|---|---|---|
| 流式输出、首字秒级 | ✅ | ❌ 寒暄 32s，plan span 常见 5–45s，**峰值 81s** |
| 改了什么可见（diff） | ✅ 并排 diff / 变更摘要 | ❌ 无 diff 事件（D8 复现） |
| 可回退 | ✅ checkpoint / Esc×2 回退 / fork | ❌ 无 |
| 运行中纠偏不重启 | ✅ Esc 停止 + 输入纠偏 | ❌ 无 |
| 完成由模型语义判断 | ✅ | ❌ 由 `write_attempted` 判定 |
| 自治度可配置 | ✅ 5 档权限 / 3 档自治 | ⚠️ 非 tty 默认 deny-all 即 abort |
| 部分结果交付 | ✅ | ❌ B1 实证丢弃 |

**七项标配，Hearth 全缺。** 而且这些不是"高级特性"，是**入场券**。

### 6.1 反驳预防：「但它有 21 个子命令，功能并不少」

**取证**：`crates/codex-cli/src/lib.rs` 中 `Commands::` **21 个**——chat / repl / resume / sessions / history / approve / deny / cancel / status / rollback / config / init / note / setup / coverage / whoami / template / tools / replay / civ / tasks。

**这份清单在数量上不输竞品。所以本报告不主张"Hearth 缺功能"——那个批评是错的，我不采用它。**

**真正的批判是：功能齐备，但功能不构成体验。** 21 个命令每一个单独都能跑，组合起来却无法完成一次体面的对话：

| 有… | 但… |
|---|---|
| `resume` | one-shot chat 中途 kill 时**会话根本没落盘**（D7 实证：三个时点 JSONL 均为 0 个新文件），resume 无从下手 |
| `sessions` / `history` | **没有 diff**——查得到历史，看不出改了什么 |
| `approve` / `deny` / `cancel` | **没有运行时纠偏**——只能在"批准/拒绝/取消"里三选一，无法"边跑边改方向" |
| `status` | 显示的是**步数与预算**，不是"用户的问题被回答了吗" |
| `coverage` / `civ` / `tools` | 服务于内部可观测性，与用户体感无关 |

**功能齐全而体验崩坏，比功能缺失更难救**——因为每一个已存在的功能都成了改动时的兼容性包袱，而它们本该共同服务的那个目标（流畅协作）**从未被明确定义**。

（同理诚实标注：本项目存根极少——`todo!`/`unimplemented!`/`TODO` 合计仅 **6 处**。它不是烂尾工程，它是**认真建成的错误东西**。）

## §7 工程治理：流程正在吃掉产品

**这一节的数据最刺眼。**

| 事实 | 数字 |
|---|---|
| 今日（9/2）产出的 docs 下 md | **27 份** |
| docs/ 累计 md | **396 份** |
| 项目根累计 md | **103 份** |
| **合计文档** | **≈ 500 份** |
| 同期产品黄金集失败率 | **80%（未改善）** |
| 同期 `loop.rs` 行数变化 | 9,916 → **10,218（+302）** |
| **近 30 天提交：涉及 `docs/`** | **45 次** |
| **近 30 天提交：涉及 `crates/`** | **23 次** |

**最后两行是本节最硬的证据——它来自 git 历史本身，无法被辩解：**

> **近 30 天，改文档的提交（45）是把代码改动的提交（23）的近 2 倍。**

这不是"偶尔写多了文档"，这是**版本控制系统记录的、持续一个月的重心失衡**。代码的改动频率只有文档的一半——而产品同时维持着 80% 的失败率。

**换句话说：这个项目过去一个月的主要产出物，是关于 Hearth 的文字，而不是 Hearth 本身。**

**今天产出的文档包括**：五件送审物评审报告、五件送审物审批裁决书、P4 测试窗口测试报告、可用性改造审批材料评审报告、G1 相关矩阵评审材料、PhaseD 评审报告、PhaseD 终审与执行窗补测指令、长程任务书 v1.0、测试窗口 campaign 施工任务书、续工单放行令……

**以及最刺眼的一份：`W1-反应回路改造设计小样 v0.1（文档级）.md`（17:30）。**
**修复方案的产出物是一份文档，不是代码。**

### 7.1 这是"用流程的勤奋掩盖产品的失败"

项目建立了完整的官僚体系：顶层 → 执行窗 → 测试窗 → 砺评审 → 顶层审批，产出派工单、评审报告、裁决书、放行令、冻结报告、补测指令……

**在一个人（+AI 窗口）的项目上跑多窗口审批制，其产出主要是关于产品的文档，而不是产品本身。**

AI agent 在这里做了什么？**它们在写关于 Hearth 的文档，而不是在改 Hearth。** 这形成了闭环自娱：AI 产出分析 → AI 评审分析 → AI 批准分析 → AI 产出下一份分析，而 `loop.rs` 只增加了行数，失败率纹丝不动。

### 7.2 破窗效应

| 已知缺陷 | 发现版本 | 当前状态 |
|---|---|---|
| `patch.rs` 中文字节切片 panic | v0.2.20（8/31 已定位到 127/135/145 行） | **v0.2.23 仍未修**——W7 标为"先行热身"，从未发货 |
| give_up 主诉 | v0.2.4 起 | **v0.2.23 仍在** |
| "需要猜结果" | v0.2.18 主诉 | **v0.2.23 复验仍存在**（A6 专门测这条） |

**一个已知两周（跨 10 个版本）、已精确定位到行号、被标记为"低风险先行"的崩溃级缺陷，至今未修。** 这不是资源问题，这是**执行力的证伪**——连"低风险先行"都发不出去，凭什么相信"架构级改造(W1)"能落地？

### 7.3 激励结构批判：这个流程在奖励什么行为？

§7.1 说了"用流程的勤奋掩盖产品的失败"。这里要问更尖锐的一层：**流程为什么会演化成这样？因为它在奖励错误的东西。**

观察这个循环的实际运作：

| 角色 | 产出 | 被评审/审批的对象 |
|---|---|---|
| 执行窗口 | 文档 + 代码 | 主要是**文档** |
| 评审窗口（砺） | 评审报告 | 执行窗口的文档 |
| 顶层 | 裁决书 / 放行令 | 评审报告 |
| — | — | **唯独没有人评审"用户能不能用"** |

**结果是可预测的**：产出文档是最安全、最容易被评审通过、最容易显示"有进展"的行为。改 `loop.rs` 风险高、可能引入回归、评审难过；写一份评审报告零风险、必然通过。

**于是理性的执行者（无论人或 AI）会最优地选择写文档。** 今天 27 份文档、0 个黄金集回归测试——**这不是执行者的失职，这是激励结构的必然产出。**

> **判据（可迁移的教训）**：一个流程若不把"用户可感知的通过率"设为硬门禁，它就**必然**退化为文档生产线。Hearth 今天的治理体系，正是这个退化的完成态。

**这是本报告对读者最有价值的一条**：即便你决定继续，也必须先修激励结构（设通过率门禁），否则再多的窗口、再严的评审，都只会生产更多关于失败的文档。

## §9 沉没成本的正面警告（这一节是给决策者的）

**27 crates、43,723 行、486 测试、500 份文档、两个月的投入——这些数字此刻正在替项目说话：「投了这么多，停了多可惜」。**

这正是**沉没成本谬误**的典型触发条件。必须说清楚：

| 看起来是资产 | 实际性质 |
|---|---|
| 27 crates / 43k 行代码 | **负债**。10,218 行的 `loop.rs`、分裂的词表、四散的魔数——接手者的认知负担远大于价值 |
| 486 个测试 | **幻觉**。测的是 helper，不是行为；全绿而 80% 任务失败 |
| 500 份文档 | **成本**。文档不会让产品变好用，它们只记录了产品为什么没变好用 |
| 沙箱/记忆/子 agent 的设计经验 | ✅ **真资产**——但它是**知识**，不是**代码**；知识可迁移，代码是包袱 |

**"差一层窗户纸"这个判断本身，就是沉没成本在替你说话。** 判断依据应该是"再投两个月，预期成功率是多少"，而不是"已经投了多少"。

### 9.5 决策论：两条路径的期望值，与一个致命的不对称

搁置情绪，做一次粗略的期望值对照（概率为主观赋值，仅用于暴露结构，不用于精确预测）：

| 路径 | 最好情况 | 中间情况 | 最坏情况 |
|---|---|---|---|
| **A. 继续自研** | 达成可用（≈15%）——**但仍与 30+ 免费竞品同质，无差异化回报** | 再投 2–6 个月，失败率降至 30–40%，**仍不值得日常使用**（≈50%） | 维持现状：文档继续产出、`loop.rs` 继续膨胀、失败率不降（≈35%） |
| **B. 转 Extend** | 2–4 周内得到可用且由上游维护的 agent（≈70%） | 1–2 个月，需适配自有流程（≈25%） | 吸收一次上游 breaking change（≈5%） |

**关键不对称（这一条决定结论）**：

1. **路径 A 的最好情况，在实用意义上等于路径 B 的中间情况**——即使 A 成功，你拿到的也只是一个与 Codex CLI / Goose 同质的 harness，而后者免费且由上游维护；
2. **路径 A 的最坏情况是"无信号的持续出血"**——因为没有任何测试盯着通过率（§5.3），**没有任何自然信号会告诉你该停**；
3. **路径 B 的最坏情况成本有界**（吸收一次上游变更）。

> **结论：A 的上界被 B 的中间态封顶，而 A 的下界是无信号的持续出血。理性选择是 B。**

**最坏情况的隐性成本（反脆弱检验）**：若继续 A 且失败，损失的不只是时间——**还有判断力**。连续 10 个版本看着 80% 失败率而不止损，会训练出"再改一版就会好"的认知惯性；这种惯性会污染你对后续项目（如 SeedLM）的取舍判断。**这才是继续的最大隐性代价。**

## §12 建议路径（停止 ≠ 放弃）

1. **停止自研**（不再新增 crate、不再扩 `loop.rs`、不再为 W1 出文档级小样）；
2. **归档**：`git tag` + 源码备份（遵循既有惯例：git archive 日期戳存 Desktop）；
3. **知识迁移**：把三条真经验带走——① 潜意识层的**护栏范式**（只对 3 条硬命令 Abandon，其余告警）是正确设计；② **完成判定权必须属于模型**、框架只留预算/安全/审批；③ 三层死锁的教训（**任何"以可测量代理指标替代语义判断"的设计，都会同时制造假阴性与假阳性**）；
