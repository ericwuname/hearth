# Hearth v0.2.18 真机盲测报告：与 CORE FREEZE 声明的直接冲突

> **测试性质**：非脚本化 benchmark，是用户在 `hearth 0.2.18 (unknown)` 上的真实、随手交互（约 90 分钟，36 轮）。
> **特殊意义**：这是 v0.2.18——也就是 `CORE FREEZE CLOSURE-01` 刚刚裁决"F0=0、零 Projection 失真、零无限循环"的**同一个版本**——第一次被非执行窗口、非脚本化的方式盲测。
> **核心结论**：本次盲测发现的证据，**直接反驳了 CLOSURE-01 的至少两条 F0 声明**，不是新增的小毛病，建议在正式确认"A——独立验证完成"之前，把这份材料并入证据链重新评估。

---

## 0. 最重要的数字：一旦进入某个状态，会永久回不来

逐轮统计本次会话的终态：

| 区间 | 成功 | 失败（give_up/stalled） |
|---|---|---|
| run-001 ~ run-012 | 10 | 2 |
| **run-013 ~ run-036** | **0** | **24（全部）** |

**从第 13 轮开始，直到用户主动喊停结束会话（第 36 轮），连续 24 轮没有一轮真正成功过。** 这不是"失败率偏高"，是**系统进入了一种一旦触发就再也无法自行恢复的状态**，靠用户耐心追问了十几轮，最后主动放弃。这个现象本身，比下面任何一条具体 bug 都更需要优先处理——因为它说明现有的失败恢复机制（P1-FAILURE-ADAPTATION-01 号称已经闭环）在真实场景下没有对这类"持续性停滞"生效。

## 1. 与 CLOSURE-01 直接冲突的证据（最高优先级）

### 1.1 裸后端错误日志直接打印到用户终端——反驳"零 Projection 失真"

**现象**：run-014、run-025、run-029 等多处，用户终端上直接出现了这样的原始行：

```
2026-08-31T05:31:03.430300Z ERROR agent_core::r#loop: do_plan_inner failed error=stalled: 2 consecutive replans produced identical TaskGraph (4 nodes) — semantic progress absent, giving up early (Tier3 T4)
```

这一行**先于**格式化过的 `✗ stalled: ... ✗ Done (N steps)` 出现，是典型的"后端 tracing 日志绕过 PROJECTION 层，直接打到终端"——这正是 Hearth Core 蓝图 §19 明确写下要杜绝的反面例子（"错误：`ERROR hearth::loop: permission denied`；正确：`✗ 工具出错 reason: ...`"），也正是 CLOSURE-01 报告 §7 声称"错误输出投影成功 = 零"的那一项。

**这是一个可以直接拿证据反驳"零"这个数字的具体反例**，不是推测。建议：这条不应该被归为"新发现"，应该被记录为**对已宣布的 F0=0 结论的证伪**，需要重新核实 CLOSURE-01 §7 那张表的"零"是怎么测出来的（大概率是用脚本化 benchmark 场景测的，没有覆盖到这种真实、非预期的报错路径）。

### 1.2 "失败自诊断死循环"——一种蓝图和 CLOSURE 报告都没有覆盖的失败模式

**现象**：从 run-013 起，用户每问一次"上一轮为什么失败/发生了什么"，系统的反应模式高度一致：

```
Plan：审查上一轮报告 → 定位失败原因 → ...
→ read 上一轮 report.md
→ bash grep 相关错误模式
→ Reflect: give_up 或 stalled
```

然后用户下一轮继续追问"这轮又失败了，怎么回事"，系统又用几乎相同的分解方式重新分析，再次 give_up。**这个循环重复了至少 15 次**（run-013 到 run-036 之间大部分回合都是这个模式）。

这不是"停滞检测正确触发了一次"，是**"用户追问失败原因"这一类任务，本身系统性地更容易撞上停滞检测**——因为这类任务的自然分解方式（读报告、grep、总结）在几轮 replan 之间很容易产生相同的 TaskGraph 结构，从而被 T4 判定"语义停滞"提前放弃。**换句话说：系统对"自己刚失败了，帮我看看为什么"这一类元诊断任务，有一个尚未被识别的系统性弱点**，而这类任务恰恰是用户在系统出问题时最自然会问的问题——这个弱点会在系统最需要自我解释的时刻发作，是最坏的时机。

这条建议单独立项（可编号 RC51），因为它和现有的 F1 项（RC48 false stop、QA completion-awareness）性质相关但触发场景不同，且后果更严重：它会让用户在系统出问题时，连"问一下发生了什么"这条路都走不通。

### 1.3 有意义的分析内容被截断，只剩状态标记——BUG-012 的真实复现，且反驳"零假完成"的相邻声明

**现象**：run-009、run-013、run-020 等多次，系统实际执行了完整的分析（读文件、diff、生成报告），过程日志清楚显示分析内容存在，但**最终呈现给用户的只有一行 `✓ Done (21 steps)` 或 `✗ Done (18 steps)`，看不到任何分析结论本身**。用户自己也当场发现了这个问题，追问"这个是不是一个问题"，系统确认并登记为 BUG-012。

这条虽然不直接是"假完成"（产物确实落盘了），但它和 CLOSURE-01 强调的"事实必须能投影给用户"这条核心原则直接相关——**如果用户永远看不到 Projection 出来的内容，"投影正确"这个属性对用户来说毫无意义，等同于没有**。建议和 1.1 一起，作为 PROJECTION 层的一次专项回归，不要只满足于"内容有没有失真"，还要测"内容有没有完整到达用户"。

## 2. 其余具体问题（按严重度排列）

### 2.1 `introspect` 被当作 bash 命令调用，报错 "命令未找到"

**现象**：run-005、run-023 出现 `bash → cmd: introspect` 以及后续的 `⚙ introspect →`两种不同调用方式混用；前者直接报 `bash: 行 1: introspect: 未找到命令`（exit code 127）。`introspect` 是一个独立的工具调用类型，不是 shell 命令，但系统有时会把它错误地塞进 bash 字符串里执行。

**建议**：审计工具选择/工具调用生成逻辑，确认是否存在把结构化工具名误当 shell 命令拼接的路径，这个应该是一个可以直接定位到具体代码分支的 bug，不需要靠猜。

### 2.2 `apply_patch` 对空白/缩进的脆弱匹配，仍未修复

**现象**：run-013，`apply_patch` 因为 "check exact whitespace/indentation" 被拒绝。这条我们在更早的手工测试里已经报过（P1-8），现在 v0.2.18 上依然复现，说明这条此前没有被排进已完成的施工批次里。

**建议**：并入下一批 Memory/Context 或独立小修，补上此前建议的"精确匹配失败后降级为忽略行尾空白/换行符差异再试一次"的容错逻辑。

### 2.3 目标锚点在长会话后期，与实际对话内容脱节

**现象**：会话后期（比如 run-032"你能回复我一下情况吗"这种简短追问），Plan 阶段生成的步骤描述依然是"Locate the ledger file / Verify step 1 is marked as Done..."这类和当前这句话毫不相关的内容，明显是延续了很早之前某个已经过时的分解框架，而不是针对这句话重新理解。

**建议**：这与我们此前讨论过的"锚点修订次数/执行轮数比值"这个 telemetry 指标直接相关——本次会话到结束时"目标已修订（revision 10）"，如果配合执行轮数一起看，比值明显偏高，建议用这次真实数据去验证那条 telemetry 指标是否真的能捕捉到这类脱节。

### 2.4 压缩摘要原样重复打印，呈现给用户的形式不专业

**现象**：run-026 到 run-030 之间，`[compacted 会话摘要] 轮次目标: Text("...")...` 这行内容在连续多个 Plan 周期里**逐字重复出现**，像是同一个摘要对象被反复读取展示，而不是每次生成新的。这本身可能是 2.1 提到的"停滞循环"在压缩摘要展示层面的一个副作用表现，但即便是副作用，直接把这种内部数据结构的 Debug 格式（`Text("...")`）暴露给终端用户，也不符合 PROJECTION 应有的呈现标准。

**建议**：和 1.1、1.3 一起，作为这次 PROJECTION 层专项回归的一部分。

### 2.5 stalled 阈值设置，用户自己提出的建议值得认真评估

**现象**：系统自己在 run-030 生成的诊断报告里也提出"stalled 检测阈值：2 次 → 3 次"这个建议。

**建议**：不要因为是系统自己提的就直接采纳，也不要因为 CLOSURE-01 已经把相关问题定为"须顶层批准，暂不修改"就完全搁置——建议至少先做一次轻量验证：把阈值临时调到 3，重放本次会话里触发 stalled 的那几个场景，看是否能避免第 13 轮开始的连锁失败，同时确认这个调整不会让真正的死循环也需要多等一轮才能被拦下来。这个验证成本很低，值得作为独立于"是否修改核心阈值"这个大决策之外的一次快速探针。

## 3. 建议的处理方式

**第一步，也是最紧急的一步**：把本报告第 1 节的三条证据（裸日志泄漏、失败自诊断死循环、内容截断）提交给顶层规划窗口和执行窗口，**明确指出这些证据与 CLOSURE-01 的 F0 声明存在直接冲突**，建议在"B——独立验证未完成"转为"A——独立验证完成"之前，把这份材料作为新增证据重新评估，而不是把 CORE FREEZE 已经既成事实地往前推进。

**第二步**：第 1.2 条（失败自诊断死循环）建议单独立项，因为它命中的场景（用户追问系统自己的失败原因）是所有场景里最不能容忍失效的一个——系统故障的时候，恰恰是用户最需要它能解释清楚发生了什么的时候，如果这条路径本身也失效，用户会彻底失去对系统状态的可见性。

**第三步**：第 2 节的具体问题，可以按现有节奏并入常规施工批次，不需要打断当前 P2-MEMORY-CONTEXT 或 P2-LONG-RUN 的既定路线。
