# Hearth 双底座架构裁定 v1.0（顶层 · 回应用户双底座提案）

> **签发**：顶层　**日期**：2026-09-02　**呈**：用户复核
> **触发**：用户提案——"自研底座与标准底座同时纳入 Hearth 项目，第二个 1 与底座分开独立成体；自研底座可继续开发但先出效果靠标准底座；这样即使自研底座失败，Hearth 仍有一个完成的作品。"
> **一句话**：**裁定：可行，且这是对 v1.1 三线结构的正确补全**——它把"引擎的生死"从"项目的生死"里解耦出来，是整个决策结构里缺的最后一块。同时实测确认了一个关键前提与三条实施红线（§三）。

---

## 一、直接回答：能做到，理由有三

1. **第二个 1 天然就是底座无关的**。宪法治理（prompt 注入）、技能库（MCP resources）、判断层观测（日志/事件采集）——这些能力的正确实现方式本来就是**独立进程 + 标准协议**，而不是长在某个引擎体内。Hearth 过去把它们焊死在 loop.rs 里，恰恰是三层死锁的放大器之一。
2. **底座可切换让自研引擎获得公平竞争**。引擎不再是"全押的唯一赌注"，而是与 Codex CLI/Goose 同台竞争的**可选 backend 之一**——同一套认知层，用户体感直接比较。自研继续开发的心理与预算定位随之健康化：它是实验线，不是生死线。
3. **软着陆结构成立**。即使引擎最终不达标：hearth-cognition（第二个 1）+ 标准底座 = **Hearth 项目的完成作品**；引擎以"L1 数据完整的实验backend"身份归档——项目没有失败，只有一次 backend 选型。这正是你要的"1+1>2"里的保险丝。

**实测前提确认**：Hearth 引擎当前 MCP 零命中（grep crates/ 无一处）、OpenAI 兼容端点已有（llm-cn crate）、自定义指令钩子已有（loop.rs/agent-types 有 instructions 相关）——即**接标准底座生态需要补 MCP client，但模型接入层无需重写**。

---

## 二、目标架构

```
┌────────────────────────────────────────────────────────┐
│  hearth-cognition（第二个 1 · 独立仓库 · 独立版本线）        │
│  宪法治理注入 · 技能库 · 判断层观测/校准 · 护栏配置 · 经验卡   │
│  出口：MCP server 集合 + AGENTS.md/指令注入 + 事件适配器      │
└───────────────┬────────────────────────────────────────┘
                │  仅标准协议：MCP / 指令文件 / 通用 hooks
    ┌───────────┼────────────────┐
    ↓           ↓                ↓
 Codex CLI    Goose      Hearth 引擎（可选底座 #3，L1 数据决定去留）
 （底座 #1） （底座 #2）  （MCP client 补齐后才具备接入资格）
```

**职责铁律**：认知层**不编排控制流**（不接管底座的循环/审批/工具调度——那是底座的职权，也是 wrapper 变厚变烂的开始）；认知层只做**语义供给**（宪法/技能/观测/标注）与**事后判定观测**（校准数据、诚实标注建议）。

---

## 三、三条实施红线（防两头烧，来自全部既有教训）

1. **接口纪律——只用标准协议**：认知层禁止依赖任何底座专属 API；某能力必须用专属机制（如 UNVERIFIED 标注需要拦截完成判定）→ 标记"可移植性债务"，做成 per-adapter 插件，不进认知层主体。（防：换底座时第二个 1 跟着殉葬。）
2. **顺序纪律——先出效果在标准底座**：第二个 1 的 MVP **先在 Codex CLI/Goose 上落地**（它们原生支持 MCP，零适配成本），**不给 Hearth 引擎写适配器排在最后**，且设双门槛：①L1 决胜局证明引擎接近可用；②MCP client 的实现成本 < 收益。**禁止让"给引擎写适配器"变成继续往 loop.rs 里投人的新借口**（E7/沉没成本教训）。
3. **范围纪律——MVP 收敛**：第一批只做协议容易表达的三件：宪法注入（AGENTS.md/指令文件）+ 技能库（MCP server）+ 校准观测（读 session 日志，per-adapter）。UNVERIFIED 诚实标注、完成判定观测与底座完成机制耦合深（RC1 教训），第二批再做。

## 四、与 v1.1 三线的合并执行图

```
L3 知识卡（今天，不变）
L2 底座对照（照跑）→ 选出主力底座
L2.5 【新增】hearth-cognition MVP 在主力底座落地（宪法+技能库+校准三件）→ 先出效果
L1 决胜局（并行，feature 分支）→ 引擎作为"底座候选 #3"的资格数据
C  适配器（最后）→ 双门槛放行才开工；不放行则引擎归档，cognition 照常交付
```

**数据合流决策点更新**：L1 + L2 + L2.5 三数据齐后总决策——
- L2.5 跑通 + L1 强 → 引擎留任为底座 #3，写适配器；
- L2.5 跑通 + L1 弱 → 引擎归档，**Hearth 项目以 hearth-cognition + 标准底座的形态交付完成作品**；
- L2.5 跑不通（认知层自身问题）→ 与底座无关，修认知层。

---

## 五、对你提案的一句话回应

> 你问"为什么不能把我们自己的东西做成一个 1，跟底座分开"——**能，而且本来就该这样**。过去两个月的最大架构错误，就是把认知层焊死在一个没造好的引擎上，让两个 1 同生共死。拆开之后：底座层变成三选一的供应商问题（标准件优先、自研件凭数据竞争），认知层成为唯一承载你愿景的长期资产。**自研底座失败的不再是项目，只是一个 backend；而 Hearth 这个名字，最终挂在那个永远活着的 1 上。**
