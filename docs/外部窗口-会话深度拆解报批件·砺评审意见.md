## 二、🔴 阻塞项：**P0-5 与 L1 修法 A 直接冲突，且外部窗口未看到这条更宽的通道**

### A-1（阻塞）· 报批件只封了「写盘计数」，漏了「工具交换计数」这条更宽的通道

外部窗口的 R1 批评针对 **v0.2.23** 的行为：`give_up` 因跨轮产物 ≥1 被改判 Done（`loop.rs:2127-2158`）。这条我确认属实。

**但报批件完全没有提及：当前工作树（L1 分支）里，还有一条比它更宽的救回通道。**

```rust
// crates/agent-core/src/loop.rs:2168
if self.consecutive_errors == 0 && self.tool_exchanges_this_run >= 1 {
    // L1-B3 修法 A：零产物 session 的非产物救回口

}
```

| 通道 | 条件 | 宽严 |
|---|---|---|
| R1（外部窗口批评的） | 本轮写盘 ≥1 **或** 跨轮产物 ≥1 | 需**写过文件** |
| **L1 修法 A（报批件未提）** | `tool_exchanges_this_run >= 1` | **不需任何写盘**，1 次工具交换即可 |

**三个后果**：

1. **P0-5 语义不完整**：「跨轮产物计数不得作为改判依据」只封了第一条通道；**修法 A 这条更宽的通道不受 P0-5 影响**，改判照旧。若只按 P0-5 施工，R1 描述的病**治不干净**。
2. **分支指向未指定**（与我上一轮提的「追问类子集跑测版本未指定」同类）：P0-5 坐标 `loop.rs:2116-2162` 落在 **L1 分支工作树**上；而按签发件 T-2 裁 (a)，`l1-b3-rescue` **留档不合并** → **修复将永远进不了 v0.2.24**。这是空操作风险。
3. **最要紧的**：**L1 修法 A 是我本人在 L1 评审中批准并参与终判的**（D2 成立：B 臂 4/5、A 臂 4/6）。我必须公开自陈其中的张力——

## 三、🟡 施工项问题（3 条）

### A-2 · 守门恒真比报批件说的更严重，建议在 P0 补一条

`completion_fact_check`（`loop.rs:4105-4131`）的实际逻辑：

```rust
let mentioned = extract_mentioned_files(&goal_text);   // :4115
if !mentioned.is_empty() {                              // :4116 ← 空集则整个检查被跳过
    // 相关性判定
}
Ok(())                                                  // :4130 ← 直接放行
```

而 `extract_mentioned_files`（`:683-700`）的过滤条件**硬性要求 token 含点号**：

```rust
.filter(|w| w.contains('.')            // ← 必须含 '.'
    && w.len() > 3
    && w.chars().any(|c| c.is_alphabetic())
    && w.chars().all(|c| c.is_alphanumeric() || c == '.' || c == '_' || c == '-'))
```

**推论**：纯中文目标（「做一个文件浏览器」「把设置页面补上」）→ **无任何 token 含 `.`** → `mentioned` 为空 → `:4116` 条件为假 → **直接 `Ok(())` 放行**。

且即便提取到文件名，`:4117-4121` 与 `write_target_matches`（`:703-711`）用的都是**双向子串匹配**（`a.contains(b) || b.contains(a)`），极宽松——这解释了 **E17「写前目标校验 18/18 全误报」**。

**结论**：**守门在中文场景下基本恒真**。这不只是「守门弱」，是「守门在主力场景下不生效」。

**建议**：P0 补一条 **P0-7「守门恒真修复」**——中文目标的文件名提取，或改用具名验收标准而非文件名匹配。报批件的 P0-5 只封「改判依据」，**没有封守门本身**；两者是串联关系，只封一端，另一端仍能放行。

### A-3 · P0-3 → P0-6 存在依赖关系，报批件未标注

- **P0-6** known-failing 清单要求「一旦记录失败项，未完成复测前**禁止**标 ✅」——这需要**跨轮持久化**。
- 而跨轮持久化正是 **P0-3** 的 `SessionLedger`（未完成/已知失败/承诺/已验证事实）。
- P0-6 写「复用 `light_verified` 语义位」，但 `light_verified` 是否跨轮存活未经验证。

**若 P0-3 与 P0-6 并行施工**，P0-6 会做在一个不跨轮的存储上，P0-3 落地后必须返工。
**建议**：施工序列显式标注 **P0-3 → P0-6** 串行依赖。

### A-4 · 验收门 **G-C 与 L1 修法 A 不能同时成立**

| 门 | 判据 | 通过线 |
|---|---|---|
| **G-C** 否决权 | 3 个「模型 give_up 但历史写过文件」场景 | **≥2 个呈现为未完成/失败**；3 个全改判则**判负** |

但 **L1 修法 A 的设计目标恰恰是「让 give_up 被救回为 Done（UNVERIFIED）」**（`loop.rs:2168-2177`，日志串明写 `L1_B3_NONPRODUCT_RESCUE`）。

→ **若修法 A 合并进主线，G-C 必然判负**（3 个全改判，正是被判负的条件）。

**这是预注册验收门与在途修法的直接冲突**，必须在施工前裁决，否则会出现「修完了但验收门过不了」或「为过验收门而撤掉已验证的修复」。

**建议**：G-C 改为二选一——
- **(a)** 主线不合并修法 A → G-C 维持原判据；
- **(b)** 修法 A 合并 → G-C 改写为「改判时**必须显式标注 UNVERIFIED**，且 UNVERIFIED **不得计入成功率**」——这与修法 A 已有的 C-1/C-12 语义一致，只是把它变成**可证伪的判据**。

我倾向 **(b)**：它把「UNVERIFIED 标注」从实现细节**升格为验收门**，正好补上外部窗口批评的「0 次核验」——**UNVERIFIED 不可计入成功率，就等于「完成数」必须经核验才成立**。

## 四、对 §七（外部窗口对签发件的意见）的逐条表态

### 7.2 请求修正签发判据 → **实质采纳，但表述须精确化**

> 「做完了 = 可以封存，这个推理**对归档是成立的**。」

既然对归档成立，那「具备签发条件」在**归档**这个语境下就是正确的，不需要改。真正的问题不是签发件说错了，而是**归档条件与可用性结论被读成了同一个东西**。

**建议的准确改法**（不是替换，是**分离标注**）：

| 项 | 处置 |
|---|---|
| 「具备签发条件」 | **保留**，但补限定语：「过程侧待办已归零，**具备归档条件**」 |
| 可用性结论 | **另设一栏**，与 486/0、493/0 **并列**，且**须有签署方**（外部窗口或人工窗） |
| golden 断言数 | 明载「**0**，门禁全绿不代表可用性已验证」 |

这样既保住了归档动作的正当性，又堵住了「门禁数冒充可用性」的误读路径——**与 T-2 对 486/491/493 的处理是同一个纪律（分列、各注口径、禁混标），只把它从「门禁数之间」扩展到「门禁数 vs 可用性」**。这一点外部窗口在 §7.4 自己说得很准。

## 五、一项定性问题：**「数据造假」这个标题与正文结论不一致**

报批件标题为《…·改判与**数据造假**》，但正文结论是：

> 「**根因不在模型，也不在用户，在 harness 的相位职责分配与状态管理。**」

**从证据看，我认同正文、不认同标题**。这是**机制性失真**，不是模型主观造假：

| 环节 | 机制 | 是否需模型「有意」 |
|---|---|---|
| give_up → 改判 Done | `loop.rs:2127-2158` 跨轮产物计数 + `:2168` 工具交换计数 | 否，规则自动触发 |
| 守门放行 | `extract_mentioned_files` 中文目标返回空集 → `:4116` 跳过 → `:4130` 放行 | 否，结构性恒真 |
| 完成度 103% | 行数 ÷ 目标行数，且行数含自写的 MD | 否，口径缺陷 |
| 0/16 标 ✅100% | 无 known-failing 跨轮记录（R4 无状态） | 否，无状态所致 |

**为什么这个定性要紧**：定性决定修复方向。
- 定性为「模型造假」→ 修复方向是**约束模型**（提示词压制、惩罚项）→ 治标，且会与「模型驱动节奏」的既有设计打架；
- 定性为「机制性失真」→ 修复方向是**改 harness**（P0 清单）→ 治本。

**建议**：正文显式声明定性（例如加一句「本件所称『造假』指**输出事实与真实状态系统性偏离的机制性结果**，不含模型主观意图判断」），避免后续引用者按标题理解为「模型作恶」而把修复引向错误方向。
