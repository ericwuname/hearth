## T2 · Deadline/retry-cap 未生效路径排查（本次最高优先级）

**现状（【评审修订 v1.1】已按源码校正）**：`agent-core/src/loop.rs:1967` **确有** `TOTAL_RETRY_CAP: Duration::from_secs(120)`，且 `loop.rs:2009` 在每次 `provider.chat()` 返回 `Err` 时检查 `retry_start.elapsed() >= TOTAL_RETRY_CAP`——即 120s 墙钟上限**真实存在且被检查**，`deadline_exceeded()` 单测也确实存在（`context.rs:519`）。但 B04/B06 两次故障中进程直到 **200s 才终止**——需澄清：**200s 是遥测脚本的外部 `timeout 200` 包裹命令，不是 Hearth 自身上限**；真正要解释的是"为何 Hearth 的内部 120s 上限没在 ~120s 自终止"。

**精确漏处机制（评审窗口指明，供执行方首查）**：`llm-openai/src/lib.rs:330` 的 provider 内部有**独立的 3× 重试循环**（每次 `send`+`read body`，受 reqwest 30s 请求超时约束，见 `lib.rs:282` `.timeout(Duration::from_secs(30))`，退避 500ms/1s/2s）。loop 层的 120s 墙钟检查**只在 `provider.chat()` 整个返回后**才生效——而一次 `provider.chat()` 内部最多可吃掉 3×30s≈90s。于是"两次 loop 重试（每次各含 3 次 provider 内重试）"可叠加到 ~180s，远超 120s 才轮到 loop 检查 `deadline_hit` 并 `give_up`。即：**上限存在，但被嵌套重试在时间维度上"穿透"了**。

**动作（【评审修订 v1.1】已对齐真实机制）**：
1. **首查嵌套重试穿透**（评审已指明根因方向）：确认 `llm-openai/lib.rs:330` 的 provider 内部 3× 重试（受 `lib.rs:282` 的 reqwest 30s 超时约束）与 `loop.rs:1969` 的 loop 层 4× 重试（受 120s 墙钟约束）是如何叠加的；计算"2 次 loop 重试 × 各含 3 次 provider 内重试 × 各 ≤30s"是否足以解释 ~180-200s 才 `give_up`。若是，则该嵌套是 B04/B06 挂起的主因。
2. **统一重试权威**：让 loop 层的 120s 墙钟成为**唯一**重试权威——要么在 `provider.chat()` 内部移除/大幅削减 3× 重试（改由 loop 的 4×/120s 兜底），要么将 loop 的 `deadline_hit` 检查改为 **tokio::select 可抢占**（在单次 `provider.chat()` 挂起时也能在 120s 到达时 abort，而非等其返回）。不允许存在任何一条网络请求路径绕开 120s 上限。
3. 确认 `TOTAL_RETRY_CAP=120s` 与任务级 `deadline_exceeded()` 的层级关系（前者管"单次 LLM 调用重试总时长"，后者管"整个任务"）；修复后当单次调用累计超过 120s，必须有明确"提前终止本次调用、把控制权交还上层 loop"的动作，而非让嵌套重试叠加到外部超时介入。

**验收·正面**：正常的、可重试的错误（如短暂网络抖动）依然能在合理次数内重试成功。
**验收·负面**：人为构造一个会持续返回"解码失败"响应的 mock provider，断言：重试在 120 秒内停止，并把控制权交还给上层 loop（产生一个明确的 `retry_cap_exceeded` 或类似的终态，而不是无限重试直到进程被外部杀死）。

## T3 · LLM 网关对"响应体解码失败"的错误分类与快速失败

**现状**：B04/B06 的根因被归类为"后端返回体无法解码，客户端重试退避直至超时"。这类错误和"网络暂时抖动"性质完全不同——**一个响应体解码失败，大概率不会因为多重试几次就突然能解码成功**（除非是网络传输中截断导致的偶发损坏，这种情况值得重试；但如果是 provider 返回了一个 schema 不兼容的响应体，重试只会一直失败）。当前显然把这类错误当成了"可重试的暂时性错误"来处理。

**动作**：
1. 参照之前已经确认存在的 T2(错误分类) 机制——`llm-openai/lib.rs` 里有"429→Transient / 5xx→Fatal / 4xx→Param"这套分类——确认"响应体解码失败"这个错误目前被归到了哪一类。如果归到了 Transient（可重试），需要重新评估：至少应该设置一个远低于 120 秒的、专门针对"连续解码失败"的独立短退避上限（比如连续 3 次解码失败就应该判定为"这个响应格式本身有问题，不是网络抖动"，转为 Fatal，快速失败并触发 FallbackChain 切换到备用 provider，而不是在同一个 provider 上反复重试同一个格式问题）。
2. 【评审修订 v1.1】把导致失败的原始响应体/错误内容记录下来（T1 已要求留存），先**确认失败层级**：B04/B06 的真实错误串 `read body: error decoding response body` 来自 `llm-openai/lib.rs:342-345` 的 **HTTP body 读取失败**（传输层，**在 serde 反序列化运行之前**），并非严格反序列化失败。因此"改用宽松反序列化 / 去掉 `deny_unknown_fields`"这一思路**对 B04/B06 不适用**——全仓 grep 确认并无 `deny_unknown_fields` 宏。正确的修法：在 `llm-gateway/src/types.rs:215` 处，将 `read body: ...` 这类**传输层 body 读取失败**从 `Transient`（会触发最长 120s 重试）重新分类为**短上限快速失败**（如连续 2-3 次即转 `Fatal`/give_up，或设远低于 120s 的专用退避上限），因为它对同一畸形/断开的流体重试不会自愈；同时保留 T1 的"留存原始 body"动作以区分"传输中断"与"schema 不兼容"两类根因（后者若真出现，再考虑宽松解析）。

**验收·正面**：正常响应体解析不受影响。
**验收·负面**：构造一个 mock 响应，返回一个 Hearth 当前解析不了的畸形/新增字段的 JSON，断言：连续失败达到新设的短上限后，触发 Fatal 分类 + FallbackChain 切换（如果配置了备用 provider），而不是无限重试。

## T4 · Plan/Reflect 停滞检测与强制熔断

**现状（【评审修订 v1.1】已按源码校正）**：B03 卡在"Reflect → Plan"死循环，tail 显示反复出现 `◆ Reflect / continue / ▸ span [plan]`，直到 200 秒（外部 `timeout`）才被杀。**但"停滞检测"并非缺失**——`planner/src/lib.rs:459-508` 已实现多层停滞→GiveUp：`consecutive_errors>=3`、`budget_remaining==0`、`budget_fraction<=15% 且 steps_without_progress>=2`、以及 `steps_without_progress>=5 且 replan_count>=3`（replan 硬上限 3，`lib.rs:493-499`）。所以本任务真正的缺口不是"没有检测器"，而是**B03 的自旋为何没触发既有检测器**。最可能的原因有二：(a) 每轮自旋仍执行了至少一步"微进展"（如重新分解/调用工具），使 `steps_without_progress` 计数器反复归零；(b) LLM 反复返回 `continue`（而非 `replan`），使 `replan_count` 永不递增，于是 `replan_count>=3` 这道硬上限永不触发。两者都导致既有检测器在"宏观停滞、微观有动"的场景下失效。

**动作（【评审修订 v1.1】从"新增"改为"审计+补强"）**：
1. **先审计既有检测器为何未触发 B03**：结合 T1 留存日志，确认 B03 自旋期间 `steps_without_progress` 与 `replan_count` 的实际取值轨迹（是 (a) 每轮归零，还是 (b) `continue` 致 `replan_count` 不增），定位失效支路。
2. **补一个不随微进展重置的语义级停滞检测（作为既有检测的补充，而非重复）**：跟踪"连续 N 次（建议 N=3）replan / Reflect 循环之间，任务的可观测**语义状态**是否发生实质性变化"——例如对比相邻两次 Plan 的 TaskGraph 拓扑哈希、或 Observation 摘要哈希；若连续 N 次哈希稳定（即计划/状态原地踏步），无论单步是否"有动"，均判定为停滞，强制转入 give_up 终态（复用既有 `Giving up: budget exhausted` 干净收尾路径，触发条件从"步数/时间用尽或微进展缺失"扩展为"语义状态原地踏步"）。
3. 第 2 项的语义级停滞检测应当独立于 `deadline_exceeded()`——即使任务级 deadline 还没到，只要检测到停滞，也应该提前终止，不需要等到把宝贵的时间/步数预算全部耗尽在空转上。

**验收·正面**：正常的、每次 replan 确实带来进展的任务不受影响。
**验收·负面**：构造一个会持续判定"需要 replan"但每次新计划都和上一次实质等价的场景（可以用一个总是给出相同建议的 mock LLM 响应模拟），断言：在连续 N 次 replan 后被判定为停滞，提前 give_up，不会一直空转到步数或时间预算耗尽。

## T5 · 13-17 步收敛失败的共性排查

> **【更正注记 · 2026-08-29 执行窗口补】**：真实 tally = **0/10 干净完成**（非"3 挂起 + 7 失败"中的口径——B02/B08/B09 被遥测 runner 以 rc=0 误标 SUCCESS，report 实为 Task failed，见 `incidents/2026-08-28-tier3/README.md` 映射表）。13-17 步聚集的根因（EC-03 同源复现证实）= **cgroup fail-closed 在无 delegation VM 打死全部 bash/write 工具** + give_up 预算落点叠加——非隐藏阈值。后续文档引用本节时以本注记为准。

**现状（【评审修订 v1.1】补充更可能的解释）**：7 例 `task_failed` 全部停在 13-17 步这个区间，不是随机分布在 1-40 步之间。这个聚集值得深挖，但评审窗口 grep 发现**存在更平淡的解释**：`codex-cli/src/lib.rs:664` 注释明确写道「REPL 中等任务 16-20 步就 give up（真机日志 "Giving up after 16 steps"）」，`tools-builtin/src/bash.rs:144` 也提到「10-run 实录 9/10 budget exhausted」。即 **13-17 步可能就是现有 give_up 预算（40 步上限 + 各道停滞/低预算检测器）的自然落点**，未必是某个隐藏阈值。候选根因需并列考虑：(a) 正常 give_up 预算落点（最可能）；(b) 上下文压缩在该步数附近触发导致行为变化；(c) 某类工具调用在此时密集出现 429/超时；(d) planner 内部计数器特殊行为。排查时先验证 (a)，避免牵强附会一个不成立的根因。

**动作**：结合 T1 留存的完整日志，对比这 7 次失败在 13-17 步这个区间分别发生了什么（是不是都恰好在这个区间触发了压缩、是不是都在这个区间开始密集调用某个特定工具、是不是这个区间对应某个隐藏的软上限）。如果找到共性根因，按根因单独处理；如果排查后发现只是巧合（样本量小，10 次里 7 次聚集在 4 步区间也可能是偶然），如实记录"未发现结构性关联，可能是样本量不足导致的巧合，建议后续更大样本量复测"，不要为了给出结论而牵强附会一个不成立的根因。

**验收·正面**：无强制正面用例（本任务是排查性质，视排查结果决定是否需要后续修复任务）。
**验收·负面**：如果找到了具体阈值根因，需要针对那个阈值构造对照实验予以证实（比如如果怀疑是压缩触发导致，构造一个刻意在第 13-17 步触发压缩的场景，看是否复现同样的失败模式）。

## T6 · 长程任务回归测试集，纳入自动化门禁

**现状**：这次的关键发现完全来自一次性的手工遥测脚本，不在任何自动化门禁里。如果 T2-T4 修复后不把"长程自主任务"这个场景固化成可重复运行的自动化测试，下次回归可能又要等到下一次手工遥测才能发现。

## T8 · 遥测 runner 脚本自身健壮性加固

**现状**：这次的遥测过程中，脚本一度把 `--budget` 参数错误地传给了 `resume <ID>`，导致 10 次 resume 全部误报失败，好在被及时发现并如实披露、重跑后拿到了正确结果。这类"测量工具本身的 bug 污染了测量结果"的情况，如果下次没被及时发现，可能会把一个假阳性的故障率当真结论汇报上去。

**验收·正面**：加固后的 runner 脚本跑出的结果与本次人工修正后的结果一致。
**验收·负面**：故意在 runner 脚本里重新引入一个类似的参数错误，确认自检机制能在跑批前捕捉到，而不是跑完 10 轮之后才发现全军覆没。
