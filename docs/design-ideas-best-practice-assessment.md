## 1. 业界最佳实践（联网调研）

### 1.1 上下文管理

| 实践 | 要点 | 来源 |
|---|---|---|
| **锚定式增量摘要**（Anchored Iterative Summarization） | **不要重新生成全量摘要**——只摘要"本次被淘汰的那一小段"，再**合并进持久锚点状态**。锚点四字段：**intent / changes made / decisions taken / next steps**。评测分数 **4.04**（Anthropic 3.74、OpenAI 3.43），在保留文件路径、错误报文等技术细节上最优 | Factory（36,000 条真实工程会话） |
| **上下文坍缩（Context Collapse）** | 反复重写上下文 → 每代更简略 → 丢领域细节。**修法：结构化条目化 + 增量追加，而非整体重写** | ACE，ICLR 2026 |
| **微压缩优先（Microcompaction）** | **先清除陈旧工具结果**，再谈摘要。工具输出压缩比 **10:1–20:1**，且"最安全"（旧结果极少被再引用） | Claude Code |
| **压缩阈值** | 业界建议 **60%**（不是 95%）；实际各家：Gemini 50%、Claude ~89%、Codex ~90%、Pi 92%、OpenCode 96–99%。**早压 = 损失小但频繁；晚压 = 少但灾难性** | 七款 agent 横评 |
| **保护区 / 压后恢复** | OpenCode 保护最近 **40k tokens**；Codex 保留最近用户消息至 **20k tokens**（assistant 与 tool_result 正文不保）；Claude 压后**重读 5 个最近文件 + CLAUDE.md** | 各家实现 |
| **钉住不变式** | 任务规格、约束、约定**必须永存**，不能指望它在摘要里活下来 → 外置到 `CLAUDE.md`/`AGENTS.md` 每轮重读 | Claude Code / Codex 共识 |
| **可逆压缩** | OpenHands 用**事件源**：append-only 日志 + 抑制标记（不删除），可完整重放、可审计 | OpenHands |
| **卸载到文件 / 结构化笔记** | 让 agent 把推理写入持久笔记再读回——被称为"**长程 agent 最可靠的单项升级**" | 业界共识 |
| **工具级即时检索** | 给 agent 一个检索工具让它按需取，而非每轮都塞 RAG 结果 | 共识 |
| **工具按阶段限定** | 每阶段只暴露相关工具，**5–8 个上限**；工具定义本身也占预算 | 共识 |

**两个关键数据**
- **context drift（上下文漂移）比上下文耗尽更致命**：2025 年约 **65%** 的企业 AI 失败归因于多步推理中的上下文漂移/记忆丢失，**而非**窗口耗尽。→ **这直接印证 RC5/W5 该升优先级。**
- **context rot**：输入从 20k 涨到 120k tokens，任务完成率下降约 **28%**（信息不变的情况下）。→ 窗口不是越大越好，**保持小而高信号**才是关键。

### 1.2 推理与规划

| 实践 | 要点 |
|---|---|
| **显式规划是 >5–6 次工具调用任务的解** | Claude Code 与 Codex **独立收敛**到同一结论："非结构化 agent 循环在需要 5–6 次以上工具调用的任务上退化，显式规划是解法" |
| **但"什么都规划"是反模式** | 仅在**真正多步**任务上用；小任务加规划=纯开销。计划须**随理解更新**，并**保持在上下文中可见** |
| **⭐ CogRouter（ICML 2026）——正是 I-1 设想** | 步级认知深度四层：**L1 本能 / L2 态势感知 / L3 经验整合 / L4 战略规划**。行为模式：**任务起点用 L4 定目标 → 常规动作回落 L1 → 遇障碍升 L3**。成绩：ScienceWorld **72.0%**（o3 54.0%、GPT-4o 22.5%），且**token 少 62%**。路由靠**模型自身置信度**（深思考若不提高下一步置信度就用轻路径） |
| **现代推理模型已内化 CoT** | 不必再提示"一步步想"；但**显式规划与反思对长程工具任务仍有价值**——它提供模型自己不维持的结构 |
| **思考的"内容"比"数量"重要** | Claude Code 把思考预算**定向**到：选哪个工具、参数是什么、可能出什么错。**比泛化 CoT 更有效** |
| **先探索、再规划、再实现** | Anthropic 官方：把研究/规划与实现分离，避免解决错误的问题（plan mode） |
| **/goal 工作流** | 设**可验证终止条件**再让 agent 跑；关键是目标必须能回答"**done 长什么样**"；且**先规划再 /goal** 效果最好 |
| **反模式** | 反思剧场（叙述但不改进行为）／计划僵化／失败死循环／过度深思 |
| **12-Factor Agents** | 掌控你的 prompt、掌控你的上下文窗口、掌控你的控制流 |

## 2. 逐条评估我们的设想

### I-1 · 显式 / 隐式推理自适应 —— ✅ 方向正确，有强研究支撑，但有前提

- **业界已经把它做出来了**：CogRouter 就是这个设想，且效果显著（+18pt 准确率、**-62% token**）。你的直觉是对的。
- **但它的前提是"知道当前这一步该用多深"**。Hearth 目前的路由器（`classify_user_input` loop.rs:324-378）连"这是不是一个任务"都判不准（RC39），更别说判"该多深"。
- **可行性**：CogRouter 的置信度路由依赖 logprobs，OpenAI 兼容接口未必稳定暴露 → **Hearth 应先用低成本方案**：按**任务类型（已有 `goal_requires_product`, loop.rs:167）+ 预估步数 + 是否失败重试**三档调度深度，不追求置信度路由。
- **建议做法**：三档即可——① 问询/QA：0 次额外推理，直答（覆盖 65% 轮次）；② 中等任务：单次定向规划（现状）；③ 多步/已失败 ≥1 次的任务：加一次**计划前定向推理**。

### I-2 · 多轮推理 —— ⚠️ 部分成立，但不是当前瓶颈；建议换一种形态

- **业界支持它是有条件的**：只在"真正多步"任务上有效；且明确把"什么都规划"列为反模式。
- **我们的数据不支持它是当前瓶颈**：成功轮中位 **2 步**、65–73% 在 1–2 步完成、**几乎不动工具**；失败轮 10–15 步、bash 70%、give_up 88%。失败集中在"**被误判成任务的对话**"（元访谈成功率仅 61%），而非"推理不够深的任务"。
- **⚠️ 还有一个反效果**：多轮推理会**大幅增加上下文消耗** → 更快撞压缩阈值 → 压得更狠 → 忘得更多（与 RC5 叠加会恶化）。
- **建议换成"决策点定向推理"**（业界"思考的内容比数量重要"）：Hearth **已有两处钩子**——`check_goal_drift`（完成点，loop.rs:970-999）、`reflect`（失败点）。补齐**起点**那一处即可：**分解前先问一次"这是什么类型的任务 / done 长什么样 / 需要几步"**。
  → 比"计划前三轮泛化推理"**更便宜、更准、且直接对症 RC43（判据与任务类型错配）**。

### I-3 · 上下文压缩机制 —— ✅ 与你的方案③一致，但我发现了一个更前置的问题

- **你的方案③（保留近几轮全量 + 更早压缩 + 历史检索）与业界共识吻合**：钉住不变式（近几轮全量）+ 压缩远端 + 按需检索。而且 Hearth **已经具备一半基础**：
  - `archive_compacted_turns`（context.rs:192-193）**已把原始轮次落盘到会话级 JSONL** → 这就是 OpenHands"可逆压缩"的雏形，只差一个检索工具；
  - R2-C 的 Continuity/Topology（loop.rs:3393 一带）**已是"钉住的不变式"**（原目标/已完成/剩余/下一步）。
- **⚠️ 但三个方案都漏了一个更前置的问题**——见 §3.1：**阈值本身是遗留常数**，导致压缩在真实容量的很小比例处就疯狂触发。不先修这个，换哪种压缩策略都会继续"高频失忆"。
- **还缺业界共识的一条**：摘要要**增量合并**（锚定式），不能像现在这样每次重新生成（`summarize_turn` context.rs:299-365 是纯规则 60 字模板，既非 LLM 也非增量）。**这一条比"何时压"更关键**——即我此前的"A（何时压）/ B（压成什么）之分"，业界数据同样支持 **B 更重要**（ACE 的上下文坍缩正是 B 层问题）。

### I-4 · 隐藏式系统提示词 —— ❌ 业界做法相反

- 业界做法是**把持久约束显式外置到项目文件**（`CLAUDE.md`/`AGENTS.md`）并**每轮重读**，而不是隐藏注入内容。
- 理由正是：**摘要必然有损**（"Compaction summaries are lossy by design"），所以安全规则、编码标准、项目约定必须**活在持久文件里**，而不是指望它在上下文里存活。
- Hearth 若做：应做**"约束外置 + 每轮重读"**（等价物），而非把注入文本藏起来。**隐藏会损失可审计性**（本轮 RC40 就是靠注入文本可见才发现的）。
- **结论：不建议 I-4 原方案；建议改为业界标准做法（外置 + 重读）。**

### I-6 · 模型能力自发现（用户新增："输入 base URL + api key 后应自动识别，而非手工维护"）

**用户原话**（2026-08-30）：「像上下文窗口，可用模型，在输入 base URL、api key 以后需要能自己识别，而不是手工维护」

**现状核实（源码）**：⚠️ **没有任何客户端侧的发现逻辑**——`grep "/v1/models"` 仅命中 Hearth **自己对外暴露**的服务端点（`service/src/routes.rs:407-408`），**没有查询上游 provider 的代码**。模型能力目前是**硬编码维护**的：
- `crates/llm-cn/src/lib.rs:412`：`max_context_tokens: Some(32_000)` ← 写死的旧模型数值，正是 §3.1 阈值的标定来源
- 各 provider 的 url/default model 也是配置表维护（RC18 已暴露"provider 与 url 不联动"的问题）

**业界做法**：OpenAI 兼容生态里没有统一的"能力清单"标准，实务上是**三段式**：
1. **模型列表**：GET `v1/models`（标准）。Agnes/DeepSeek/智谱/vLLM 大多支持；vLLM、llama.cpp 还会在返回里带 `max_model_len`。
2. **上下文窗口**：**标准 API 不提供** → ① 内置**已知模型表**（如 `agnes-2.5-flash → 512K`）作为快路径；② 表未命中时**实测探针**（用递增长度的上下文二分探测，直到报 context-length 错误），**只做一次并缓存**；③ 始终允许**手工覆盖**。
3. **其它能力位**：是否支持 function calling / 流式 / `reasoning_effort` / 视觉——可用探针请求或小样本试调用判定，同样缓存。

**可行性**：✅ 高。第 1、2 步成本低；探针（第 2 步②）会消耗一次长上下文调用，但**只在表未命中时执行一次并持久化**。
**建议做法**：
- 新建 `model_caps` 模块：`/v1/models` 拉取 → 已知模型表匹配 →（可选）探针 → 落盘缓存（含探测时间戳与来源标记：`listed / table / probed / manual`）
- 配置项：`HEARTH_CONTEXT_TOKENS`（手工覆盖，优先级最高）、`HEARTH_MODEL_CAPS_CACHE`
- **暴露给上下文层**：`COMPACT_CHAR_THRESHOLD` 改为 `window_tokens × 百分比`（默认 60%，业界建议值；Agnes 512K → 约 300K tokens 阈值，**压缩次数预期从 14–18 次降到 1–2 次**）
- **顺带收益**：自动发现可用模型后，可缓解 RC18（provider 与 url 不联动）——配置时直接给可选模型列表，而不是让用户手填。

**验收判据（建议）**：新增 `hearth models` 子命令，输出每个模型的 `context_tokens / 来源(listed|table|probed|manual) / 支持能力位`；断言 Agnes 512K 被正确识别为 512000 且来源可追溯。

### I-7 · 异议识别与提问交互改进（用户新增反馈："僵硬、问得不关键"）

**用户原话**（2026-08-30）：「目前的异议识别，与向用户提问的这块弹窗我觉得设计的不是特别好，感觉比较僵硬，提问的也不是特别的关键，或许多轮推理以后加入会变好，目前单轮推理做的不太好」

**现状核实（源码锚点）**
- `planner/lib.rs:15-16`：gap 契约——每条 gap 必带 `from`+`why`；`blocking=false ⇒ auto_assumed=true`（不打断，自行假设）
- `planner/lib.rs:45-50, 86-87, 154-155`：`ambiguous_option` → **blocking** 澄清，走"二选一实现"语义（产品红线"AI 不得问废话"）
- `planner/lib.rs:146`：注释自陈——英文任务描述里的并列 `or` 会造成 **50% 误触发**，已收紧
- `loop.rs:2113-2152`：blocking gap → `InteractionRequested{kind="clarification"}`，答案回写 scratch
- `render.rs:200-205`：以 `❓ 要问你 {from}: {why}` 内联呈现在规划草案里

**数据（本轮实测）**
| 现象 | 数据 |
|---|---|
| 待问=0 占比 | v0.2.8 **100%**（0/40）、v0.2.10 **94.3%**（82/87）→ 几乎从不提问 |
| 非阻塞假设噪音 | `missing_goal_source` 全语料 **1148 次 / 574 份草案**，且**每份草案渲染 ×2**（RC34）→ 满屏"假设[...]" |
| 用户提问的反向失效 | 8 次"你还记得吗"**全被转成 revision，0 次被回答**（RC36/α）→ 交互是单向的 |

**问题拆解（三处，性质不同）**
1. **问题质量低**：gap 由**规则**触发（"或/或"、"来源"等字面检测），只能问出表层歧义（"用 A 还是 B"），问不出**决策关键**（"范围边界在哪 / done 是什么 / 哪个约束优先"）。
2. **噪音掩盖信号**：非阻塞假设被反复渲染（×2），真正的 blocking 问题淹没在"假设[...]"里 → 观感"僵硬"。
3. **单向**：系统不问关键问题（1）+ 不回答用户的问题（α）→ 对话无法收敛。

**业界做法**
- **好问题需要前置探索**：Anthropic 官方"先探索 → 再规划 → 再实现"。没探索过就问，只能问出浅问题。
- **提问形态**：给出 **2–4 个具体选项 + 描述 + 推荐默认值**，可多选，允许 "Other"（Claude Code `AskUserQuestion` 模式）；**一次只问一个**；在**决策点**问，而不是开局连问。
  → Hearth 已有"每个 plan 最多一个 blocking 缺口"的约束（防连环澄清），**这一点已经做对了**，缺的是选项化与默认值。
- **降低噪音**：非阻塞假设应折叠（如 `假设×3（展开查看）`）或仅 verbose 模式显示。

**对用户的假设"多轮推理后会变好"的评估：机制上正确，但不必上多轮**
- ✅ **正确的部分**：问题的质量取决于"提问前想清楚没有"。单次直出规划时，agent 还没探索，自然问不出关键问题。**增加一次探索/推理，问题质量会显著提升。**
- ⚠️ **更便宜的解法**：不必上 N 轮泛化推理（成本高且撑大上下文），只要在**分解前加一次定向推理**（I-2'：这是什么任务 / done 长什么样 / **当前最不确定的一点是什么**），就足够生成"决策关键型"问题。
- ⚠️ **但还有两处不是推理能解决的**：噪音渲染（RC34）与单向失效（α/RC36）——这两处改了，即使推理轮数不变，观感也会明显改善。

**建议做法（按性价比）**
1. **降噪**：非阻塞假设折叠为一行（RC34，成本极低，立刻改善"僵硬"观感）
2. **选项化提问**：blocking 澄清改为「问题 + 2–4 选项 + 推荐默认 + Other」，沿用现有"每 plan 最多一个"约束
3. **决策点定向推理**（I-2'）作为问题质量的来源
4. **先修 α**（RC39），让用户的问题能被回答，交互才双向

**验收判据（建议）**：构造含真实歧义的任务，断言 ① 提问命中"决策关键点"（人工评分 ≥4/5）② 非阻塞假设渲染 ≤1 行 ③ 用户连续 3 次提问**不产生** GoalChanged 且被回答（A-36）。

## 3. ⭐ 更好的思路（比上述设想更前置 / 更高杠杆）

### 3.1 【最高杠杆】压缩阈值是遗留常数——字符制、固定 32k、与模型窗口无关

**源码锚点**
- `context.rs:169`：`COMPACT_CHAR_THRESHOLD: usize = 32_000` —— **字符**，不是 token
- `context.rs:174-181` `estimate_chars()`：`format!("{:?}", m.content).len()` —— 用 **Debug 格式化后的字符串长度**估算（与 RC6 同源：Debug 包装会虚增字符，`\n` 变两字符、引号等）
- `loop.rs:1071-1074`：`fill_pct = total_chars / 32_000 × 100` —— 这就是 RC40 的根因：**"上下文填充率"实际是"距压缩阈值的距离"**
- `crates/llm-cn/src/lib.rs:412`：`max_context_tokens: Some(32_000)` —— 阈值显然是按 **32k token 的老模型**（deepseek/llm-cn 时代）标定的

**问题**：切到 Agnes 之后，模型窗口若远大于 32k tokens，**32,000 字符 ≈ 12–25% 的真实容量**就触发压缩；叠加 Debug 格式化虚增，只会更早。
→ **这解释了单会话 14–18 次压缩、以及用户"怎么每轮都在压"的体感**（RC42）。
→ **也解释了为什么压缩后立刻失忆**：不是压得太狠，是**压得太早太频繁**。

**✅ 已实测确认（用户 2026-08-30 提供）：Agnes = 512K 上下文窗口，模型 `agnes-2.5-flash`。**

**重算**：32,000 字符 ≈ 21k–53k tokens（中文约 1–2 字符/token）→ **约为 512K 窗口的 4–10%**（即便按最宽松的 1:1 折算也仅 6%）。
→ **我们在真实容量不到十分之一、甚至是个位数百分比的地方就开始销毁上下文。**
→ 这解释了单会话 **14–18 次**压缩、用户"怎么每轮都在压"的体感（RC42）、以及压缩后立刻失忆（RC37）。
→ **注意：这不是"压得太狠"，是"压得太早太频繁"。**

**为什么这是最高杠杆**：改它**几乎零成本**（常量 → 按模型窗口百分比 + token 化计量），却直接把"破坏次数"降一个量级。**先做这个，再谈摘要质量**——少破坏优先于破坏得好看。

**⚠️ 但它有一个前置依赖**：要按百分比设阈值，就**必须先知道窗口多大** → 见 **I-6（模型能力自发现）**。两者应作为**同一批次**交付（先 I-6 后 3.1）。

### 3.2 微压缩优先（工具结果清除）

业界称**最便宜、最安全**的一档（10:1–20:1，旧结果极少被再引用）。Hearth 的 bash 输出很大（日志里满屏 `ls`/`find` 结果），**先清这些，能把压缩触发大幅推后**。
建议：对超过 N 轮的工具结果，只保留**结论摘要 + 引用指针**（文件/路径），原文留在归档里按需回读。

### 3.3 让"完成"可验证（产出物契约）

这是**业界共识**，且直接对应我们已有的 **D1 / RC43**：
- Anthropic 官方："**Give Claude a way to verify its work**"
- /goal 工作流：目标必须能回答 "**what does done look like**"
- 我们的数据：progress 只认写（loop.rs:3487-3495）与任务构成（写类仅 2.8%）严重错配 → 判据与任务类型不匹配是 give_up 88% 最深根因

**这条不是新想法，但它现在有了外部背书**——建议顶层在裁决 D1 时把这条业界共识纳入考量。

### 3.4 工具按阶段收敛（5–8 个上限）

业界明确：工具定义本身占预算，且过多工具会分散注意力、抬高错误率。Hearth 若始终全量暴露工具，可考虑按 PDCA 相位/任务类型裁剪。（与 RC25 读范围同族，可一并评估。）

### 3.5 卸载到文件（结构化笔记）

业界称"长程 agent 最可靠的单项升级"。Hearth 已有 `civ_note`/报告落盘等机制，可 formalized 为：**每 N 步把"目标/已完成/失败尝试/下一步"写进工作区文件，压缩后自动重读**。这与 3.1 的"钉住不变式"互补——**不变式放上下文，详细笔记放文件**。

| 项 | 可行性 | 成本 | 依赖 | 具体做法（锚点） | 验收判据 |
|---|---|---|---|---|---|
| **3.1 阈值修正** | ✅ 高 | **极低** | 需先测 Agnes 窗口 | `COMPACT_CHAR_THRESHOLD` → 改为**按模型窗口百分比 + token 计量**（或至少 chars/4 粗估），可配置；`estimate_chars` 去掉 Debug 包装 | B-7：真实长会话压缩次数 ≤ 5 次/会话；A-40 同步修（fill_pct 拆分） |
| **3.2 微压缩** | ✅ 高 | 低 | 无 | 新增工具结果老化策略：>N 轮只留结论+指针，原文入归档 | B-8：工具结果占上下文比例 ≤ 30% |
| **3.5 结构化笔记** | ✅ 高 | 低-中 | 无 | 每 N 步写 `intent/decisions/failed/next` 到工作区；压后重读 | A-5（≥8 轮后能复述第 1 轮事实） |
| **I-3 压缩（B 层：锚定式增量摘要）** | ✅ 中-高 | **中**（每次压缩 1 次 LLM 调用，非每轮） | 先做 3.1/3.2 | `summarize_turn` 改为：只摘要本次淘汰段 → 合并进持久锚点（intent/changes/decisions/next/**failed**） | A-5 + 新增：跨 3 次压缩后仍能答出首轮关键事实 |
| **I-3 检索** | ✅ 高 | 中 | 归档已存在 | 把 `archive_compacted_turns` 已落盘的 JSONL 暴露为 `archive_search` 工具 | A-5b：能检索并引用 3 轮前的细节 |
| **I-2' 决策点定向推理** | ✅ 中 | **低-中**（每个任务 1 次，非 N 次） | **α（RC39）先修** | 分解前加一次结构化提问："任务类型/done 长什么样/预估步数" | A-36 + A-5 + 复杂任务成功率 |
| **I-1 三档深度** | ✅ 中 | 中 | 同上 + 3.1 | 按类型/步数/失败次数选档 | B-1（问询 ≤2 步 0 工具仍成立）+ 复杂任务成功率 |
| **I-4 → 改为外置重读** | ✅ 高 | 低 | 无 | 约束外置到项目文件，每轮重读 | 约束在压缩后 100% 存活（可断言） |
| **I-5 修 RC24-B** | ✅ 高 | **极低** | 无 | 复测 TC-8b（`FS_FILE_ONLY` 已落） | B-5：introspect 零失败 |

**关于"成本红线"的重要说明**：代码里多处注释写着"不新增 LLM 分类调用——成本红线"（这是**每轮/每条消息**级别的限制）。
但上面的方案里，LLM 调用都是**每任务 1 次**（决策点推理）或**每压缩 1 次**（锚定式摘要）——**量级完全不同**。且 Agnes 配额为周 75,000 次。
**建议顶层重新审视这条红线的适用范围**：应从"禁止任何新增 LLM 调用"改为"**禁止每轮级的新增调用；任务级/压缩级允许，但需计量与上限**"。

## 5. 建议顺序（守门人意见，非裁决）

```
①  修 RC24-B（I-5 内观恢复可用，成本极低）
②  I-6 模型能力自发现（/v1/models + 已知表 + 探针 + 手工覆盖）
      ↑ 3.1 的前置依赖：不知道窗口就无法按百分比设阈值
③  3.1 阈值修正 —— 零成本、直接把压缩次数从 14-18 次/会话 降到 1-2 次   ← 最高杠杆
④  3.2 微压缩（工具结果清除）—— 便宜且安全，进一步推后压缩
⑤  α（RC39 输入分类）+ I-7①降噪 —— 修一根闭合三条 RC，且是所有推理/提问类改动的前提
⑥  I-7②提问选项化（问题 + 2-4 选项 + 推荐默认）—— 直接改善"僵硬"观感
⑦  I-3 B 层：锚定式增量摘要 + 3.5 结构化笔记（合并进 W5）
⑧  I-2' 决策点定向推理（起点那一次）+ 3.3 让"完成"可验证（D1/RC43）
      ↑ 同时是 I-7③（问题质量）的来源
⑨  I-1 三档深度（在 ⑤⑧ 验证有效后再上）
⑩  I-3 检索（archive_search）
⑪  I-4 → 改为"约束外置 + 每轮重读"（不做隐藏）
```

**取舍要点**：**先"少破坏"（3.1/3.2 减少压缩次数）→ 再"破坏得少"（锚定式增量摘要）→ 最后"能找回"（检索）**。这个顺序把成本最低、收益最直接的动作放在最前。
