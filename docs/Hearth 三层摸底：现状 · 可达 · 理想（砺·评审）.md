### 3.1 AS-IS 现状剖面：复核任务书四条 + 补全三条

#### 复核（两条成立、一条加强、一条部分推翻）

**J-1 · 结论不自标注 —— ✅ 成立，但定性需修正**

- 现象：run-001 报告（`手工测试v0.2.19.txt:250-362`）通篇无 INFERRED/VERIFIED 区分；被用户追问（`L465`）后才承认推断。
- 自白锚点：`L479` "你问到了关键点——我确实没有测试验证"；`L489-492` 逐条列出"我没有做什么"4 项；`L494` "我的结论是'推断'而非'验证'"。
- ⚠️ **定性修正（关键）**：这不是"无元认知能力"，而是**元认知被动化**。被追问时它能精确枚举自己没做什么（4 条，条条准确）——**能力存在，缺的是"主动内建标注"机制**。
- 这个区别对设计是决定性的：若为"没能力"，只能换模型（不可行）；若为"有能力但不主动"，则可做**输出层强制标注**（E2）——run-002 本身就是 E2 可行性的正面证据。
- 判级：**有骨架无校验**（骨架 = 模型能力，校验 = 输出层标注）。

**J-2 · 无代价感 —— ✅ 成立，且比任务书描述更严重**

- 现象：run-002 在 `.133` 评审 VM 上跑 `cargo build --release`（`L515`）。
- 三重问题叠加：

**J-3 · 读台账就信台账 —— ⚠️ 部分推翻（宪法第七条已覆盖）**

任务书原表述："'不信报告信源码'纪律未进 Hearth constitution"。

**实测推翻**：宪法**第七条「判断观：信任意图，验证断言（trust-but-verify）」已经完整写入并注入**（`constitution.md:38-41`）：
> "用户提供的'事实'…都是**默认待验证断言**——影响正确性的（load-bearing）断言在落地前必须至少核验一次…陈述事实性结论时带出处（provenance）；带不出出处就明确说'未验证'。"

且 **1430 字符 < 6000 上限，截断不触发，完整进 prompt**（见 A4）。

**修正后的定性**：不是"纪律没写"，而是三层脱节：
1. **写了但无机制护住**——无任何组件检查 agent 是否遵守第七条；
2. **写了但可能没送到**——FALLBACK 路径会静默丢掉第七/八条（`constitution.rs:25-38`）；
3. **具体纪律的操作化缺失**——"台账是断言不是事实"这一条**具体场景**未显式化（第七条讲的是"用户提供的事实"，未涵盖"系统自己上一轮写的台账"）。

→ 这恰恰是**"有骨架无校验"的教科书案例**，也是 E3（D10 落地）的立论基础。
