# Hearth 可用性对标诊断：为什么不如 Codex / Claude Code / WorkBuddy

> 分析性质：只读源码 + 手工测试日志交叉验证。**未改动 `crates/` 任何代码**（用户指令"只分析不执行"）。
> 关联缺陷清单：`docs/core-issues-summary-v0222.md`（P0-α/β/δ/ε/ζ、P1-7/P1-8）。

## 0. 结论先行（一句话）

Hearth 的**架构质量并不差**——六相状态机、预算闸门、沙箱、stuck/goal-drift 检测都是真资产。真正的体感差距来自**"智能体与用户的契约层"错配**：它把一次任务切成了"每步都要过栅栏的批处理流水线"，而竞品是"模型在单轮内边看结果边反应"的对话式循环。架构是护栏，被你用成了每步的减速带。

## 1. 竞品的对标契约（Hearth 缺什么）

| 能力 | Claude Code / Codex CLI / WorkBuddy | Hearth 现状（源码实证） |
|---|---|---|
| 推理模型 | **react-interleaved**：单轮内 工具调用→看结果→再调用→…→给最终答案，模型可连续做多个动作 | **plan-execute-gated**：每周期 1 次 LLM 调用（Plan），模型"盲规划"一批动作，执行后必须走 Observe/Reflect 才能再推理 |
| 完成的形态 | **文本回答即交付物**（"解释一下 X" 直接 Done） | "NEVER text, ONLY tool_calls"（loop.rs:2214）；产物类目标必须 `write_file` + 构建绿才 Done |
| 失败恢复 | 工具报错→**同轮换方案重试**，不轻易放弃 | 任何错误/卡死→`give_up`（loop.rs:2820）；无同轮恢复路径 |
| 进度可感 | 流式可读叙事（做了什么、为什么） | "✓ Done (N steps)" 计数，无解释（测试日志 v0.2.23:1276/1331-1358） |
| Unicode 健壮性 | 中文补丁/长文本稳健 | 中文长 search 块 `&search[..80]` 字节切片 panic（patch.rs:127/135/145，P0-ζ） |

## 2. 五层病灶（由深到浅，源码锚点）

### L0 推理模型错配（最根本，决定"笨不笨/卡不卡"）
- `loop.rs:3159` 是 Plan 阶段唯一 `provider.chat` 出口；响应 `tool_calls` 存入 `pending_tool_calls`（`loop.rs:3271`）后交 Act 执行。
- 即：**每个推理周期 = 1 次 LLM 调用**，且这一次调用必须在"看不到工具结果"的前提下把本周期所有动作规划好。
- 模型无法"看一眼结果立刻改主意"——每动一步就被 Observe/Reflect 栅栏拦下，下一轮推理要重新带全量历史进 Plan。
- 代价：N 个动作 = N 次往返 + N 次全量历史的 Plan 调用（延迟与 token 双高）；模型丧失原生的"链式反应"能力。
- 竞品把这一步留给模型自己在一个 turn 内完成，harness 只在旁做护栏。

### L1 完成语义错配（决定"做不做得出有用的事"）
- 系统提示 `loop.rs:2206-2214`："You are a coding agent that ONLY uses tool_calls (NEVER text)."
- 完成判定：`goal_requires_product(goal)` 为真时（loop.rs:3291），纯文本回答不算 Done，强制 replan/写文件；纯读类任务反复注入"You MUST call write_file… build is green"（loop.rs:3366-3371），直到预算耗尽才诚实失败。
- 后果：**任何"分析/解释/汇报/问答"类任务，在默认 coding-agent 契约下要么被逼写文件、要么耗尽预算 give_up**。这正是测试日志里"✓ Done 不知做了什么""报错就 give_up"的体感来源（P0-α/δ）。

### L2 失败即放弃（决定"靠不靠得住"）
- T4 卡死检测有恢复逻辑（loop.rs:2700-2827，三层级），但**终止出口散落**：Plan 臂 `Err`(loop.rs:2820)、Reflect 臂、预算臂各自 return；RC52 回填在 Plan 臂(2816)与 Reflect 臂重复（P1-8）。
- 工具/LLM 一报错，默认路径是 `give_up` 而非"同轮换方案重试"。测试日志 v0.2.23:2289/2451："报错就 give_up 而不是重新思考新方案"。

### L3 感知黑箱（决定"信不信得过"）
- 进度只报步数（P0-δ）；中文补丁 panic（P0-ζ）让工具在你最常用中文场景崩；`call./done./glob.` 被误判写目标（P1-7）制造噪音告警。

### L4 prompt 契约过窄（决定"像不像个助手"）
- "NEVER text" 把模型锁成工具型人格，连"先解释再动手"都做不到；对话式任务体验生硬。

## 3. 根因层级：哪一层卡住哪类任务

```
L0 推理模型  ──► 所有任务都"慢/笨/卡"（延迟 + 失去链式反应）
L1 完成语义  ──► 非写类任务"做不出有用结果 / 乱写文件"
L2 失败恢复  ──► 遇错任务"直接放弃"
L3 感知黑箱  ──► 所有任务"看不懂 / 不信任"
L4 prompt    ──► 对话类任务"不像助手"
```

## 4. 最高杠杆修复（按"体感提升 / 改动量"排序）

1. **#1 把六相状态机从"每步栅栏"降级为"护栏"**：允许模型在单轮内连续 emit 多个 tool_use 并消费结果，Observe/Reflect 改为可选守卫（预算/安全/goal-drift 仍为硬闸）。这是唯一能直接追平 Claude Code"流畅感"的改动。
2. **#2 完成语义补"交付物 = 答案"分支**：`goal_requires_product` 误判时允许以文本回答 Done；对非写类目标移除 write_file 强制。
3. **#3 同轮失败恢复**：工具/LLM 报错不直接 give_up，先在同轮换方案重试（竞品默认行为）。
4. **#4 可读进度叙事**：把步数换成"刚做了 X / 因为 Y / 下一步 Z"。
5. **#5 Unicode 稳健 + 消噪**：修 patch.rs:127/135/145 字节切片；收紧 P1-7 扩展名过滤。

> 改动量评估：#1 架构级（最大），#2/#3 中等（逻辑层），#4/#5 小（展示/鲁棒性）。但 **#4/#5 当天可做且立刻提振信任**；#1 是"追平竞品"的必要项。

## 5. 反驳"架构白搭"

架构没有白搭。要改的不是架构，是**架构对外暴露的契约**：
- **保留**：六相可观测性、预算闸门、沙箱、stuck/goal-drift 检测——这些是竞品也想要的护城河。
- **改**：把这些从"每步必须过的栅栏"变成"异常才触发的护栏"，并把"单轮连续反应"还给模型。
- 一句话：**把状态机从"导演"改成"监理"**——模型自己导，监理只在越界时叫停。
