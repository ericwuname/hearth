## 一、缺陷（同一函数内两个，都是既有缺陷类）

```rust
let fut = tokio::process::Command::new(program).args(args).output();
match tokio::time::timeout(Duration::from_secs(timeout_secs), fut).await { … }
```

| # | 缺陷 | 机理 |
|---|---|---|
| 1 | **超时不收尸** | `Command::output()` 的 `kill_on_drop` **默认 `false`**（tokio 源码 `Command::output → self.spawn() → wait_with_output`）。`timeout` 触发时只是**丢掉 future**，子进程**不被杀** |
| 2 | **输出无界** | `wait_with_output` 内部两个 `read_to_end` 无上限——与 D-18 / D-21 / D-29 / D-31 同类 |

缺陷 1 的后果很具体：**`cargo check` 超时（本函数给它 180s）后继续在后台跑**，
连同它派生的 **rustc** —— 既吃 CPU，又占着 `target/` 目录锁，
而调用方已经拿到"检查超时"的结论走人（后续构建还会因为锁被占而卡住）。

## 二、修复

`spawn` → 两路**有界并行排空** → 超时则**杀整棵进程树** + **有界收割**：

```rust
cmd.… .kill_on_drop(true);                 // 兜底：任务被 abort 也终止直接子进程
let mut child = cmd.spawn()?;
let pid = child.id();
let timed = timeout(…, async { join!(drain_capped(stdout), drain_capped(stderr), child.wait()) }).await;
match timed {
    Ok(((out,o_t),(err,e_t), Ok(status))) => { /* 摘要，截断留痕放在**开头** */ }
    Ok((_, _, Err(e))) => (false, format!("{program} 执行失败: {e}")),
    Err(_) => {
        if kill_check_process_tree(pid) { … } else { let _ = child.start_kill(); }
        let _ = timeout(2s, child.wait()).await;     // 有界收割
        (false, format!("检查超时（{timeout_secs}s）"))
    }
}
```

三个刻意的设计点：

1. **截断留痕放在摘要「开头」而非末尾** —— `self_check_html` 依赖脚本约定
   "**末行**是 JSON"，把留痕追加到末尾会破坏它；放开头则 `lines().rev()` 仍能看到 JSON。
2. **树杀**（Windows `taskkill /T /F`）——`Child::kill` 只到直接子进程，`cargo check`
   派生的 **rustc** 会成孤儿（与 D-20 同型）。
3. **有界收割** `timeout(2s, child.wait())`——见第五节，这是**红检过程中抓出来的**。

## 五、红检意外收获：我自己差点引入一个新的挂起源

第一版修复里，超时分支写的是 **`let _ = child.wait().await;`**（无条件等子进程结束）。

- 正常情况：kill 生效 → `wait()` 毫秒返回，看不出问题；
- 但**红检第一次跑出来是"通过"**——因为 `child.wait()` 一直等到 `ping -n 5` **自然跑完**
  （≈4 秒）才返回，等函数返回时进程早就自己退了。**测试被"等待"掩盖了。**

顺着这条线看下去就发现真正的风险：**如果 kill 没生效（perm/环境异常），
`wait()` 会把调用方无限期挂住——"超时保护"自己变成了新的挂起源。**

修法：`timeout(2s, child.wait())` 有界收割，并同步把红检改成"完全不收尸"的忠实模拟
（第一次红检其实是**假红**——它只断了 `taskkill`，`start_kill` 仍在收尸，所以被测行为没被还原）。

**教训**：**"红检没红"有两种可能——① 修复无效，② 红检没真的还原旧行为。**
必须像读生产代码一样读自己的红检。
