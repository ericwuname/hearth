# Hearth Harness 务实补全设计（瘦身版）

> 版本：v0.2（规划稿）　|　日期：2026-08-22　|　适用：hearth v0.1.x → v0.2
> 受众：hearth 开发设计团队　|　目标：用**最小工程代价**让 hearth 从"演示级"跨入"单人稳定生产级"
>
> 本文是 `hearth-harness-improvement-design.md`（原稿 v0.1）的**修正版**。原稿诊断框架正确，但治疗方案严重超前（按 Codex 完整生产级运行时估算 5-10 万行），与当前"贪吃蛇都跑不完"的现状错配。本版把它拉回地面。

---

## 1. 结论先行（修正版）

hearth 与 Codex CLI 的差距，**不在 Agent Loop，而在 Loop 之外的 Harness 工程厚度**——这个诊断**认同**。

但"补 Harness" ≠ "照 Codex 重写一套生产级运行时"。当前真机崩的三个现象，**没有一个需要 ThreadStore / App Server / 跨平台沙箱**。它们是：
- **超长输出接不住**（write_file 截断 / missing path / missing content）—— 几百行参数容错 + 流式累积可解；
- **供应商传输层脆弱**（deepseek read body 失败盲目重试 6 次卡死）—— 几百行重试/降级可解；
- **自报完成但产物未必可用**（无确定性验证）—— 轻量校验钩子可解。

**原稿把"补丁级 bug"拔高成"架构级重构"，本版纠正。**

> 💡 一句话：**发动机够用，底盘漏了三颗螺丝。先拧紧螺丝，别急着换整车。**

## 2. 概念澄清：Agent Loop vs. Harness（保留）

| 维度 | Agent Loop | Harness |
|---|---|---|
| 关注范围 | 循环执行逻辑 | 完整运行系统 |
| 工具调用 | 决定何时调用 | 注册、执行、限制、**记录** |
| 上下文 | 消费并更新 | 构造、裁剪、**压缩**、持久化 |
| 权限沙箱 | 通常不直接负责 | 通常负责 |
| 错误处理 | 决定是否继续 | 提供超时、重试、**恢复和降级** |

**hearth 现状**：四阶段显式 Loop（Plan→Act→Observe→Reflect）+ EnvelopedEvent + Gap 三元组**已优于 Codex 黑盒**，必须保留。缺的是 Harness 的"车身与安全系统"——但只缺**当前跑不稳所必需的几块**，不是全部。

## 3. 差距分层：必做 vs 后置（核心修正）

原稿列了六块 P0/P1。本版按"**是否关乎当前单人稳定输出**"重排，并标注代码量现实：

### 3.1 必做（v0.1.2 已派 / 即将派）

| 能力 | 对应真机问题 | 最小修复 | 代码量 |
|---|---|---|---|
| 超长输出抗截断 | write_file 截断 / missing path/content | 参数容错全字段覆盖（path+content+pattern）+ 流式累积 + max_tokens 上调 | 数百行（v0.1.2 P0-A 已覆盖 content） |
| 供应商传输降级 | 象棋 read body 失败 6 次卡死 245s | 非流式改 SSE 流式累积 + 传输错误短退避/fail-fast | 数百行（v0.1.2 P0-B 已覆盖） |
| 错误分类框架（轻量） | 盲目重试同请求仍失败 | 错误分"瞬时/参数/不可恢复"三级，分别 retry/replan/give_up | ~1-2k 行（v0.2 任务书） |

### 3.2 强烈建议下一站（v0.2 核心）：确定性验证层

**问题**：agent 自报"完成"即结束，无 per-step 验证。文件写出后不验证产物是否真可用（如游戏能否运行、代码能否编译）。这是"自报完成实则没跑通"的直接根因。

**目标行为（轻量版，单人场景）**：
- 每个**写盘类工具**（write_file / edit / bash 落盘）执行后，调度器自动追加一次**产物校验**：
  - 文件类：`ls -la <path>` 确认存在 + 字节数 > 0 + 扩展名匹配。
  - 代码类（可选增强）：若写出 `.rs`/`.py`/`.html`，跑对应 `cargo check` / `python -c "compile(...)"` / 简单 DOM 解析，失败则回喂错误让 loop replan。
- 校验结果作为**结构化事件**进入 EnvelopedEvent 流（BE 给语义"verify:pass/fail"，FE 给颜色），不破坏事实产生权。

**代码量**：~2-3k 行（不含各语言 checker 的穷举，先做文件存在性 + 字节数 + 一种语言起步）。

**为何放 v0.2 而非现在**：v0.1.2 先把"能写出完整文件"修好，否则验证层会一直报 fail（地基没稳就装警报器没意义）。

### 3.3 坚决后置（v1.0+ 再说，不进 v0.2 排期）

以下内容**原稿列为 P0/P1，本版判定为超前基建**，理由写在右侧：

| 原稿能力 | 原估代码量 | 后置理由 |
|---|---|---|
| ThreadStore（会话持久化/resume/fork） | 10-20k | 单人一次性 chat/repl，进程挂了重跑即可，**不需要断点续跑**；多用户云端才必需 |
| App Server（JSON-RPC 长驻进程） | 8-15k | 当前 CLI 直跑足够；为"像 Codex"硬加长驻进程与 §7 原则 3"先稳定后平台"矛盾 |
| 上下文压缩 Compaction | 8-15k | **当前非瓶颈**。真机崩的是单轮超长输出（LLM 侧 max_tokens），不是百轮 context rot。等出现"百轮任务注意力衰减"实测再补 |
| 跨平台沙箱（macOS/Windows） | 5-10k | 用户明确"主要 Linux VM 用"，单人场景无需 |
| MCP Server | 3-5k | 生态接入，非稳定输出必需 |
| Skills / Hooks 框架 | 5-10k | 社区扩展，非稳定输出必需 |
| 可观测性（trace/metrics/replay） | 3-6k | 有价值但可先用现有 WARN/ERROR 日志 + 本次已加的 commit 版本号过渡；等错误率降下来再系统化 |

## 6. 分阶段方案（修正版）

### 阶段一：堵住"跑不完"（v0.1.2，已派发）
- 超长输出抗截断（参数容错全字段 + 流式累积）
- 供应商传输降级（SSE + 短退避/fail-fast）
- cgroup 日志降级
- **验收**：用同款 5 游戏任务重跑，能写出首个文件、不再 missing path/content 连撞、象棋不再 245s 卡死。

### 阶段二：让"完成"可信（v0.2，建议下一站）
- **确定性验证层**：写盘类工具执行后自动校验产物（存在性/字节数/可选编译），失败回喂 loop replan。
- **轻量错误分类**：瞬时/参数/不可恢复三级，分别 retry/replan/give_up，替代"盲目重试 6 次"。
- **验收**：贪吃蛇/象棋任务自报完成后，`~/snake_game` 下 index.html+style.css+game.js 三文件齐全且能 `python -m http.server` 打开；中途单步失败能被验证层捕获并 replan，而非自报成功。

### 阶段三（后置，不排期）：平台化
- 上下文压缩、ThreadStore（若单人出现长任务断点需求）、可观测性系统化、跨平台沙箱、MCP、Skills。
- **触发条件**：单人日常用 v0.2 数月无意外，且出现明确的多任务/多用户/长驻需求。

## 7. 设计原则（保留并强化）

1. **保留白盒灵魂**：四阶段状态机 + EnvelopedEvent + PlanDraft 前置 + Gap 三元组是差异化优势，**不得为像 Codex 改回黑盒**。
2. **Loop 不改，补 Harness**：阶段一/二不重构 Loop。
3. **先稳定后平台**：当前只做"跑得完 + 完成可信"，ThreadStore/App Server 等平台化基建**坚决后置**，任何"顺手做"都稀释稳定性目标。
4. **对抗过度设计**：每个新增能力必须回答"它解决当前哪个真机崩溃现象"，答不出就不做。
5. **验收以长任务产物完整性为准**：不以 `cargo build` 通过为判据，以贪吃蛇/象棋能否完整落盘且可运行为准。
