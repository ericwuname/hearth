## 2. 两个新发现（源码实锤）

### 2.1 【A1】read-body 失败与 **deepseek 通道**强相关——不是"修好后复发"

日志里的错误完全一致：`plan chat failed … error=transient provider error: read body: error decoding response body retries=N class=Transient deadline_hit=true`

但关键在于**各次测试实际跑的是哪个通道**（用运行时 `provider=` 标签核验，而非命令里的提及次数）：

| 日志 | `provider=` 运行时标签 | read-body 次数 |
|---|---|---|
| v0.1.5 | `deepseek` ×5 | **24** |
| v0.2.3 | `deepseek` ×5 | **12** |
| v0.2.4 | **`openai` ×8（无 deepseek）** | **0** |
| v0.2.5 | 无 tag（不可判定） | 0 |
| **v0.2.8 遥测（本轮）** | `deepseek` | **复发（B04/B06）** |

→ **更可能的解释：这是 deepseek 通道的特有问题**（出现在每次 deepseek 运行期，在 openai 运行期为 0），而非"v0.2.4 修好、v0.2.8 又退化"。
→ **对 T3 的实操含义**：除「改错误分类」外，应**专查 deepseek 响应处理**（建议同一任务在 deepseek 与另一通道各跑一次做对照，即可证伪/证实）。
→ 诚实标注：v0.2.5 无运行时标签，故"是否曾真正修好"**不可判定**。

### 2.2 【B1】bash 30s 超时修复**只覆盖了一半路径**（新缺陷）

- 修复本身存在：`dispatcher.rs:149-160` **H1 (v0.2.4)**，注释明写动机即手工测试原文「`tool 'bash' timed out after 30s` 反复出现，cargo build 类长命令全灭」。
- `BashTool::declared_timeout()` = **610s**（`tools-builtin/src/bash.rs:88-90`）。
- 但修复入口 `register_with_declared_timeout()` 在生产代码中**只有一处调用**：

| 注册点 | 方式 | bash 实际超时 |
|---|---|---|
| `codex-cli/src/run_local.rs:238`（**chat 直跑**） | `register_with_declared_timeout` | **610s** ✅ |
| `service/src/main.rs:389`（**service 守护进程**） | `register()` | **30s** ❌ |
| `agent-core/src/loop.rs:4143/4309/4387` | `register()` | 30s（测试代码，可接受） |

**根因**：`register()`（`dispatcher.rs:133-135`）**只插 `tools`、不写 `timeouts`** → `dispatch()` 回落到 `default_timeout`（`dispatcher.rs:126` = 30s，见 `:212` `.unwrap_or(self.default_timeout)`）。

→ **影响**：`hearth chat` 下 bash 已放宽到 610s；但 **`hearth service` 路径下 bash 仍被 30s 卡死**，任何编译/长命令照旧全灭。
