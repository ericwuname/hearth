## 一、缺陷族：一句话

> **"输出多少"这件事，代码里从来没有上限。**

三条路径、同一句话：

| # | 位置 | 原写法 | 读入量 |
|---|---|---|---|
| **D-18** | `sandbox` LinuxSandbox 读线程 | `Read::read_to_end(&mut buf)` | **无上限** |
| **D-29** | `sandbox` NoopSandbox（**Windows 走这条**） | `Command::output()` | **无上限** |
| **D-21** | `tools-builtin` `read` 工具 | `tokio::fs::read_to_string` | **无上限**（`limit` 只管"返回多少行"） |

**后果**：一条 `yes`、`cat /dev/zero`、死循环打印，或一个 10 GiB 的单行文件，
就能把 hearth **自身** OOM —— 这不是沙箱逃逸，是**被沙箱执行的命令把宿主 agent 打死**。

**为什么"截断"救不了**：三处的截断（若有）都发生在**读完之后**——内存已经吃满。

## 二、关键设计点：**必须继续排空**，不能图省事 `take(cap)`

这是本卡唯一一处"看起来更简单但会引入新缺陷"的地方：

- 天真修法：`reader.take(cap)` —— 读到上限就 EOF，**不再读**。
- 后果：子进程继续写 → 管道缓冲区写满 → **子进程永久阻塞**；父进程在 `wait()`，
  `wait()` 等子进程，子进程等管道被读走 → **死锁**。等于把 OOM 换成了挂死。

所以正确修法是：**持续读到真正的 EOF**（把管道读干），但**只保留前 `cap` 字节**，
并回报"是否截断"。这条不变式被写进了单测断言（见下）：

```rust
assert_eq!(cursor.position(), data.len() as u64,
    "必须继续排空到 EOF——若用 `take(cap)` 提前停读，子进程会因管道写满而永久阻塞");
```

## 三、修复

### 3.1 新增两个有界排空辅助（`sandbox` crate 顶层）

```rust
pub const MAX_CAPTURED_BYTES: usize = 8 * 1024 * 1024;

pub fn drain_capped_std<R: std::io::Read>(r: R, cap: usize) -> (Vec<u8>, bool);       // Linux 阻塞读线程
pub async fn drain_capped_async<R: tokio::io::AsyncRead + Unpin>(r: R, cap: usize)    // NoopSandbox
    -> (Vec<u8>, bool);
```

**刻意放在 crate 顶层**（而不是 `cfg(target_os = "linux")` 模块内）：这样它们在
**Windows 上也会被编译并被单测覆盖**——本机即可验证边界行为，而不是"写完就没人看过"。

### 3.2 NoopSandbox：`.output()` → spawn + 有界并行排空

```rust
let (out_res, err_res, status_res) = tokio::join!(
    drain_capped_async(stdout_pipe, MAX_CAPTURED_BYTES),
    drain_capped_async(stderr_pipe, MAX_CAPTURED_BYTES),
    child.wait(),
);
```

**并行是必须的**（只读一路会让另一路管道写满互锁）。其余语义（`kill_on_drop`、
超时、`exit_code`、`timed_out=false`）**一字未改**。

### 3.3 截断**不静默**

两个后端都在 stderr 追加结构化留痕：

```
[hearth sandbox] stdout 超过 8 MiB 上限，仅保留前 8 MiB。
```

（沿用"不静默降级"红线：限制生效必须可见，而不是让调用方以为拿到了全部输出。）

### 3.4 `read` 工具：按字节有界读取

```rust
(&mut file).take(MAX_READ_BYTES + 1).read_to_end(&mut raw).await?;   // +1 用于探测"还有没有"
```

- `MAX_READ_BYTES = 8 MiB`：远大于 `DEFAULT_LINE_CAP`（2000 行）的正常源码体积
  → **正常用法零影响**（既有 R5-5 分页测试全部原样通过）。
- 截断点可能切断多字节字符 → 退到最后一个合法 UTF-8 边界（**不引入替换符、不报错**）；
  **未截断时保持原语义**（非 UTF-8 一律报错，不静默 lossy）。
- 输出末尾留痕：`[note: 文件超过 8 MiB，本次只读取前 8 MiB …]`——否则上面那句
  "共 N 行 / 续读提示"会让人误以为已看到全貌。

## 六、方法论沉淀（第 7 个变体）

> **"假设对手/意外的规模是有限的。"**

前 6 张卡是"假设某物存在/成立"；本卡是**假设某物不会太大**：
- 假设子进程输出不会撑爆内存；
- 假设文件不会大到读不下；
- 假设"限了行数"就等于"限了内存"（**单位错了**：行数 ≠ 字节，单行可以是 10 GiB）。

**固化为检查项**（补充至 D-23 专项，未实施）：
1. **凡"读入内存"的调用（`read_to_string` / `read_to_end` / `output()` / `wait_with_output`），
   必须能回答"上限是多少、在哪里"**——答不出的即缺陷；
2. **凡"截断"，必须问它在读入之后还是读入之前**——之后的截断对内存无效；
3. **凡加上限，必须同时确认"加了上限之后被读方不会卡死"**（`take(cap)` 的管道死锁陷阱）；
4. **限制生效必须留痕**（不静默），否则调用方会基于"截断后的假全貌"做判断。

## 七、附带产出：Linux 专用代码的交叉类型检查（**长期门禁缺口**）

D-18 位于 `#[cfg(target_os = "linux")]` 模块内 —— 在本机（Windows MSVC）**根本不参与编译**，
"改了没人验证"是真实风险（本规划此前把 `.131/.133` VM 不可达列为 D-7 阻塞项）。

本卡实测**可打通**：

```
rustup target add x86_64-unknown-linux-gnu
cargo check -p sandbox --target x86_64-unknown-linux-gnu   # exit 0
```

`cargo check` 不需要链接器，只做类型检查——**足以挡住"Linux 分支写错类型/写错名字"这一
类事故**。已把本次改动（4 元组解构、`drain_capped_std` 换入）**实测通过**。

**登记为 D-30（能力，非债）**：后续凡改动 `cfg(target_os="linux")` 代码，**必须**补跑
该交叉 check；是否把它并入常规门禁（步 2）待顶层裁定——因为它会额外拉一份 Linux 依赖图。
