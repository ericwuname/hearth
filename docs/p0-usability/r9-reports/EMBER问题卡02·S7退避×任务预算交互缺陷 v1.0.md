# EMBER 问题卡 #2 · S7 长退避 × 任务墙钟预算交互缺陷（2026-09-11）

- **来源**：EMBER M1 施工（.133，hearth-slim + agnes-3.0-flash）
- **级别**：P1（韧性机制交互缺陷——两个"正确"机制组合出错误行为）
- **实况**：M1 施工被 `✗ deadline exceeded: 1114s >= 900s（任务级 wall-clock 上限）` 杀死，**用时 1134s、仅 11 步**——死在"写 ember.py"之前（tools.py 已写，主程序未升级）。

## 一、因果链（实测日志）

```
Agnes provider 多次 transient 故障（本时段抖动频繁）
  → S7 长退避启动：30s → 1m → 2m（忠实执行设计）
  → 每次退避消耗 wall-clock（任务级预算 900s）
  → 累计 1114s > 900s → deadline 杀（任务失败）
  → S8 断点已存（hearth 诚实提示：提高 HEARTH_TASK_TIMEOUT_SECS 后可 resume）
```

**讽刺之处**：S7 的存在意义是"不让任务被基础设施抖动杀死"——但它的耐心退避**恰恰让任务被自己的超时机制杀死**。两个机制各自正确，组合出错。

## 二、根因

**S7 退避不感知任务剩余预算**：
- 退避时长（30s/1m/2m/5m）+ provider 抖动次数，与任务 `budget.max_time_secs`（900s）**无协调**；
- 对比：`deadline_clamped` 机制（P1-LTR-01）已存在——**工具级** timeout 会被任务 deadline 收紧（min(declared, remaining)）——但**provider 退避层没有同样的收紧**。

## 三、需求（建议入下一批手术）

**S7+ · 退避预算感知 + 与 S8 暂停协同**：
1. 退避前计算 `remaining_task_time()`；
2. 若本次退避时长 > 剩余预算的 **30%**（阈值可调）→ **不再硬等**，直接走 **S8 暂停语义**（"⏸ 暂停（provider 持续故障）——断点已存 + resume 指引"）；
3. 退避循环内也要检查（长退避期间任务被外部打断 → 立即收手）；
4. **投影**：`[retry] ... 等 2m（剩余任务预算 5m——退避占 40%，超阈值 → 改走暂停）`。

## 四、附带发现

- **本时段 Agnes 抖动确实频繁**（M1 施工期内多次 transient）——单卡施工建议 `HEARTH_TASK_TIMEOUT_SECS=3600`（已用于 resume 验证）；
- **S8 暂停语义再次被证明有价值**（deadline 杀后断点完整、hearth 主动给 resume 指引——续跑成功启动）；
- 施工日志中观察到畸形目录名 `{'path': '`（工具调用参数以 dict 形态被当路径）——疑为模型侧参数序列化边缘案例，**待复现确认**（暂记观察项，未达问题卡级别）。
