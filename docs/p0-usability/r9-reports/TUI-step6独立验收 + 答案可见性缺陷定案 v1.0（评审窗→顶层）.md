### 1.2 D11 的"证据"其实是不可失败的断言

- 卡/战报的证据形态是「`done detected at t=3s/4s`」。**但修复前的老代码也满足这个数字**——只要 `child` 在最后一行输出后 1 秒内退出，新旧代码的 `done` 时刻就观察不到差别。
- 我的高分辨率复测（`data/v15b-poll-d11.txt`，0.4 s 轮询，同步记录子进程存活数）：

```
23:54:30 alive=1  │[fold:off scroll:0/0] / running... (0s) ⚙ ▸ span [plan] ...
23:54:30 alive=1  │[fold:off scroll:0/0] - running... (0s) ⚙ ── 收尾 | 依据: ...
23:54:31 alive=1  │[fold:off scroll:0/0] | running... (1s) ⚙ ── 收尾 | 依据: ...
23:54:31 alive=0  │[fold:off scroll:0/16] done (2s)
```
→ **`done` 出现的那一采样点，子进程计数已经是 0**：`Done` 之前之后都看不到"子进程还活着"的窗口，D11 想消除的等待**在本机根本没发生**。
- **⇒ 代码改动正确、无害；但"状态栏更早翻 done"这一收益在当前条件下不可证伪。**
- 要真正证成需二者之一：① 找到一个 `hearth` 末行输出后仍停留 >1 s 的真实场景；② 轮询降到 100 ms 并在子进程侧打时间戳。**建议不再投入**（收益本就在亚秒级）。

## 2. ⭐ 本轮最高价值：D14「用户看不到答案」

### 2.1 现象（双窗口对照，产品级证据）

同一条 `只回答一个数字：3+4=?`，两个窗口尺寸：

**高窗口（110×45，全部内容可见）** — `data/v16-tall-full-conversation.txt`，共 29 行对话内容：

| 行 | 内容 |
|---|---|
| 1 | `> 只回答一个数字：3+4=?` ← 用户输入回显 |
| 2-4 | `· diagnostics → ...` / `🔒 landlock+seccomp` / `🔓 会话级审批委托已开启…`（含换行占 2 行） |
| 5-7 | `> 只回答一个数字：3+4=?`（**引擎再回显一次**）/ `🎯 任务目标已锚定` / `▸ span [plan]` |
| 8 | `· ───── 结果 ─────` |
| **9-10** | **`7  ◂ span 耗时 622ms`** ／ **`7✓ Done (1 steps)`** ← **这才是答案** |
| 11-15 | `收尾×3` + `📄 执行报告` + `✓ Task completed` |
| 16-18 | `收尾×3` ← **逐字重复一遍** |
| 19-29 | `任务总结` 区块 11 行 |

**小窗口（100×24，用户的真实尺寸）** — `data/v16-small-after-done.txt`：

```
┌ conversation ────────────────────────────────────────────────────────────────┐
│·   ── 收尾 | 依据: 完成决策 = accepted: all_done gate + verify passed；验证状态 = UNVERIFIED
│  ═══════════ 任务总结 ═══════════
│  【一句话】任务完成，正确回答了简单算术题 3+4 的结果为 7。
│  【产物】无 / 【过程要点】… / 【问题与处理】无 / 【剩余/建议】无 / 【质量自检】未跑
└──────────────────────────────────────────────────────────────────────────────┘
│[fold:off scroll:0/17] done (2s)
```

- 对话区视口 **15 行**，内容 **29 行** → 只有尾部 15 行可见。
- **用户输入回显、答案 `7` 两行全部落在视口之上**：`grep` 结论 = `hearth answer line NOT VISIBLE (scrolled off)` / `user echo NOT VISIBLE`（`data/v16-visibility.txt`）。
- 按一次 PageUp 也只看到 `📄 执行报告` / `✓ Task completed` / 收尾块（`data/v16-small-pageup.txt`），**答案仍不在屏上**。

### 2.2 量化

| 指标 | 值 |
|---|---|
| 引擎 stdout 总行数 | **31**（`data/v16-engine-stdout-canonical.txt`，直跑捕获） |
| 答案占行 | 2（L10-11）= **6.5%** |
| **答案之后**的行数 | **21 行 = 68%** |
| 其中"逐字重复" | `收尾×3` 整块重复（L12-14 ≡ L17-19，byte-identical） |
| 结尾叙述块 | `任务总结` 11 行（`【一句话】/【产物】/【过程要点】/【问题与处理】/【剩余/建议】/【质量自检】/（完整过程…）`） |

→ **一个 3+4 的提问，屏上留下的是 15 行过程叙述；用户要按 PageUp 才能找到 `7`。**
这是本 TUI 车道至今**最影响"好不好用"的缺陷**，且**不是 TUI 的错**——TUI 是忠实管道，噪声在引擎侧。

### 2.3 归属定案（关键：TUI 还是引擎？）

用**绕开 TUI 直跑引擎**的方式做了归属判定（这是本轮的关键实验设计）：

```
cd /tmp/v17w && hearth chat "只回答一个数字：3+4=?" --budget 40 --approve-within session > stdout 2> stderr
```
- stdout **31 行**，其中 L12-14 与 L17-19 **逐字重复**（`data/v16-engine-stdout-canonical.txt`）。
- **⇒ 重复账与"答案被埋"账都在 hearth-slim（引擎），TUI 只做转发。** TUI 侧唯一能做的是呈现策略（默认折叠/答案置顶），属缓解而非根治。

## 6. 评审窗自曝（两处仪表错误，本轮必修）

1. **E1（浪费 4 次 LLM 调用）**：v15 首版把 `done (` 的检测 grep 打在状态块的**边框标题行**（`┌ model: agnes…`）上，而 `done (` 实际在状态块的**内容行**（`│[fold:off scroll:0/N] done (2s)`）。→ 4 次真 LLM 全部误判为"未完成"，整轮 v15 作废。已在 v15b 改正（锚内容行）。
2. **E2**：我按记忆里的旧格式 grep `> you:` / `hearth:` —— 这两个前缀**早在 fix2 就被删除**（现状：用户行 `> <消息>`、答案行 2 空格缩进无前缀）。一度据此差点得出"答案根本不在缓冲区"的错结论，靠读**全尺寸抓屏**才纠正为"在缓冲区、但在视口之上"。
3. E3（无害）：`pgrep -fc … || echo 0` 在 0 命中时输出两行 `0`，污染了轮询日志的字段（仅记录格式，不影响判定）。
→ **沉淀：跨轮复用旧"格式知识"前必须重新 grep 一次现状**（陈旧记忆会骗人）。
