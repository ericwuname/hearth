# Hearth 当前问题总结（供修复参考）

> 生成时间：基于本轮会话（Ember 开发 + 对标 Codex/Claude Code）过程中观察到的真实行为
> 目标读者：负责修复 Hearth 的开发者
> 范围：聚焦“为什么简单任务也要几十轮对话才解决”这一根因

---

## 1. 问题总述（一句话）
Hearth 当前的问题核心是：**预算管理规则过强 + 出网策略不透明 + 缺少可观测/可恢复状态**，导致 agent 在“简单任务”上也频繁触发收口、反复试错、重复探索，最终表现为“轮数爆炸”。

## 2. 三个根因（按影响排序）

### 2.1 根因一：预算告警/强制收口规则过于激进
**现象（本轮实际触发）**
- 多次出现：
  - `[budget-warn] 预算已用 83%...请评估剩余工作能否在预算内完成`
  - `[budget-critical] ...立即收口：停止开启新子任务...`
- 实际结果：
  - 一个“让 ember 查资料 + 分析 + 出计划”的中等任务，被反复打断
  - 出现“连续 3 步无新事实且无产物变更 → 强制收口”的硬性规则
  - 用户感受：简单问题也要几十轮

**根���判断**
- `budget-critical` 当前语义 ≈ “禁止任何新的探索/子任务”
- 这使得必要但低成本的关键步骤（如：读源码、跑一次验证、写一份文档）也被拦
- 收口逻辑与“任务进展是否真的停滞”解耦了——只看步数比例，不看“是否已有实质进展”

**修复方向（最小改动）**
- 将 `budget-critical` 从“禁止新任务”改为：
  - “优先收敛；仍允许 1-2 个低成本的必要步骤”
- 增加一个判定：**是否已产生新产物/新事实**
  - 若已产生（如写入文档、跑通命令），则不应继续触发“强制收口”
  - 若未产生且连续多轮无进展，才真正收口

**可验收标准**
- 同类任务（查资料+分析+写计划）在预算警告后，允许完成“写入文档”这一步
- 不再出现“明明已产出文档，仍被判定为无进展而强制收口”

---

### 2.2 根因二：出网策略（allowlist）不透明，工具失败路径不清晰
**现象（本轮实际触发）**
- `web_search` 直接报错：
  - `出网被拒：域名 html.duckduckgo.com 不在 HEARTH_EGRESS_ALLOWLIST 白名单`
- 但用户/agent 并不知道：
  - 默认策略到底是“全放行”还是“白名单制”
  - 白名单配置在哪里改
  - 白名单为空时是什么行为
- 结果：agent 反复尝试，浪费轮数

**根因判断**
- 出网策略与工具错误信息不一致：
  - 工具描述说“默认放开（S2）”，但实际运行环境可能是“白名单制”
  - 错误信息只说“域名不在 allowlist”，但不给“下一步该做什么”
- 缺少“失败可恢复路径”（fallback）：
  - 搜索失败后没有自动降级到本地资料/缓存/其它源
  - 没有明确的“配置指引”输出

**修复方向（最小改动）**
- 明确并文档化三条规则：
  1. 默认策略：`HEARTH_EGRESS_ALLOWLIST` 为空 = 全放行 / 白名单制（二选一并固化）
  2. 配置路径：`HEARTH_EGRESS_ALLOWLIST`（env）或项目内文件（如 `.hearth/egress_allowlist.txt`）
  3. 失败行为：非白名单域名 = 立即失败并输出“如何配置”的提示
- 工具错误信息增强：
  - 在 `web_search/web_fetch` 的报错里直接附上：
    - “请设置 HEARTH_EGRESS_ALLOWLIST=...” 的具体命令示例
    - “或清空该变量以启用默认全放行”的选项

**可验收标准**
- agent 在第一次 `web_search` 失败时，能从错误信息直接知道修复方法
- 不再需要用户重复解释 allowlist 语义

---

### 2.3 根因三：缺少可观测/可恢复状态，导致���复探索
**现象（本轮实际触发）**
- 多次“搜不到结果”后，agent 重新读源码、重新尝试，而不是直接引用已有产物
- 缺少“任务清单/审计日志”这类一等公民状态
- 结果：同样的步骤被反复执行

**根因判断**
- 没有结构化的“已做/未做”记录（todo/checklist）
- 没有“审计日志”来避免重复试错
- 上下文压缩后，早期事实容易丢失（本轮也出现了 `[history note]` 说明早期消息被裁掉）

**修复方向（最小改动）**
- 引入 `todo_write` 工具（对标 Claude Code 的 task checklist）：
  - 持久化到 `.hearth/todo_<session>.json`
  - agent 在长任务中主动维护
- 引入审计日志（M1）：
  - 每次工具调用/响应落 JSONL
  - 便于“可回放/可定位/可避免重复”

**可验收标准**
- 长任务中断后可恢复清单继续
- 同一任务不会因“忘了已经做过什么”而重做

## 3. 修复优先级（建议顺序）
| 优先级 | 修复项 | 理由 |
|---|---|---|
| P0 | 预算规则改“优先收敛 + 允许必要低成本步骤” | 直接解决“简单任务几十轮”的最痛点 |
| P1 | 出网策略与错误信息固化 | 避免反复试错的常见诱因 |
| P2 | todo/审计日志 | 降低长任务重复探��成本 |
