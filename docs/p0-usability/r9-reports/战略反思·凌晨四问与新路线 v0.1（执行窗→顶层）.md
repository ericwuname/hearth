## 二、执行窗增量发现（凌晨自查，用户四问之外）

### 2.1 【最重磅】注意力税不是一次性税，是复利

对 0.2.26 r1 全套 29 条日志（blind 15 + corpus c 14）的 prompt tokens 统计：

| 指标 | 值 |
|---|---|
| 单条任务累计 prompt 输入 | **总计 1,743,939 / 均值 60,135 / 最大 451,914 / 最小 4,314** |
| 调用次数 | 162（≈5.6 次/条） |

三个推论：
1. **治理文本是每次调用全额重复支付的常驻税**（9K 基底 × 162 次调用 ≈ 145 万 tokens，占总税单八成以上）；
2. **上下文滚雪球没有被 compaction 压住**：单条任务 45 万 tokens 累计输入（max），说明压缩阈值/策略对长任务实际失效——这是继"编排病"之后第二个未被诊断的框架病，暂名**"膨胀病"**；
3. 这解释了此前所有墙钟数据形态：A 臂快在 B 臂相位调用的消除，但**基底税和滚雪球在 A 臂同样存在**——单循环救了流程，没救账单。新路线的瘦身（2K 基底 + 激进压缩）同时治两者。

## 三、新路线 v0（凌晨与用户达成的共识）

1. **垂直切片**：一条最细路径端到端跑通 → 每次只加一个功能 → 每加一个保持闭环绿。
2. **单循环四件套**：消息循环 + 工具执行 + 预算（硬停+透明报进度）+ 会话持久化。give_up 仪式、PDCA 相位机、账本判定门不在核心内（降级为可选模块）。
3. **prompt 瘦身**：基底 ≤2K；治理文本全部走投影层（事后展示，不占事前注意力）。
4. **+1 准入纪律**：codex 有而 Hearth 缺的优先；自创功能进 backlog 冷却。
5. **验收标准换代**：自设判分口径降为参考，**用户真实使用（连续 3 个真实小任务不骂人）为主验收**；外部同条件对照（codex 同模型同题）为归因工具。
6. **底座 A/B 被路线吸收**：第一条闭环在瘦身 Hearth 跑通 → 留用；跑不通 → 同定义搬 codex 底座再跑，无需提前辩论。
7. **"做完"重定义**：第 1 闭环 1-2 周，之后每周 +1 节奏。
