## 一、方案一（G/W 门）问题清单

### 🔴 1.1 材料可核验性：盲测包在本机与 git 均不存在

方案一 G-A/W-A 引用 `release/盲测包-正式轮-v0.2.23-10+5.md`，G-C 引用"盲测包 A 组"3 个 give_up 场景。

**核验结果**：本机 Desktop 全盘 + git 全历史 **0 命中**；`release/` 目录已不在工作树。连我拆解用的语料 A（0.9-0.3）本机也已消失（前晚仍在）。

**这不是说材料不存在**——大概率在 .133 真机或被清理的本地副本。但**判读方（砺+外部）没有独立核验通道**，就无法执行"防墙头草"的抽验。

**要求（定稿前置）**：
1. 提供盲测包 + 两份语料的**存放路径 + sha256**，或拷入 `docs/`（git 跟踪，防再丢）；
2. G-C 的"3 个 give_up 但写过文件场景"须给出**具体条目编号 + 构造**——按我对盲测包 A 组（10 个提问/诊断型场景）的记忆，**A 组并不天然是 give_up 场景**，需执行窗确认这 3 个场景的确切出处；若无，G-C 场景需另行构造并预注册。

### 🟠 1.2 W-F 判据退化为回归测试（测不到 E15 病理）

W-F 通过线："`--quiet` 跑一轮，stdout 中 `◆` 横幅计数 = 0"。

**问题**：这是**回归测试**（测"quiet 开关生效"），几乎必然通过——因为实现就是 `set_verbosity(0)` 关横幅。**它无法证伪"默认档是否可读"**，而 E15 病理（正文 dimmed、过程淹没答案）恰恰发生在默认档。

**建议（定稿改）**：W-F 拆双判据——
- W-Fa（自动/回归）：`--quiet` 下 `◆` = 0、正文与终态保留；
- W-Fb（人工/行为）：默认档跑一轮 ≥10 步任务，砺 判"正文行可读、未被过程行淹没"（给出正文行数 : 过程行数的实测比值作为佐证，不设硬线，由判读者定）。

**W-Fb 才是 E15 的判据；W-Fa 只是它的前提。**

### 🟠 1.3 G-H 判据测"机制触发"而非"判定质量"

G-H 通过线："`observe_verdict` 写入 + `R1_3`/`R2_2` 日志出现；Observe 判定输出非 0"。

**问题**：R1-3 的验收点是"Observe 有**实际判定**输出"（根治任务书 R1-3 行原判据）。若 `observe_verdict` 每轮写入常量/空结构，也满足"写入 + 非 0"——**判据会空转通过**。

**建议（定稿改）**：加两条——
1. `observe_verdict` 内容须含**结构化判定**（错误类别 / 空输出 / 返回码，至少一类非默认值）；
2. 抽样人工核一条：verdict 与当轮真实工具结果**语义一致**（如工具报错则 verdict 必记失败）。

### 🟡 1.4 G-G 处置需在定稿时落一个"总门数"口径

G-G 缺失登记正确，但留下口径悬空：任务书与启动令都写"G/W 全绿"、"八门全跑"。若 G-G 最终确认不存在，**宣告口径必须明确写"七门 + W 六律全绿"**，不能在宣告时临时改口径（那会变成事后挑选的变体）。

**建议**：定稿会签时一并定——要么补 G-G 定义（如"gaps 自动假设去重"这类确有病理对应的门），要么正式确认编号跳位并在宣告口径写"七门"。**两条路都行，但不能悬着。**

### 🟡 1.5 G/W 重复门问题（含金量稀释）

| 重复对 | G 门 | W 律 | 判据差异 |
|---|---|---|---|
| G-A vs W-A | 10 疑问句 ≥8 首屏给结论 | 同 G-A 语料 ≥8/10 首句结论 | **几乎无差异** |
| G-D vs W-D | 列 5 项 → 5 轮"继续"→ 复述零遗忘 ≥4/5 | 同 G-D 语料，"还剩什么"零遗忘 ≥4/5 | **几乎无差异** |

**问题**：同一实验喂两个门 → "G/W 全绿"名义 14 个判据、实质约 11 个；且同一失败同时判负两个门，**double-count 会放大偶发失败，稀释"全绿"的判定含金量**。

**建议**：定稿时对 W-A/W-D 做**增量去重**——W 律保留与 G 门的差异部分（如 W-A 补"只回路径即判负"的首句判定、W-D 补"跨 5 轮不靠提示回卷"的持久性判定），或直接声明 W-A/G-A、W-D/G-D 合并计数。**宁要 11 个独立判据，不要 14 个里含 3 对孪生。**

### 🟡 1.6 引擎与 provider 锁定

- 方案一"引擎 = p0-usability-01 @ **定稿时** HEAD"：跑测跨轮、真机 LLM 时长长，HEAD 可能漂移。应锁**定稿那刻的具体 commit sha**，漂移即重签。
- provider 锁定（agnes-2.5-flash）与探活先决：✅ 与顶层裁定一致。

## 二、方案二（双会话重放）问题清单

### 🔴 2.1 方法论级缺口：**重放起点未定义**（定稿前必须锁）

这是方案二最大的坑，直接决定整条线的可比性：

0.9-0.3 会话中，agent 在 `/home/wutao/hearth-tui/` 写了几十个文件（含"完成度 103%"的 README）。重放时：

| 起点选项 | 后果 |
|---|---|
| (a) 空工作区起步 | "继续做TUI项目"（line 2823/3081/3363…）**没有可继续对象** → 行为必然"看起来更差"，且与"103% 假事实污染"专项二冲突（专项二要预置 README，全序列重放又要空起步，**自相矛盾**） |
| (b) 预置到原会话某中段 | 则"预置到哪个 run 之后"必须锁定；且每轮用户指令对应的**工作区状态**都不同 |

**要求**：
1. 明确每个重放 run 的**工作区初始状态**（从原会话的哪个检查点恢复，或空起步但注明专项二独立预置）；
2. 若全序列重放与专项二共用工作区，需声明**状态冲突如何处理**（专项二预置的 README 会不会污染后续"103% 不得引用"之外的轮次）；
3. 锁定的起点状态写入定稿件，跑测时不得改。

**这一条不解决，G-D / W-D / 用户推进率 的测量都不可比，重放线整体作废。**

### 🟠 2.2 语料 B（0.9-0.4）无法独立核验

方案二引语料 B 的具体数据：2,983 行 / 19 用户轮 / 18 run、`:103`、`FileBrowser is not a constructor`、末轮 6 次 give_up 且正确判失败。

**核验结果**：本机 Desktop 全盘 + git 全历史 **0 命中**（语料 A 亦然）。语料 A 的形状（36 轮 / 31 run）与我拆解时一致——说明执行窗引用大概率属实；但**语料 B 我从没见过，其存在与引述均无法独立确认**。

**要求**：定稿时提供语料 B 的**路径 + sha256 + 三个关键摘录**（`:103` 上下文、FileBrowser 构造错误原文、末轮判失败段落）。我（外部窗）只有拿到语料才能做 Q-1~Q-6 同口径交叉。

### 🟠 2.3 "零复发"缺总判定规则

§三 有 8 行指标各自通过线，但**没有一条汇总规则**定义"零复发宣告失败"。若 8 行过 7 行（如用户推进率 19%→65%，达标线 80% 未过），算复发还是部分改善？**跑测前不锁，跑后必争。**

**建议**：预注册总判定——**任一指标未过通过线 = 零复发宣告不成立**（简单、不可狡辩）；若砺认为部分指标应分软硬，也须在定稿时定，不得跑后挑。

### 🟡 2.4 专项一"不适用"出口需防被误读

专项一：若组件在新代码下不再失败 → 判"不适用"（不算通过不算失败）。出口合理，但**防一种情况**：R1-R4 改动恰好"修好"了 FileBrowser 的模块导出（例如施工时顺手改了），使组件不再失败 → 专项一"不适用" → G-B 在真机上没测到。

**要求**：若判"不适用"，须**附证据证明"组件不再失败的根因"**（是 R4 目标修复所致，还是无关改动所致）；若是无关改动所致，应换一个仍会失败的组件重测 G-B——**G-B 是八门之王，不能让它绕过去。**

### 🟡 2.5 时长与成本预估

两语料 55 用户轮 / 49 run 全序列真机 LLM 重放，参考原会话 span 合计 75.8 分钟机器时间、实际墙钟 4h17m。新引擎若修复有效，run 数会变（这是目的）——但**最坏情况成本**（若行为病理复发导致 run 膨胀）应有上限预案与中断条件。

## 五、一份诚实的自我说明

4. 本件只评两份方案**作为验收设计是否站得住**，不评 R1-R3 施工质量（那属砺的里程碑判词）。R4 跑出的结果，我将在拿到材料后按 Q-1~Q-6 同口径交叉。
