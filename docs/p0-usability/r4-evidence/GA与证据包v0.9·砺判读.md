## 三、🟠 新发现：**VERIFIED 授予判定过松**——"假完成"病理的新形态（源码坐实）

### 3.1 实测

- A-draft 记"UNVERIFIED 7 + VERIFIED 1 + 其余 10 待对账"；**砺实测：裸"目标达成"（VERIFIED）= 11 个**（2751/2935/2994/3133/3312/3447/3499/3696/3712/4112/4215），7+11=18 对账闭合。证据包 §四 W-B"24 轮全带标注"**字面成立**，但把含金量问题藏在了"待对账"里。
- **抽验 3 个 VERIFIED 的验证证据**：@2751（25 步）= `ls` 文档文件列表；@2935（26 步）= `ls` 文档列表；@3499（**5 步**）= 只列了 test-*.js 文件名，**未跑任何测试**。3/3 均为"文件存在即验证"。
- 另有一轮（10 步 VERIFIED）：模型正文自述"**⚠️ 待修复：FileBrowser 组件测试需要修复 DOM mock**"，终态却是"✓ Task completed——**目标达成**"（详见 §六）。

### 3.2 源码根因（`loop.rs:904-913`，当日实测）

```rust
const READ_ONLY: [&str; 15] = ["cat","ls","head",…,"echo","true","read"];
cmd.split(['|',';','
','&']) … .any(|w| !READ_ONLY.contains(&w))
```

**`any` 语义 = 只要任一段首词不在只读表，整条命令就算"验证命令"**。于是：
- `bash -c "cat x"` → 首词 `bash` → **算验证**；
- `cd /x && cat y` → 首段 `cd`（**cd 不在只读表**）→ **算验证**；
- 纯 `ls` 不算——但模型只要加一层包装就绕过。

这正是**外部拆解一已诊断的"非只读即验证判定过松"（28 次假 VERIFIED 机制），未被纳入 R1 包**——R1-1 只重造了改判臂（强制 UNVERIFIED），**正常 Done 相位的 VERIFIED 授予仍走旧松判定**。定性：**存量病理，非 R1-R3 回归**。

### 3.3 判读与处置

- **W-B 门**：字面通过（全带标注）。但"**报完成中经核验比例**"从此**禁用**——"VERIFIED"标注本身不可信（与"497 裸写禁引"同款处理）。
- **零复发宣告**：**不阻塞**——硬层防的是"假完成改判/已知失败标 ✅"，本项是另一维度。
- **"可用"宣告**：**阻塞**——用户体感测试必撞（问"做完了吗"→ 答"已验证" → 实际是 ls）。
- **处置**：**返工包第二项（新增，与 R3-1 REPL 并列）**：①`is_verification_command` 收紧（`bash -c`/`sh -c` 解包后再分类；`cd` 入只读表；或改为"退出码 0 的**测试/构建类**命令才算验证"）；②历史语义兼容审查（VERIFIED 授予点 grep 全查）。返工后随用户体感测试复验。
