# 对《consolidated-remediation-ledger》的补充审查意见

> 审查对象：`consolidated-remediation-ledger.md`（RC1-30 + 四条根因链）+ `Hearth_CLI_手工测试补充审查报告_2026-08-29.md`（ChatGPT，NEW-01~28）
> 目的：不重复已覆盖内容，只列**真正新增**或**需要拆开处理**的点，供 GLM 折入下一版任务执行书
> 总评：本轮工作扎实——尤其是用全语料频次表核实/推翻了外部回函的多条单次观察（含我自己"审批 67.9s"那条被证伪），这是正确的方法论，不是走过场

---

## 1. 一个必须拆开处理的决策：密钥轮换不该被"是否 filter-repo 擦历史"绑架

**观察**：台账 §9.1 把 `T-#0b`（轮换 6 个明文 key）标注为"⏸ 暂缓（用户批示）"，而 `T-#0c`（filter-repo 擦历史 + 强推）标注为"⛔ 待顶层拍板"。两者在决策表里被列在同一个"#0"事项下，容易被当成一个先后耦合的整体来处理。

**问题**：这是**两个独立、风险等级完全不同的动作**：
- 在 Agnes/DeepSeek 控制台把已泄漏的 key 吊销/轮换——**零成本、可逆、和 git 历史无关**，现在就能做，做了也不影响任何决策空间。
- 用 `filter-repo` 改写 git 历史——**有成本、不可逆、需要团队协调**（所有人要重新 clone），这条确实值得慎重拍板。

如果"暂缓轮换"背后的真实原因是"轮换了会打断正在进行的测试链路（怕连不上 Agnes/DeepSeek）"，这是一个合理的操作考量，但应该被**明确写成一个有时限的决定**（比如"本轮测试收尾后 24 小时内轮换"），而不是挂在"等顶层对不可逆的 git 操作拍板"这件事后面变成无限期暂缓——这两件事的决策时钟不应该绑在一起。**建议任务执行书把 T-#0b 独立成一条有明确 deadline 的待办，不再依附于 D7 的裁决进度。**

---

## 2. `edit` 工具全语料零使用——建议列为独立调查项，而非归并进"重写偏好"

**观察**：台账 §7.11.1 频次表显示 `write_file / apply_patch / edit` 三个工具在全部 9 份日志、33,100 行里的调用次数分别是 **75 / 33 / 0**。`edit` 工具**一次都没有被调用过**。

**这比我上一轮提出的"write_file 相对 apply_patch 偏多、可能倾向整份重写"这个观察要更进一步**：如果存在一个专门做局部编辑的 `edit` 工具，但它的调用次数是精确的 0（不是"少"，是"从未"），这里有两种可能，性质完全不同：
1. 工具选择逻辑/提示词里没有给 `edit` 足够的曝光或使用场景说明，导致 LLM 从不主动选它（提示词/工具描述问题，好修）；
2. `edit` 工具本身在当前版本里就是废弃/半成品/有已知 bug 导致从不被路由到（代码问题，需要先确认它是否还能正常工作）。

**建议**：任务执行书里加一条最小验证——在一次任务里**显式指名要求使用 `edit` 工具**做一次局部修改，观察它能不能正常工作。如果它本身没问题，再去看提示词/工具描述层面为什么从未被自然选中；如果它本身就跑不通，这条应该单独立项，不能被"重写偏好"这个措辞轻描淡写地带过。

---

## 3. 目标漂移已被用户在两次独立会话中当场亲口指出，建议单独立项而非归并进 RC4

**观察**：台账 §7.65 记录了第 10 份日志里用户在 L767 说"你的目标与你的规划完全偏离啊"，并把它标注为"RC4 规划漂移——用户现场确认，不再是推断"。

**补充**：这不是这类现象第一次被用户当场抓到。我在上一轮分析 v0.2.4 日志时，找到过另一处完全独立的实例（v0.2.4:L14181）：用户在一次长时间无人值守授权之后回来，发现 assistant 刚刚总结的是"从零构建了一个全新的 Codex CLI 骨架项目"，原话是"我们一开始做的不是 hearth 的测试吗……我怎么觉得偏离很远啊"。

**这两次实例**：
- 发生在**不同版本**（v0.2.4 和第 10 份新日志，版本相隔较远）；
- 都发生在**长任务/自主执行阶段**，不是普通单轮对话里的小偏差；
- 用户的原话措辞高度相似（"偏离很远" / "完全偏离"），是**用户自发、独立地用几乎相同的语言描述同一类现象**，不是我或 GLM 主观归类出来的相似性。

**建议**：这个模式目前被放在 RC4（"规划不执行 + replan 塌缩"，标 P2）里，我认为归并级别偏低了。RC4 现有的证据（"7 步计划 49 步只跑 ls/df/find"）描述的是"计划没被认真执行"，而这两次用户抓到的是**任务目标本身被替换成了另一件事**，是更严重的一类问题——不是"绕路走到了目的地附近"，是"去了另一个地方"。建议单独开一条 RC（比如 RC31 "长程自主执行期目标替换"），标 P1 或以上，验收标准可以设计成：给一个长程无人值守任务，在任务结束时用一个独立的判据（比如让另一次调用比对"最终产物"和"原始目标关键词"的语义相关度）自动检测是否发生了目标替换，而不是只能靠用户事后自己发现。

---

## 4. 建议把 12 跑/18 跑矩阵固化进 CI，不要只当一次性诊断用完即弃

**观察**：台账 §7.6/§8'' 的 12 跑、18 跑矩阵是这几轮所有材料里信息密度最高的产出——纯读任务 0% 成功率这个数字，比任何静态代码分析都更有说服力。

**建议**：这套矩阵目前看起来是评审窗口手动跑出来的一次性诊断脚本。W3 的验收标准写的是"Tier3 长程实测：0 完成 → 有完成"，这暗示了会重跑，但没有明确说"重跑"是指**再手动跑一次**，还是**从此变成 CI 里的常驻回归测试**。考虑到这套矩阵已经证明了自己的诊断价值，建议明确要求：把这 4 类任务（写文件/三步链/纯读/纯问询）各选 1-2 个代表性用例，固化成 CI 里能自动跑、自动判定成功率的回归测试，每次发版前跑一遍，而不是依赖"下次又有人手动发现问题、又手动写一套矩阵"这种模式——现在这套宝贵的诊断能力，价值不应该止于这一轮。

---

## 5. 建议把"结构化执行报告"重新排上日程——这几轮的挖掘成本本身就是证据

**观察**：从最早的手工测试记录分析，到这次 GLM 用 `mine_logs.py`/`mine2.py`/`mine3.py` 三个脚本对全语料做频次挖掘，中间消耗了大量人力和多轮 AI 分析成本，才把"纯读任务 0% 成功""审批弹窗 21 次全为真人应答"这类结论坐实。

**建议**：这恰好反向证明了更早一轮任务书里提出的"结构化执行报告"（每次任务结束落一份机器可读摘要：目标/工具调用序列/终态/给出的原因）这件事的价值——如果这个机制存在，这一轮很多结论（活性信号断裂、纯读任务失败率、审批弹窗次数）本来可以直接从结构化数据里查出来，不需要事后对着几万行 raw log 写正则脚本去挖。这件事之前在 P1 优先级，鉴于这几轮反复验证了它的价值，建议在这次更新任务书时把优先级提前，甚至可以和 W4（观测投影）合并成一个批次——反正 W4 本来就是在处理"事实产生了但没投影"这一类问题，结构化执行报告是同一个病根的系统性解法，不只是给 RC8/RC9 打补丁。

## 6. 两处小的一致性核对，供确认

- 台账 §7.11.1 统计"missing_goal_source"全语料 1148 次、Plan 草案 574 次，得出"每份计划≈×2"。这个"×2"是否是因为每次 replan 都会在新的 Plan 草案里重复标注同一个目标（即同一个任务在 replan 循环中被反复标注），而不是一份计划里真的出现两条不同的假设？如果是前者，这个倍数其实是 RC1（活性断裂导致的强制 replan）的一个副作用指标，值得在 RC26 的处置建议里提一句"修好 RC1 后，这个×2 大概率会自然下降，不需要单独在 RC26 里额外处理重复标注的问题"，避免执行窗口把这当成两个独立要修的地方，重复花工。
- ChatGPT 报告 NEW-15（resume 幂等性/exactly-once 语义）在台账里没有看到被单独验证或并入现有 RC 的记录，只在"交叉验证"表格里被归入"已知项"，但没有具体给出验证结论。这条如果确实还没有专门测过，建议保留在下一批任务书里，不要因为"看起来像是已知问题的一种"就默认它已经被现有测试覆盖了。

## 一句话总结

这一轮真正的新增内容不多（说明前几轮的分析已经把这个项目摸得很透了），但第 1 条（密钥轮换不该被 git 历史决策绑架）和第 3 条（目标漂移应该独立立项、提高优先级）这两条，建议在更新任务执行书时明确写进去，不要被现有分类结构"消化掉"。
