## §1 根因三层死锁（全部源码实证）

### 第一层：目标路由层——用户的新意图进不来

**代码**：`classify_user_input`（loop.rs:324-413），三分类：TaskControl / Conversation / GoalMutation。

**关键规则**（按命中顺序）：

| 序 | 规则 | 行号 | 判定 | 后果 |
|---|---|---|---|---|
| 1 | 空输入 | 328-330 | TaskControl | 不改目标 |
| 2 | 以 ✓/✗/⏹ 开头 | 333-335 | TaskControl | 不改目标 |
| 3 | 含 completed/task failed + 步/step | 336-340 | TaskControl | 不改目标 |
| 4 | **TASK_CONTROL 14 词**（含"继续""接着""resume""怎么样了""发生什么了"） | 343-360 | TaskControl | **不改目标** |
| 5 | 短输入(≤12字) + 寒暄词 | 363-374 | Conversation | 不改目标 |
| 6 | **疑问句（含 ?/什么/怎么/为什么/吗…）且无产物动词** | 381-410 | **Conversation** | **不改目标** |
| 7 | 其余 | 412 | GoalMutation | 改目标 |

**只有 GoalMutation 会更新目标**（loop.rs:4643 `goal_changed = matches!(input_kind, GoalMutation)`；4652 `GoalMutation => goal.text.clone()`）。

**规则 6 的加设动机**（代码注释自陈，378 行）：
> 「纯疑问输入…→ Conversation——不动 goal、不 revision++（**revision 峰值 71 实证的机械侧收口**）」

**即：为了压住目标版本号暴涨到 71，把所有疑问句判为"不改目标"。副作用 = 用户提问永远无法成为新目标。**

**规则 4 的副作用**：A8 的三条编号指令「1.继续尝试…2.…3.先登记…」因含"继续"整条被判 TaskControl → **三条指令全部作废**。

### 第二层：产物判定层——默认兜底把一切推向"必须写文件"

**代码**：`goal_requires_product`（loop.rs:~167-306），判定顺序：

1. 命中产物动词（中文 34 词 + 英文 10 词：create/generate/implement/fix/refactor/build/add/update/delete/optimize/deploy）→ **true（产物）**
2. 命中论说信号（中文 40 词 + 英文 6 词：what/why/how/explain/describe/compare）→ **false（问答）**
3. 纯负向约束 → false
4. **不确定 → 默认 true（产物）**（304-305 行，注释「EC-03 安全方向」）

**致命处**：**兜底方向是"产物"**。任何不含中英文论说信号的输入——**包括英文报错日志**——一律被判为产物任务。

后果：套上 product 系统提示（loop.rs:2213-2272）：
- "You are a coding agent that **ONLY uses tool_calls (NEVER text)**"
- "CRITICAL… you **MUST end by calling write_file**…"

→ 模型被强制规划分解 + 写文件，**即使任务本质是"解释一下这个报错"**。

---

### 第三层：完成判定层——完成只有"写盘"一条路，且任务图节点永不完成

**3a. 完成的两条出路**

| 出路 | 条件 | 行号 |
|---|---|---|
| ① 问答直答 | `!goal_requires_product(goal)` **且** 模型**纯文本、零工具调用** | 3291-3299（"qa goal: no tool_calls with text answer — Done"）；2952-2957（all_done 版本） |
| ② 写盘完成 | `self.write_attempted`（模型**尝试过** write_file/edit） | 2959-3005、3318-3326 |

**product 目标下若既无写入又输出文本**（3393-3405）：注入强制指令——
> "You MUST use tool_calls (not text)… reading files is NOT completing the task… a response with no tool_calls after reading is treated as incomplete and will be re-planned."
→ 强制 replan。

**3b. 任务图节点永远 Pending（死锁的关键铆钉）**

通读 `TaskStatus::Completed` 的全部赋值点：

| 行号 | 位置 | 说明 |
|---|---|---|
| 4099 | `mark_nodes_completed_on_accept()` | **唯一调用点在 5127，位于 Done 相位**——即"已判定完成之后"才标记 |
| 4014 / 4123 | do_observe / do_reflect | **仅**处理子 agent 回传结果 |
| 4345 | Replan 分支 | Failed → Pending（回退） |
| 6826/9124/9161/9168/9300 | — | 测试代码 |

**结论：在非委派（主 agent 自执行）的正常路径上，没有任何代码把节点标记为 Completed。**

→ `all_done`（2943，要求全部节点 ∈ {Completed, Skipped, Failed}）**恒为 false**
→ **第一层的问答逃生通道（2952-2957）永不触发**
→ v20 all_done 门（2959-3032）永不触发

## §2 完整失败链（10 步闭环，逐步源码锚定）

```
① 用户输入被判为 Conversation/TaskControl（疑问句规则 / "继续"关键词）
      → 目标不更新，停留在陈旧文本            [loop.rs:405-410 / 343-360]
                    ↓
② 陈旧目标（如英文报错日志）无中英论说信号
      → goal_requires_product 兜底默认 = 产物   [loop.rs:304-305]
                    ↓
③ 套 product 提示："NEVER text" + "MUST write_file"   [loop.rs:2214 / 2254]
                    ↓
④ decompose 出 5 步计划，全部节点 [Pending]          [planner/lib.rs]
                    ↓
⑤ 模型输出文字回答 + 工具调用（两者同一轮）
      → 因 tool_calls 非空，走 Act 分支，文字回答不算完成  [loop.rs:3276]
                    ↓
⑥ Act 执行只读工具（bash/glob/read）→ 无写盘
      → write_attempted 保持 false
                    ↓
⑦ 节点无人标记 Completed → all_done 恒 false
      → 问答逃生通道永不触发                    [loop.rs:2943 / 2952]
                    ↓
⑧ do_reflect：any_completed=false 且 fact_progress=false
      → steps_without_progress ++               [loop.rs:4233-4237]
                    ↓
⑨ planner.reflect 提示词喂给裁决模型的信号只有：
      「Tasks completed: 0/5」「Successful artifact writes: 0」
      「Steps without progress: N」——无"是否已回答用户"字段  [planner/lib.rs:554-597]
                    ↓
⑩ 快路径（连续错误≥3 / 预算=0 / 剩余<15%且无进展≥2 / 无进展≥5→replan×3→GiveUp）
      或 LLM 慢路径判 give_up                    [planner/lib.rs:479-534 / 628-643]
                    ↓
   ✗ Task failed —— 而模型中途其实已经给出了不错的文字回答
```

## §4 假阳性侧（B2/B4）——同一个根因的另一面

| # | 现象 | 机制 |
|---|---|---|
| B2 | 写完 plan.html 即判 ✓ 完成，**第 3 步"告诉我文件在哪、每步做了什么"从未回答** | 完成判据 = `write_attempted`（2959）。**只要"尝试过"写入就获得完成资格**，与用户意图是否被满足无关 |
| B4 | 重复执行**上一轮**任务（重写 unverified_probe.txt）后判 ✓ 完成，**用户要的三点总结从未给出** | 同上；且因目标未更新，规划仍在跑陈旧任务（第一层死锁） |

**同一条判据（write_attempted）同时制造：无写入 → 假阴性失败；有写入 → 假阳性完成。**

## §8 修正后的修复方向（三个精确断点，替代上一轮的笼统"归还模型"）

> 仍为**问题描述级**，不含 patch；实现细则归执行窗口。

| 断点 | 位置 | 建议改法 | 预期解开的结 |
|---|---|---|---|
| **B1 目标铆钉** | loop.rs:405-410（疑问句→Conversation） | 疑问句不应一律不改目标；改为「疑问句 **且** 当前有未完成目标 → 允许更新目标」，或引入 revision 软上限（如窗口内合并而非硬封死） | 用户追问/指令能成为新目标，解 A4/A5/A7/A8/A10 |
| **B2 兜底方向** | loop.rs:304-305（不确定→产物） | 不确定时**默认改判问答**，或交模型自证（"这任务需要改文件吗？"一次低耗调用） | 英文日志、模糊指令不再被逼写文件，解 A3/A9 |
| **B3 完成铆钉** | 无代码标记节点 Completed（4099 仅在 Done 后调用） | 让主 agent 执行路径能标记节点完成（工具成功且产出符合节点描述即可标 Completed），使 `all_done` 可达 | 让 2952 问答逃生通道与 v20 门真正可达，解"有文字回答却 failed" |

**配套（不改判定权，只改喂给裁决模型的信号）**：
- `Observation`（agent-types/src/lib.rs:76）与 reflect 提示词（planner/lib.rs:554-597）**增补"本轮是否已向用户输出文字回答"字段**——这是成本最低、风险最小的一刀，可直接解 A3/A6/A10 型"答得好却判失败"。

**建议施工顺序**：B3（解死锁铆钉）→ 配套信号（解终态背离）→ B2（解兜底误判）→ B1（解意图进入）。B3 与配套信号可先行，二者均为低风险且直接命中 80% 失败率。
