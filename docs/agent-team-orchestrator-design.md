# Agent Team Orchestrator 设计（多角色协作编排框架）

> 状态：v0.1 设计稿（顶层视角，非实现）。目标：把"人定方向、AI 组队自动协作"从手工配合变成可复用框架。
> 关联：codex-rust 的窗口纪律（`MEMORY.md` 分工铁律）、基因系统 G0-G3（`gene-expression-system-design.md`）、维护规程（`maintenance-protocol.md`）。

## §0 结论摘要

- **可行性：完全可实现。** 本环境已具备全部积木——`Agent` 子agent、`SendMessage` 双向通信、`TeamCreate` 团队、任务追踪、技能绑定、自动化（cron）。codex-rust 本身就是这套思想在"单一 agent 内部"的雏形。
- **核心产物**：一个 **编排器（Orchestrator）** + **角色目录（Role Catalog）** + **工作流引擎（Workflow DAG）** + **原则内核（Principles）** + **共享工件库（Artifact Store）**。
- **最大风险点（也是你担心的）**：信息共享失真。解法不是"让 agent 自由聊天"，而是**结构化交接工件 + 单一事实源**，下文 §7 专述。
- **落地形态建议**：封装为一个可复用 **Skill `multi-agent-team`**，人接任务后一句话触发编排。

## §1 现状核实：双向沟通的真机制

| 层 | 机制 | 是否真能双向通信 | 说明 |
|---|---|---|---|
| codex-rust "窗口" | 共享 memory 文件 | 否（约定） | 无运行时隔离、无消息队列；靠人肉同步 |
| WorkBuddy 子agent | `Agent` + `SendMessage` | **是（工具能力）** | 子agent 可主动给主agent/队友发消息（`type=message`），支持 `broadcast` |
| 团队协调 | `TeamCreate` + 共享 TaskList | 是 | 队友在统一任务列表认领/交接 |

> 设计必须建立在第二行，而非第一行。这是我们"不信计划信源码"纪律的直接应用——别把约定当机制。

## §2 总体架构（ATO）

```
                    ┌─────────────────────────────┐
                    │     Orchestrator(编排器)      │
                    │  接任务→分类→组队→派工→守门   │
                    └──────────────┬──────────────┘
                                   │ 调度/消息
        ┌──────────┬──────────┬────┴────┬──────────┬──────────┐
      PM(产品)   Architect  CoreDev  Reviewer  TechWriter  DevOps/Sec
        └──────────┴──────────┴────────┴──────────┴──────────┘
                                   │
                    ┌──────────────┴───────────────┐
                    │   共享工件库 (Artifact Store)   │
                    │  markdown/规范/代码/测试 单一事实源 │
                    └───────────────────────────────┘
                                   │
                    ┌──────────────┴───────────────┐
                    │   质量闸门 (Quality Gates)       │
                    │  lint/test/typecheck/wiring 断言 │
                    └───────────────────────────────┘
                                   │
                       人类闸门 (Human-in-loop)
```

- **Orchestrator**：唯一调度者。持 TaskList，按工作流 DAG 派活，在每阶段结束前强制质量闸门，在约定检查点暂停等人。
- **角色目录**：每个角色 = 系统提示 + 允许工具 + 绑定技能 + 产出契约 + 质量闸门。
- **共享工件库**：所有角色读写同一组结构化文件（非自由聊天），杜绝失真。
- **人类闸门**：需求澄清、方案选型、代码终审、发布批准——人只在"决策点"出现。

## §3 角色目录（可扩展）

| 角色 | 职责 | 绑定技能/工具 | 质量闸门（角色结束前必跑） |
|---|---|---|---|
| **PM（产品经理）** | 需求澄清、范围界定、验收标准 | 文档/对话、AskUserQuestion | 需求文档含可测验收条目 |
| **Architect（架构师）** | 方案设计、技术选型、权衡 | codex 架构知识、画图 | 方案含决策记录 + 风险 |
| **CoreDev（核心开发者）** | 编码实现 | 写码、Bash、Git worktree | `fmt && clippy && test` 全绿 |
| **Reviewer（代码审查员）** | 初审、安全/规范 | grep/读码、审计方法论 | 列出阻塞项 + 非阻塞项 |
| **TechWriter（文档工程师）** | 文档生成 | 文档技能 | 文档与代码 API 一致 |
| **DevOps/Sec（运维安全）** | 部署、流水线、安全审计 | Docker/CI/密钥审计 | `/healthz`+真探活、无硬编码 key |

> 每个角色是"岗位描述 + 工具白名单 + 技能绑定 + 产出契约"，不是一个人格。这就是 codex-rust "G0 审批门 / G1 wiring 断言"在协作层的映射：人类闸门=G0，自动闸门=G1。

## §4 工作流引擎（按项目类型选模板）

**软件开发模板（你的例子）：**
```
需求澄清(人主导)
   → 方案设计(Architect 生成 → 人评估选择)
   → 代码实现(CoreDev 编码 → Reviewer 初审 → 人终审)
   → 测试验证(QA/Reviewer 生成用例+执行 → 人探索性测试)
   → 文档交付(TechWriter 生成 → 人审核)
   → 部署上线(DevOps 自动化 → 人批准发布)
```
每个箭头 = 一次**结构化交接**（产出文件落入工件库 + 闸门校验通过），而非口头传递。

**其他模板**：文档写作（PM→Writer→人审）、研究（Researcher→Writer→人审）、运维（DevOps 人审）。模板可注册进目录，新增项目类型只加一条模板。

## §5 执行原则 → 具体机制映射

| 原则 | 在本框架如何实现 |
|---|---|
| **Plan Mode 先行** | Orchestrator 先让角色出计划 + 人审批，再派执行活（对应 Agent 的 `mode=plan`） |
| **并行隔离** | 每角色 subagent 在独立 git worktree / 独立子目录工作，互不踩文件 |
| **即时反馈（质量闸门）** | 角色结束前 Orchestrator 校验其闸门（lint/test/断言）；不过则打回重做 |
| **夜间编码 + 日间审查** | 用 `automation_update` 设 02:00 cron 跑"批量模式"编排器；白天人审工件 |
| **模型分级** | 派活时给角色指定 `model`：简单（lite）、复杂推理（reasoning）、默认（main） |

## §6 与 codex-rust 原语的映射（为什么靠谱）

| codex-rust | 本框架 | 含义 |
|---|---|---|
| `LoopPhase` Init/Plan/Act/Observe/Reflect | 每个角色的微循环 | 单 agent 内循环 → 多角色各自循环 |
| **G0 审批门** | 人类闸门（需求/方案/终审/发布） | 不可绕过 |
| **G1 wiring 断言** | 质量闸门（lint/test/断言） | 自动、必挂 |
| **G2 经验** | 工件库历史 + 复盘 | 可检索 |
| **G3 宪法** | 框架总则 + 项目约束文件 | 偏置，≤10 条 |

> 这证明你的想法不是空想——codex-rust 已经在一个 agent 内部验证了"相位 + 硬边界 + 降级通道"的有效性。本框架只是把"一个 agent 的多相位"放大成"多个岗位 agent 的多相位"，并加上真实的跨 agent 通信。

## §7 信息共享失真的解法（你最担心的点）

手工配合失真，根因是**信息靠自由文本在人间/窗口间传**。本框架用三条硬规则消弭：

1. **单一事实源**：所有结论落工件库文件（需求.md / 方案.md / 代码 / 测试报告），角色只读文件、不读"别人说过什么"。
2. **结构化交接契约**：每个阶段产出有固定模板（背景/决策/风险/验收），下游角色按字段消费，不靠理解。
3. **闸门即校验**：Reviewer/Orchestrator 在交接点校验"上游产物是否达标"，不达标打回——失真在闸门处被截住，不会放大。

> 这正好对应你之前在 codex-rust 定的"三层审查（存在→行为→表达力）"：工件库让每一层都可核验。

## §8 可行性评估 + 诚实缺口

**已实现（真能力）**：子agent 调度、双向消息、团队任务、技能绑定、cron 自动化、模型分级、质量闸门（靠角色 prompt + 编排器校验）。

**缺口（必须正视）**：
- **上下文隔离**：subagent 各自有独立上下文，"共享大脑"不存在——靠工件库补，不是自动的。
- **闸门非强制**：subagent 不会自动跑闸门，需 Orchestrator 在派活后主动校验（或角色 prompt 强约束 + 编排器复核）。
- **subagent 漂移**：复杂任务可能偏航，需人类闸门兜底 + 阶段小步快跑。
- **worktree 隔离**：依赖 git worktree，多角色并发改同一仓时需 Orchestrator 管合并。

## §9 分阶段实施计划

- **P0（骨架）**：角色目录（6 角色描述文件）+ Orchestrator 提示词（分类→组队→派工→守门）+ 工件库目录约定。先用手工触发验证。
- **P1（工作流）**：软件开发模板 + 文档模板 + 人类闸门点定义 + 质量闸门校验逻辑。
- **P2（自动化）**：封装为 Skill `multi-agent-team`；加 cron 夜间批量模式；模型分级落地。
- **P3（观测）**：每轮协作产出"交接追溯链"（谁在哪个阶段产了什么、哪道闸门拦截过），给人复盘。

## §10 建议的首个落地形态

封装为 **Skill `multi-agent-team`**：
- 触发：「组个队做 X」「按软件开发流程跑 Y」。
- 行为：问清项目类型 → 调对应模板 → 派角色 subagent → 跑闸门 → 在 human gate 暂停等人。
- 复用：角色描述、工作流模板、原则都存技能目录，跨项目可用。

> 这把"人定方向、AI 组队"从你的手工协作，变成一句口令触发的标准动作。
