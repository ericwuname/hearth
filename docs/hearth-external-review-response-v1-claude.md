## 一、对预注册问题 Q1-Q6 的正式应答

### Q1：三层死锁 + B 臂 27%→80% 复测，根因诊断是否成立？有哪些未被排除的替代解释？

**成立，但只成立于"给出解释的那一部分"，不能推广为"完整解释"。**

三层死锁模型（目标路由/产物判定/完成判定）本身证据充分：外部深挖报告 10/10 回代命中、B 臂经过**干预实验**（不是相关性观察，是真的改代码再测）从 27% 提升到 80%，这是因果证据，不只是描述性统计。这部分我认可。

**但至少两处替代解释/覆盖范围问题尚未排除**：

1. **A 臂数据仍然缺失**（材料自己在 §10-4 已披露）。A 臂原本的"15/15 伪通过"掩盖了 11 次隐藏的 give_up（靠曾经写过盘侥幸救回）。修法 A 新增的救回口（`tool_exchanges_this_run ≥1`）救的是 B 臂那种"criteria 空"的场景，**没有证据表明它同样能救回 A 臂那 11 次隐藏 give_up**——那 11 次的前置条件可能和 B 臂完全不同。在 A 臂 post-fix 数据出来之前，"根因诊断成立"这句话只能限定在"B 臂代表的那一类失败"上，不能扩大到"解释了 80% 失败率的全部构成"。
2. **这个模型没有覆盖我在更早一轮独立盲测（v0.2.18，非本包引用的语料）里发现的另外两类失败**：①用户一句情绪性吐槽被误判成需要选择的"目标变更"，机械切成两个语法不通的选项；②用户追问"上一轮为什么失败"这类元诊断问题，会系统性地更容易连续撞上 T4 停滞检测，形成连续 20+ 轮无法恢复的失败序列。这两类现象**不经过"产物判定/完成判定"这条链路**——它们是在更早的"意图分类"阶段，或者是"停滞检测对元诊断类任务的适应性"上出的问题，和三层死锁模型描述的机制不是同一条因果链。如果这两类现象仍然存在（材料没有提到已经修复或已经排除），那么"三层死锁"顶多是**造成失败的多个独立机制之一**，不是唯一根因——这个限定语气上的差别，建议在冻结材料里明确写出来，不要让"根因坐实"这个措辞暗示"已经找全了所有根因"。

**建议**：把 golden 集/SimUser 语料库明确检查一遍，确认里面有没有覆盖"纯情绪表达被误判"和"追问失败原因导致连续停滞"这两类具体场景。如果没有，这不是苛求——这两类是目前唯一一次真实盲测里被直接观察到、且造成了整个会话不可逆失败的现象，理应进测试语料，而不是停留在旧文档里没人跟进。

### Q2：RC1 教训（完成置位=事实校验，非 LLM 自报）与"模型驱动节奏"的合成架构是否正确？在成熟底座上如何避免重蹈"模型自报假完成"？

**架构判断正确**，而且这正是我在上一轮直接指出"战略转向路径书"最大技术风险的那条——很高兴看到材料把它从"叙事错误"改成了正式的架构原则（"判定权分层：模型驱动节奏 + 事实校验守门 + 问答路径补全覆盖"）。这不是各打五十大板式的妥协，是把两个原本被文档描述成互斥的立场，正确地拆成了互不冲突的两层。

**在借来的底座上如何落地，材料目前没有回答，这正是 Q2 真正在问的部分**：三红线里"不改底座内核"意味着 Hearth 没法在 Codex CLI / Goose 自己的完成判定逻辑里插一刀。唯一站得住的做法是：**让"事实校验"完全活在 Cognition 层，做成一层独立于底座完成信号的、事后审计式的复核**——底座说"完成了"，Cognition 层的 Evidence 模块独立去检查实际产物/测试结果，校验不通过就在投影给用户时标注"未验证"，不管底座自己怎么宣称。

**这直接影响战略地图 v3.0 的排期**：地图里把 Evidence/Verification OS 放在 S5（第 5 阶段，Discovery 之后），但按 Q2 这个要求看，这不是一个可以往后排的"进阶能力"，是**Cognition MVP（S3）如果没有它，第一天就会在新底座上重演"模型自报假完成"这个已经用两个月证明过会发生的问题**。建议把 S5 里"独立于底座完成信号的最小事实校验"这一小块拆出来，提前并入 S3 的验收范围，不要等到 S5 才做。

### Q3：FZ-RFC-1/2b 事后追认，是否同意签署？S-2 补测是否为必要前置？

RFC-2b：材料给出的四锚点核对方式清楚，残留 OD-1 已显式登记，**同意签署**。

RFC-1：**S-2 是必要前置，不是"建议尽快补"的可选项**——材料自己写的风险是"`tool_env` 注入被清 → egress 白名单静默失效"。这是一类我们在这几周反复遇到过的模式：**一个安全控制在没有覆盖到的场景下会安静地失效，而不是报错**（同一类问题在更早的 cgroup fail-closed 测试上也出现过）。在这类"静默失效"风险被 S-2 集成测试排除之前，我的建议是**不要用"有条件签"这种模糊状态**——要么明确写成"未签署，阻塞项=S-2"，要么等 S-2 数据到手再签，不要让"有条件"变成事实上已经签了、只是嘴上留了个尾巴。

### Q4：v0.2.23-final 归档 + 引擎降级为可选底座 + 认知层独立成体，有哪些未识别的风险与盲点？

三个材料里都没有覆盖到的风险：

1. **底座的扩展面本身不受 Hearth 控制，会变**。Codex CLI / Goose 都是由别的组织在快速迭代的项目，它们的 MCP/hooks/extension 接口今天存在，不代表半年后还是同一个形状。"三红线"里的"只走标准扩展面"防的是 Hearth 自己手贱改底座内核，但**防不住底座自己改扩展面**。建议在 HCC（Host Capability Contract）的 H6 Extension 这一项里，除了"有没有扩展机制"，加一条"这个扩展机制过去一年的破坏性变更频率"作为选型判据，不然半年后可能出现"底座团队重构了扩展 API，Hearth Cognition 层大面积返工"这个新版本的"抄错答案"。
2. **测试基建（SimUser/analyzer/correlation matrix/personas/scenarios）目前深度耦合在驱动 Hearth 自己的 CLI 上**。golden 集/盲测矩阵这套东西是这两个月最值钱的资产之一，但换底座之后，PTY driver 需要驱动的是 Codex CLI 或 Goose 的命令行/REPL，不是 `hearth` 这个二进制——这个移植成本，目前三份材料的路线图里都没有单独列出来，容易被当成"顺手就能改"，但实际上可能是 Cognition MVP 阶段一笔不小的隐藏工作量，建议现在就估一下。
3. **"1+1"对一个人维护的项目，认知负荷不一定真的比"1"低**。同时维护"理解一个外部 27-crate 项目的内部行为、跟踪它的版本变化"和"设计维护自己的认知层"，这两件事加起来需要跟踪的东西，不见得比"维护自己完全掌控的一套系统"更少——这不是反对转向，是提醒一句：转向节省的是"重复造轮子"的工程量，不必然节省"需要持续跟踪、理解的系统数量"，这两者是不同的成本维度，规划资源时值得分开算。

### Q5：双底座三红线是否足以防"两头烧"与"wrapper 变厚"？需要补哪条？

不够，"不做 wrapper 增厚"目前是一句原则，没有可操作的判据——这正是这个项目反复吃过亏的那种"说得对但落不了地、检查不出违规"的表述方式（"不擅自扩 scope"这条铁律，这几周已经被违反过至少两次，都是先做了才被发现）。建议补两条：

- **第四条：可归属性**——Cognition 层新增的每一块代码，必须能明确对应到六个认知能力（Intent/Evidence/Discovery/Memory/Learning/Interaction）里的哪一个，并且能回答"如果这块代码不存在，盲测里哪个具体场景会重新失败"。答不出来就是 wrapper 增厚，不用等事后靠感觉判断。
- **第五条：定期复健**——安排一个周期性检查点（比如每隔一段固定时间），把当前 golden 集重新在"当前底座 + 当前 Cognition 层"上跑一遍。理由很直接：Hearth 自己的引擎就是在"没人定期回头拿真实数据检查"的情况下，一路优化到 80% 失败率才被发现——不要让同样的模式在新底座上无声重演。

### Q6：在 502:0（测试:行为断言）与 50:24（文档:代码）的激励结构证据下，最优先的流程修正是什么？

**把 golden 集回归跑批做成核心逻辑变更的强制门禁**，而不是停留在"以后要注意"的治理原则层面。具体说：任何触碰完成判定/意图路由/停滞检测这类核心决策逻辑的改动，合入前必须带一次 golden 集（哪怕只挑一个小子集）复跑，且有明确的不回归阈值，跑不过不能合——这样"测试要覆盖用户行为"这件事，从一句大家认同但没人强制的原则，变成一道机器会拦人的门。产出秩序令（D6）管的是文档纪律，是对的，但它依赖自觉；把 golden 集接成 CI 门禁，依赖的是自动化，不依赖自觉，后者更结构性、更难被绕过。

## 二、材料自身未发现的补充问题

### 2.1 RC51（裸 ERROR 泄漏到终端）的独立验证锚点缺失

材料 §3.2 提到"RC51-A/B（tracing 直灌终端）已在 P4 Node 05 修复"，但 §8.1 的可复现验证命令清单里，**没有一条专门对应这次修复的 grep/测试**。这个 bug 是我在更早一轮盲测里发现的、直接反驳当时"零 Projection 失真"声明的那个具体反例，是这几周材料里最硬的一条反证——它的修复理应有和其他根因链条同等级别的、可以直接执行核对的锚点，不该只用一句"已修复"带过。建议补一条命令进 §8.1，比如确认对应的 `tracing::error!` 调用点是否已经改成不再直写 stderr，或者补一个能触发原场景、确认裸 ERROR 不再出现的最小复现步骤。

### 2.2 数字口径分歧的处理方式，值得肯定，但还有一步没走完

§10 把 61vs63、18vs12、497vs502 三处口径分歧都解释清楚了（前两处是"度量对象不同"，后一处是"统计时点/统计方式不同"）——这个处理方式我认可，比上一轮"直接采信一个数字"要诚实得多。但"未裁决"不应该是终点：既然已经搞清楚了两种口径分别在测什么，**建议明确规定以后统一用哪个口径对外报告，另一个作为内部细节保留**，不然以后每次引用这几个数字，都要重新解释一遍"看你说的是哪种口径"，这个成本会一直累积下去。

### 2.3 战略地图 v3.0 里一处内部矛盾

地图 §0 的架构图把"Standard Host"画成"身体/执行环境"、把"Hearth Cognition"画成"大脑之外的认知环境"——但 Q2 已经确认的架构原则是"事实校验守门"，**校验这个动作，性质上更接近"大脑"该干的事（做判断），不是纯粹的执行环境该有的能力**。这不是文字游戏：如果"认知层"被理解为"纯粹附加在执行层上面的观察/建议层，不介入判定"，那么 Q2 要求的那种"底座说完成了，Cognition 层独立复核并有权改变用户看到的最终判断"就无法实现——这需要 Cognition 层对最终呈现给用户的结果有**否决权/改写权**，不只是并列观察。建议在 HCC 或 Cognition MVP 的设计里明确写清楚这一点，不要让"身体/大脑"这个比喻不小心把"认知层只能建议、不能否决"这个错误预设带进后续设计。

## 三、总体建议

三份材料的方向我认为是对的，比一个月前那份仓促的"战略转向路径书"扎实太多——尤其是把"引擎失败"和"项目失败"解耦这个判断（§七"取消自研 Harness 对整个项目的生杀大权"），是这几轮讨论里最重要的一次认知升级，值得保留并坚持。

在正式把战略地图定版为"Hearth v1.0 战略蓝图"之前，建议按优先级处理：

1. **A 臂数据补齐**，明确"根因诊断"的适用范围到底覆盖了多大比例的原始失败；
2. **把 Q2 的架构含义（Cognition 层需要对完成判定有否决权）写进 HCC 设计**，不要等做到一半才发现地图的比喻和实际需求打架；
3. **五条红线**，防止半年后在新底座上，重新发明一遍这个项目已经花两个月学到的教训；
4. **golden 集接入 CI 门禁**，把 502:0 这个数字，变成一件已经被结构性修好的事，而不是一条被反复提起的教训。
