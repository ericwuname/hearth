# 一、对 Claude 四点的复核

## 1. 「Node 01/Node 04 判级被提前写死」—— ✅ 成立，且我认领一半责任

任务书 Node 01 写「**不是 F0-6 反例**」、Node 04 写「**登记 F9/拦截链可观测性缺口**」——这两句确实是我上一份总览里的判断，被直接搬进了施工任务书。**判断本身可以留在评审报告里（那里有推理链），但写进任务书就变成了预设结论**，执行窗口会去"证明"而不是"查明"。

**改法（把结论换成判级口径，结论留空）**：

- **Node 01 判级口径**：F0-6 的判据是「**错误输出被投影为成功**」。
  - 若实测满足（错误被渲染成成功态）→ `NEW F0`，立即上报顶层；
  - 若仅泄漏而未被投影为成功 → 按 **Projection isolation + completeness** 登记（F1/F2 由执行窗口按影响面判），并给出 CLOSURE §7 的拆分建议（isolation / completeness / correctness 三行）。
- **Node 04 第 2 条判级口径**：give_up 字样与 completed 共存，**先做定性再判级**：
  - 是报告文本命中 → `FALSE POSITIVE`，须写出反证；
  - 是拦截行为却无痕迹 → 登记可观测性缺口；
  - 两者都排除 → `EVIDENCE GAP`。

> 一句话原则：**任务书写"怎么判"，不写"判成什么"。**

## 2. 「fresh 组复用旧 probe 数据，但缺 planner dump」—— ✅ 成立，**且比 Claude 说的更严重**

Claude 说的问题是"没有 dump 数据 → Node 03 对比做不了"。**还有一个更强的混杂变量他没提**：

> 我的 probe 用的是 **one-shot `hearth chat`**（每次独立进程、跑完即退）；而盲测是 **REPL 长会话（单进程持续累积状态）**。

也就是说，若 Condition A 沿用我的数据、Condition B 用 REPL 重放，那么两组之间差了**两个变量**：①会话内容是否被污染 ②会话形态（one-shot vs REPL）。**这样做出来的 diff 无法归因。**

**改法**：
- Condition A **必须重跑**，且**会话形态与 B 对齐（都用 REPL）**；
- A 侧先跑 N 轮**非污染填充对话**（N 与 B 的前缀轮数相同），再发同一请求 → **唯一变量 = 前缀内容**；
- 两组都开 `HEARTH_DEBUG_PLANNER_INPUT=1`，dump 字段清单与归档格式预先写死（prompt 快照 / TaskGraph fingerprint / 压缩摘要全文 / anchor / goal_revision / T4 触发点 / Reserve / 终态）。

## 3. 「重放截止点未定死」—— ✅ 成立，**我给出决定性依据，可以直接定死**

任务书写的是「run-001…012 **或**至首个 T4 触发点」——这是二选一，不同人跑会产出不同的"污染态"。

**本窗逐轮归因的一手数据**：

| 事实 | 数值 |
|---|---|
| 首个 T4 事件 | **run-003**（该轮 **成功**） |
| run-004 ~ run-012 | **连续 9 轮成功，零 T4 事件** |
| 吸引子起点 | **run-013**（此后 24 连败） |

→ **结论：截止点必须定死为「run-012 结束处」。**
理由（可复核）：首个 T4 出现在 run-003，而此后还有 9 轮成功——若按"首个 T4 触发点"截断，重放出来的是一个**历史上并不失败的会话**，整个 B 组实验会失去意义。
→ 附带结论：**T4 是必要非充分条件**（run-003 曾 T4 而成功），Node 03 不应把 T4 当作吸引子的定义特征。

## 4. 「环境快照缺失」—— ✅ 成立，**我补具体清单 + 一个 Claude 没注意的机器差**

必须先把**原始盲测当时的运行环境**固定下来，三组实验统一复用：

| 项 | 要求 | 备注 |
|---|---|---|
| **主机** | **盲测在 `.133`；我的 probe 在 `.131`** | ⚠️ **这是一个真实的机器差**，Claude 未提。三组必须同机（建议 `.133` 以贴近原始盲测），或在另一机重跑盲测一小段做机器漂移校验 |
| binary | `--version` + **sha256**（不能只报版本号） | v0.2.18 (unknown) 不足以锁定 |
| env | `HEARTH_ALLOW_NO_CGROUP`、`HEARTH_URL` 必须 unset、`HEARTH_TASK_TIMEOUT_SECS`、新增的 dump 开关 | 缺一项即漂移 |
| 运行参数 | `--budget` / `--deadline` / cwd / 是否 `repl` | 我的 probe 用 budget 30，与盲测不同 |
| provider/model | Agnes / agnes-2.5-flash + config.toml 快照 | |
| 时间口径 | 时间戳统一 UTC；**Agnes 历史延迟波动 28–55s** | 必须错峰 + 每条件 ≥3 跑，否则差异可能来自 provider 抖动而非会话污染 |

# 二、本窗的两条补充（Claude 未覆盖，其中一条改变归因方向）

## 补充 A（重要）：压缩时序**否证**了 Node 03 的摘要链主假设

任务书 Node 03 §4 提出假设（标注为"本窗推测，须证伪或证实"）：
> 「60 字墓碑 + Debug 格式摘要 + 锯齿式压缩 → planner 看到的历史退化 → 每轮拆出同构图 → T4 → 更多摘要 → 恶性循环」

**本窗一手数据**：

| 事件 | 轮次 |
|---|---|
| 吸引子起点（24 连败开始） | **run-013** |
| **首次压缩摘要出现** | **run-024**（仅 run-024/025/026 共 16 行，首现 L2809） |

→ **压缩比吸引子起点晚了 11 轮。** 因此"摘要链 → 同构图 → T4 → 吸引子"这条因果链**在时序上不成立为起因**；压缩更可能是**后果/放大器**（失败轮堆积 → 上下文膨胀 → 触发压缩 → 摘要质量差 → 更难恢复）。

**建议改法**：Node 03 §4 从"待证实的主假设"下调为「**已否证为起因，保留为放大器假设**」，并把主因搜索资源转向补充 B 的方向。**不要让执行窗口把主因押在压缩上。**

## 补充 B（重要，并含我的自我修正）：吸引子的入口是「继续」型输入，不是元诊断型

**run-012 → run-013 边界原文**（一手）：

```
L1582 [run-013 的输入]  hearth> 〉继续你的提议吧
L1776 [run-013 的结果]  📄 执行报告: .../run-013.md
L1777                   ✗ Task failed — status=failed（18 步）
L1779 [run-014 的输入]  hearth> 〉当前轮出现了✗ Done (18 steps)，这个是出现了什么情况呢
```

→ **进入 24 连败的那一轮，用户输入是「继续你的提议吧」（继续型），不是元诊断型。** 用户是在 run-013 失败之后，才转成"为什么失败"的元诊断追问——**元诊断失败是继发，不是入口**。

**由此我修正自己上一轮的结论**：
- 我此前写「fresh 元诊断任务 2/2 completed → 归因于会话污染」。该数据仍然真，但**它只排除了"元诊断任务天然易停滞"，并没有证明"会话污染是主因"**——因为入口事件是继续型，而我 fresh 侧从未测过继续型。
- **修正后的表述**：`元诊断型请求在 fresh 下可通过（2/2）；污染不是元诊断失败的充分条件。吸引子入口为「继续」型输入失败，须补测 fresh 继续型后再定因果。`

**给 Node 02 的硬要求**：两种请求型**都要测**——①元诊断型（已有 fresh 2/2）②**继续型（新增，且优先级更高）**。
并给出一个**更具体的可证伪假设**供 Node 03 检验：
> **RC52 可能与 RC47（"继续"续轮 planner give_up / 已完成+继续形态）同族**——入口是决策层缺陷（planner 不知道任务已完成），而会话污染是**放大器**不是起因。
>
> 判定实验：fresh 会话中复现"已完成 + 继续"形态（先跑一个能完成的任务，再发"继续你的提议吧"）：
> - 若 fresh 也失败 → **主因 = RC47 族（决策层）**，会话污染为放大器；
> - 若 fresh 成功、polluted 失败 → **主因 = 会话污染**。

# 三、对《拟真用户测试台》规划书的评审

总体：设计扎实，`tools/simuser/` 定位为**开发侧工具、不进 Core** 这条红线保住了冻结边界；双通道日志（终端侧 vs Hearth 侧）恰好把 P0-C 的四层 completion 变成可测量——这是整份规划里最有价值的一处。以下四点是补强，不是反对。

## 3.1（🔴 建议改）模拟用户应与被测 Hearth **异源**

规划书写"模拟用户与 Hearth 同用 Agnes（同源）→ 结论标注 same-provider simulation"。**只标注不够**：同源意味着同一个模型的盲区会在"用户侧"和"系统侧"**同时出现**，这类缺陷永远测不出来——这就是验证悖论的另一种形态（我在生产级 QA 框架调研里也得到同一结论：模拟器须与被测通道不同）。

**改法**：默认用**异源 provider** 驱动模拟用户（智谱 / 本地 Ollama `qiyuan-8b` 均可），把"同源"作为**对照条件**显式跑一组并标注。成本极低（用户侧调用远小于系统侧）。

## 3.2（🟡 建议补）persona 库缺「元访谈者」

现有五种 persona（explorer / taskdriver / diagnoser / chatty / longsession）覆盖了大部分形态，但漏了**本项目历史上最高产的探针**：

> **元访谈者**：连问同一个问题、质疑具体数字（如"填充率 83%→65% 回落不太准吧"）、追问"你记得我的第一个问题吗"。
> 历史证据：RC36（8 问 0 答）、RC39（输入分类无疑问句）、RC40（fill_pct 语义错位）**全部由这一类交互暴露**，而它们此前躲过了所有脚本化测试。

建议新增 `personas/meta-interviewer.md`，语料直接取自四份手工日志的元访谈段落，**优先级排在 diagnoser 之前**。

## 3.3（🔴 建议补）`file_issue` 必须有**确定性触发兜底**

规划书 §3.2 已写明"self-report ≠ evidence"（INV-G 血统），方向正确。但还有一个洞：

> **file_issue 由模型自己发起 → 依赖模型自觉，而"不自觉"恰恰是本系统已知缺陷之一**（历史上多次"自述已验证"为假）。

**改法**：双通道——
1. **确定性触发（系统侧，不依赖模型）**：`stalled` / `give_up` / `approval_denied` / `verify_failed` / 工具五态异常 命中时，由 loop 自动写一条结构化 issue（与 F9 `giveup_unverified` 标记同构）；
2. **模型补述（可选）**：模型在此基础上补 category/描述，但**不得删除确定性记录**。
并明确：issues 落盘 **session 隔离**（复用 RC49 的 session 绑定教训），且**不进 LLM 可见上下文**（除 `known-issues.md` 摘要），避免成为第二事实源。

## 3.4（🟡 建议细化）第一验收标准要能复现**入口事件与时序**，不只是"后段连败"

现有验收："用 longsession + pollution-prefix 复现『前段高成功率 + 后段 T4 连败』形态"。
建议**加严为三条可判定形态**（都用本窗一手数据作基准）：
1. 前段成功、后段连败的形态；
2. **入口事件 = 「继续」型输入失败**（run-013）；
3. **压缩晚于入口 ≥10 轮**（入口 run-013 vs 首压 run-024）。
→ 三条同时复现才算测试台有效。只复现第 1 条，可能只是"随便都会失败"，不足以证明测试台保真。
