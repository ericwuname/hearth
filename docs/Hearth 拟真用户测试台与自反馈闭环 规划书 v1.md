# 0. 可行性结论（先给答案）

**三个设想全部可行，且大部分积木已经存在**：

| 用户设想 | 可行性 | 关键判断 |
|---|---|---|
| 模拟不同种类的人使用 Hearth，生成测试日志，跑几十上百次 | ✅ 可行 | 拟真用户 = "另一个 LLM 角色驱动 hearth 终端"+ persona 语料库（四份手工日志就是现成种子）+ 双通道日志。**纯开发侧工具，不进 Core，不碰冻结边界** |
| 测试一边测一边改 vs 测试/修复分离 | **必须分离** | 理由见 §4（blind 原则 + 归因纯净 + 已有多窗口工作流，分离成本为零） |
| Hearth 内 AI 自记录问题 → 开发收集评估修复 → 反馈回 Hearth 的闭环 | ✅ 可行 | Core 内加一个最小 `file_issue` 工具（append-only，随下个修复批落地）+ 开发侧收集器/判级流水线 + CHANGELOG 回注。与既有 civ_note / run report / InteractionRequest 复用衔接，不建第二套 |

**最重要的架构红线**：拟真测试台是**开发侧工具**（`tools/simuser/`），永远
不进 Hearth Core——它测 Core，不是 Core 的一部分。这保住冻结边界。

# 1. 为什么做：盲测证明的覆盖缺口

CLOSURE-01 的教训（四方共识）：**脚本化验证的覆盖范围 ≠ 真实交互可靠性**。
四包脚本化证据没有暴露的东西，用户 90 分钟盲测全暴露了（24 连败吸引子、裸
ERROR 泄漏、内容截断、introspect 误路由）。但手工盲测有两个工程缺陷：
①不可重复（人的状态/输入不可复现）；②样本量太小（1 个会话）。

拟真测试台 = **把盲测工程化**：保留"真实感"（LLM 演用户，自由追问、失败后
诊断、情绪化输入），补上"可重复"（seed/persona/剧本版本化）和"规模化"
（几十上百跑）。

# 2. 拟真用户测试台（SimUser）设计

## 2.1 架构（五个组件，全在开发侧）

```text
tools/simuser/
├── personas/          # 用户人格库（语料来自四份手工日志挖矿）
│   ├── meta-interviewer.md  # 元访谈者：连问同题、质疑具体数字、追问记忆
│   │                        # （RC36/RC39/RC40 全由此类交互暴露——历史最高产
│   │                        #   探针，优先级排在 diagnoser 之前，砺 §3.2）
│   ├── explorer.md      # 探索型：乱翻功能、闲聊、自我认知追问（v0.2.8 风格）
│   ├── taskdriver.md    # 任务型：明确的编码/文件任务，验结果（各版本任务轮）
│   ├── diagnoser.md     # 元诊断型：失败后追问"为什么失败了"（RC52 触发者）
│   ├── chatty.md        # 闲聊/情绪/模糊输入（交互面回归）
│   └── longsession.md   # 长会话型：50+ 轮混合输入（污染累积场景）
├── scenarios/         # 场景剧本（seeded，可确定性重放）
│   ├── pollution-prefix.md   # v0.2.18 盲测 run-001..012 逐字重放
│   ├── rc48-sortlib.md       # RC48 复现条件
│   └── ...
├── driver.py          # PTY 驱动 hearth（chat / one-shot），进程级隔离
├── runner.py          # campaign runner：N 跑 × persona × scenario，版本冻结
└── analyzer.py        # 原始记录 → 指标 + 异常段自动标记
```

## 2.2 关键机制

1. **双通道日志（本设计的核心价值）**：
   - 通道 1 = 终端侧：用户（模拟）看到的一切（含裸 ERROR、截断内容）；
   - 通道 2 = Hearth 侧：telemetry + scratch + archive 时间戳 + （归因期开启的）
     planner 输入 dump；
   - 按 session_id + 时间戳对齐 → **"系统做了什么"vs"用户看到了什么"的 diff**
     直接量化 Projection isolation / completeness（P0-C 的四个 completion 层
     从此可测）。
2. **拟真的关键 = 自适应而非回放**：模拟用户 LLM 看到 Hearth 的真实输出后
   自己决定下一句（追问/换任务/情绪化/放弃）——只有"污染前缀重放"类场景用
   逐字剧本。LLM 演用户时**盲于 Hearth 内部**（只准看终端输出，禁止读 .hearth/
   telemetry），否则测的不是用户体验。
3. **确定性控制**：persona 版本 + scenario seed + provider/model/温度 + budget
   固定并记录；每跑记录 full event log（§24 数据纪律沿用）。
4. **异源模拟用户（v1.0 采纳砺 §3.1，默认而非可选）**：模拟用户默认用
   **异源 provider**（智谱 / 本地 Ollama `qiyuan-8b`）驱动——同源意味着同一
   模型的盲区会在用户侧与系统侧同时出现，这类缺陷永远测不出来（验证悖论）。
   同源（Agnes）作为**显式对照组**跑一组并标注 same-provider。用户侧调用
   成本远小于系统侧，异源成本可忽略。
5. **诚实性纪律**：判定指标全部用确定性比对（RESULT 文件、测试通过、日志
   计数），模拟用户的"感觉"只做线索不做证据（INV-G 同构）。

## 2.3 成本估算（Agnes 75k 次/周）

每 run ≈ 40-60 步 × (Hearth 调用 + 用户模拟调用) ≈ 100-150 次 LLM 调用；
**100 跑 ≈ 1.0-1.5 万次/周**，占配额 15-20%，完全可行。可先 30 跑起步。

## 2.4 验收标准（测试台自己的先红后绿——v1.0 加严为三形态，砺 §3.4）

**第一验收：复现手工测试的行为时序**，三条可判定形态**同时**复现才算测试台
有效（基准 = 本窗一手数据）：
1. 前段成功、后段连败的形态（run-013 起 24 连败）；
2. **入口事件 = "继续"型输入失败**（run-012 completed → run-013 "继续你的
   提议吧" failed）；
3. **压缩晚于入口 ≥10 轮**（入口 run-013 vs 首压 run-024，L2810）。

只复现第 1 条可能只是"随便都会失败"，不足以证明测试台保真。
不能复现 = 测试台或剧本有问题（先修测试台，不碰 Core）。

# 3. Hearth 内 AI 自记录问题闭环（file_issue 机制）

## 3.1 闭环全图

```text
Hearth 运行中（住户 AI）
    ↓ 发现异常（自己的失败/工具怪象/交互问题）
file_issue{category, severity, evidence 指针, description}   ← Core 内新工具
    ↓ append-only: .hearth/issues/<session>.jsonl
开发侧收集器（aggregator 脚本）
    ↓ 跨会话聚合 + 去重 + 三角验证（issue 指针 vs 会话日志/telemetry 实证）
评审窗口判级（CONFIRMED / NEW F1 / FALSE POSITIVE / DEFERRED）
    ↓
顶层立项 → 执行窗口修复 → 测试窗口回归 campaign
    ↓
CHANGELOG + known-issues.md 更新
    ↓ 回注 Hearth（constitution/会话上下文注入摘要）
Hearth 内 AI 知道"哪些已修/哪些已知/哪些该报" → 闭环闭合
```

## 3.2 设计要点（防走样的五条纪律）

1. **self-report ≠ evidence（INV-G 血统）**：issue 记录是**线索指针**不是事实
   ——必须带 session_id/step/tool call/日志路径等可复核指针；开发侧三角验证
   通过才算 CONFIRMED。防"AI 自嗨式报 bug"。
2. **确定性触发兜底（v1.0 采纳砺 §3.3，双通道）**：模型自觉不可依赖（本系统
   已知缺陷）——
   - **系统侧自动记录**：`stalled` / `give_up` / `approval_denied` /
     `verify_failed` / 工具五态异常命中时，由 loop **自动**写一条结构化 issue
     （与 F9 `giveup_unverified` 标记同构，不依赖模型）；
   - **模型补述（可选）**：模型在此基础上补 category/描述，但**不得删除确定性
     记录**。
3. **落盘与可见性边界**：issues 按 session 隔离落盘（复用 RC49 session 绑定
   教训）；**不进 LLM 可见上下文**（除 `known-issues.md` 摘要），避免成为第二
   事实源。
4. **限流与去重**：每会话 file_issue ≤3 条；known-issues.md 注入会话上下文，
   已知问题不重复报。
5. **复用不新建**：file_issue 是 civ_note（v13 自我反思）、run report、
   InteractionRequest 的**收敛出口**——把散落的自我观察收进一个结构化通道，
   不建第二套事实模型（M8）。
4. **冻结边界**：file_issue 是 Core 代码改动（新工具，加性、零权威变化、
   sandbox 内 append-only 写）。**必须在 freeze-suspended 状态下走正式任务书
   审批**，随 v0.2.19 修复批落地——不悄悄进。

## 3.3 反馈回注的最小实现

known-issues.md + version-CHANGELOG-summary 两份文件，Hearth 会话启动时注入
精简版（constitution 通道已有先例）。这让住户 AI：①不重复报已修问题；②知道
新能力边界；③它的反馈被响应了——闭环的心理面与工程面同时闭合。

# 4. 窗口分工裁决：**测试与修复必须分离**

用户的两个选项，明确选**分离**，理由三条：

1. **Blind 原则**：修 bug 的人再测，会不自觉绕开雷区（已知哪些输入会崩），
   测试就退化为"验证修复"而非"发现未知"。本轮盲测的全部价值来自"非执行
   窗口、无预设剧本"——工程化时不能把这个属性弄丢。
2. **归因纯净**：campaign 期间 Hearth 版本冻结；若边测边改，同一批数据横跨
   多个 binary，归因直接失效（CFR 阈值优先级缺陷刚教训过我们：证据必须绑定
   精确版本）。
3. **零成本**：多窗口工作流（测试窗口/执行窗口/评审窗口）已现成，分离只是
   按既有节奏走。

**运转节奏**（campaign 制，非流水线制）：

```text
测试窗口：campaign N（30-100 跑，版本冻结）→ 原始记录 + 一手机器分析
评审窗口：判级（CONFIRMED/NEW F1/FP/DEFER）→ 按层归聚类
顶层：立项修复批（一次性攒批——既有约定）
执行窗口：批量修复 + 单元级 smoke 自测
测试窗口：campaign N+1（含 N 轮失败场景重放 = 回归）
```

折中许可：执行窗口修复后可跑**单元级/fixture 级**自测（先红后绿照旧）；
**campaign 级验证必须由测试窗口独立执行**。

# 5. 历史手工日志的挖矿结论（SimUser 的语料基础）

四份日志 = 四类真实用户行为的天然语料 + 跨版本基线：

| 版本 | 规模 | 成功/失败 | T4 停滞 | 用户行为特征（persona 素材） |
|---|---|---|---|---|
| v0.2.8 | 2482 行 | 11 / ~50 | 0 | 探索型：翻"住户反馈"目录、resume 失败排查、自我认知提问 |
| v0.2.10 | 5209 行 | 54 / ~48 | **10** | 自我认知深聊（体感/天赋/模型身份）、任务+闲聊混合 |
| v0.2.15 | 2120 行 | 11 / ~26 | 0 | 跨会话记忆测试、session 边界探测、"住户"视角反馈 |
| v0.2.18 | 3703 行 | 10 / 24（**24 连败**） | **27** | 元诊断追问、失败报告逐字回贴、长会话污染累积 |

用途：①persona 语料（真实措辞、追问模式、情绪模式——不是拍脑袋编的"用户"）；
②回归场景种子（污染前缀重放、RC48 条件重放）；③跨版本指标基线（SimUser
跑出的分布与手工分布对齐 = 测试台有效性验证）。
