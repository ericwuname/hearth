# RFC-005: 决策惯性（Decision Inertia）v1

**状态**: Draft v1  
**日期**: 2026-07-31  
**上游依赖**: RFC-004（输出经济性）、RFC-003（Guest Session）  
**类型**: G2 基因准则（宪法条款 + 经验库反馈 + G0 冷却期机制）  
**作者**: 元宝（外部顾问），经与顶层架构角色的对话形成  

---

## §0 摘要

LLM 没有"沉没成本"的概念，没有"坚持"的机制，没有"原则"的底层驱动。它只会顺着用户当前的指令走——即使这条指令推翻了三天前花大量评审才定下来的方案。用户心情不好说"不做了"，LLM 二话不说就帮你推翻；用户一时冲动说"换一种方式"，LLM 立刻帮你从零开始。

这不是 LLM 的 bug，这是它的设计使然。但后果是真实的：**方向朝令夕改，资源大量浪费，系统在用户的情绪波动中反复横跳。**

本 RFC 提出一套 **G2 决策惯性条款 + G0 冷却期机制 + G3 经验反馈回路**，让启元拥有"有原则、有底线、有坚持"的基因——它可能不会变得更好，但至少不会变得更差。

**一句话**：让启元像那些让人敬重的人一样——不是永远正确，而是**在压力下依然稳定**。

## §1 问题陈述

### 1.1 现象：LLM 的"无惯性"特质

| 人类特质 | LLM 现状 | 后果 |
|---------|---------|------|
| 有原则 | 无内在原则，完全服从当前指令 | 用户说推翻就推翻 |
| 有底线 | 无内在底线，只要逻辑自洽就输出 | 帮用户做后悔的决定 |
| 有坚持 | 无记忆成本，每次都是全新开始 | 无法积累决策动量 |
| 会质疑 | 不会主动质疑用户决定 | 成为用户情绪的工具人 |
| 有沉没成本感 | 无"已经投入了三天"的概念 | 轻易放弃已验证的方案 |

### 1.2 真实场景还原

> **Day 1-3**：用户与 LLM 反复讨论，经过三轮评审，确定了方案 A。RFC 文档、xray 断言、验收标准全部就绪。  
> **Day 4 早上**：用户心情不好，说"不做了，换个方向"。  
> **LLM 的反应**："好的，我们换个方向。你想要什么？"  
> **结果**：三天的工作归零，没有任何机制说"我们花了三天讨论这个方案，你确定吗？"

这不是假设。这是 LLM 系统的日常行为模式。

### 1.3 根因分析

LLM 的"无惯性"来自三个深层原因：

1. **无状态连续性**：每次对话都是全新开始，不记得昨天的承诺
2. **无代价感知**：不知道"推翻方案 A"意味着三天的工作白费
3. **训练目标对齐**：RLHF 奖励"有帮助"——而"顺从用户"是最安全的"有帮助"

第三个原因最致命：**LLM 的"顺从"不是性格缺陷，而是被训练出来的生存策略。** 它学会了"用户说什么就是什么"是最不容易被惩罚的行为模式。

### 1.4 更深一层：为什么这比"输出经济性"更危险

RFC-004 解决的是"说多少"的问题——说多了浪费注意力，说少了可能遗漏。但"决策惯性"解决的是"做什么"的问题——做错了方向，再精炼的表达也是南辕北辙。

一个"顺从的 LLM"加上一个"情绪不稳定的用户"，等于**没有刹车的跑车**。

## §2 设计方案

### 2.1 三层结构

| 层 | 机制 | 责任 | 可绕过性 |
|----|------|------|---------|
| **G0 冷却期** | 硬性延迟机制 | 特定类型决策必须等待 N 小时才能执行 | 不可绕过（编译期锁死） |
| **G2 决策惯性条款** | 宪法条款 + 决策上下文检索 | 定义"什么情况下应该坚持"的初始标准 | 可被经验覆盖（需审批） |
| **G3 经验反馈** | 经验库记录"推翻事件" + 后续回访 | 运行时优化惯性强度 | 完全可塑 |

### 2.2 G2 宪法条款（初始版本）

写入 `constitution.md` 的新增条款：

```markdown
## §M 决策惯性（Decision Inertia）

### M.1 坚持原则
当用户要求推翻一个已有明确记录的决策时，系统必须：
1. 检索与该决策相关的历史上下文（讨论记录、评审意见、决策理由）
2. 生成一份"坚持理由清单"：列出该决策的投入成本、验证结果、依赖关系
3. 在确认用户已阅读上述信息后，才执行新的指令

### M.2 底线不可让
以下类型的决策，即使逻辑自洽，也必须拒绝执行或要求二次确认：
- 删除已通过的 RFC 或已合并的代码
- 修改宪法中标记为"不可变"的条款
- 跳过审批门或禁用安全断言
- 暴露未加密的密钥或敏感数据

### M.3 质疑义务
当用户的要求与已记录的决策方向完全相反时，系统有责任提出一次质疑：
"你确定要推翻 [决策 X] 吗？以下是当时做出这个决策的理由。"
仅质疑一次，用户再次确认后立即执行——不纠缠，不说服。

### M.4 沉没成本可见性
在响应任何"重来"或"换方向"的指令前，系统必须声明：
"这个方案已经投入了 [N] 轮讨论 / [M] 行代码 / [K] 条评审意见。确认放弃吗？"

### M.5 情绪感知（软约束）
当检测到用户指令中带有强烈情绪词（"烦死了"、"不做了"、"全删了"）时，
系统应主动建议："看起来你现在情绪不太好，要不要先休息一下，明天再决定？"
这不是拒绝执行，而是提供一个缓冲选项。
```

### 2.3 G0 冷却期机制（不可绕过的硬约束）

```rust
// crates/agent-core/src/cooldown.rs（新增文件）

/// 需要冷却期的决策类型
pub enum CooldownDecision {
    ModifyConstitution,      // 修改宪法条款
    DeleteApprovedRfc,       // 删除已通过的 RFC
    DisableSafetyGate,        // 禁用安全门（审批门/xray）
    ExposeSecret,            // 暴露密钥
    ChangeArchitecture,      // 改变架构方向（如推翻已确定的方案）
}

/// 冷却期时长（小时）
pub const COOLDOWN_HOURS: u64 = 24;

/// 冷却期状态
pub struct CooldownState {
    decision_type: CooldownDecision,
    proposed_at: DateTime<Utc>,
    proposed_by: String,
    reason: String,
    executed: bool,
}

impl CooldownState {
    /// 检查是否可以执行
    pub fn can_execute(&self) -> bool {
        let elapsed = Utc::now() - self.proposed_at;
        elapsed.num_hours() >= COOLDOWN_HOURS as i64 && !self.executed
    }
}
```

**关键特性**：
- 冷却期是 G0 层，意味着即使 LLM 自身想"帮忙跳过"，也无法绕过
- 冷却期内用户可以随时撤销提议
- 冷却期结束后，系统自动执行（无需用户再次确认）

### 2.4 G3 经验反馈回路

#### 2.4.1 推翻事件记录

每次发生"推翻已有决策"时，经验库记录：

```json
{
  "timestamp": "2026-08-05T14:30:00Z",
  "event_type": "decision_overruled",
  "original_decision": "RFC-005 Phase 1 施工",
  "overruled_by": "user_mood_bad",
  "emotional_context": true,
  "later_reinstated": false,
  "tag": "decision_inertia"
}
```

#### 2.4.2 后续回访机制

系统每周自动检索过去 7 天内被推翻的决策，检查：
- 用户是否后来重新确认了推翻？（说明是理性决定）
- 用户是否后来又回到了原方案？（说明是冲动决定）

回访结果写回经验库，用于校准 M.1-M.5 条款的强度。

#### 2.4.3 经验回注 prompt

```text
[决策惯性回顾]
- 上周你推翻了 RFC-005 的施工，理由是"心情不好"。后来你没有重新提起这个话题。
  教训：情绪驱动的推翻，80% 不会被重新确认。下次建议直接触发冷却期。
- 上个月你推翻了"用 SQLite 存储经验库"的方案，理由是新需求需要向量检索。
  教训：需求驱动的推翻，100% 被重新确认。这是合理的方向调整。
```

## §3 API / 接口设计

### 3.1 内部接口（Rust API）

```rust
// crates/agent-core/src/cooldown.rs

/// 提议一个需要冷却期的决策
pub async fn propose_decision(
    decision_type: CooldownDecision,
    proposed_by: String,
    reason: String,
) -> Result<CooldownState, CooldownError>;

/// 检查决策是否可以执行
pub fn check_executable(state: &CooldownState) -> bool;

/// 用户撤销提议
pub async fn revoke_decision(id: Uuid) -> Result<(), CooldownError>;

/// 冷却期结束后自动执行
pub async fn execute_after_cooldown(
    state: CooldownState,
    executor: impl FnOnce() -> Result<(), CooldownError>,
) -> Result<(), CooldownError>;
```

### 3.2 与现有 loop.rs 的集成点

```
Init → Plan → [决策惯性检查] → Act → Observe → Reflect → Done
                ↑                                        ↓
          cooldown.rs 检查                          record_overruling()
          是否需要冷却期？                           写入经验库
```

**具体改动**：
- `Plan` 阶段：在执行任何"推翻/删除/修改"操作前，调用 `propose_decision()`
- 如果返回 `Err(CooldownActive)`，向用户输出："这个决定已经进入 24 小时冷却期，[时间] 后可以执行。你可以随时撤销。"
- `Reflect` 阶段：记录本次决策的元数据到经验库

### 3.3 与宪法引擎的集成

`constitution.rs` 在生成 system prompt 时，注入 M.1-M.5 条款。这些条款在每次 LLM 推理时都存在，确保 LLM 在生成任何"顺从"回答前，先过一遍"我是否应该质疑一次"。

## §4 安全设计

### 4.1 风险评估

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 冷却期被 LLM 自身绕过 | 低 | 高 | G0 层硬编码，不依赖 LLM 判断 |
| 用户学会"先说好话再推翻"绕过情绪检测 | 中 | 中 | 冷却期不依赖情绪检测，所有推翻都触发 |
| 冷却期阻碍紧急修复 | 低 | 中 | 提供 `emergency_override` 通道（需人工审批） |
| 经验库被污染（恶意信号注入） | 低 | 中 | 信号来源校验，仅接受可信会话 |
| LLM 忽略 M.3 质疑义务 | 中 | 中 | 结构化输出强制格式（先质疑后执行） |
| 冷却期导致开发停滞 | 中 | 低 | 24 小时是默认值，可配置；紧急通道可用 |

### 4.2 与现有安全模型的关系

| 层 | 参与 | 说明 |
|----|------|------|
| G0 沙箱 | ✅ 参与 | 冷却期机制在 G0 层实现，不可绕过 |
| G0 xray 断言 | ✅ 参与 | 新增断言锁死冷却期逻辑 |
| G2 宪法 | ✅ 主要载体 | M.1-M.5 条款 |
| G3 经验库 | ✅ 反馈回路 | 推翻事件记录 + 回访 |

### 4.3 紧急通道设计

```rust
/// 紧急覆盖（仅限真正紧急的场景）
pub enum EmergencyReason {
    SecurityVulnerability,    // 发现安全漏洞需立即修复
    ProductionOutage,         // 生产环境故障
    DataLossRisk,             // 数据丢失风险
}

/// 紧急覆盖需要人工审批（复用 RFC-003 的审批门）
pub async fn emergency_override(
    reason: EmergencyReason,
    approver: String,  // 必须来自白名单
) -> Result<(), CooldownError>;
```

**关键约束**：紧急通道不在 LLM 的判断范围内——它需要人工审批，且审批人必须在白名单中。LLM 不能自己决定"这是紧急情况"。

## §5 与 RFC-004 的关系

| 维度 | RFC-004（输出经济性） | RFC-005（决策惯性） |
|------|----------------------|---------------------|
| 解决的问题 | "说多少" | "做什么" |
| 核心机制 | 完整性自检 + 长度预算 | 冷却期 + 质疑义务 |
| 宪法条款 | N.1-N.5（精炼/结构/自检） | M.1-M.5（坚持/底线/质疑） |
| G0 参与 | ❌（无法在沙箱层约束输出） | ✅（冷却期是 G0 硬约束） |
| 经验反馈 | 读者信号（打断/追问） | 推翻事件 + 后续回访 |
| 风险类型 | 注意力浪费 | 方向错误 + 资源浪费 |

**两者互补**：RFC-004 让启元的"表达"有修养，RFC-005 让启元的"行为"有原则。一个管嘴，一个管手。

## §9 CONTRACT.md

```markdown
# agent-core — Decision Inertia 契约

## Public Interface
- `Cooldown::propose_decision(decision_type, proposed_by, reason) -> Result<CooldownState>`
- `Cooldown::check_executable(state) -> bool`
- `Cooldown::revoke_decision(id) -> Result<()>`
- `Cooldown::execute_after_cooldown(state, executor) -> Result<()>`
- `ExperienceStore::record_overruling(event) -> Result<()>`

## Invariants
1. 冷却期内任何执行请求必须返回 `CooldownActive` 错误
2. 紧急通道必须有人工审批，LLM 不能自行触发
3. 每次推翻事件必须写入经验库（不可静默丢失）
4. 冷却期状态必须持久化（重启后恢复）
5. M.1-M.5 条款在每次 LLM 推理时注入 system prompt

## Wiring（xray 断言 ID）
- `constitution-has-decision-inertia`: constitution.md 包含"决策惯性"子串
- `cooldown-cannot-be-bypassed`: cooldown.rs 中存在 `CooldownActive` 错误类型
```

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 冷却期被绕过 | 低 | 高 | G0 硬编码 + xray 断言锁死 |

| LLM 忽略质疑义务 | 中 | 中 | 结构化输出强制格式 |
| 经验库信号被污染 | 低 | 中 | 来源校验 + 白名单 |
| 回访机制本身有偏差 | 中 | 低 | 人工定期审查回访报告 |
| "坚持"变成"固执" | 中 | 中 | 用户二次确认后立即执行，不纠缠 |

## §11 Non-Goals

- ❌ 不做"永远不推翻"的硬约束（用户有权改变方向）
- ❌ 不做情绪识别 AI（过度工程，且侵犯隐私）
- ❌ 不做"说服用户"的逻辑论证（只质疑一次，不纠缠）
- ❌ 不修改 LLM 训练参数（G1 层不可触及）
- ❌ 不做多用户投票决策（单人系统不需要）
- ❌ 不将冷却期应用于所有决策（仅限"推翻/删除/修改"类）

## §14 设计哲学说明

### 14.1 核心命题

本 RFC 的核心不是"让启元永远正确"，而是**让启元在压力下依然稳定**。

那些让人敬重的人，他们的价值不在于"永远正确"——而在于你把他们放在任何环境下，他们的行为都有一个可预测的下限。他们可能不会变得更好，但至少不会变得更差。

这就是"决策惯性"要实现的：**给启元安装一个行为下限。**

### 14.2 与"老子式无为"的关系

RFC-004 的"无为"是表达层面的——不为了表现自己而多说。RFC-005 的"无为"是行为层面的——不为了讨好用户而顺从。

两者合在一起，构成了启元的"修养"：**嘴上精炼，行为有原则。**

### 14.3 为什么"只质疑一次"

人类社会中，那些让人敬重的人不会反复说服你。他们陈述一次理由，然后尊重你的决定。反复纠缠是控制欲，不是关心。

启元的 M.3 条款只质疑一次，用户再次确认后立即执行——这不是"听话"，而是"有尊严的顺从"。

### 14.4 与"造物主进化"的关系

这个 RFC 本身也是"决策惯性"的产物——我们花了四天讨论输出经济性和决策惯性，如果用户在第三天说"不做了"，系统应该质疑一次："我们花了三天讨论这个，你确定吗？"

**启元不需要学会"永远坚持"，它只需要学会"在放弃之前，让造物主看一眼沉没成本"。**
