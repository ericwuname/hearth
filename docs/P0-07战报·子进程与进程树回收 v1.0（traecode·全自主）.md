## 一、缺陷族：一句话

> **"我杀掉的，只是我以为我杀掉的那个进程。"**

Rust 的 `Child`（std 与 tokio 皆然）**drop 时既不 kill 也不 wait**。于是有两条泄漏路径：

| # | 位置 | 泄漏物 | 触发条件 |
|---|---|---|---|
| **D-19** | LinuxSandbox `apply_cgroups_impl(pid, …)?` | 已被 spawn 的**整个命令**（含进程组与两条管道） | cgroup 不可用/写失败（RT4 fail-closed），**可达** |
| **D-20** | NoopSandbox 超时 | **孙进程**（`cmd /C start …` / `bash -c "… &"`） | 命令超时，Windows 运行时必经 |

两者都符合本主线：**代码假设"出错时会自动收尾"，而实际上没有任何东西负责收尾。**

## 二、D-19 · cgroup fail-closed 必须连带"收尸"

**病灶**：

```rust
apply_cgroups_impl(pid, &cfg_for_cgroups_inner)?;   // ← 失败时 child 被丢出作用域
```

`?` 一上抛，`child` 就被 drop —— 而 drop **不 kill 不 wait**：子进程继续跑成
**孤儿**（还带着 `pre_exec` 刚建立的进程组、两条管道写端），把资源占着；而调用方
只看到一句 `command failed`。**fail-closed 的本意是"宁可不跑"，结果变成了"跑着不管"。**

**修复**：失败分支显式收尾，再上抛错误。

```rust
if let Err(e) = apply_cgroups_impl(pid, &cfg_for_cgroups_inner) {
    unsafe {
        if libc::getpgid(pid as libc::pid_t) == pid as libc::pid_t {
            let _ = libc::kill(-(pid as libc::pid_t), libc::SIGKILL);   // 组杀
        }
        let _ = libc::kill(pid as libc::pid_t, libc::SIGKILL);
    }
    let _ = child.wait();                       // 收割，避免僵尸
    cleanup_cgroup(pid, &cfg_for_cgroups_inner); // cgroup 可能已部分创建
    tracing::warn!("…已组杀并收割子进程 (pid {pid}) —— 不留孤儿");
    return Err(e);
}
```

`getpgid` 校验沿用既有不变式（`pre_exec` 的 `setsid` 保证 child 是组长；
非组长则退化为单杀——**不误伤优先**）。

## 三、D-20 · 超时必须杀**整棵进程树**

**病灶**：超时后内层 future 被 drop → `kill_on_drop` 生效 → 但它只终止**直接子进程**。
Windows 上 `cmd /C start x`、`bash -c "x &"` 派生的**孙进程**不在其列：

- 继续占着 CPU / 端口 / 文件锁；
- 而父进程已经报"超时"走人，**没有任何人会再想起它**。

**修复**（Windows 走系统自带工具，**不引入新依赖**）：

```rust
fn kill_process_tree(pid: u32) -> bool      // Windows: taskkill /T /F /PID
```

并把 `child` **提到 `timeout` 之外**（原写法把 child 藏在被 drop 的内层 future 里，
根本拿不到 pid 与句柄）：

```rust
let mut child = …spawn()?;
let pid = child.id();
let timed = tokio::time::timeout(timeout, async { /* drain + wait */ }).await;
match timed {
    Ok(v)  => …,
    Err(_) => {
        if kill_process_tree(pid) { /* 树杀 */ } else { let _ = child.start_kill(); }
        let _ = child.wait().await;          // 收割
        return Err(anyhow!("command timed out after {:?}", timeout));
    }
}
```

两处细节值得记下：
1. **必须 `let timed = ….await;` 再 `match`** —— 直接写 `match timeout(…).await {…}` 时，
   临时 future 会存活到整个 `match` 结束，`child` 的可变借用无法在超时分支复用（借用检查器会挡）。
2. **`kill_on_drop(true)` 保留**：它是"任务被 abort"场景的兜底；超时分支走显式树杀。

## 四、验证：**两个都是真实验，不是"看着对"**

### 4.1 D-20 —— 本机实测红 → 绿（关键证据）

探测设计（避开 `cmd /C` 的嵌套引号地狱，改用 `.bat` 承载脚本）：

```
直接子进程 = cmd /C probe.bat
  ├─ ① start /B "" cmd /C "ping -n 3 … & echo done> marker.txt"   ← 孙进程，2 秒后写哨兵
  └─ ② ping -n 60 …                                               ← 让直接子进程活到超时
```

判据：**超时后孙进程若存活，`marker.txt` 就会出现。**

| 步骤 | 操作 | 结果 |
|---|---|---|
| **红** | 临时把 `kill_process_tree` 短路为 `false`（等价于修复前行为） | **FAILED**：`孙进程必须随超时被一起杀掉（修复前它会活下来并写出 marker.txt）` |
| **绿** | 恢复 `taskkill /T /F` | **ok** |

再补一条"正常语义不变"的测试（`cmd /C echo` 真跑）：退出码 0、stdout 正确、无截断留痕。

> 过程中还顺手抓到测试自身的一个陷阱：NoopSandbox 会 `env_clear()`，而 `ping` 是**外部 exe**
> （不是 cmd 内建）——不显式注入 `PATH` 就会 `not recognized` 直接结束、**根本不会超时**，
> 测试会"假绿"。已在测试里显式注入 PATH 并注明原因。

### 4.2 D-19 —— 交叉类型检查（执行在 Linux）

本机（Windows）无法执行 `cfg(target_os="linux")` 代码，故：
- 新增 Linux-only 测试 `test_p0_07_cgroup_fail_closed_reaps_child`
  （哨兵法：cgroup 失败 → 若未收尸，`sh` 会活满 5 秒写出 `marker.txt`）；
- 用 P0-06 打通的 `cargo check -p sandbox --target x86_64-unknown-linux-gnu --all-targets`
  确认**可编译**（exit 0）。

> 该测试的 `writable_paths` 被显式设为临时目录——否则 landlock 会拦住子进程写 marker，
> 让"红侧"因为"写不进去"而**假绿**。这类"测试自身的假阴性"是本卡反复遇到的坑。

## 七、方法论沉淀（第 8 个变体）

> **"假设清理会自动发生。"**

- `Child` 的 drop **不是**清理（Rust 里"析构"≠"回收外部资源"，进程是外部资源）；
- `kill_on_drop` **不是**树杀（只到直接子进程那一层）；
- `?` 早退**不是**回滚（它只是把控制权交出去，已经有副作用的部分没人管）。

**固化为检查项**（补充至 D-23 专项，未实施）：
1. **凡 `spawn`/`open`/`create*` 之后存在 `?`、`return`、`break`、`panic` 的路径，
   必须逐条回答"这里的资源谁来收"**；
2. **凡涉及进程，明确说出杀到哪一层**（自己 / 直接子进程 / 进程组 / 整棵树），
   并验证该层的机制在**目标平台**上真实存在（Windows 无 setsid/kill(-pgid)）；
3. **凡写"红侧"测试，先自问"失败会不会是因为测试自己没跑起来"**（PATH/env/权限/
   landlock 都会制造**假绿**）——本卡两次踩到。
