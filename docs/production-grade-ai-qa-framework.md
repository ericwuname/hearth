## 0. 先直接回答你的三个问题

### Q1：这类问题怎么定义？

**它有名字：行为层缺陷（Behavioral Defects），位于 Agent 评估三层模型的第 2 层与第 3 层。**

业界把 agent 评估分成三层：

| 层 | 评估什么 | 例子 |
|---|---|---|
| **第 1 层：最终答案** | 最后一句话对不对 | 答对数、任务是否 completed |
| **第 2 层：轨迹（Trajectory）** | 走到答案的**过程**好不好 | 工具选对没、3 步的事走了 20 步、有没有死循环、失败后有没有换路 |
| **第 3 层：单轮（Per-turn）** | 每一轮交互的**意味** | 提示词泄漏、策略违规、**用户在这一刻受挫了** |

> 业界对第 3 层的原话：「这些**不会改变状态码、延迟或 token 数**，因此在日志和链路追踪里**不可见**。」

**我们这一路攒的问题，几乎全在第 2/3 层**：
- "一动工具就危险"（bash 70% ↔ 成功 0-2%）→ **第 2 层**
- 追问被吞、8 次"你还记得吗"0 次被答 → **第 3 层**
- 提问僵硬、问得不关键 → **第 3 层**
- 模型能力靠手工维护 → 属**配置层**，但症状（阈值按 32k 老模型标定）暴露在第 2 层
- 压缩导致失忆 → **第 2 层**

**传统单测只覆盖第 1 层**，所以它们抓不到——这不是测试写得不认真，是**测试范式不对**。

### Q2：必须要你人肉识别吗？

**不必。但前提是：你得先建检测器。**

现在的真实状况是——**你就是 Hearth 唯一的"第 3 层传感器"**。每一个问题要么是你用出来的，要么是我事后花几小时手挖日志挖出来的。**这两种都不可扩展、且都是事后。**

业界 2026 年的答案很明确：有三套互补机制可以替代人肉，见 §2–§4。

### Q3：通过什么手段能找到？

三套机制（对应三种"以前只能靠人"的场景）：

| 以前靠什么 | 替代机制 | 手段 |
|---|---|---|
| 靠**用户上报**"这里别扭" | **用户行为摩擦遥测** | 隐式信号：重复提交、改写到接受比、放弃、rage prompt（§2） |
| 靠**守门人读日志**三小时 | **轨迹/单轮自动评估** | 代码化 grader（可判定的全用代码）+ 小模型 LLM-as-judge（语义部分）+ 校准（§3） |
| 靠**碰运气撞上**某个用户类型 | **模拟用户 / 角色驱动测试** | persona 包 + 对抗原型 + agent-to-agent 对打，进 CI（§4） |

## 1. 为什么现在只能靠你人肉：Hearth 的现状诊断

| 能力 | 业界 2026 基线 | Hearth 现状 |
|---|---|---|
| 第 1 层（最终答案） | 必备 | ✅ 有（415 tests、终态判定、CI gate） |
| 第 2 层（轨迹） | 必备 | ⚠️ **只有我事后手挖的脚本**（mine_*.py），**未进运行时、未进 CI** |
| 第 3 层（单轮交互质量） | 分层评估 + 在线采样 | ❌ **无** |
| 用户行为遥测 | 摩擦信号是标配 | ❌ **无**——"继续"×99 是我在日志里数出来的，不是系统报的 |
| 模拟用户 | persona 包进 CI | ❌ **无** |
| 变异测试（验证测试本身有效） | 60–80% 目标分 | ❌ **无**——且已有实证表明需要（见下） |

**⚠️ 最关键的一条实证——我们自己的"验证悖论"**：
R2-C v0.2.9 门禁时，执行窗口新写的 6 个测试里，**3 个失败的原因是测试写法错**（没调 `do_plan_inner()`、没设 `original_goal`、断言字符串不在格式里），**不是逻辑缺陷**。
这正是业界所说的 **verification paradox**：同一个模型既写实现又写测试，**测试是从它自己的实现里推导出期望值的** → "bug 和自己达成了一致"。

## 2. 机制一：用户行为摩擦遥测（替代"用户上报"）

> 核心洞察：**只有 5–15% 的用户会给显式反馈，且这批人是统计离群值**（偏"很满意"和"很愤怒"两端）。**真正在日常使用、信号最干净的 85–90% 沉默用户，不产生任何可行动数据。**

业界已命名的信号栈（Hearth 可逐一对照实现）：

| 信号 | 定义 | 业界阈值 | **Hearth 的对应现象（我们其实早就见过）** |
|---|---|---|---|
| **Re-prompt rate** | 用户改写重提同一意图 | >8% 报警 | "继续" ×99（旧版）、6→2（v0.2.8→2.10） |
| **Edit-to-accept ratio** | 用户接受前改了多少 | 直接质量度量 | 用户纠偏 11 次（v0.2.10 意图分类里"纠偏"类） |
| **Abandonment** | 开始没完成就走 | >15% 报警 | 失败轮 24 次（v0.2.8/2.10 各 24） |
| **Rage prompt rate** | 挫败信号（脏话/重复尝试/全大写） | Pendo 已产品化 | ⭐「**又出现相同的问题了**」(L635)、「为什么你的上下文填充感觉不太准」(L2309) |
| **Escalation / override** | 转人工 / 手工接管 | — | 用户手工 `chmod`/`install`（RC27 场景） |
| **Session depth / D7 回访** | 多轮深度、7 日留存 | 习惯形成指标 | v0.2.10 会话 71 轮（深度够，但质量衰减 Q3 59%） |

**Hearth 该做什么**：把这些做成**运行时事件**，而不是事后 grep。
```rust
// 建议的事件（示意）
record_event("hearth.friction.nudge",      run_id, /* 用户发"继续" */);
record_event("hearth.friction.re_request", run_id, original_run_id, similarity, gap_secs);
record_event("hearth.friction.correction", run_id, /* 纠偏类输入 */);
record_event("hearth.friction.abandon",    run_id, step_reached);
record_event("hearth.friction.rage",       run_id, /* 挫败信号 */);
```
⚠️ 注意一个**易错点**（业界明确提醒）：abandonment 必须**按查询复杂度分桶**——简单查询后立刻离开＝成功；复杂查询后立刻离开＝失败。

## 3. 机制二：轨迹 / 单轮自动评估（替代"守门人读日志"）

### 3.1 分层打分：能写成代码的绝不交给模型

| 判定 | 用代码 grader（快/便宜/可复现/好调试） | 用 LLM-as-judge（语义/开放） |
|---|---|---|
| 轨迹 | 步数、循环检测（同一动作重复）、工具选择是否正确、每步成本归因 | 轨迹是否"合理" |
| 单轮 | 格式校验、敏感信息、注入检测 | 语气、是否有帮助、**用户此刻是否受挫** |

**成本可行的关键做法（2026 通用模式）**：
- **规则先行**，只对语义部分调小模型 judge → 达成 **100% 生产覆盖**且成本可接受
- **judge 也要被校准**：先拿 20+ 条人工标注对齐；**"一个未校准的 judge 比没有 judge 更危险，因为它给你虚假信心"**
- **离线与在线用同一个 rubric** → 分数可比，一眼看出"上了生产掉了多少"
- **打分用二值 pass/fail，别用 1–5 量表**（量表需要更大样本才有统计显著性）
- **闭环**：生产里抓到的每个失败 → 回流成离线数据集的新 case（"那条大多数团队忘记的虚线箭头"）

### 3.2 ⭐ 我们其实已经有这套东西的雏形

| 已有资产 | 对应业界组件 | 还差什么 |
|---|---|---|
| `manual-test-mining-dimensions.md`（维度字典） | 缺陷分类学 / grader 规格 | 转成可执行断言 |
| `mine_l678.py` / `mine_l9b.py` / `mine_l910.py` | **第 2 层代码化 grader** | 从"事后脚本"→"运行时 + CI" |
| 成功率/步数/工具失败率/失败近压缩% | 轨迹指标（task completion、step count、tool accuracy、cost per step） | 接到遥测与告警 |
| R2-C 的**独立盲评 rubric** | **LLM-as-judge 先例**（项目内已用过且有效） | 校准 + 复用为常驻 |
| 12/18 跑矩阵 | 离线回归集 | 进 CI（Claude 回执 §4 已建议） |

**也就是说：我们已经把该造的东西造了一半，只是它们是"人跑的脚本"而不是"系统里的检测器"。**

## 4. 机制三：模拟用户 / 角色驱动测试（替代"碰运气撞上"）——这就是"用户的视角"

> 这段直接回答你的"能不能找到用户的视角"。**不需要真人去当新手/急躁者/困惑者——可以造出来。**

**做法**：
- **Persona 包**：为 Hearth 定义用户原型，每个带明确行为轴（耐心、表达完整度、技术深度、是否透露信息）
- **对抗原型（adversarial archetypes）**：针对**已知失效模式**设计，如
  - "**矛盾机**"（前后说法不一致）→ 打状态追踪
  - "**延迟揭示者**"（先不说关键信息，等 agent 问）→ 打提问能力
  - "**元访谈者**"（反复问"你感觉如何/你还记得吗"）→ ⭐ **就是你自己这一类，正是 RC36/RC39 的来源**
  - "**纯问询者**"（不要求任何文件产出）→ 打 RC43（progress 只认写）
- **Agent-to-agent**：simulator_agent（扮用户）↔ Hearth ↔ evaluator_agent（打分），进 CI 自动跑多轮
- **Red-teaming with personas**（PersonaTeaming）

**效果证据**：Amazon 的可控 persona 框架用 10 个原型打 5 类失效模式，跑出 800 段多轮对话，暴露出**有状态追踪的 agent 达成率 75–77%，普通 agent 只有 39%——37 个百分点的差距**，且跨模型规模一致。

**⚠️ 两个必须注意的坑（业界实测）**：
1. **性格旋钮是非线性的**：41% 的性格-行为对有大效应，但**只有 19% 呈线性**。校准模拟器不能只测两端。
2. **模拟器本身也有偏见**（继承训练数据偏见）→ 需要有意识地做 persona 分布平衡，否则只会放大多数群体的行为模式，**反而掩盖小众失效**。

## 5. 让 AI 写的代码真正生产级（你问题的后半段）

这部分的业界结论非常锋利，而且**好几条与我们自己的铁律完全吻合**：

### 5.1 变异测试 —— 验证"测试本身有效"（= 我的铁律 #2 的量化版）

> "**删掉断言，测试还过，那它从来没验证过任何行为。**"

| 数据 | 值 |
|---|---|
| AI 直出测试套件的变异得分（HumanEval-Java） | **53%** |
| 把变异结果反馈回测试生成后 | **89.5%** |
| 另一实测：98% 行覆盖率 vs 变异得分 | **75%**（**23 个百分点**的盲区） |
| 业界门槛 | 关键逻辑 **60–80%** |
| Rust 工具 | `cargo-mutants` |

**⚠️ 这一条对 Hearth 是硬需求**：R2-C 那 3 个"因写法错而失败"的测试，就是测试套件存在盲区的直接证据。**建议对变更文件跑 `cargo-mutants`，先测出我们 415 个测试到底能抓住多少注入缺陷。**

### 5.2 属性测试（PBT）—— 抓边界（Rust 用 `proptest`）

- **弱属性**＝伪装成属性的样例测试：`sort([3,1,2]) == [1,2,3]` ❌
- **强属性**＝真正的不变量：`排两次结果相同` / `解析再格式化回原始串` / `打折永不增加总额` ✅
- 检出率：约 **61% 边界类缺陷**
- 进阶技巧 **"负面不变量挑战"**：不问"什么应该成立"，而问"**什么一旦成立就证明实现是坏的**"——防止 agent 生成弱属性
- **Hearth 最该上的地方**：压缩（不变量：压缩前后原目标不变、写盘清单不丢）、任务图（无环、状态单调）、路径处理（穿越拒绝）

### 5.3 规格优先 + 盲审（破解验证悖论）

- **规格优先**：先写规格（输入/输出/不变量/失败模式）→ **从规格生成测试** → 再看实现
- **盲审模式（Blind Auditor）**：让一个**全新的、看不到实现代码**的子 agent 只根据规格生成测试。**实现 agent 若过不了这些"盲测"，说明是需求理解分歧，而不只是 bug。**
- 断言的所有权：**AI 可以写脚手架，最后那行期望值必须来自人或规格**

### 5.4 契约测试 / 依赖来源校验

- 契约测试（Pact 式）防"schema 幻觉"（AI 客户端假设了不存在的响应结构），集成失败降 **38%**
- 依赖 provenance 校验：新 import 必须在 PR 之前就存在且有发布历史 → 防依赖幻觉

### 5.5 ⭐ 独立验证 agent 的自述（这条最重要）

> 业界原话：「如果 agent 报告"测试通过"或"迁移完成"，**让另一个流程重新推导这个断言**——重跑测试、重数行数——而不是接受它自己的总结。
> **把"done"当成一个待验证的声明，而不是一个可以信任的状态更新。**」

**这正是 RC21（假失败）、RC37（压缩后假完成）、A-37 判据的根因**，也是我这个守门人岗位存在的理由。业界把它写成了通用工程原则——**建议把它升级为 Hearth 的架构级约束**（系统不得采信自身的完成声明，须由独立校验通路复核）。

### 5.6 其它值得抄的门禁

- 覆盖率**不等于**正确性：「高 AI 测试覆盖率只说明**代码跑过**，不说明它**功能正确**」
- **重复代码 / 改动churn **作为 CI 信号（同一文件两周内被大幅重写多次 → 标记）
- **AI 归因缺陷率**：无结构化验证时，AI 生成代码的缺陷密度是人工的 **2.3 倍**
- 审核心态：「**先假定它是错的，直到 diff 向我证明它是对的**」

## 7. 需要顶层裁决的问题

1. **是否把"第 2/3 层评估"立为正式工作项**？（这是"问题必须靠人肉发现"的根因，也是本文件所有建议的总纲）
2. **摩擦遥测是否接受采集用户行为事件**？（涉及隐私与本地优先原则，需明确边界——建议默认本地落盘、可关闭）
3. **是否引入 `cargo-mutants` / `proptest` 作为门禁**？（会拉长 CI 时间，需权衡；建议只跑变更文件）

5. **"不得采信自身完成声明"是否升为架构级约束**？（影响 W3/W4 的既有设计）

- 业界实践来自 2026-08-29/30 联网检索（含 LangSmith/AWS、morphllm、LangChain、Pendo、Mixpanel、Amazon persona 论文、PersonaTeaming、mutation/PBT 多篇）。**具体数值（阈值、检出率）来自各来源自述，应视为参考区间而非普适定律。**

- **移动基线警告**：执行窗口持续施工，复审前先 `git log -1` 对齐。
