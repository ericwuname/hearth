## 洞察 1 · 今晚所有"异常"可能有一个共同来源：**常量标定在一个已经不存在的环境里**

**源码证据（全部实测）**

| 常量 | 值 | 锚点 | 对照现实 |
|---|---:|---|---|
| 压缩阈值 | **32,000 字符** | `context.rs:169` | 512K 窗口的 **4–10%** |
| **子 agent 上下文预算** | **4,096 tokens** | `loop.rs:4796 / 4907 / 4939`、`code-index:351` | 512K 的 **0.8%** |
| 静态截断族 | 200 / 60 / 8000 / 6000 / 4096 | `render.rs` `tool_result`、`summarize_turn`、`web.rs:17`、`constitution.rs:20`、`agent-types:540` | 5 处全无标记 |
| provider 上下文声明 | deepseek 32k / local 128k | `llm-cn:412`、`llm-local:382` | Agnes **512K 未在表内** |
| 规划计数器 | 3 / 5 / 6 | `planner:234/235/259` | 未随任务类型分化 |

**推论**：这些数字几乎全部来自 **32k 级模型 + 昂贵/稀缺配额** 的年代（deepseek 余额 ¥4.4、本地 4K 模型），**此后模型换了（512K）、配额换了（周 75,000 次），常量一个没动。**

**⭐ 由此产生的新判断**：**Hearth 现在基本是"拉着手刹在跑"**——拥有 512K 的窗口，却主动在 4–10% 处销毁上下文，并给子 agent 只留 0.8%。
→ 这**可能**同时解释：失忆、重复定位、忘目标、子 agent 结果不可靠、以及"复杂任务必失败"。
→ **因此建议：先做一次"常量体检"（W13），再谈摘要质量（I-3 B 层）。** 若体检后失忆类问题大幅自愈，I-3 的优先级应下调——**少破坏优先于破坏得好看**（与业界共识一致）。

**可验证预测**：仅修正阈值与子 agent 预算（不改摘要算法），单会话压缩次数应从 **14–18 次降到 1–2 次**，且"失败紧邻压缩点"比例（现 53–60%）应显著下降。

## 洞察 2 · **一条公理可以解释六个 RC：「任何系统不得对自身产出做终局判定」**

| 现象 | 表现 | 现状 |
|---|---|---|
| RC1 | LLM 自报完成即算完成 | ✅ 已修——改为 **verify 事实校验驱动**（`mark_nodes_completed_on_accept`） |
| RC10 / RC21 / RC37 | 无校验 / 假失败 / 压缩后假完成 | ❌ 未修 |
| R2-C 测试缺陷 | **6 个新测试 3 个因写法错而失败**——模型给自己写测试，测试推导自实现 | ❌ 未修（业界称 verification paradox） |
| R2-C 独立盲评之所以有效 | 正因为引入了**外部判定** | ✅ 已验证有效 |

**关键观察**：**RC1 的修复其实已经在践行这条公理**（把"LLM 自报"换成"事实校验"），只是没人把它提升为架构级原则。

**推论**：把它写成 Hearth 的第七条宪法级原则，**未完成项和未来风险可以一次性收敛**：
- 完成判定必须走独立通路（→ A-37）
- 测试必须由"看不到实现的盲审 agent"从规格生成（→ 破解验证悖论）
- judge 必须校准（→ 否则给虚假信心）
- **Observer OS（第三权·零执行权）正是这条公理的天然载体**（见洞察 5）

## 洞察 3 · 战略重估：Hearth 最值钱的能力**不是"做得更好"，而是"知道什么时候不该动手"**

| 证据 | 数据 |
|---|---|
| 成功轮长什么样 | 步数中位 **2**、65–73% 在 1–2 步完成、**几乎不动工具**（bash 0–2%） |
| 失败轮长什么样 | 步数中位 10–15、**bash 70–71%**、烧掉总步数 44% |
| 轮次构成 | 问询 + 元访谈 = **65%**（v0.2.10 46/71 轮）——**本就不该进任务循环** |
| 最差意图类型 | 元访谈成功率 **61%** |

**推论**：**α（输入分类，RC39）不是众多缺陷之一，而是总开关。**
→ 当前大部分失败不是"任务执行得不好"，而是**"不该被执行的东西被执行了"**。
→ 预测：修 α 之后，成功率提升主要来自"**65% 的轮次根本不再进入任务循环**"，而非任务执行质量改善。

**建议新增北极星指标：正确弃权率（correct abstention rate）**——"不该动手时确实没动手"的比例。
（若只盯成功率，会误把优化方向引向"把任务做得更好"，而真正的收益在"少做"。）

## 洞察 4 · 五处静默截断的**复合效应**：系统"又聋又瞎但自认为正常"

- 单看每一处都合理（显示 200 字、摘要 60 字、网页 8000、宪法 6000、注入 4096）
- **合起来**：agent 基于残缺信息做判断，且**没有任何一处告知"你看到的是被截断的"**
- **512K 让这件事变得讽刺**：明明有巨量余量，却在 5 个点上主动丢弃

**推论**：这可能是 **RC31 目标漂移** 与**路径幻觉**（`C:\Users\Administrator\...` 被拼进 `/home/wutao/`）的温床——**看不到完整路径，就只能拼**。
**建议**：截断必须显式标记（A-35）+ 全量入归档可回读（与 I-3 检索同源）。

## 洞察 5 · **Observer OS 早就为这套评估栈留好了位置——不是加器官，是把已有的器官长出来**

- 项目既有架构：**三端口**（Human OS / AI OS / **Observer OS 第三权·零执行权**）
- 生产级 QA 框架要求：**L1/L2/L3 三层评估 + 摩擦遥测 + 模拟用户 + 独立判定**

**这两者是同一个东西。** Observer OS 的定位（第三权、审计、零执行权）**正是洞察 2 那条公理的载体**。

**双重收益**：
1. **对内**：解决 Hearth 自身"只有 L1 评估"的困境（当前用户是唯一的 L3 传感器）
2. **对外**：这是产品差异化——**自带生产级评估的 harness**。项目的核心承诺是"可信委托"，而**没有评估就没有委托**（你无法委托一个你无法验证的对象）

→ 建议：**评估栈不另起炉灶，落在 Observer OS 上**（与 §洞察 2 的公理、§洞察 6 的 persona 包天然成套）。

## 洞察 6 · **最该被模拟的 persona 是"吴涛本人"**

- 今晚**价值最高的发现几乎全部来自你的交互方式**：元访谈式提问、连续追问同一个问题、质疑具体数字（83%→65%）、要求内观。
- 换言之：**你的提问风格是一个高效缺陷探针**——但它目前是隐性的、不可复现的、且消耗你本人。

**推论**：把你的交互特征固化成 **persona #1（元访谈者 / 质疑者 / 连续性追问者）**，就能把"用户人肉发现"变成 CI 里的自动发现。
→ 这是成本最低、针对性最强的一条：**RC36（8 问 0 答）与 RC39（输入分类）本该由这个原型自动发现**。

## 洞察 7 · 修复形状规律：**已闭合的全是"语义型修复"，剩余的全是"语义型缺陷"**

| 已闭合 | 修复形状 |
|---|---|
| RC20 | 字符串猜判 → **结构化 is_error** |
| RC24 | 字符串黑名单 → **语义化审批** |
| RC1 | LLM 自报 → **事实校验驱动** |
| RC31 | 无检测 → **独立 LLM 判定** |

| 剩余 | 缺陷形状 |
|---|---|
| RC43 / RC39 / RC5 / RC40 / RC34 | **信号的意思不对**（记分语义 / 分类语义 / 摘要语义 / 填充率语义 / 渲染语义） |

**可验证预测**：**继续用"加一条规则/启发式"打补丁，不会闭合剩余项**——它们必须用与已闭合项相同的形状修（**结构化语义 + 独立判定**）。
→ 可直接用作设计评审检查项：**任何修复方案若仍然是"加一条规则"，大概率无效。**
