## 🔴 错误解读

```
ERROR agent_core::loop: do_plan_inner failed
error=stalled: 2 consecutive replans produced identical TaskGraph (4 nodes)
semantic progress absent, giving up early (Tier3 T4)
```

### 发生了什么？
Hearth 的 Agent 在执行复杂任务时，会：
1. **生成 TaskGraph**（任务依赖图）
2. **逐步执行节点**
3. **定期 replan**（重新规划剩余路径）

但这个 Agent **连续 2 次 replan 生成了完全相同的 4 节点 TaskGraph**——说明它在原地打转，没有语义进展，所以主动放弃了。

### 可能原因
| 原因 | 说明 |
|------|------|
| 🔄 **循环检测失效** | 状态没变但规划算法认为"还在推进" |
| 📉 **进度追踪缺失** | 没有机制判断"这步是否真正改变了什么" |
| 🎯 **终止条件不完善** | 卡在某个子任务无法分解 |
| 🧩 **Task 太复杂** | 4个节点互相依赖，形成死锁 |

---

## 🛠️ 需要做什么？

这是 **Hearth 框架层**的问题，不是我（Agnes）能直接修的。如果你想解决：

1. **查日志** → 看哪个 Task 卡住了
2. **看原始计划** → `do_plan_inner` 输入了什么
3. **加 diversity constraint** → 让 replan 每次尝试不同路径
4. **加 backtracking** → 允许撤销上一步重做

## 问题诊断结论

**Tier3 T4 失败的根本原因**：`loop.rs` 中目前**没有** "2次连续 replan 产生相同 TaskGraph → 提前放弃"的逻辑。session `eee3d4f9` 中的 `stalled: 2 consecutive replans produced identical TaskGraph` 错误来自**旧版本**二进制，当前代码库中该检查已不存在。

当前代码只依赖：
- `consecutive_errors >= 3` → GiveUp（仅错误计数）
- `steps_without_progress` + 反射器决策 → GiveUp（但反射器是 LLM 调用，无法保证检测）
- `replan_count >= 3` 强制 GiveUp（纯计数上限）

**缺失**：TaskGraph 结构一致性检测（相同节点数+相同节点ID+相同描述 → 视为无语义进展）。

## 当前情况总结

### 1. 发生了什么？

你多次看到 `✗ Done (N steps)` 的终止标记，核心问题是 **stalled 检测机制**：

```
stalled: 2 consecutive replans produced identical TaskGraph (X nodes)
        — semantic progress absent, giving up early (Tier3 T4)
```

**翻译成人话**：
- Agent 尝试规划任务 → 执行失败/无进展 → 重新规划
- 如果连续 **2 次** 重新规划生成的 TaskGraph（任务图）完全一样
- 系统判定"没有语义进展" → 触发 Tier3 中止 → `give_up`

### 2. 为什么直接 give_up？

这是设计上的问题：

- Tier3 的中止逻辑是 **"检测到停滞就立即放弃"**
- 没有尝试：澄清问题、缩小范围、换策略、请求用户帮助
- 用户期望：报错后应该"重新思考、规划新方案"
- 实际行为：直接中止，留下未完成任务

### 3. 数据证据

从运行记录看：

| 轮次 | Steps | 错误 |
|------|-------|------|
| run-014 | 22 | stalled (4 nodes) |
| run-015 | 5 | give_up（承接上一轮失败） |
| run-020 | 9 | stalled |
| run-022 | 6 | stalled (2 nodes) |
| run-023 | 5 | stalled |
| run-026 | 8 | stalled (4 nodes) |
| run-034 | 9 | stalled |

**规律**：一旦触发 stalled，后续轮次容易重复这个模式。

### 4. 根本原因推测

1. **stalled 检测过于敏感**：2 次相同规划就放弃，可能任务本身需要更多尝试
2. **缺乏恢复机制**：检测到停滞后应该有多种应对策略，而非直接放弃
3. **用户指令模糊**：你的问题如"又出现了✗ Done"比较开放，Agent 难以确定具体行动

### 5. 建议的改进方向

| 优先级 | 改进项 | 说明 |
|--------|--------|------|
| P0 | stalled 后添加恢复步骤 | 不是直接 give_up，而是尝试不同策略 |
| P0 | 改进 ✗ Done 报告 | 明确说明卡在哪里、为什么放弃 |
| P1 | 增加澄清机制 | 当任务不明确时，主动询问用户 |
| P1 | 调整阈值 | 考虑将"2次相同"改为"3次"或更智能的判断 |
