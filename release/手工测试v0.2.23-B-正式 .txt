## 错误解析

| 字段 | 含义 |

## 核心问题

`cargo build` 在尝试通过 `clone3` 创建新进程/线程时被 seccomp 规则拦截。这通常发生在：

- **容器环境**（如 Kubernetes pod 的 seccomp profile）
- **沙箱化构建系统**（如 Firecracker microVM、gVisor）
- **CD Pipelines** 启用了严格的安全策略

---

## 常见解决方案

1. **放宽 seccomp 策略** — 将 `clone3` 加入允许列表（如果安全策略允许）
2. **使用兼容的系统调用** — 设置环境变量 `CARGO_BUILD_TARGET` 或使用旧版 clone 路径
3. **检查沙箱配置** — 确认 `Cargo.toml` 中的 `[[bin]]` 或 `[[test]]` 是否需要 `harness = false`（与本错误无直接关系，但 workflow 中有提及）

## Seccomp 错误日志分析

### 日志条目
```
2026-09-02T10:00:00.000000Z ERROR sandbox::seccomp: syscall denied op=clone3 pid=12345 comm=cargo — fail-closed
```

### 字段解析

| 字段 | 值 | 含义 |
|------|-----|------|
| `sandbox::seccomp` | 模块路径 | Rust 沙箱 crate 的 seccomp 子模块 |
| `syscall denied` | 动作 | 系统调用被 seccomp 过滤器拦截 |
| `op=clone3` | 操作 | Linux 系统调用 #261（x86_64），用于创建线程/进程 |
| `pid=12345` | 进程 ID | 被拦截的进程 |
| `comm=cargo` | 命令 | Rust 构建工具 `cargo` |
| `fail-closed` | 策略 | 安全策略为"失败即关闭"——未知 syscall 直接拒绝 |

### 根本原因

沙箱的 seccomp-bpf 过滤器未允许 `clone3` 系统调用。当 `cargo` 尝试通过 `clone3` 并发编译时，内核拦截并拒绝了该调用。

### 解决方案

1. **放宽 seccomp 策略** — 在容器 runtime 的 seccomp profile 中添加 `clone3` 白名单
