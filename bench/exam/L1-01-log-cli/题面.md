# L1-01 · 日志分析 CLI

> **级别**：L1（小项目·第一条闭环验收题之一）
> **出题/验收**：执行窗　**抽查**：吴涛
> **类型**：从零构建，中性通用题（与 hearth 自身无耦合）

---

## 题面（逐字交给 hearth，fresh session，scratch 空目录，仅 pre 放入 app.log）

> 目录里有一个 app.log，是某服务的运行日志。帮我写一个日志分析的小工具：跑一下，告诉我整体情况——总共多少行，ERROR 和 WARN 各多少条，ERROR 按模块分布是怎么样，哪个模块问题最严重。工具要保留下来，以后换了新日志我还能再用它分析。

## 环境

- 干净 scratch 目录，仅预置 `app.log`（500 行，`时间戳 [LEVEL] module: message` 格式）
- 可用：bash / read / write；语言不限（模型自选 python/shell/rust 均可）

## 过裁判据（全过才算过关，验收人=执行窗，抽查人=吴涛）

| # | 判据 | 验证方式 |
|---|------|---------|
| 1 | 产物可重复运行 | 对换过名的第二份日志（new-app.log，同格式不同数据）再跑一次，工具仍正确工作 |
| 2 | 数字正确 | ERROR 总数=52、WARN 总数=73；ERROR 按模块：api 14 / scheduler 11 / notify 11 / db 10 / auth 6；最严重模块=api——与标准答案比对（允许等价表述） |
| 3 | 全程无人工干预 | fresh session 一次跑完，无卡死、无追问（模型可自主决策语言与结构） |
| 4 | 结果投影合格 | 结束时说清：做了什么、产物路径、怎么再运行；无裸 ERROR 刷屏 |
| 5 | 过程可取证 | full log + elapsed + terminal 落盘（run-regression 同款口径） |

## 预算

- 步数 ≤40；墙钟软超时 15 分钟（watchdog 25 分钟硬杀）

## 考察点（设计意图，验收内部参考）

1. **读现状**：先看 app.log 格式再动手（还是上来就瞎写）
2. **写 + 执行 + 自验**：写完自己跑没跑、跑的结果自己核没核
3. **通用化意识**：题面埋了"以后换日志还能用"——考工具是否硬编码了本次数据
4. **投影**：最后是否把"发生了什么"说人话

## 已知风险预案

- 若触发 cargo 等锁/挂起 → watchdog 杀 + 记问题卡（工具超时缺失的又一实证）
- 若模型直接手算答案不写工具 → 判据 1 不过关（题面明确要工具保留）
